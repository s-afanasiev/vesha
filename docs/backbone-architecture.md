# Костяк — сайт, воронка, ассистент и инструмент ниши (MVP)

Оглавление MVP по [методу оглавлений](app-tables-of-contents.md): костяк из четырёх слотов (решение 15.10.2026, [automation-leads-architecture.md](automation-leads-architecture.md)) и первый инструмент — разбор заявки в счёт ([карточка 4.1-E/08](economic-strength/4-method/4.1-E-cards/08-b2b-order-to-invoice.md)). Замеры встроены с первого дня: они дают эффект r и масштаб q, которые решают, какой инструмент из пары лидеров делать дальше ([4.1-E](economic-strength/4-method/4.1-E-candidates.md), 6.3).

Статус: **шаги 1–5 из 6 сделаны, шаг 6 — в части кода (16–18.10.2026)** — доска с журналом, разбор заявки в черновик счёта, замеры из журнала с теневым режимом и выгрузка в xlsx для 1С, витрина с окном статуса и квитанциями, ассистент на витрине; магазин и каталог — из кабинета (§10). Первый клиент — магазин крепежа и сантехники из ниши hardware «Кому автоматизировать», который получает заявки списком от строителей и организаций. Канон — [oop-principles.md](oop-principles.md); компоненты — [ui-components.md](ui-components.md); ассистент — [chat-engine-architecture.md](chat-engine-architecture.md).

## 1. Предложение и миры

**Ш0:** *каждое обращение клиента становится заявкой, путь которой видят обе стороны.*

| Мир | Что в нём | Для костяка |
|---|---|---|
| снаружи — клиент | розничный покупатель, строитель, снабженец организации; пишет на сайте или в чате | зачинщик заявок и вопросов |
| снаружи — учёт магазина | 1С, МойСклад или прайс в Excel: позиции, цены, остатки, кратность | источник каталога; приёмник счёта |
| снаружи — языковая модель | шлюз VESHA (`llm.js`, квота) | размечает строки, которые не разобрали правила; черновики ответов |
| внутри — магазин | владелец и менеджеры | двигают заявки, правят черновики, настраивают доску |
| внутри — костяк | каталог, заявки с журналом, доска, окно статуса, ассистент, слот инструмента, замеры | своё |

**Кто задаёт темп:**
- клиент — входящими;
- менеджер — кнопками;
- таймеры — выгрузкой каталога, проверкой тишины и замерами;
- модель — асинхронно, через очередь.

**Ядро и спутники.** Ядро — заявка с журналом переходов (О15). Без него нет ни доски, ни окна статуса, ни замеров. Спутники — сайт, ассистент и инструмент: каждый работает по своему контракту и выключается без ущерба ядру. Тест выключения (П30): без модели заявки принимаются, доска работает, черновик счёта собирают правила для простых строк, а менеджер — вручную для остальных.

## 2. Сюжеты

| Сюжет | Зачинщик | Единица | Исход | Конец |
|---|---|---|---|---|
| заявка списком → счёт | клиент (сайт, чат) | заявка | счёт отправлен → оплачено → выдано; или отказ с причиной | `done` или `refused` |
| вопрос ассистенту | клиент | вопрос | ответ из фактов: наличие, цена, статус, часы; иначе черновик менеджеру; список из разговора — новая заявка | ответ отправлен |
| настройка доски | владелец | колонка | своя колонка со смысловым типом | доска сохранена |
| обновление каталога | таймер или кнопка | выгрузка | каталог с индексом атрибутов; несопоставимые строки выгрузки — список, а не тишина | каталог заменён целиком (О17) |
| тишина | таймер | заявка | срок в типе превышен — бейдж и уведомление менеджеру | заявка сдвинулась |
| замер | таймер (раз в день) | окно в 7 дней | метрики из журнала; сравнение «тень» и «помощь» | недельный отчёт |

## 3. Лестница единиц и роды узлов

```text
магазин (shop)                         — ключ всех сущностей с первого дня, в MVP один
└─ заявка (order)                      — сущность с путём; журнал событий
   └─ строка заявки (line)             — «Саморез по металлу 4,2х19 — 3 уп.»
      └─ кандидат каталога (match)     — позиция + уверенность
каталог (catalog)
└─ позиция (item)                      — артикул, наименование, атрибуты, цена, остаток, кратность
доска (board)
└─ колонка (column)                    — название, цвет, лимит, смысловой тип
```

| Узел | Род (П10) | Один глагол |
|---|---|---|
| `Shop` | данные | хранит, кто этот бизнес: контакты, часы, ниша, настройки |
| `Catalog` | данные | отдаёт позиции и индекс; один на троих читателей |
| `CatalogFeed` | адаптер | читает выгрузку учёта |
| `Journal` | сущность | хранит события заявок — единственный источник доски, окна и замеров |
| `Orders` | работа | принимает, ведёт по пути и сторожит тишину |
| `Intake` | повторитель (реестр каналов) | сводит каналы в одну заявку |
| `Order` | сущность | держит путь, строки, черновик, квитанции |
| `Board`, `Columns` | правило + данные | отвечает, в какой колонке карточка и куда её можно перенести |
| `ToolSlot` | обёртка | даёт любому инструменту контракт «вход → результат → заявка» |
| `OrderToInvoice` | работа | превращает текст заявки в черновик счёта |
| `Lines`, `Matches` | повторители | строка за строкой |
| `StockCheck` | чистое действие | решает про остаток и кратность |
| `Measures` | чистое действие над журналом | считает метрики |
| `Site`, `StatusPage`, `Assistant` | адаптеры к людям | показывают и принимают |

## 4. Оглавление

```js
const stageTypes = ['inbox', 'working', 'waiting_client', 'done', 'refused']  // смысловые типы колонок: на них держатся окно и замеры

const shop = new Shop({ slug: 'krepezh-kursk', niche: 'hardware', tz: 'Europe/Moscow', hours: '09:00–19:00' })

const catalog = new Catalog(                                       // общее — один раз: читают сайт, ассистент и инструмент (П5)
  new CatalogFeed(new XlsxFile(shop.feedPath)),                    // выгрузка 1С / МойСклад / прайс; честный простой узел — файл (О6)
  new CatalogIndex({ attributes: hardwareAttributes }),            // размер, стандарт, класс, покрытие — из наименований, один раз при загрузке
  new Synonyms(),                                                  // «шуруп по дереву» → позиция; растёт из правок менеджера
)

const journal = new Journal()                                      // события заявок; доска, окно статуса и замеры — его проекции (О15)

const orders = new Orders(                                         // хозяин заявок: приём, путь, тишина (пример 5 тетради)
  new Intake({                                                     // реестр каналов: всё сходится в одну заявку (О14)
    site: new SiteIntake({ maxFileMb: 5 }),                        // форма «заявка списком»: текст или файл
    chat: new ChatIntake(),                                        // список из разговора с ассистентом
  }, { key: (r) => [r.contact, r.contentHash] }),                  // тот же список дважды — одна заявка (П36)
  new Order(new Path(stageTypes), new Receipt()),                  // путь + квитанция клиенту на переходе (О13)
  new SilenceWatch({ inbox: '1h', waiting_client: '2d' }),         // тишина дольше срока — состояние с выходом
  journal,
)

new Backbone(
  shop,
  new Site(catalog, orders.intake.site, new StatusPage(journal)),            // витрина: каталог, заявка списком, окно статуса, виджет
  new Board(                                                                 // канбан с конструктором колонок
    new Columns(templates[shop.niche], shop.columns),                        // шаблон ниши + свои колонки владельца
    { types: stageTypes, required: ['inbox', 'done', 'refused'] },           // тип у каждой колонки; обязательные типы не исчезают
    orders,                                                                  // перенос — только через дверь заявок
  ),
  new Assistant(chatDesk, new ShopFacts(catalog, orders.byClient, shop),     // ответы только из фактов (О18); видит лишь заявки собеседника (О20)
    { auto: ['stock', 'status', 'hours'] }),                                 // три вопроса — сам, остальное — черновик менеджеру
  new ToolSlot(                                                              // слот: вход → результат → заявка
    new OrderToInvoice(catalog, { autoAccept: 0.9, ask: 0.6, maxLines: 200 }),
  ),
  new Measures(journal, new Baseline({ shadow: '14d' })),                    // замеры из журнала с первого дня; теневой режим — база «до»
)
```

Внутри инструмента — конвейер форм данных, названный по выходу (О1):

```js
new OrderToInvoice(
  new InvoiceDraft(                                                    // черновик счёта: позиции, суммы, вопросы клиенту, «нет в каталоге»
    new StockCheck(catalog, { pack: 'ask' }),                          // 37 шт. при упаковке по 50 — вопрос клиенту, а не молчаливое округление
    new Matches(                                                       // повторитель: строка → позиция с уверенностью (О3)
      new Match(catalog.index, catalog.synonyms, { autoAccept: 0.9, ask: 0.6 }), // без модели: атрибуты + похожесть + синонимы
    ),
    new Lines(                                                         // строки: наименование, размеры, количество, единица
      new RuleLines(),                                                 // сначала правила: «наименование — количество ед.»
      new ModelLines(new Guarded(llm, { timeoutMs: 20_000 }), { verify: digitsInSource }), // модель — для остатка; цифры сверяются с текстом (О18)
    ),
    new RequestText({ text: PlainText, xlsx: SheetRows, pdf: PdfTextLayer }), // только текстовый слой; скан — именованный отказ (О10)
  ),
  new Review(new Lanes({ draft: 1 })),                                 // менеджер правит строки; один редактор на черновик (О16); правка → синоним
  new InvoiceExport(new XlsxFile()),                                   // файл для загрузки в 1С; прямой обмен — после MVP
)
```

## 5. Честная сборка — кто задаёт темп

```js
new BackboneLoop(
  new OnIncoming(intake, (o) => toolQueue.push(o)),                  // клиент: заявка открыта, разбор — в очередь
  new Queue(1, toolSlot),                                            // модель не задерживает приём: один воркер, сбой — бейдж
  new Ops(access.act, { move, configureColumns, editLine, sendInvoice, attachInvoice, refuse }), // кнопки людей — через полномочия
  new Every('1h', catalog.refresh),                                  // выгрузка учёта
  new Every('15m', silenceWatch),                                    // тишина
  new Outbox(new Retry(5, receipts)),                                // квитанции клиенту — отдельно от перехода (П35)
  new Every('1d', measures),                                         // замеры
)
```

## 6. Узлы крупно

### 6.1. Заявка и журнал

- **Одна сущность от обращения до выдачи:** заявка → счёт → оплата → выдача — это путь одной заявки, а не три объекта.
- **Журнал — события, а не колонки:** `received`, `parsed`, `draft_ready`, `parse_failed`, `reviewed`, `invoice_sent`, `client_replied`, `paid`, `issued`, `refused(reason)`, `moved(from, to)`. У каждого события — кто, когда, почему. Колонка — это вид, а событие — факт; замеры читают события.
- **Квитанция клиенту** — на `received` («заявка получена, номер …, ответ до …»), `invoice_sent` (счёт и ссылка на окно), вопрос клиенту (`waiting_client`), `issued`, `refused` с причиной. Канал квитанции — тот же, через который пришла заявка.
- **Тишина** — состояние с выходом: заявка в `inbox` дольше часа рабочего времени, в `waiting_client` — дольше двух дней. Это бейдж на карточке и уведомление, а не пропажа.

### 6.2. Доска с конструктором колонок

Канбан `kanban@1` с источником колонок из настроек магазина вместо статичной декларации.

- **Шаблон ниши** — колонки по умолчанию. Магазин крепежа: «Новая заявка» (inbox) → «Разбор» (working) → «Вопрос клиенту» (waiting_client) → «Счёт отправлен» (waiting_client) → «Оплачен, собираем» (working) → «Выдан» (done) / «Отказ» (refused). Цех металлообработки: «Заявка» → «Расчёт» → «Согласование» → «В работе» → «Готово» → «Выдано» / «Отказ». Шаблоны — данные, не код.
- **Конструктор:** добавить, переименовать, переставить, удалить колонку, сменить цвет и лимит, выбрать тип.
- **Инварианты** — проверяет `Board`, а не рендерер:
  - у каждой колонки ровно один тип;
  - типы `inbox`, `done`, `refused` всегда есть хотя бы в одной колонке;
  - удаление колонки с карточками требует выбрать, куда их перенести;
  - каждая правка доски — событие журнала: кто и когда.
- **Почему тип обязателен (О24).** Окно статуса показывает клиенту не названия колонок, а шаги по типам: «получена → в работе → ждём вас → готово». Замеры считают время между типами. Владелец переименовывает и переставляет колонки как хочет — смысл не ломается.
- **Изменение контракта `kanban@1`** (ui-components.md, §2а):
  - `GET /meta` берёт колонки у источника при каждом запросе;
  - новая дверь `POST /columns {op, …}` — операции конструктора, правило проверяет домен;
  - в колонке появляется поле `type`.

  Рендерер получает режим «настроить колонки».

### 6.3. Сайт

Витрина магазина без лишнего.

- **Каталог:** поиск по наименованию и размеру, фильтры по типу изделия, наличие и цена из каталога.
- **Карточка позиции:** атрибуты, кратность.
- **«Отправить заявку списком»:** текст или файл xlsx и pdf, плюс телефон или почта для ответа.
- **Окно статуса по ссылке** (`stages@1`).
- **Виджет ассистента** (chat-engine).

Корзины в MVP нет: целевой клиент присылает список, а не кликает по позициям.

Сайт собирает телефон и почту, значит нужны согласие на обработку персональных данных и хранение в России (152-ФЗ).

### 6.4. Ассистент

Надстройка над `chat-engine`: `ChatDesk` + `ReplySuggester`, черновики менеджеру, одна дверь этапа.

- **Сам отвечает на три вопроса** — по фактам, каждое число со ссылкой на позицию или заявку (О18):
  - есть ли позиция и почём;
  - где моя заявка;
  - часы и адрес.
- **Остальное** — черновик менеджеру, как сейчас в chat-engine.
- **Видит только заявки собеседника** (О20): `orders.byClient` — дверь, а не фильтр в промпте (в коде — `BackboneDesk.clientOrders`).
- **Список в разговоре** («мне нужно: …») — предложение отправить его заявкой; согласие → `ChatIntake`.
- **Модели не уходят контакты:** телефон и почта вырезаются до вызова.

**Карта зависимостей ассистента от chat-engine (17.10.2026).** Сайт магазина отпочкуют от VESHA ([backbone-handover.md](backbone-handover.md)), поэтому зависимость одна и явная: костяк → ядро chat-engine из четырёх классов. Ядро не тянет ни других экспериментов, ни пакетов: у четырёх файлов нет ни одного `require`, база и модель приходят через конструктор (П7).

| Файл chat-engine | Что даёт ассистенту | Что тянет сам | В сборку магазина |
|---|---|---|---|
| `ChatDesk.js` | дверь разговора: входящее посетителя, разговор для виджета, ответ менеджера, черновик — отправить, править, отклонить | ничего | **да** |
| `DialogueRepository.js` | истина разговоров: таблицы `chat_engine_*`, гашение черновика новым входящим, дедуп по `external_id` | ничего (`db` — аргумент) | **да** |
| `ReplySuggester.js` | черновик менеджеру: промпт из персоны, карточки и истории | ничего (`completeChat` — аргумент) | **да** |
| `Funnel.js` | этапы разговора (их ждут `ChatDesk` и `ReplySuggester`) | ничего | **да** |
| `db/migrations/012_chat_engine.sql` | таблицы диалогов, сообщений, журнала этапов, персона по умолчанию | — | **да** |
| `index.js` | общая сборка демо: глобальная персона, модель без квоты | `server/db.js`, `server/services/llm.js` | нет — костяк собирает своё в `backbone/index.js` |
| `components.js`, `pages.js` | канбан воронки лидов демо | `server/components` | нет |
| `server/routes/chat-engine.js` | ручки демо без магазина | `llmGuard.js` | нет — у витрины свои ручки в `backbonePublic.js` |
| `public/experiments/chat-engine/*` | дашборд и виджет демо | — | нет — виджет магазина `public/backbone/assistant.js` |

Платформа, которую ассистент берёт сверх ядра, — из списка допустимого для сборки: `server/db.js`, `server/services/llm.js` и `llmGuard.js` (черновик менеджеру — через `GuardedLlm` разбора), `server/middleware/identity.js` (гость витрины — ключ собеседника), `server/components` (экран ассистента в кабинете). В VESHA таблицы `chat_engine_*` общие с демо chat-engine: разговоры магазинов видны и на его дашборде, ключ посетителя у них — `<id магазина>:<гость>`. В сборке магазина демо нет — разговоры только свои. В манифест сборки `dist/shop` входят четыре файла ядра и миграция `012`.

**Как это сделано в шаге 5** (18.10.2026, `server/services/backbone/assistant/`, миграция `026`):

- **Дверь — `Assistant`.** Разговор хранит ядро chat-engine, заявки ведёт `BackboneDesk`, события разговора пишутся в журнал магазина, поток `chat`: `assistant_answered`, `assistant_deferred`, `list_offered`, `list_sent`, `manager_replied`. Разговор магазина — ключ посетителя `<id магазина>:<гость>`.
- **Факты — `ShopFacts`.**
  - Каталог — магазина по версии выгрузки (`Catalogs.of(shop)`), тот же, что у витрины и разбора.
  - Позиции под вопрос отбирает правило `Match` разбора: размер, стандарт, класс и покрытие, если названы, не противоречат позиции.
  - Заявки — только через дверь `BackboneDesk.clientOrders`; часы — `WorkingHours` магазина.
- **Три автоответа — `AutoAnswers`**, реестр правил без модели, порядок: статус → часы → наличие.
  - Наличие: в вопросе есть тип изделия или размер («М10», «4,2х19», «1/2″»). Ответ — до 5 позиций: наименование, цена за единицу, упаковка, «в наличии / под заказ / наличие уточняйте», артикул. Остаток числом наружу не уходит — как на витрине. «М10×50» — резьба: дюбель 10×50 идёт после болтов. Позиции нет — ответ «не нашёл» и передача менеджеру.
  - Статус: «где заявка 42?» — шаг окна статуса, с какого времени, ссылка; без номера — до трёх своих заявок.
  - Часы: «пн–сб 09:00–19:00 (время московское)», открыто ли сейчас, когда откроемся. Адреса в описании магазина нет — о нём ассистент не говорит.
- **Только своему клиенту (О20).**
  - Клиент — гость витрины: подписанная cookie платформы. У заявки с сайта и из чата — `client_key` (миграция `026`), ручные заявки ключа не имеют.
  - Чужой и несуществующий номер получают один и тот же ответ «среди ваших не вижу», без ссылок.
  - Заявку, отправленную с другого устройства, клиент видит по ссылке из квитанции.
- **`ChatIntake` — список из разговора.**
  - Список узнают правила разбора `RuleLines`: две строки с количеством или одна без вопроса. Ассистент предлагает отправить список заявкой; виджет просит контакт и согласие 152-ФЗ.
  - Ключ «контакт + содержимое» — общая с сайтом функция `contentKey`; вступление «Мне нужно:» в ключ не входит.
  - Тот же список с сайта и из чата — одна заявка и `received_again` с каналом. Квитанции получают и заявки из чата.
- **Менеджеру — экран кабинета `?page=assistant`.**
  - Разговоры: сколько ответил сам, сколько ждали менеджера, заявки из чата. Сообщения: ответы ассистента помечены по журналу.
  - «Предложить ответ» — `ReplySuggester` ядра через `ShopPersona`: общая персона chat-engine плюс название, часы и правило «цены, наличие и статус называет не черновик».
  - Модель — `GuardedLlm` разбора, квота нажавшего; телефоны и почта вырезаются из всего, что уходит модели (`withoutContacts`). Демо без сети — запись в `recorded-llm.json`.
  - Посетителю — уведомление «передал менеджеру» один раз на серию вопросов.
- **Виджет — `public/backbone/assistant.js`**, одна строка в витрине, без общего `VeshaUI`; пока открыт — опрос раз в 4 с. Частота — 30 сообщений посетителя за 10 минут; заявка из чата идёт в общий счёт формы (5 за 10 минут с адреса). Числа — в `backbone/index.js`.
- **Замер** «ассистент без менеджера» (§6.6) — строка экрана «Замеры» из потока `chat`.
- **Проверено** (18.10.2026):
  - тесты `test/backbone-assistant.test.js` — 11, в том числе Postgres через публичные ручки;
  - сервер без границы на 127.0.0.1:3020 и Postgres: «есть ли М10х50?» → три позиции с ценой и наличием; заявка №6 с витрины → «где заявка 6?» — шаг и ссылка, «где заявка 7?» (чужая) — «не вижу»; тот же список в чат → «уже у нас — заявка №6»; вопрос о доставке → «Предложить ответ» → «Отправить черновик» → ответ в виджете; мобильная ширина — без горизонтальной прокрутки.
- **Не сделано:** мессенджеры (адаптеры над `ChatDesk`), правка общей персоны в сборке магазина, адрес магазина. Разговоры кабинета — фильтр по ключу из всех диалогов: при росте нужен фильтр в `DialogueRepository`, а это правка ядра.

### 6.5. Слот инструмента и разбор заявки в счёт

**Контракт слота (О26)** — один для любого инструмента ниши (расчёт по чертежу, разбор видео, подбор крепежа):

```js
// инструмент объявляет, что принимает, и умеет run(input, ctx) → результат с фактами;
// слот кладёт результат в заявку, пишет события в журнал и узел в дерево процессов
interface Tool { accepts: string[]; run(input, ctx): Result }   // Result: { draft, questions, facts, failures }
```

**Разбор заявки в счёт** — конвейер из раздела 4:

1. **`RequestText`** — текст из сообщения, строки листа xlsx, текстовый слой pdf. У скана нет текстового слоя — это именованный отказ «нужен текст или таблица», а не попытка OCR (правило VESHA «только текстовые источники»).
2. **`Lines`** — сначала правила (строка вида «наименование — количество единица»), потом модель — для того, что правила не разобрали. Модель возвращает строки по схеме: наименование, атрибуты, количество, единица. Каждая цифра ответа должна найтись в исходном тексте, иначе строка помечается «проверить».
3. **`Matches`** — без модели:
   - **разбор атрибутов наименования:** `4,2х19`, `М10х50`, `DIN 933`, `8.8`, `оцинк.`; кириллическая «х», латинская «x» и «*» приводятся к одному виду, десятичная запятая — к точке;
   - **отбор позиций** по типу изделия и размерам;
   - **ранжирование** по похожести наименования и синонимам.

   Уверенность от 0,9 — строка принята; от 0,6 до 0,9 — показаны 2–3 кандидата; ниже 0,6 — «нет в каталоге».
4. **`StockCheck`** — остаток и кратность. Нехватка или некратное количество — вопрос клиенту, а не молчаливая правка.
5. **`InvoiceDraft`** — позиции, суммы, вопросы, отсутствующие позиции.
6. **`Review`** — менеджер видит строки с уверенностью и исходным текстом рядом, принимает, правит или заменяет. Каждая правка — событие `reviewed` с решением `verdict`: `accepted`, `edited` (количество), `replaced` (позиция). Синоним «фраза клиента → позиция» рождается при замене и при подтверждении кандидата строки «выбрать»; принятие и без того принятой строки — не новость. Разбор пишет `parsed` (строки: правила, модель, не разобрано, проверить) и `draft_ready` (принято, выбрать, нет в каталоге, вопросы, сумма); отказ — `parse_failed` с кодом и причиной.
7. **`InvoiceExport`** — файл xlsx для загрузки документа в 1С; счёт формирует учётная система, а не костяк.

Каждый прогон инструмента — узел дерева процессов: «Заявка 42: 18 строк, 15 сопоставлено, 2 вопроса, 1 нет в каталоге» (О10, О11). В шаге 2 сводка прогона — `facts.summary` и данные `parsed` / `draft_ready` в журнале; узел дерева — вместе с фоновыми прогонами (разбор пока идёт в запросе менеджера, до 5 заявок за раз).

**Как это сделано в шаге 2** (16.10.2026, `server/services/backbone/invoice/`):

- **Уверенность** — сумма весов совпадений: размер 0,45, стандарт 0,15, класс 0,1, покрытие 0,1, слова 0,2. Названный клиентом и совпавший атрибут — полный вес; не названный — 0,85 веса (у позиции он может быть другим); противоречие — позиция отбрасывается. Второй кандидат ближе 0,08 к первому снижает уверенность до 30 % — так «Болт М8х40» без покрытия становится «выбрать: оцинк. или A2», а «Болт DIN 933 М10х50 кл.8.8 оцинк.» — принят. Синоним даёт 0,97. Числа — в декларации `Match` (П6).
- **Строки модели** — один вызов на остаток заявки, через `runGuarded` от имени того, кто нажал «Разобрать», серверный пресет шлюза; квота кончилась или модель недоступна — строки с цифрами остаются «не разобрано» и видны менеджеру. Цифра ответа, которой нет в исходной строке («штук пятьсот» → 500), — пометка «проверить», уверенность не выше 0,85.
- **xlsx** читается без библиотек: центральный каталог zip, `inflateRaw`, первый лист книги; шапка таблицы отбрасывается. **pdf** — только текстовый слой (`pdf-parse`); меньше 10 знаков текста — отказ `scan`. Фото — тот же отказ.
- **Вход файлом** (xlsx, pdf) — у `RequestText` и инструмента уже есть; дверь приёма файла — `SiteIntake` шага 4. В шаге 2 заявку разбирают из текста.
- **Заместитель модели** — `RecordedLlm`: в тестах и на демо (`BACKBONE_MODEL=recorded`, ответы `invoice/fixtures/recorded-llm.json`) — без сети и ключа.
- **Живой прогон** (16.10.2026, один, с разрешения пользователя): демо-заявка через дверь → `GuardedLlm` → `runGuarded` → шлюз `openai/gpt-5.6-luna`, 3,0 с. Ответ — чистый JSON, разбор и сверка цифр прошли без правок: правила 18 строк, модель 2, не разобрано 0; принято 16, выбрать 4, нет в каталоге 0, вопросов клиенту 5; «штук пятьсот» → 500 — «проверить». Модель оставила «4,2 на 16» без «×» — `CatalogIndex` читает это как те же размеры.

### 6.6. Замеры с первого дня

Все метрики считаются из журнала событий — отдельных счётчиков нет (О19, О21).

| Метрика | Из каких событий | Зачем |
|---|---|---|
| время до первого ответа клиенту | `received` → первый `invoice_sent` или `moved` в тип `waiting_client`, `done`, `refused`; квитанции шага 4 добавятся сюда же | скорость реакции |
| доля заявок с ответом в течение часа рабочего времени | то же; в знаменателе — отвеченные и те, что ждут дольше часа | обещание клиенту |
| **время до счёта** | `received` → `invoice_sent` | главный эффект инструмента |
| **минуты менеджера на заявку** | помощь: серии `reviewed`, `invoice_exported`, `invoice_sent` после `draft_ready`, паузы дольше 10 мин не считаются, минута на серию; в тени не видно — менеджер работает в 1С | экономия времени → r |
| **точность черновика** | тень: `invoice_sent` со сверкой черновика против счёта из 1С; помощь: доля строк без `reviewed` edited / replaced | качество разбора; порог включения помощи |
| доля «нет в каталоге» и вопросов | `draft_ready` (missing, questions) / строки | полнота каталога и синонимов |
| **конверсия заявки** | заявки, чей тип колонки сейчас `done`, против `refused`, по неделям приёма | эффект на продажи |
| тишина | сейчас: входящие дольше часа рабочего времени, «ждём клиента» дольше 2 дней | надёжность |
| ассистент без менеджера | поток `chat`: `assistant_answered` против `assistant_deferred` (шаг 5) | нагрузка на менеджера |
| доля B2B-заявок | `draft_ready.lines` от 5 или `received.org` (форма юрлица в имени клиента) | масштаб q для карточки 08 |

**Теневой режим — база «до» без риска (О25)** (`Baseline({ shadow: '14d' })`):

1. Первые две недели инструмент разбирает каждую заявку, но черновик менеджеру не показывает.
2. Менеджер работает как обычно и прикладывает к карточке итоговый счёт — файл из 1С, одна кнопка.
3. Так с первого дня известны время до счёта при ручной работе и точность черновика против настоящего счёта.
4. Режим «помощь» включается решением с мерой (О19): точность от 0,8 строк без правки. Решение и снимок «до» — событие журнала.

**Как это сделано в шаге 3** (17.10.2026, `server/services/backbone/measures/`, `invoice/InvoiceExport.js`, `invoice/FinalInvoice.js`):

- **Режим** — колонка `backbone_shops.mode` (`shadow` / `help`) и `mode_since`, миграция `020`. Магазины, которые работали с черновиками до неё, остались в помощи; новый магазин начинает с тени. Смена — `BackboneDesk.switchMode`, событие `mode_changed` (поток `shop`) с причиной; переход в помощь несёт снимок «до».
- **Правило помощи** — `Baseline({ shadowDays: 14, accuracy: 0.8, minLines: 20 })`: тень шла не меньше `shadowDays`, сравнено не меньше 20 строк, точность от 0,8 — иначе отказ с причиной. Вернуть тень можно всегда — это новая база. У демо-магазина `shadowDays: 0`: помощь включается по точности, не по календарю.
- **Тень на экране** — черновик скрыт (таблица строк, сводка заявки, бейджи доски), пока к заявке не приложен счёт. «Приложить счёт из 1С» — менеджер вставляет табличную часть счёта (строки через табуляцию); позиция — по артикулу или уверенно по наименованию. Нет черновика — он строится тут же. Точность = совпавшие строки (позиция + количество) / объединение строк черновика и счёта: каждая лишняя или пропущенная строка — правка.
- **Помощь** — «Выгрузить в xlsx для 1С» (событие `invoice_exported`, файл — `GET /api/backbone/files/invoice/<id>.xlsx`): лист «Счёт» без шапок и итогов — только принятые строки «Артикул — Номенклатура — Количество — Ед. — Цена — Сумма»; «выбрать», «нет в каталоге» и вопросы — на листе «Вопросы и пропуски». «Счёт отправлен» — `invoice_sent` с долей строк без правки.
- **Замеры** — `Measures` над журналом магазина целиком: карточка заявки из её событий; режим заявки — тот, что был при приёме; минуты — рабочие (`WorkingHours`: пояс магазина, дни и часы из описания магазина). Экран `?page=measures`: «до и после» с разницей и недели.
- **Проверено** на Postgres (17.10.2026): выгрузка → файл читается обратно, 16 строк в счёте; «счёт отправлен» — без правки 19 из 20; «вернуть тень» → черновики скрыты, «включить помощь» — отказ «сравнено строк: 0 из 20»; новая заявка + счёт из 1С → совпало 18 из 20, точность 0,82 → помощь включена.

**Куда идут замеры.** Недельный отчёт для магазина и строка в [4.1-B](economic-strength/economic-strength-roadmap.md) (протокол замера эффекта):

```text
r = (Δ минут на заявку × заявок в год × стоимость минуты + Δ конверсии × заявок в год × средняя маржа) / стоимость владения в год
```

Доля B2B-заявок у первых клиентов уточняет q. Оба числа обновляют карточку 08 и решают, остаётся ли разбор заявки первым инструментом или его обгоняет мониторинг или раскрой ([4.1-E](economic-strength/4-method/4.1-E-candidates.md), 3.5).

## 8. Пробы

**Пересказ без машинерии.** Строитель присылает список на сайт. Магазин сразу отвечает: «получено, номер 42, счёт пришлём до 15:00». Через минуту у менеджера готов черновик: 15 строк найдены, по двум нужно выбрать, одной нет в каталоге. Менеджер правит три строки, выгружает счёт в 1С и отправляет. Клиент по ссылке видит «счёт отправлен», потом «оплачен», «собран», «выдан». В конце недели магазин видит: на заявку уходило 25 минут, теперь 8.

**Сценарии:**

| Сценарий | Что происходит | Узел |
|---|---|---|
| тот же список пришёл на сайт и в чат | одна заявка по ключу «контакт + содержимое»; второй канал — событие, не дубль (проверено 18.10.2026) | `BackboneDesk.receive`, `ChatIntake` (П36) |
| «саморезы 4,2 на 19 — 3 коробки», а в каталоге упаковки по 1000 и по 200 | строка принята по атрибутам, количество — вопрос клиенту: «коробка — это 1000 или 200 шт.?» | `StockCheck` |
| позиции нет в каталоге | строка «нет в каталоге» с ближайшими по размеру; менеджер предлагает замену или вычёркивает | `Match`, `Review` |
| модель недоступна | заявка принята, квитанция ушла; черновик собран правилами для простых строк, на карточке бейдж «разбор неполный» | `Guarded`, `RuleLines` (П30) |
| клиент прислал скан | квитанция «получено» и просьба прислать текст или таблицу; менеджер видит заявку с именованным отказом | `RequestText` (О10) |
| владелец удалил колонку «Вопрос клиенту» с пятью карточками | система спрашивает, куда перенести; тип `waiting_client` остаётся у колонки «Счёт отправлен»; метрики не прерываются | `Board` |
| два менеджера открыли один черновик | второй видит «правит Анна, 3 мин.» — полоса занята | `Lanes` (О16) |
| клиент открыл ссылку статуса через месяц | видит путь заявки до «выдан 12.10» — окно не исчезает | `StatusPage` |
| клиент спросил ассистента о чужой заявке по номеру | ассистент не видит её: дверь `clientOrders` отдаёт только заявки собеседника; чужой и несуществующий номер — один ответ (проверено 18.10.2026) | `ShopFacts` (О20) |
| выгрузка каталога пришла битой | каталог не подменяется, пока новая выгрузка не прочитана целиком; ошибка — в списке «не загружено» | `CatalogFile`, `Catalogs` (О17) |

**Соседи — стало ли проще:**
- **automation-leads.** Лид шага 2 — та же форма «сущность с путём и журналом», что заявка; журнал и `stages@1` пишутся один раз на обоих.
- **chat-engine.** Получает `ChatIntake` и факты магазина без правки ядра.
- **Исследование.** Получает протокол замера 4.1-B на живых данных вместо оценок.

## 11. Открытые вопросы

- **Учёт первых клиентов.** 1С УТ, УНФ, МойСклад или прайс — от этого зависят формат выгрузки каталога и файла счёта. Узнать у первых трёх магазинов ниши. С 17.10.2026 каталог читается из любой xlsx-выгрузки с сопоставлением колонок; `.xls` и выгрузки с многострочной шапкой — честный отказ или ручное «Указать колонку». Сверить на живых файлах.
- **Атрибуты крепежа и сантехники.** Список атрибутов `hardwareAttributes` (тип изделия, размеры, стандарт, класс прочности, покрытие, форма головки) нужно сверить с реальными выгрузками; сантехнике нужен свой словарь (диаметры, резьба в дюймах, материал).
- **Канал квитанций.** Почта — в MVP. Мессенджеры — после, через адаптеры chat-engine.
- **Где обрабатываются данные модели** — провайдер с хранением в России или локальная модель. Контакты в модель не уходят в любом случае.
- **Цена.** 5–15 тыс. ₽ в месяц — допущение карточки 08. По модели окупаемости [4.1-E v0.3](economic-strength/4-method/4.1-E-candidates.md) (6.2) отдельной подпиской за 10 тыс. ₽ команда из двух человек окупается 64 месяца; за 22 — от 24,5 тыс. ₽. Значит, продавать пакет костяка с разбором заявки — от 25 тыс. ₽ в месяц, а подключение каталога делать удалённым. Цену проверить на первых клиентах вместе с замером.

# Оглавления приложений — от рассказа к прототипу

Рабочая тетрадь метода: как записать любое приложение одним экраном объектов — **оглавлением** — и почему это путь к очень быстрым прототипам в любой предметной области, а в перспективе — к движку, который собирает приложение из описания. Здесь идея, грамматика, разобранные примеры, первые общие паттерны и упражнения. Документ растёт занятиями: каждое новое оглавление добавляется в журнал, а повторяющееся в нём — в паттерны.

Канон, на который опирается метод, — [oop-principles.md](oop-principles.md) (главная формула, П3, П4, П5, П31, П42). Зеркало UI — [process-tree-ui-canon.md](process-tree-ui-canon.md) и [ui-components.md](ui-components.md). Живой пример исполненного оглавления — [automation-leads-architecture.md](automation-leads-architecture.md).

## 1. Идея

Главная формула канона: сначала проектируется язык описания приложения из объектов предметной области, затем приложение записывается **предложением на этом языке**. Имена объектов — словарь, вложенность — грамматика, `run()` превращает описание в работающую систему.

Оглавление — это и есть такое предложение, записанное на верхнем уровне:

- **читается вслух** как описание системы и не врёт (П3);
- **каждый объект — одна роль** с одним глаголом и контрактом, по сути потенциальный микросервис: снаружи — имя, вход и выход, внутри — своё оглавление (узел фрактален);
- **по нему видно архитектуру, план работ и экран сразу**: узлы — это файлы и задачи, связи — контракты, а UI выводится из дерева (зеркало процессов и сущностей), а не верстается заново.

Почему это быстро:

1. **Узел можно сначала сделать честно простым.** Оглавление исполняется от входа до выхода в первый же день: заглушка с настоящим контрактом, чтение из файла вместо сети, записанный ответ модели вместо вызова. Дальше каждый шаг углубляет один узел, а целое остаётся работающим (П31, сквозной прогон).
2. **Экран не пишется.** Шаг, который сообщает о себе через узел дерева процессов, виден без фронтенда; результат показывают складские компоненты (`table@1`, `kanban@1`, `tree@1`) по спеке страницы.
3. **Спор решает проба, а не вкус** (П42): пересказ, выдуманный сценарий, соседи. Плохое оглавление видно до кода.

Главная цель — **движок**: описание предметной области → оглавление → работающий прототип с UI-зеркалом → углубление узлов. Путь к нему — раздел 6.

## 2. Грамматика оглавления

Кратко; подробности — в каноне.

| Правило | Суть | Канон |
|---|---|---|
| Шесть видов связи | `A(B)` — это часть, конвейер, реестр, прототип, обёртка или политика; не опознаётся — нужен именованный параметр или поддерево | П4 |
| Конвейер — по выходу | узел называется по тому, что выдаёт: `Lines`, а не `SplitText`; каждый поднимает данные на одну ступень | П4 |
| Много и один | `Layers(Layer())`: повторитель во множественном числе, прототип экземпляра — в единственном | П16 |
| Числа — в декларации | таймаут, порог, доля, шаг сетки — аргумент узла в оглавлении, а не константа внутри | П6 |
| Общее — один раз | узел с двумя читателями объявляется отдельно и передаётся обоим | П5 |
| Родитель решает | дети сообщают факты, решение и инвариант — у родителя; братья друг друга не знают | П2 |
| Честность | видимая вложенность совпадает с реальным владением, потоком управления и временем жизни | П3 |
| Восемь родов узла | работа, сущность, данные; правило, чистое действие, повторитель, обёртка, адаптер | П10 |

**Процедура** (П30, П31): одно предложение без «и» → миры (снаружи и внутри, ядро и спутники, кто задаёт темп) → сюжеты (зачинщик, единица, исход, конец) → лестница единиц («для каждого» — новый этаж) → род каждого узла → оглавление одним выражением → пробы. Слова рассказа подсказывают вид узла: «сначала… потом» — конвейер, «для каждого» — повторитель, «если» — ветка, «не чаще» — лимит, «не дольше» — таймаут, «решаем, кому» — политика.

**Меры** (чтобы метод не стал обрядом): узел заводится, когда за него что-то получено — судьба, замена, проверка (П13, П34); управляющие конструкции без судьбы остаются синтаксисом (П17–П19); оглавление ускоряет каркас, но не заменяет знания о домене.

## 3. Примеры

### Пример 1. Первая треть кадров видео

Задача: извлечь первую треть кадров из видеофайла.

```js
new FrameExtract(new FramesAmount(new FileInfo()))
```

- `FileInfo` — получает данные о файле;
- `FramesAmount` — на их основе считает число кадров;
- `FrameExtract` — извлекает кадры.

Разбор. Чистый **конвейер**: данные поднимаются по ступеням «файл → сведения → число → кадры». Первые две ступени названы по выходу (`FileInfo`, `FramesAmount`), последняя — работа, которая даёт итог. Каждая ступень заменяема по отдельности: другой способ узнать длительность меняет только `FileInfo`. Одно уточнение по П6: «треть» — число поведения, ему место в декларации, а не внутри узла:

```js
new FrameExtract(new FramesAmount(new FileInfo(), { share: 1 / 3 }))
```

### Пример 2. Разметка слоёв поверх изображения

Задача: браузерное приложение. Загружаем произвольное изображение, поверх рисуется сетка с шагом, например, 20 пикселей; создаём N слоёв и в каждом размечаем объект произвольной замкнутой фигурой; слои можно добавлять и удалять; в конце сохраняется числовая матрица положения всех слоёв.

```js
new App(
  new Iface({
    LoadImgAction: new LoadImgAction(),
    AddZoneAction: new AddZoneAction()
  }),
  new Field(
    new ImageCanvas(new LoadedImage()),
    new Layers(new Layer(new Canvas()), new SavedMatrix())
  )
).run()
```

Разбор. Две половины: `Iface` — **реестр** действий (кто и чем запускает изменения), `Field` — **части** состояния (что меняется). `ImageCanvas(LoadedImage())` — короткий конвейер «файл → изображение → холст». `Layers(Layer(Canvas()), …)` — **прототип**: повторитель держит правило «добавить, удалить, выбрать», каждый слой — свежий экземпляр со своим холстом (П16). `SavedMatrix` — выход поля. Из этого же приложения родилось правило П2: на клик слои отвечают «попал / не попал», а решение «выбран ровно один» принимает `Layers`. По П6 шаг сетки — параметр поля: `Field({ grid: 20 }, …)`.

### Пример 3. Разведка востребованности региона: радары спроса и перемен

Задача: два эксперимента — радар спроса (`pain-radar`: что людям нужно и где этого не дают, по отзывам с карт) и радар идей (`idea-radar`: что меняется в регионе и с какой даты, по лентам и госактам). Вопрос был: одно у них оглавление или два.

Верхний уровень — одно оглавление, но не один конвейер:

```js
const collectors = new Collectors({ rss, pravo, trudvsem, twogis }) // внешние источники: одна дверь, троттлинг, сырьё
const niches     = new Niches('ru-46')                               // общий язык: ниши и регион
const llm        = new Guarded(llmGuard, completeChat)               // квота и слот — обёртка

const demand = new DemandRadar(collectors, niches, llm)   // что людям нужно и где этого не дают
const shifts = new ShiftRadar(collectors, niches, llm)    // что меняется, для кого и с какой даты
const ideas  = new Ideas(demand, shifts, new IdeaRank())  // идея = спрос × сдвиг × человек

new RegionScout(demand, shifts, ideas).run()
ideas.run(person) → Idea[]                                // анкета — вход запуска, а не зависимость
```

Хребты двух радаров — конвейеры одной формы:

```js
new ShiftMap(                 // шум · слабый · сильный сигнал; календарь сроков
  new ShiftCounts(            // неделя × предмет × ниша ÷ поток источника
    new Shifts(               // 0…N на сюжет: тип, предмет, адресаты, дата, цитата
      new Stories(            // один факт в пяти изданиях — один сигнал
        new Publications(     // заголовок, лид, текст госакта
          new Feeds())))))    // ленты региона

new DemandMap(                // дефицит · смешанно · насыщено · слабый сигнал
  new NeedCounts(             // по организациям: «не получили» / «ценят, что есть»
    new DemandSignals(        // потребность × полярность × услуга, цитата
      new Reviews(            // отзывы клиентов
        new Places()))))      // места ниши — они же знаменатель
```

| Форма | Радар перемен | Радар спроса |
|---|---|---|
| совокупность, она же знаменатель | `Feeds` | `Places` |
| сырой текст | `Publications` | `Reviews` |
| единица независимости | сюжет: статьи не считаем | организация: отзывы не считаем |
| сигнал (модель + справочник + сверенная цитата) | `Shifts` | `DemandSignals` |
| вердикт — чистое действие | `ShiftRank` | `NeedVerdict` |

Что показало оглавление:

- «Радар идей» назван не по выходу — его выход сдвиги, а идеи делает корневой читатель (честное имя — `ShiftRadar`);
- переименование «боли → спрос» поменяло состав узлов, а не только имена: исчез фильтр негатива, появилось правило автора;
- склейка госактов нарушала различимость (до 64 актов в одном сюжете);
- знаменатель должен быть объявлен один раз.

Урок честности (П3): конвейер называет формы данных, но ступени не вызывают друг друга в памяти. Их связывает БД, а запускают разные зачинщики. Поэтому честная сборка показывает темп обёртками:

```js
new ShiftRadar(
  new Every(6h, new Refresh(publications, stories)),      // таймер: опрос → склейка
  new Ops({ actTexts, mark }),                             // кнопки админа: платное и тяжёлое
  new ShiftMap(new ShiftCounts(feeds), new ShiftRank()),   // чтение страницы — ничего не пишет
)
```

### Пример 4. Кому автоматизировать — оглавление, исполненное за одну сессию

Задача: найти в нише города компании, которым программист может предложить автоматизацию (сайт с каталогом, умного ассистента, канбан-воронку), и показать, что предложить и почему.

```js
const tree = new ProcessTreeStore({ keepRoots: 20 })              // вехи прогонов: что реально произошло

const scan = new NicheScan({
  worldOf: (niche) => ({                                          // внешний мир прогона
    source: new NicheFiles(dataDir, niche.files),                 // честный простой узел: файлы вместо 2ГИС
    marking: new RecordedMarking(dataDir, niche.files),           // записанная разметка вместо LLM
  }),
  places: new Places(),                                           // места ниши: рубрика ≠ ниша
  each: new EachPlace(new PlaceAudit({                            // узел дерева на каждое место
    card: new CardFacts(),                                        // каналы, гигиена, масштаб
    site: new SiteFacts(),                                        // каталог, цены, заказ, чат
    reviews: new ReviewFailures({ catalog: new FailureCatalog(), freshFrom: '2024-01-01' }),
  })),
  plan: new LeadPlan({ gaps: new DigitalGaps(), rule: new LeadRule({ maxBranches: 3 }), offers: new OfferCatalog() }),
})

const scans = new Scans({ scan, tree, niches: NICHES })           // хозяин прогонов: start ↔ stop
```

UI — спека страницы из четырёх блоков; своего фронтенда у эксперимента нет:

```js
Pages({ main: { title: 'Кому автоматизировать', blocks: [
  { kind: 'table@1', src: '…/niches', title: 'Ниши' },      // пульт: «Разобрать» / «Остановить»
  { kind: 'table@1', src: '…/leads', title: 'Лиды' },       // проекция результата
  { kind: 'table@1', src: '…/products', title: 'Продукты' },
  { kind: 'tree@1', src: '…/scans', title: 'Прогон' },      // зеркало процесса
] } })
```

Что показал этот пример:

- **Путь «оглавление → работающий прототип» прошёл за одну сессию.** 150 мест, 604 узла дерева, 106 лидов с цитатами; узлы-заместители (`NicheFiles`, `RecordedMarking`) потом заменяются живыми без правки дерева.
- **Набросок на бумаге поправила проба соседями.** Работы аудита сначала назывались `CardGaps` и `SiteGaps`, а стали `CardFacts` и `SiteFacts`: дети сообщают факты, пробелы и вердикт решает чистое действие.
- **Зеркало само указало на свой изъян.** У группы из 150 мест было видно «✓ 150», а 68 пропусков «сайта нет» прятались уровнем ниже. Так в проекции появилась свёртка исходов по глубине.

### Пример 5. Заявка, которая не потерялась

Ситуация из практики госорганизации. Работодатели подают заявки на субсидию на выплаты работникам при простое компании; заявка — письмо по электронной почте с приложенными документами. Письмо не дошло — выплат нет, и обе стороны узнают об этом слишком поздно. Если бы этапы фиксировались — «отправлено → получено → обработано» на доске, которую видят обе стороны, — потеря обнаружилась бы в первый день. Даже без доски помог бы второй канал: бумажный экземпляр или звонок.

```js
new Applications(                                    // хозяин заявок: приём, путь, тишина
  new Intake({                                       // реестр каналов: все сходятся в одну заявку
    email: new MailboxIntake(),
    form: new SiteForm(),
    paper: new PaperIntake(),
  }, { key: (a) => [a.inn, a.period] }),             // одна заявка, сколько бы каналов её ни принесли (П36)
  new Application(                                   // сущность: путь заявки (П21)
    new Stages('sent → received → checked → approved | returned(причина) → paid'),
    new Receipt(),                                   // квитанция отправителю на каждом переходе (П39)
  ),
  new SilenceWatch({ received: '1d', checked: '5d' }), // тишина дольше срока — состояние с выходом (П38)
  new Board(),                                       // канбан сотрудников — проекция путей
  new StatusPage(),                                  // окно отправителя: шаги 1 → 2 → 3 этой заявки (О15)
)
```

Разбор:

- **Универсален не канбан, а форма промежутка между сторонами** (П38). «Отправил и жду» — состояние со сроком, владельцем и выходом, а не тишина. У электронной почты нет квитанции, поэтому потеря невидима. Канбан — лишь проекция пути заявки.
- **Квитанция — выход для входа** (П39): отправитель узнаёт, что заявка принята, там же, где отправил.
- **Бумажный экземпляр или звонок — это outbox в жизни** (П35). Второй канал даёт «хотя бы раз», а ключ заявки (ИНН и период) не даёт удвоить её (П36).
- **Две проекции одной сущности:** доска для тех, кто двигает карточки, и окно статуса для того, кто ждёт. «Письмо не дошло» лечит именно второе, и именно его нет во внутреннем канбане `chat-engine`.
- **Почему это работает почти везде.** Процесс любой организации — цепочка передач между сторонами: клиент → магазин → склад → доставка; работодатель → госорган → казначейство. Самая частая авария — передача, потерянная в тишине. В отзывах из примера 4 это линии «связь и статусы» и «доставка и сроки».

### Пример 6. Умный дашборд управления компанией — контур и станция

Задача из вакансии: объединить данные Битрикс24, 1С, TrueStats, WB и Ozon в «умный AI-дашборд». Он должен показывать руководителям состояние бизнеса и причины отклонений; выявлять риски, несоответствия и точки роста; помогать решать и запускать согласованные сценарии; учитывать роли; оценивать отделы и планёрки; фиксировать эффект в деньгах, времени, качестве и скорости.

Ш0: *платформа замыкает петлю «факт → отклонение → решение → эффект» для каждого отдела компании.* Хребет — конвейер форм данных:

```js
new Effects(                  // эффект в ₽, часах, качестве, скорости; эффект платформы — их свёртка
  new Decisions(              // вариант из каталога, владелец, согласование, запуск
    new Causes(               // дерево драйверов (арифметика) + рассказ модели со сверенными цифрами
      new Signals(            // разрыв метрики в срезе с базой; у сигнала есть путь
        new Facts(            // метрика × срезы × период, со свежестью источника
          new Extracts()))))) // выгрузки источников как есть
```

Честная сборка — кто задаёт темп:

```js
new ControlLoop(
  new Every('1h', new Refresh(sources, facts, signals)),               // таймер: выгрузки → факты → сигналы
  new Ops(access.act, { own, dismiss, decide, approve, launch, stop,   // кнопки людей — через полномочия
                        ask: new Ask(llm, facts.scoped(access.see)) }),
  new Outbox(new Retry(5, effectors)),                                 // действия в мир — отдельно (П35, П36)
  new Every('1d', effects),                                            // замер по окнам решений
  new Weekly(new Meetings(signals, decisions)),                        // планёрка: повестка из петли
  new Cabinets(access.see, cabinetSpec),                               // только чтение
)
```

Второй заход — с высоты: что каркас, а что модуль. Каждое требование вакансии делится на две доли:

| Требование | В каркас сразу | Модулем сбоку |
|---|---|---|
| объединять данные | форма факта, общие справочники с ключами, каталог метрик | адаптер на каждый источник |
| состояние и причины, риски, рост | сигнал как сущность, дерево драйверов в каталоге | детекторы, рассказчик-модель |
| помогать решать, запускать сценарии | решение с путём; согласование, полосы, отложенная доставка, отмена | советник-модель, каждый сценарий |
| роли | охват × полномочия на двери фактов | шаблоны ролей |
| оценка отделов и планёрок | метрики петли из журнала решений | виды |
| эффект | снимок «до» и мера в решении | формула замера |

Каркас целиком — с отсеками, приборами, правилами приёма из источников и стыковки — вынесен в живой документ [company-station.md](company-station.md).

Пробы сценариями: API WB молчал шесть часов — ячейка «не проверяли», а не «−100 %» (О10); руководитель спрашивает ассистента о марже всей компании — модель видит только его срез (О20); «выручка ниже плана» пересчитывается каждый час — одна сущность сигнала по ключу, а не 24 уведомления; подняли цену, продажи упали — решение уходит в `not_confirmed`, и «вернуть цену» доступно там же, где запуск (П39); два руководителя правят цену одного товара — полоса занята, второму отказ с причиной (О16).

Что показал этот пример:

- **«AI-дашборд» назван не по выходу** — как «радар идей» в примере 3. Дашборд — проекция; выход системы — решения с измеренным эффектом. Честное имя корня — контур управления.
- **AI — не слой, а четыре места:** объяснить причину, подобрать вариант, ответить на вопрос, подытожить текст. Детектор — арифметика. В ядре модели нет: по тесту выключения (П30) без неё станция находит, решает и меряет, только без рассказов.
- **Объединяется не всё, а форма наблюдения и ключи.** Универсального формата всех данных нет, и он не нужен. REA (ресурсы, события, участники, обязательства) говорит, что есть в мире; Кимбалл (процесс, зерно, согласованные измерения) — как это мерить. «Выручка ≠ выручка» — родня «рубрика ≠ ниша»: каталог метрик с хозяином истины — первый артефакт.
- **Уклон в торговлю — свойство вакансии, а не каркаса.** У экономического события две формы: обмен (торговля — граница компании) и превращение (производство — её внутренность). Обмен есть везде, поэтому кажется, что торговля — это всё; но торговля — отсек. Технологии и рецептуры живут в MES и PLM, станции от них нужны нормы.
- **Четыре вида сигналов — один сигнал с осями** (О23). Вопросы «отклонение — всегда недостача? точка роста — его антоним? риск — крайнее отклонение?» развели оси: база, время, сторона, вес, доверие. Отклонение бывает с любой стороны (у метрики — направление пользы или коридор); риск — отклонение в будущем времени, а опасность — отдельная ось веса; точка роста — потенциал тиражирования; несоответствие — сигнал о доверии к остальным.
- **Двойственность REA дала детектор, не зависящий от ниши** — разорванную пару (О22).

| О20 | Политика на двери фактов | роль режет данные там, где их читают все потребители: кабинет, модель, уведомление, выгрузка; новый потребитель не может забыть фильтр (П27); роль — две оси: охват по оргструктуре × полномочия | ассистент, который не видит больше спрашивающего (6) |
| О21 | Ритуал — вид на петлю | планёрка, отчёт, оценка отдела — не модуль со своими данными: повестка собирается из открытых сигналов и судьбы прошлых решений, итог — новые решения, оценка — метрики петли за период | планёрки и эффективность отделов (6) |
| О22 | Разорванная пара | у экономического события есть вторая половина: обмен (отгрузка ↔ оплата, предоплата ↔ поставка) и превращение (расход сырья ↔ выпуск); половина без пары дольше срока — сигнал. | О23 | Сигнал с осями | сигнал — один: разрыв между значением метрики в срезе и базой. Новый вид сигнала — новая база, а не новый механизм; опасность — ось веса, а не отдельный вид | отклонение, риск, точка роста, несоответствие (6), [company-station.md](company-station.md) §4.6; полярность «не получили / ценят» и сила сигнала в радарах (3) — оси стороны и веса |

## 5. Как тренироваться

Формат одного упражнения:

1. **Дано:** предметная область в 1–3 предложениях.
2. **Рассказ** в 5–9 предложениях: кто зачинщик, что единица работы, чем кончается.
3. **Оглавление** одним выражением: хребет, пульт, общие узлы.
4. **Пробы:** пересказ без машинерии; выдуманный сценарий (повтор, отказ, двое одновременно, человек вернулся); соседи — стало ли им проще.
5. **Паттерны:** какие из раздела 4 встретились, что нового — кандидат в таблицу.
6. **По желанию — исполнить:** сквозной прогон на честных простых узлах.

Кандидаты на ближайшие занятия:

- **три универсальных продукта** — сайт с каталогом, умный ассистент, канбан-воронка: их всё равно писать, оглавление — первый шаг;
- **модуль «Подбор крепежа»**: параметры, совместимость, линейка 1:1;
- **определитель резьбы по фото** — другая порода: клиентское приложение, камера, обработка сигнала, микроплатежи;
- **запись к мастеру** (барбершоп, шиномонтаж) — время, отмена, неявка;
- **переписка менеджера с клиентом** — для сравнения с готовым оглавлением `chat-engine`;
- **чужая система** — заход в чужой код через оглавление (три вопроса П31).

## 6. Путь к движку

Движок — то, что превращает описание предметной области в работающий прототип. По ступеням:

| Ступень | Что умеет | Состояние |
|---|---|---|
| 0 | человек пишет оглавление по канону, агент исполняет его в коде | есть: пример 4 |
| 1 | каталог паттернов (раздел 4) и складских кирпичей: адаптеры источников, обёртки, хозяин прогонов, компоненты UI, дерево процессов | собирается: компоненты и process-tree есть, паттерны — с этого документа |
| 2 | агент по рассказу строит оглавление и пробы сам, человек правит | впереди |
| 3 | оглавление исполняемо: из декларации сразу получается каркас — узлы-заместители с контрактом, узлы дерева, спека UI, тесты на контракты | впереди |
| 4 | редактор оглавления: правка дерева = правка системы | впереди |

Что для этого нужно:

- **словарь ролей и связей** (восемь родов узла, шесть видов связи) как машиночитаемая грамматика;
- **кирпичи со стандартным контрактом** `run(input, ctx)` и узлом дерева в `ctx`, чтобы любой узел сразу был виден в зеркале;
- **заместитель для каждого внешнего мира** — файл, запись, фиксированный ответ, — чтобы оглавление исполнялось с первой минуты;
- **пробы как проверки**: пересказ, сценарий, соседи — сначала вопросами агенту, потом тестами.

Честные границы:

- Оглавление ускоряет каркас, а не прозрение. «Рубрика ≠ ниша», «похвала = насыщение», «консультации жалуются в основном на сети» пришли из данных, не из дерева.
- Движок, который строит «любое приложение», рискует стать интерпретатором поверх языка: длинные стеки, деревья из `ManagerHelper`, объекты ради объектов. Мера канона (П13, П34) действует и здесь.
- Правило проверки: оглавление, которое нельзя прочитать вслух как описание системы, — не оглавление, даже если оно исполняется.

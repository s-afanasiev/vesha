## Краткая формулировка парадигмы

Подход можно назвать **декларативным композиционным ООП**:

1. объект — это прежде всего именованная роль или исполняемое намерение;
2. имя объекта описывает его единственную цель, а `run()` исполняет её;
3. приложение представляется графом маленьких объектов с доменными именами;
4. CompositionRoot записывает этот граф как исполняемую декларацию;
5. вложенность выражает владение, преобразование, набор возможностей или прототип — и вид связи должен быть понятен;
6. долгоживущий повторитель создаёт свежий процесс для каждой итерации;
7. `for`, `if/else`, retry, timeout и parallel могут становиться явными объектами-комбинаторами;
8. стабильная топология отделена от свежего состояния задачи;
9. единый lifecycle позволяет запускать и останавливать поддерево как один узел;
10. команды идут вниз, события готовности и результата — вверх;
11. вариативность достигается заменой узлов и реестрами участников;
12. реальные зависимости не имеют права существовать вне нарисованного графа;
13. крупные поддеревья получают собственные имена и становятся новыми словами архитектурного языка;
14. декомпозиция начинается с глаголов, повторений, решений и времён жизни;
15. декларация ценна не красотой скобок, а точностью отображения системы.

Главная формула (Gpt §1): **сначала проектируется язык описания приложения из объектов предметной области, затем конкретное приложение записывается предложением на этом языке.**

# Часть I. Основы

## §0. Главное правило: никакой «плоской простыни»

Один большой файл-сервис с последовательностью действий — запрещён. Любой процесс сначала разбивается на **смысловые шаги**, каждый шаг — отдельный класс с одной ответственностью. Процесс выражается **композицией** этих объектов:

```js
// корневой сценарий ← промежуточный шаг ← базовый шаг
new FrameExtract(new FramesAmount(new FileInfo()))
```

- `FileInfo` — получает данные о файле
- `FramesAmount` — на их основе считает число кадров
- `FrameExtract` — извлекает кадры

Каждый объект маленький, тестируемый, заменяемый. Читая композицию в точке сборки, видно весь процесс сверху, без чтения тел методов.

**Композиция — это одновременно архитектура и декларативное описание процесса.** Код читается как оглавление: видно, какой объект — корень операции, из каких шагов она состоит, как распределены уровни ответственности. Обсуждать архитектуру можно на уровне терминов предметной области, не погружаясь в детали.

Правила дерева композиции (однонаправленная иерархия):

- родитель управляет дочерними объектами; поток координации идёт сверху вниз;
- дети не знают о дереве целиком и не лезут к «братьям» напрямую;
- детали прячутся внутри поддеревьев — внутренний узел можно заменить, не ломая корень;
- собранное поддерево — самостоятельный переиспользуемый модуль.

Корневой объект композиции — по сути агрегат в духе DDD: он инкапсулирует законченный фрагмент бизнес-логики, а наружу выставляет не внутреннюю механику, а понятную точку входа (`run(data)`) и события жизненного цикла.

**Проверка себя:** если класс делает «получил → посчитал → сохранил → отправил» — это четыре класса, а не один.

### В iron-back

В репозитории уже есть модуль, который сделал этот шаг наполовину — и это самый сложный модуль проекта. [`push-notification.service.ts`](../src/modules/push-notification/push-notification.service.ts), 1475 строк, содержит **девять классов**:

```
PushNotificationService          @Injectable, корень
  UserSubscriptionWatchersCollection
    UserSubscriptionWatcher
      ProductLessonsStorage
      TaskTracker
      BranchTracker
      ViewedLessonTracker
  PushNotificationPostman
    AppleAPN
```

Имена ролевые (§8), композиция идёт через конструкторы, есть `run()` / `init(logger)` / `terminate()` — то есть жизненный цикл §5. **Это не простыня, это правильное дерево, не разложенное по файлам.** Что там реально не так:

1. **Всё в одном файле.** Адаптер к внешнему миру (`AppleAPN`) лежит вплотную к доменной логике; ни один узел нельзя переиспользовать или протестировать отдельно.
2. **Нет контрактов.** `PushNotificationPostman` знает конкретный класс `AppleAPN`, а не абстрактного «отправителя пуша». Подменить APNs на заглушку в тесте нельзя, не тронув код.
3. **Композиция собирается внутри корня**, а не в точке сборки модуля, — состав дерева не виден снаружи.

Хорошая новость: миграция такого модуля дёшева. Разложить по файлам → вынести два-три интерфейса → поднять сборку в `providers`. Логику трогать не надо.

Для сравнения, остальные крупные сервисы — [`sales.service.ts`](../src/modules/sales/sales.service.ts) (761), [`admin.service.ts`](../src/modules/admin/admin.service.ts) (695), [`order.service.ts`](../src/modules/order/order.service.ts) (614) — именно плоские: один класс, длинные методы. Вот они и есть образец того, чего быть не должно.

### E8. Агрегатор решает — дети только сообщают

В region_selector клик по полю раздаётся всем слоям, слои сообщают о попадании, а решение принимает **только** агрегатор:

```js
Object.keys(this._layers).forEach(layer_id => {
    this._layers[layer_id].square_click(x_square, y_square, hit => hits.push(hit));
});
if (hits.length == 0)      this.iFace.selected_layer(false);
else if (hits.length == 1) this.iFace.selected_layer(hits[0]);
else console.error("unexpected behavior. more than one layers selected:", hits);
```

Ни один слой не знает о существовании других и не решает, выделен ли он «в итоге». Заодно инвариант («одновременно попасть можно ровно в один слой») проверяется в одном месте — там, где он вообще осмыслен.

Та же логика на поверхности: ребёнок не трогает чужой DOM, а отдаёт элемент владельцу территории — `field.attach(canvas, "grid")` / `field.detach("grid")`, `iFace.attach(this.dom)`. В коде это даже проговорено комментарием: «say to field to append canvas».

**Правило:** дети сообщают факты («попал», «готов», «не смог»), родитель превращает факты в решение и владеет инвариантом. Как только ребёнок начинает рассуждать о результате целиком, дерево перестаёт быть однонаправленным.

Смежное: Gpt §12 (§7) — про совпадение дерева объектов и дерева UI; здесь — про распределение права решать.

## §1. Каркас и реализация — две разные сущности

Приложение делится на:

1. **Каркас (skeleton)** — доменно-нейтральный механизм. Не знает про Telegram, блогеров, Trello, Kafka, браузеры — и, в этом репозитории, про уроки, экспертов, продукты, Vimeo, Тинькофф.
2. **Реализация (плагины/адаптеры)** — конкретные модули, подключаемые к каркасу через DI и реализующие его контракты.

В naf это выражено буквально:

```
src/naf/core/      каркас: contracts, gateway, queue, router, runtime, ...
src/naf/domains/   плагины: mock, development, marketing, bloggers
```

**Правило чистоты ядра:** в каркасе запрещены доменные слова (blogger, trello, content...). Если доменный термин просочился в имя метода, события или параметра каркаса — это регресс, чинить сразу.

**Критерий правильности границ:** «голый каркас» должен запускаться на моках — принимать задачи, раздавать их фейковым исполнителям и выдавать фейковые результаты, не требуя ни одной реальной интеграции (`tests/skeleton/`). Если для smoke-теста приходится править ядро — граница выбрана плохо.

### В iron-back

В NestJS граница выражается модулями. Каркасное здесь — `guards/`, `filters/`, `inteceptors/`, `modules/logger`, `modules/config`, `modules/cache`. Доменное — `modules/lessons`, `modules/products`, `modules/experts`, `modules/order` и т. д.

**Правило чистоты каркаса:** в каркасных модулях запрещены доменные слова. Если `lesson`, `expert`, `vimeo`, `tinkoff` просочились в имя метода, события или параметра каркаса — это регресс, чинить сразу.

**Критерий правильности границ:** каркас должен подниматься на моках — без реальной БД, без Vimeo, без APNs. Если для smoke-теста приходится править каркас, граница выбрана плохо. Заготовка для этого уже есть в ветке `ai26` (`modules/mock-db` на `pg-mem`, `modules/mock-cache`) — её стоит забрать отдельным PR, но **не внутри апгрейда** (§12).

### E20. Каркас и домен: три механические проверки

§1 объявляет, что каркас и реализация — разные сущности. `me_preview` добавляет то, чего там нет: **как это проверить не на глаз**.

**Критерий правильности — голый каркас запускается.** Не «выглядит нейтрально», а буквально: собираем дерево из каркасных модулей и моков, гоняем N партий, считаем подтверждения. Ни одной строки про браузеры, очередь, почту.

```
AppOrchestrator
  ├ MockTaskSource        (выдаёт батчи каждые 5 с)
  ├ BatchProcessor        (каркас, без изменений)
  └ AgentService          (каркас, без изменений)
      ├ ResourceAllocator (каркас, без изменений)
      ├ MockResourcePool  (3 виртуальных ресурса)
      └ MockTaskWorkflow  (спит 1–3 с, иногда «падает»)
```

Критерии успеха теста сформулированы так, что их нельзя пройти обманом: ни один файл `src/` не правится, нет обращений к внешним системам, все аренды освобождены, счётчик подтверждений равен числу партий, в дереве процессов нет висячих обещаний.

**Словарный тест.** Ревью-чек-лист на любой PR, трогающий каркас: есть ли в диффе слова `browser`, `chrome`, `cdp`, `puppeteer`, `gmail`, `kafka`, `ftp`, `mongo`. Если да — либо убрать, либо явно обосновать. Это самая дешёвая защита от протечки, какая бывает: она выполняется грепом и не требует понимания кода.

**Таблица переносимости.** Мысленно переносим систему на другую платформу и смотрим, какие строки меняются:

| Модуль | браузеры | Android-ферма | ферма кодировщиков |
|---|---|---|---|
| **BatchProcessor** | **каркас** | **каркас** | **каркас** |
| **ResourceAllocator** | **каркас** | **каркас** | **каркас** |
| ResourcePool | `BrowserPool` | `AndroidDevicePool` | `EncoderWorkerPool` |
| ExecutionEnvironment | обёртка CDP | обёртка adb | обёртка процесса |
| TaskWorkflow | `MultiClientTask` | `AndroidScreenshot…` | `EncodeOneFile…` |

И вывод, ради которого таблица нужна: **«если мысленный пример требует менять batch-processor, значит граница абстракции выбрана плохо».** Это готовый тест на любую границу, а не только на каркасную.

**Паспорт модуля.** Каждый каркасный узел описан одинаково: роль, контракт (вход/выход), зависимости, текущая реализация, мок для теста. Пять строк — и модуль можно заменить, не читая его код.

**Честная оговорка, которой обычно не делают.** Тот же проект от одного из контрактов сознательно отказался: источник задач формализовывать не стали — второго источника не предвидится, а «голый каркас» решается моком, мимикрирующим под текущую реализацию. Отсюда правило: **мок можно написать и против неявного контракта; вынос контракта в отдельный модуль — отдельная покупка со своей ценой** (§9, и подробнее — E27).

Где контракты всё-таки зафиксировали — их проверяют **на старте**: описание плюс runtime-валидатор, а смоук прогоняет не только правильные реализации, но и девять заведомо поломанных. Питоновский аналог — `Protocol` плюс проверка при сборке дерева: несовместимость ловится в точке сборки, а не на первом вызове в проде.

**В telebot.** Явного каркаса там нет, и выдумывать его не надо. Но два узла ведут себя как каркасные и стоят словарного теста: приём вебхука (`vanna/webhook_intake.py` — дедуп и ранний ACK не знают, что такое блогер) и очередь исходящих (`vanna/outbound_queue.py` — захваты и ретраи не знают, почему сообщение отправляют). Если в них появятся слова из воронки — это регресс, видимый грепом.

### E9. Транспорт — тонкий адаптер с единым конвертом

`main.js` iPhone-проекта — образец того, как должен выглядеть внешний слой:

```js
function asyncRoute(handler, routeLogger = logger) {
    return async (req, res) => {
        try {
            const result = await handler(req, res);
            if (!res.headersSent) res.json(result);
        } catch (err) {
            routeLogger.error(err);
            res.status(500).json({ ok: false, error: err?.message ?? String(err), ...steps });
        }
    };
}

app.post('/api/disconnect', asyncRoute(async () => ({
    ok: true,
    result: await controller.disconnect(),
    status: await controller.getStatus(),
})));
```

Что здесь стоит забрать:

- **Ни одного `try/catch` в ручках.** Обработка ошибок и формат ответа — один раз, в обёртке. Новый роут не может «забыть» конверт.
- **Ручка — одна строка делегирования.** Бизнес-логики в транспорте нет вообще; заменить HTTP на Telegram/CLI/очередь = переписать один файл.
- **Каждый ответ несёт снимок состояния** (`status`, `productionRuntime.health()`), а не только результат команды. Клиенту не нужен второй запрос, чтобы перерисовать себя, и рассинхрон UI с системой становится невозможным. Это дешёвая версия наблюдаемости из §7: состояние прикладывается к каждому ответу, а не собирается отдельным механизмом.

**В telebot:** хендлеры Telegram — тот же тонкий адаптер к корню территории; вся логика — в корне, в хендлере остаются разбор апдейта, вызов сценария и единый конверт ответа/ошибки.

## §2. Контракты вместо наследования

**В доменной логике наследование запрещено.** Классы нашей бизнес-логики не наследуют друг от друга и не образуют иерархий — ни глубоких, ни «всего в один уровень». Классическое «`Square` и `Circle` наследуют от `Shape`» — ровно то, чего у нас не бывает. Расширяемость и переиспользование — только через **контракты (интерфейсы/Protocol) + композицию + агрегацию + адаптеры**:

- нужен общий контракт для семейства классов — `Protocol` в Python, `interface` в TypeScript (структурная типизация, без наследования от базы);
- нужен «родитель» для группы объектов — класс-**агрегатор**, который держит их списком или полями (композиция), а не базовый класс;
- нужно переиспользовать кусок логики — вынести его в отдельный объект и передать через конструктор, а не «отнаследоваться и переопределить».

Почему жёстко: наследование связывает классы самым сильным из возможных видов связи — ребёнок зависит от потрохов родителя, правка базы молча меняет поведение всех потомков, а иерархия быстро становится ложной таксономией. Композиция даёт ту же выразительность с явными, заменяемыми связями.

Единственное исключение — **технические базы платформы**, без которых язык или фреймворк не работает: `Exception` для именованных ошибок, `Protocol` в объявлении контракта; в NestJS и TypeORM — `HttpException`, базовый `Logger`, `PartialType()` из `@nestjs/mapped-types`, `BaseEntity`. Это требование среды, а не способ переиспользовать нашу логику; доменного наследования не бывает вообще.

Правило при этом **не маниакальное**: оно про доменные таксономии, а не про техническую обвязку фреймворка. Там, где наследование — штатный способ работы с NestJS, TypeORM или платформой, оно остаётся как есть и не считается долгом (§2.2).

Пример из naf — точка расширения завода:

```python
class DomainPlugin(Protocol):
    name: str
    bot_type: BotType
    default_role: str

    def workflows(self) -> list[WorkflowSpec]: ...
    def tools(self) -> list[Tool]: ...
    def routing_rules(self) -> RoutingRules: ...
```

Новый домен = новая реализация протокола, ядро не меняется. `MockDomain` — «вечный житель» каркаса: минимальная корректная реализация контракта, одновременно smoke-тест и образец для новых доменов.

### §2.1. TypeScript: интерфейс исчезает в рантайме

Главное отличие от Python, где `Protocol` работает и в аннотациях, и в проверках. В TypeScript **интерфейс стирается при компиляции**, поэтому вот так DI не соберётся:

```ts
// не работает: Nest не может отрезолвить интерфейс — в рантайме его нет
constructor(private readonly sender: PushSender) {}
```

Рабочий паттерн — интерфейс для типа + токен для DI:

```ts
// contracts/push-sender.ts
export const PUSH_SENDER = Symbol("PUSH_SENDER");

export interface PushSender {
  send(deviceToken: string, payload: PushPayload): Promise<void>;
}
```

```ts
// потребитель зависит от контракта, а не от AppleAPN
constructor(@Inject(PUSH_SENDER) private readonly sender: PushSender) {}
```

```ts
// точка сборки — providers модуля
providers: [{ provide: PUSH_SENDER, useClass: AppleAPN }]
```

**Про `abstract class` как контракт.** Распространённый в Nest обходной приём: абстрактный класс существует в рантайме, поэтому годится и типом, и DI-токеном сразу. Пользоваться им можно, но с одним условием — **`implements`, а не `extends`**. TypeScript это позволяет: класс реализует форму абстрактного класса, не наследуя его. Так контракт остаётся контрактом и не превращается в базу с логикой. Если в абстрактном классе появился хоть один непустой метод — это уже наследование, откатываем к `interface` + `Symbol`.

### §2.2. Что в репозитории сейчас

Инвентаризация всех `extends` вне entity-файлов:

| Случай | Шт. | Вердикт |
|---|---|---|
| `*Exception extends HttpException / NotFoundException / BadRequestException` | 3 | ✅ техническая база платформы |
| `Update*Dto extends PartialType(Create*Dto)` | 5 | ✅ штатный механизм `@nestjs/mapped-types` |
| `CustomLoggerService extends Logger` | 1 | ✅ техническая база платформы |
| `*Entity extends BaseEntity` | 24 | ✅ паттерн TypeORM |
| DTO наследует Entity (`UserDTO`, `MediaDTO`, `FavoriteDTO`, `MappedFavoriteDTO`, `CreateOrderResponseDTO`, `GetOrderResponseDTO`) | 6 | ✅ приемлемо, см. ниже |
| `ExpertWithLessonsDTO extends ExpertDTO` | 1 | ✅ то же |
| `ExpertsService extends TypeOrmCrudService<ExpertEntity>` | 1 | ⚠️ уходит вместе с `@nestjsx/crud` |

**Доменных таксономий в проекте нет.** Ни одного случая вида «`Circle` и `Square` от `Shape`» — того, ради чего правило и написано. Это хорошая новость: главный анти-паттерн здесь просто не завёлся.

Про два оставшихся случая:

* **DTO наследует Entity** — это переиспользование формы данных, а не доменная иерархия, и в рамках NestJS/TypeORM это нормальный приём. Оставляем как есть. Единственное, о чём стоит помнить при правках: связь двусторонняя — новая колонка в таблице автоматически попадает в ответ API. Поэтому при добавлении полей в Entity полезно глянуть, не уезжает ли наружу лишнее. Это повод для внимательности, а не для переписывания.
* **`ExpertsService extends TypeOrmCrudService`** — здесь дело вообще не в стиле. Пакет `@nestjsx/crud` заброшен и лезет в приватные потроха Nest, поэтому [шаг 3 плана апгрейда](upgrade-plan.md) убирает его по чисто технической причине. Наследование исчезнет попутно.

**Где реальный разрыв — не в наследовании, а в контрактах: 9 `implements` на 282 файла, ни одного `.interface.ts`.** Именно это отделяет текущий код от целевого стиля, и именно с этим имеет смысл работать.

### §2.3. Правила работы с контрактами

- **Контракты лежат в отдельном месте** — `core/contracts/` в naf, `src/contracts/` или `<модуль>/contracts/` здесь — и являются самым стабильным слоем. Изменение контракта — решение уровня архитектуры, не рядовой задачи. Расширять добавлением — можно.
- **Модуль зависит от контракта соседа, а не от его конкретного класса.** `TaskAssigner` не знает, кто исполнит задачу — для него исполнитель это абстрактный agent с методом `executeTask(task)`.
- **Мысленный тест на границу:** «что придётся заменить, если вместо X средой станет Y?» Вместо браузера — Android, вместо Telegram — email; здесь — вместо Vimeo YouTube, вместо APNs FCM, вместо Тинькофф другой эквайринг. Если ответ «править каркас» — абстракция протекла.

### Gpt §13. Стаб и режим являются заменяемыми участниками структуры

В `Zoopark` рядом с реальными объектами видны `SpecialControllerMode`, `NormalControllerMode` и заглушки. Намерение здесь шире обычного тестирования: режим работы является участником композиции, а не россыпью глобальных флагов.

Правило:

> Вариативное поведение выражается заменой узла графа, а не условными ветками, размазанными по всем узлам.

Лучше передавать объект с минимальным контрактом `LauncherPort` или `AgentTransport`, чем неструктурированный `{stub: true}`: декларация должна показывать не только факт подмены, но и роль подменяемого элемента.

**Сверка (E).** С диагнозом согласны, но рецепт «вместо `{stub:true}` вводить `LauncherPort`» провоцирует плодить протоколы там, где достаточно честной реализации с говорящим именем (`StubLauncher`). Контракт заводим, когда есть ответ на «что заменяем» (§9). Смежное: E3 (§3) — там про настройку узла, здесь про его подмену; в части II — «флаг режима внутри узла» среди того, что мы не берём.

## §3. Dependency Injection и точка сборки как язык

- Все зависимости приходят **через конструктор** (или `init()`), объект сам ничего не импортирует напрямую из инфраструктуры и не создаёт синглтоны.
- Всё дерево объектов собирается в **одной точке** — CompositionRoot (`main`, `apps/gateway.py`). Именно там выбираются конкретные реализации под контракты. Точка сборки читается как декларация архитектуры:

```
ChromeApp(
  kafkaService,
  batchProcessor,
  agentService(
    browserPool,
    clientScope(gmailClient, yandexClient, ...),
    multiClientTask(oneClientSubtask(oneScreenshot(onePrepare(oneNavigate)))),
  )
)
```

- При переносе каркаса в другой проект переписывается только CompositionRoot и адаптеры; каркасные модули не меняются.

### В iron-back

В NestJS роль CompositionRoot играет массив `providers` каждого модуля — точка сборки распределённая, но она есть. Для деревьев из §0 используется `useFactory`:

```ts
@Module({
  providers: [
    { provide: PUSH_SENDER, useClass: AppleAPN },
    {
      provide: PushNotificationService,
      inject: [PUSH_SENDER, CustomLoggerService, getRepositoryToken(UserProductEntity)],
      useFactory: (sender, logger, userProducts) =>
        new PushNotificationService(
          new UserSubscriptionWatchersCollection(userProducts, logger),
          new PushNotificationPostman(sender, logger),
        ),
    },
  ],
})
```

Так состав дерева виден снаружи, а подмена любого узла на мок в тесте — одна строка.

**Что считать нарушением:** `new` от инфраструктурного класса внутри метода сервиса. Сейчас все найденные `new` в сервисах — это `new LessonEntity()`, `new ProductEntity()` и подобное, то есть создание данных, а не захват зависимости. Это нормально и правилу не противоречит.

### Gpt §1. Граф объектов как исполняемый язык

Главная повторяющаяся идея — точка сборки не просто создаёт зависимости, а **описывает систему**:

```js
new App(
  new Iface({
    LoadImgAction: new LoadImgAction(),
    AddZoneAction: new AddZoneAction()
  }),
  new Field(
    new ImageCanvas(new LoadedImage()),
    new Layers(new Layer(new Canvas()), new SavedMatrix())
  )
).run()
```

Такой код занимает промежуточное положение между программой и конфигурацией. Это **исполняемая декларация**: имена объектов образуют словарь, вложенность — грамматику, а `run()` превращает описание в работающую систему.

Отсюда более точная формула парадигмы:

> Сначала проектируется язык описания приложения из объектов предметной области, затем конкретное приложение записывается предложением на этом языке.

Хорошая точка сборки отвечает на вопрос «из чего состоит система», но не «как внутри реализован каждый элемент».

**Сверка (E).** Эта формула точнее всего, что есть в разделах E: она объясняет не «как устроено», а **зачем** композиция вообще ценна — имена дают словарь, вложенность грамматику. Считаем её главной.

### Gpt §2. Архитектура должна быть видна до чтения реализаций

В `MUMO` один короткий фрагмент показывает крупные территории: `ManagersHub`, `ManagersControl`, `ManagersBroadcast`, `TrackedJobs`, `RunningJobs`, `ConnectedUsers`. В `Zoopark` видны сервер, страницы, браузерные клиенты, кластер хостов, launcher, controller и jobs.

Это даёт критерий качества:

> Читатель должен суметь набросать схему приложения, прочитав только CompositionRoot и имена конструкторов.

Если для понимания состава системы нужно заходить в тела методов, декларация недостаточно выразительна. Если точка сборки переполнена настройкой сокетов, SQL, DOM или алгоритмами, в неё протекла механика.

### Gpt §3. Вложенность выражает смысл связи, а не просто передачу аргумента

В примерах скобки несут архитектурный смысл:

```js
new Layer(new Canvas())
new RunningJobs(new RunningJob())
new HostCluster(new HostAsPair(new Launcher(), new Controller()))
```

Вложенность читается как «состоит из», «управляет», «применяет» или «создаёт экземпляры по прототипу». Поэтому порядок аргументов конструктора — часть архитектурного языка, а не случайная техническая деталь.

Правило:

> Вкладывать объект в объект стоит только тогда, когда связь можно назвать устойчивым доменным глаголом.

Если связь нельзя ясно прочитать (`A(B)` не означает ни «A использует B», ни «A содержит B», ни «B — следующий шаг A»), лучше ввести именованный параметр, отдельный агрегат или именованное поддерево.

**Сверка (E): требование сказано слишком узко.** Глагольность отсекает половину законных случаев: `FrameLimit(ExtractFrame)` — не глагол, а обёртка; `Layers(Layer())` — не глагол, а прототип. Правильнее мягче: связь должна опознаваться как **один из известных видов** — и список видов (часть II, «Виды композиции») важнее требования глагольности.

### Gpt §14. Глубокая композиция требует именованных поддеревьев

У исполняемого DSL есть предел: слишком глубокая вложенность превращается в «архитектуру из скобок». Особенно это видно в больших корнях `Thumbnail` и `Zoopark`.

Поэтому:

> Как только поддерево получает самостоятельный смысл, ему нужно имя.

Вместо одного выражения глубиной в десять уровней можно собрать:

```js
const fileInfoPipeline = FileInfoPipeline(...)
const frameExtractor = FrameExtractor(fileInfoPipeline)
const hostRuntime = HostRuntime(...)

App({ frameExtractor, hostRuntime }).run()
```

Это не разрушает декларативность. Напротив, именованные поддеревья вводят в язык новые смысловые слова и позволяют читать архитектуру в нужном масштабе.

**Сверка (E).** Прямая и нужная поправка к E1 (лестница абстракций): лестница требует резать процесс на ступени, но десять уровней в одном выражении читать невозможно. Как только группа ступеней получает самостоятельный смысл, ей нужно имя — и оно становится новым словом языка из Gpt §1.

### E11. Оглавление без шума

Мелкая, но повторяющаяся во всех пяти файлах привычка: **точка входа — первая исполняемая строка**, определения ниже (`main();` в Zoopark, `new App().run();` в MUMO, `main(cb)` в Thumbnail). Файл открывается тем, что делает система, а не двадцатью `require` и первой попавшейся процедурой.

И следствие: в точке сборки не должно быть ничего, кроме сборки. Всё служебное — в один явно названный метод, который в оглавлении занимает одну строку:

```js
this.run = () => {
    const aLog = new ALog().run();
    const dataBase = new DataBase().run(aLog);
    this.extra(aLog, dataBase);      // ← перехват console.debug, process.on(...)
    new HttpUserServer().run();
    ...
}
```

`extra()` — честное имя: «здесь то, что нужно, но не является архитектурой». Лучше одна такая строка, чем пять технических вставок посреди декларации.

### E3. Параметры поведения объявляются в декларации, а не прячутся в узле

Zoopark задаёт политику живучести прямо в точке сборки:

```js
new Launcher(
    {stub:true},
    new SocketKeepAliveConfirmation({msg_to_receive:"i_am_alive", time_to_panic:60000})
)
```

Читая корень, видно не только «есть keepalive», но и **на каких условиях**: какое сообщение считается признаком жизни и через сколько поднимать тревогу. Тот же приём — `new SavedMatrix("./arr.json").testmode()` в region_selector: подмена источника данных объявлена сверху, одной строкой.

Контрпример из того же набора — Thumbnail: предел параллельных ffmpeg живёт модульной константой и проверяется внутри:

```js
const FFMPEG_LIMIT = 3;                                   // где-то вверху файла
isAllowLimit: function(){ return (this.limit < FFMPEG_LIMIT); }   // глубоко внутри MemDb
```

Дерево при этом выглядит одинаково в обоих случаях, но в первом декларация отвечает на вопрос «как система себя ведёт», а во втором — только «из чего она собрана».

**Правило:** число, которое меняет поведение системы (таймаут, лимит, размер окна, порог), — часть декларации. Его место — аргумент узла в точке сборки или явный конфиг, переданный туда же. Внутри узла остаются только величины, не имеющие смысла снаружи.

**Проверка себя:** «где посмотреть, через сколько секунд мы считаем агента мёртвым?» Если ответ — «надо найти класс и прочитать метод», параметр спрятан.

Смежное: Gpt §13 (§2) — там про подмену узла, здесь про его настройку.

### Gpt §9. Коллекция возможностей тоже является декларацией

В `region_selector` действия интерфейса передаются объектом-реестром. `Iface` не перечисляет конкретные кнопки внутри себя, а применяет единый ритуал ко всем подключённым действиям:

```js
Object.keys(actions).forEach(name => {
  actions[name].init(this).run(field)
})
```

В `Zoopark` похожую роль играет fluent-описание страниц:

```js
new Pages()
  .with("/", new Page("/"))
  .with("/io_address", new Page("/io_address", address))
```

Отсюда два принципа:

1. **Одинаковые возможности подключаются данными**, а не новыми ветками `if`.
2. **Добавление участника не должно менять агрегатор**, если контракт участника уже существует.

Реестр — это не service locator, если он принадлежит конкретному агрегату, содержит только его участников и не доступен глобально.

**Сверка (E).** Эта граница «реестр ≠ service locator» важна и для таблиц-диспетчеров из E17 (часть III): таблица обработчиков законна, пока принадлежит своему агрегату.

### Gpt §10. Fluent API полезен, когда он формирует законченную структуру

Метод `.with()` превращает императивное «создай страницу, положи в карту, зарегистрируй маршрут» в предложение «страницы с такими маршрутами».

Хороший fluent API:

- использует слова предметной области;
- на каждом шаге сохраняет валидную структуру;
- не скрывает неожиданных внешних эффектов;
- заканчивается явной границей исполнения (`build`, `run`, `start`);
- формирует данные или граф, а не заменяет цепочкой всю бизнес-логику.

То есть fluent-цепочка — это **строитель декларации**, а не самоцель.

### Gpt §15. Нельзя превращать родителя в неявный контейнер зависимостей

В старом `Thumbnail` функция `CallbackProps2(this, parent)` динамически прокидывает ребёнку `cbLog`, `cbDb`, `cbRes` и другие возможности родителя. В этом видна хорошая цель: не импортировать глобальные сервисы и обеспечить единый поток событий. Но конкретный приём опасен:

- контракт ребёнка не виден в конструкторе;
- ребёнок фактически зависит от устройства предка;
- возможности появляются динамически;
- рефакторинг дерева может молча сломать поведение.

Уточнённый принцип:

> Ребёнок получает не `parent`, а минимальный именованный контекст возможностей.

Например:

```js
step.init({
  events: processNode,
  logger,
  taskRepository
})
```

Ещё лучше — стабильные зависимости передавать в конструктор, а в `init` оставлять только контекст конкретного запуска. Так сохраняется направление старой идеи без скрытой сцепленности.

**Спор (E).** Диагноз верный (`CallbackProps2` прокидывает возможности динамически), но `init({events, logger, taskRepository})` — тот же мешок с фиксированным списком ключей: контракта по-прежнему не видно в конструкторе, опечатка ловится в рантайме. Честнее: **сквозные службы вообще не являются зависимостью узла** — журнал, аудит и метрики становятся обёрткой (E4, часть II) либо узел эмитит события, не зная подписчиков (§7).

**Поправка по цене (E26).** «Не зная подписчиков» — верно, но из этого не следует полноценный observer. Он стоит двух прыжков глазами вместо одной самодокументирующейся строки; дешёвый шаг с тем же эффектом для тестов — инъекция вместо синглтона.

### Gpt §16. Композиция не оправдывает глобальное состояние

`global_base64image`, `app.locals.*`, общие mutable-поля и произвольный доступ к `Iface.global_vars(name)` показывают места, где декларативная структура ослабевает: реальная зависимость перестаёт совпадать с нарисованным деревом.

Проверка:

> Если объект может изменить значимое состояние другого узла, не имея явной связи с ним в CompositionRoot или контракте события, граф врёт.

Общее состояние должно принадлежать ближайшему общему агрегату. Дети либо задают ему смысловые команды, либо получают immutable snapshot, либо публикуют события. Глобальная переменная — связь вне архитектурной схемы.

**Сверка (E).** Готовая острая проверка, применяем как есть.

### Gpt §17. Декларативность — это честность структуры, а не минимум строк

Короткая запись сама по себе ничего не гарантирует. Выражение может выглядеть красиво, но скрывать:

- создание инфраструктуры внутри `run`;
- неявный доступ к предку;
- общую мутабельную зависимость;
- несовместимые lifecycle;
- случайный порядок запуска;
- объект, который делает несколько несвязанных работ.

Итоговый критерий:

> Декларативный код хорош тогда, когда видимая структура совпадает с реальными владением, потоком управления, границами состояния и порядком жизни объектов.

**Сверка (E).** Дополняет критерий из E18 (часть IV): там сказано «должен появиться один экран, объясняющий систему», здесь — «и этот экран не должен врать про владение, поток управления и порядок жизни». Два критерия работают только вместе.

## §4. Говорящие методы: объекту задают вопрос, а не читают его поля

Объект инкапсулирует своё состояние и отвечает на **смысловые вопросы**. Снаружи не должно быть арифметики над чужими полями:

```js
// плохо: вызывающий знает устройство объекта
if (browser.busyFlag === false && browser.currentTaskApi === null) { ... }
if (myObject.someProperty > 0) { ... }

// хорошо: объект сам знает ответ
if (browser.isFree()) { ... }
if (myObject.isSomeQualityPositive) { ... }
```

То же на TypeScript:

```ts
// плохо: вызывающий знает устройство объекта
if (userProduct.expiresAt > new Date() && userProduct.status === 2) { … }

// хорошо: объект сам знает ответ
if (userProduct.isActive()) { … }
```

Реальные примеры из наших проектов: `pool.hasAvailableResource()`, `router.can_route(message)`, `agent.release()` (а не «сбрось три флага»).

Следствия:

- Имя метода или свойства читается как фраза естественного языка: `isFree`, `hasAvailableResource`, `canRoute`, `shouldCancel`, `isActive`, `hasAvailableLessons`, `canBeRefunded`, `shouldNotify`.
- Если условие в `if` требует комментария — значит ему не хватает говорящего метода у объекта.
- Логика проверки живёт в одном месте (внутри объекта), а не размазана по вызывающим.

### В iron-back

Живой пример — [`products.service.ts`](../src/modules/products/products.service.ts), где условие активности продукта собирается из полей на месте вызова (и где, по пункту P2 из [todo-month.md](todo-month.md), закомментирован `.where("isActive = true")`). Ровно тот случай: правило «продукт активен» должно быть одним методом в одном месте, а не строкой в каждом запросе.

Образцы, уже написанные по этому правилу, — объекты-значения в `src/modules/order/values/` (`iron-account-share.ts`, `bank-card.ts`): им задают вопрос, они же объясняют отказ, и тестируются без БД.

### Gpt §11. Поведение располагается рядом с состоянием, которое оно охраняет

Примеры `isAllowLimit()`, `has_min_length()`, `health()`, `getStatus()`, `selected_layer()` подтверждают общий мотив: внешний код не должен повторно вычислять смысл чужого состояния.

Дополнительный вывод:

> Метод объекта — это не только операция, но и именованная политика.

Например, `isAllowLimit()` лучше сравнения чужого счётчика, потому что владелец лимита может позже учесть резерв, приоритет или режим остановки, не меняя вызывающий код.

### E5. Правило принятия решения — отдельный объект-понятие

В Zoopark целый ряд узлов — не сервисы, а **овеществлённые правила**:

```js
new Manifest(new DirStructure(), new DirsComparing())   // как сравнивать состав каталогов
new HostCluster(..., new AgentRecognizing())            // как понять, что агент — наш
new Jobs(JOBS_CONFIG,
    new SpecialControllerMode(),
    new NormalControllerMode())                         // два режима — два объекта
```

Имя такого объекта — существительное, называющее само правило (`AgentRecognizing`, `DirsComparing`, `RedundantAgentsReservation`), а не действие над данными. Заменить правило = заменить одну строку декларации; `if (mode === 'special')` внутри `Jobs` при этом не появляется никогда.

Это развитие §4: говорящий метод отвечает на вопрос об объекте, а объект-политика **владеет самим вопросом** — вместе с его параметрами (E3) и возможностью быть подменённым в тесте.

Когда заводить: правило нетривиально (больше одного условия), может измениться отдельно от носителя, или его хочется проверить тестом без всего окружения. Когда не заводить — см. §9: одно сравнение, которое никогда не поменяется, объекта не требует.

### E25. Чистое действие: решение отдельно от применения

Самый неожиданный род узла из `me_preview` — **действие без побочных эффектов**:

```
AllocationRoundAction  — один «чистый» проход подбора:
    берёт ожидающие аренды, выкидывает отменённые, в порядке очереди
    сопоставляет их со свободными ресурсами
    → возвращает { cancelledCount, matches } и НИЧЕГО не делает

ResourceAllocator      — применяет: помечает ресурс занятым, выдаёт handle,
                         резолвит обещания, индексирует аренду
```

Решение и применение разведены. Что это даёт:

- **раунд подбора тестируется как функция** — вход список, выход список; ни пула, ни таймеров, ни моков;
- в журнале видно «что решили» отдельно от «что применили» — а это два разных вопроса при разборе инцидента;
- решение можно **посчитать и не применить**: сухой прогон получается бесплатно, без флага `dry_run` внутри рабочего кода.

**Чем отличается от политики (E5):** политика отвечает на один вопрос («этот агент — наш?», «сейчас тихие часы?»). Действие строит **план на множестве** («кому из ожидающих какой ресурс достанется»). Имя — существительное про решение: `…Action`, `…Plan`, `…Decision`.

**В telebot.** Напоминания: «кому сегодня напомнить» — это план (список решений с причинами), «разослать» — применение. Разделив их, получаем и тест без БД, и возможность показать менеджеру, что бот собирается сделать, до того как он это сделает. Тот же приём — для предложений объединить дубли карточек: `BloggerDuplicateReconciler` уже строит предложение (`MergeProposal`), а применяет его другой шаг — это ровно нужная форма.

**Третий случай, самый назревший (23.08).** Выбор формы, в которой разбор доходит до человека — `vanna._after_blogger_analysis`, цепочка из пяти веток (авто-отправка / карточка+черновик / подводка+черновик / «нужно решение» / «ответа нет»). Сегодня каждая ветка И решает форму, И шлёт: поэтому проверить решение, не подсунув Telegram, нельзя.

Нужная форма — `ManagerHandoff.plan(...)` возвращает план (форма, карточка, черновик, задача), `HandoffSender` его применяет. Что это даёт сверх общего списка выше:

- **замок сможет ВЫЗЫВАТЬ решение, а не грепать исходник.** Это прямой урок 09.08: «✍️ Уточнить» уехала на прод сломанной, а замок был зелёным всё время — он искал подстроку в тексте файла;
- новая форма доставки становится новым значением плана, а не шестой веткой в `if`.

Почему по этому месту, а не по соседним простыням, — E14.1 (история правок). Решение и условие возврата зафиксированы в `iron.telebot/docs/plan/PLAN_2026-08-12_APP_MAP_AND_REFACTOR_DECISIONS.md` §2.7.

## §5. Единый lifecycle объектов

У долгоживущих объектов один и тот же ритм:

- **конструктор** — принимает зависимости (DI), ничего не запускает;
- **`init(...)`** — принимает конфигурацию и runtime-сервисы (logger и т.п.);
- **`run()` / `start()`** — запуск;
- **`stop()`** — остановка.

Оркестратор приложения (AppOrchestrator) вызывает `init/run/stop` у всех сервисов в правильном порядке — и больше ничего не делает.

Для короткоживущих объектов — паттерн **`instance()`**: один экземпляр на одну задачу. Прототип собирается один раз в CompositionRoot, а на каждую задачу клонируется свежий экземпляр с теми же прототипными зависимостями. Никаких общих мутабельных состояний между задачами.

Состояния объекта — явные и именованные (state machine), а не набор булевых флагов:

```
WAITING_TICKET → WAITING_AGENT → EXECUTING → COMPLETED
                                    ↓
                        (при stop) → CANCELLED
```

### В iron-back

В NestJS для ритма есть штатные хуки: `OnModuleInit`, `OnApplicationBootstrap`, `OnModuleDestroy`, `OnApplicationShutdown`. **В проекте сейчас не используется ни один** — при том что [`main.ts`](../src/main.ts) уже вызывает `app.enableShutdownHooks([SIGTERM, SIGINT])`, то есть механизм включён вхолостую. Новый код с фоновой работой обязан реализовывать `OnModuleDestroy` и гасить свои таймеры и подписки — иначе редеплой на Swarm рвёт работу на полуслове.

Для короткоживущих объектов — один экземпляр на одну задачу, без общего мутабельного состояния. В Nest это `Scope.TRANSIENT` / `Scope.REQUEST` и `app.resolve()`. Проект уже так делает: `AuthService` помечен `Scope.TRANSIENT`, `CustomLoggerService` — `Scope.REQUEST`.

Состояния — явные и именованные. `UserLessonState` в push-модуле уже сделан так, там даже есть `canChangeState()` — это образец для остального кода.

### E2. Конструктор — из чего состоит, `run/init` — где живёт

Во всех примерах два канала зависимостей строго разведены.

Через **конструктор** — постоянное устройство (дерево):

```js
new ManagersHub(
    new ManagersControl(mumo, new StartedRender(), new ConsoleControl()),
    new ManagersBroadcast(mumo, new JobLifeBroadcast()),
    new TrackedJobs(new InterestingJob()),
    new ManagersAutoSyncOps(...)
)
```

Через **`run()/init()`** — окружение текущего запуска (БД, логгер, родительский DOM-узел, сосед по дереву):

```js
.run(dataBase, aLog)                          // MUMO
iface.init(parentDiv, outputDiv).run(field)   // region_selector: init — место, run — связь
```

Отсюда три следствия, которые стоит соблюдать сознательно:

1. **Одно и то же дерево запускается в разном окружении** — прод, тест, другой инстанс БД. Пересобирать структуру для этого не нужно.
2. **`run()` возвращает `this`** — и точка сборки превращается в топологический порядок, где следующая строка получает уже запущенную предыдущую:

   ```js
   const aLog     = new ALog().run();
   const dataBase = new DataBase().run(aLog);
   const ioServer = new IoServer(new HttpForIoServer()).run(dataBase);
   ```

   Порядок запуска перестаёт быть устным знанием — он записан.
3. **Сиблингов знакомит родитель, в момент `run`,** а не они друг друга:

   ```js
   this.managersBroadcast.run(dataBase, managersControl, aLog);
   this.managersControl.run(dataBase, managersBroadcast, aLog);
   this.trackedJobs.run(dataBase, managersBroadcast, aLog);
   ```

   Это тот же однонаправленный поток (§0), но выраженный в фазе запуска: связь между братьями существует потому, что её выдал общий родитель, а не потому, что один нашёл другого.

Уточнение к §5: `init` там описан как «конфигурация и runtime-сервисы» — примеры показывают более резкую границу. **Конструктор отвечает на «что это», `init/run` — на «где и с кем это сейчас работает».**

### Gpt §5. Топология стабильна, рабочее состояние свежее

В `Thumbnail` и `region_selector` встречаются `create()` и `instance()`: дерево зависимостей собирается заранее, но для отдельной задачи создаётся новый объект с тем же внутренним устройством.

Это отдельный важный принцип:

> Переиспользуется не мутирующий экземпляр, а рецепт его устройства.

CompositionRoot фиксирует **топологию** системы. Фабрика `instance()` создаёт **свежее состояние** для конкретного задания. Так архитектура остаётся общей, а данные параллельных операций не смешиваются.

Современная реализация может называться `factory`, `spawn`, `createTask` или `cloneDependencies`; важно явно обозначить границу свежести. Какое состояние живёт в долгоживущем хозяине, а какое — в экземпляре, разобрано в E15 (часть III).

### Gpt §6. Единый lifecycle делает граф рекурсивно запускаемым

Повторение `init()`, `run()`, `onRes()`, `onErr()` показывает стремление сделать любой узел графа одинаково управляемым. Родитель может запустить поддерево, не зная его внутренностей.

Отсюда следует:

> Одинаковый lifecycle — это не стилистическое соглашение, а протокол рекурсивной композиции.

Если каждый узел поддерживает согласованные `init/run/stop` и события готовности, то агрегат может обращаться с целым поддеревом как с одним узлом. Поддерево становится заменяемым модулем.

Особенно важна различимость фаз:

- конструктор — связывает стабильные зависимости;
- `init` — принимает контекст конкретного окружения;
- `run/start` — начинает работу;
- `ready` — сообщает, что узел действительно способен принимать запросы;
- `stop` — симметрично освобождает поддерево.

`run()` и `ready` не всегда одно и то же: сервер может быть запущен, но ещё не готов обслуживать работу, пока не готовы база или дочерний процесс.

**Сверка (E).** В E2 фазы разведены слабее: различение `run()` и `ready` берём отсюда.

### Gpt §7. Готовность распространяется снизу вверх, команды — сверху вниз

В `Thumbnail` внешний сокет начинает слушать запросы только после готовности `Picturer`, а тот — после готовности обработчика кадров. Это выражает полезную асимметрию:

> Управление и входные данные идут сверху вниз; готовность, результат и ошибка поднимаются снизу вверх.

Такой ритм позволяет родителю владеть порядком запуска, не раскрывая детям всю систему. Он также естественно ложится на дерево наблюдаемости: `start` идёт вниз, `ready/result/fail` собираются вверх.

### E10. Остановка — зеркало запуска

Запуск идёт снизу вверх (Gpt §7), остановка — строго в обратном порядке и с изоляцией ошибок:

```js
async function shutdown(signal) {
    await controller.disconnect().catch(err => appLogger.error('disconnect failed:', err.message));
    await app.locals.productionRuntime?.stop?.().catch(err => appLogger.error('production runtime stop failed:', err.message));
    await app.locals.iphoneRuntime?.stop?.().catch(err => appLogger.error('runtime stop failed:', err.message));
    process.exit(0);
}
process.on('SIGINT',  () => shutdown('SIGINT'));
process.on('SIGTERM', () => shutdown('SIGTERM'));
```

Три вещи, которые обычно забывают:

- **Каждый `stop` со своим `catch`** — падение одного не мешает остановить остальные. При остановке ошибка логируется, а не бросается.
- **`?.` на всём, что могло не стартовать.** Остановка обязана быть корректной из любого состояния, включая «упали на старте».
- **Хуки среды — на границе процесса**, а не в бизнес-узлах: `uncaughtException` и `unhandledRejection` объявлены в самом низу модуля, рядом с точкой входа.

## §6. Гарантии освобождения ресурсов, бюджеты времени и ошибки

- Всё, что взято (браузер, вкладка, соединение, транзакция, lease), возвращается в **`finally`** — независимо от успеха или ошибки.
- Методы освобождения (`release()`) — **идемпотентны**: повторный вызов безопасен.
- У каждого уровня — свой таймаут, и таймауты образуют иерархию (внутренний короче внешнего): задача агента 5 мин > подзадача одного клиента 2 мин.
- Промежуточные шаги не роняют весь процесс: подзадача возвращает `{ ok, errorCode, details }`, а не бросает исключение наверх; решение о retry/провале принимает уровень выше.

### В iron-back

Это не абстрактное требование. В инциденте с Vimeo живой запрос к внешнему API внутри `GET /lessons/{id}` держал ответ **+33 секунды**, потому что таймаута не было ни на одном уровне. Правило прямое: **ни одного вызова во внешний мир без явного таймаута** — Vimeo, Тинькофф, APNs, ur-integration, Google API.

### E6. Ресурс не выдают наружу — внутрь передают действие

Самый сильный приём в iPhone-проекте:

```js
async runWithDeviceDriver(action, { timeoutMs = config.IPHONE_MANUAL_COMMAND_TIMEOUT_MS } = {}) {
    const acquire = this.resourceAllocator.enqueueAcquire({ timeoutMs });
    const { resourceId, resourceHandle } = await acquire.promise;
    try {
        return await action({ driver: resource.driver, resource, resourceId });
    } finally {
        resourceHandle.release();
    }
}
```

Вызывающий не получает устройство — он **отдаёт функцию, которую над устройством надо выполнить**:

```js
runViaProductionRuntime(({ driver }) =>
    controller.runCommandWithDriver(driver, req.body.command, 'productionRuntime'))
```

Забыть `release()` физически невозможно: тот, кто мог бы забыть, никогда не держит handle. Это сильнее договорённости «всегда освобождай в `finally`» (§6) — здесь договорённость встроена в форму вызова.

Два следствия, которые в примере тоже видны:

- **У дефицитного ресурса один владелец.** UI-роут не создаёт вторую WDA-сессию, а спрашивает `hasProductionRuntime()` и идёт через владельца.
- **Отказ конкретен и по-человечески сформулирован.** Не `null`, не пустой ответ: «Production runtime сейчас стартует и создаёт WDA-сессию. Повторите команду после завершения старта.» Промежуточное состояние при этом **названо** (`productionRuntimeStarting`), а не выражено отсутствием объекта, — это минимальная форма state machine из §5.

**Куда применить:** пулы браузеров, соединения к БД, слоты Telegram-API, блокировка на блогера. Форма — `withX(action)`, а не `acquireX()` + надежда.

### E22. Ожидание — тоже вещь: билет, аренда, handle, остывание

E6 говорит, как отдавать дефицитный ресурс: внутрь передают действие. `me_preview` показывает вторую половину темы — **само ожидание тоже овеществлено**, и это оказался самый переиспользуемый узел всей системы.

**Билет.** `acquireAgent` синхронно возвращает номер в очереди и асинхронно — ресурс. Место в очереди существует сразу: на него можно сослаться, его можно отменить, про него можно спросить. Ожидание перестаёт быть «висящим await» без имени.

**Аренда — сущность с жизненным циклом** (ровно E12, применённый к ожиданию):

```
pending → in_use → cooling_down → completed
   ↓         ↓
cancelled | timed_out | failed | broken
```

У неё есть идентичность, именованные переходы, снапшот для UI и события наружу (`lease_enqueued`, `lease_fulfilled`, `lease_broken`, …). Не флаг `is_busy`, а предмет со своей судьбой.

**Наружу выдают не ресурс и не адрес владельца, а handle с одной кнопкой.**

```js
const { resourceId, resourceHandle } = await allocator.enqueueAcquire({ timeoutMs });
// ...
resourceHandle.release();   // идемпотентно; маршрут возврата потребителю неизвестен
```

Потребитель не знает, что возврат технически идёт через аллокатор, а потом в пул. Он не может вернуть ресурс «не тем путём», потому что другого пути ему не показали. Это E6, доведённое до конца: скрыт не только ресурс, но и **маршрут его возврата**.

**Остывание.** Между «вернули» и «можно выдать снова» бывает пауза (`BROWSER_RELEASE_COOLDOWN_MS`), и она — отдельный маленький жизненный цикл (`inactive → cooling_down → elapsed`), а не `sleep` в чужом методе.

**Две правды, и это не дублирование.** Пул знает, **свободен ли ресурс**. Аллокатор знает, **можно ли его выдать сейчас** — с учётом остывания и уже назначенных аренд. Производный факт принадлежит владельцу политики, а не владельцу ресурса; поэтому аллокатор считает доступность сам, а не переспрашивает пул.

**Окно партии.** Дисциплина ожидания — тоже политика (E5): по истечении окна те, кто ещё не получил ресурс, отменяют билеты и уходят, а те, кто уже начал, доигрывают. Одна фраза в декларации вместо россыпи проверок «не поздно ли».

**Пометка потребителя.** У аренды есть поле «кто её просил» (`batch`, `tooling`, `repl`). Оно **не меняет поведение** — приоритетов нет; оно отвечает на вопрос «кто сейчас ждёт и кто держит». Самая дешёвая наблюдаемость, какая бывает: одно поле в момент постановки в очередь.

**В telebot.** Захваты в `vanna/outbound_queue.py` — это уже аренда, только без имени и без снапшота. Тот же приём просится на слоты ИИ, на живой peer бизнес-бота (он «протухает» от тишины — то есть у него есть остывание наоборот) и на взятие блогера в работу: «кто ждёт и кто держит» — ровно тот вопрос, который менеджеры задают вслух.

### E21. Каскад бюджетов: у вложенности объектов есть вложенность времени

Дерево объектов задаёт не только поток управления, но и **вложенность допустимого времени**. В `me_preview` она выписана явно:

```
BROWSER_ACQUIRE_TIMEOUT (120 с)    — ждём свободный ресурс
  WAIT_WINDOW_TIMEOUT (60 с)       — окно ожидания партии
AGENT_EXECUTOR_MAX_TASK_TIME (5 м) — задача целиком
  ONE_CLIENT_SUBTASK_TIMEOUT (2 м) — одна единица внутри задачи
WAIT_FINISH_ALL_TIMEOUT (10 м)     — ждём завершения всех начатых
```

**Правило:** бюджет ребёнка строго меньше **остатка** бюджета родителя, и разница оставлена на то, чтобы ребёнок успел отчитаться о неудаче. Равные бюджеты — это уже инверсия: гонка, кто первый.

Инверсия даёт две беды, и обе диагностируются плохо:

- **сирота** — родитель сдался и ушёл, ребёнок продолжает работать и держит ресурс. Внешне: «задача завершилась», а пул пуст;
- **немая смерть** — ребёнка убивают раньше, чем он успевает сказать, на чём споткнулся. В логе — только таймаут снаружи, причина потеряна навсегда.

**Передавать вниз дедлайн, а не таймаут.** Длительность на каждом уровне складывается («по 40 секунд на шаг» × 5 шагов = 200), абсолютный дедлайн — делится. Тогда вложенные шаги делят один бюджет, а не суммируют свои.

Само число — часть декларации (E3): в точке сборки должно быть видно, сколько система готова ждать, без чтения классов.

**В telebot.** Самый явный случай — вызовы ИИ: клиент собран на умолчаниях SDK, то есть **10 минут на попытку и до трёх попыток — порядка получаса** внутри пути, где на другом конце живой менеджер ждёт черновик (`iron.telebot/docs/plan/PLAN_2026-07-25_LLM_FALLBACK.md`; там же предложенные 40 секунд и явные ретраи). Тот же вопрос стоит задать отложенной отправке и часовым тикам: у них бюджет не объявлен вообще, а значит — бесконечен.

**Проверка себя:** можно ли, глядя только на точку сборки, назвать худшее время ответа системы? Если нет — бюджеты спрятаны.

### E23. Где ошибка перестаёт быть исключением

В любой системе есть граница, на которой падение перестаёт быть аварией и становится **фактом**. В `me_preview` она проведена сознательно:

```js
// OneClientSubtask — единица работы
// Возвращает { ok, url?, errorCode?, details? } — никогда не бросает наверх
```

**Правило:** на границе единицы работы исключение конвертируется в результат. Выше этой границы неудача одной единицы — обычный элемент отчёта, а не повод рушить проход. Ниже — исключения живут нормально и не маскируются.

Отсюда три следствия, которые видны в том же коде:

- **Повтор — это отдельный проход по неудачам, а не `try` внутри шага.** `MultiClientPass` идёт по всем клиентам, собирает провалившихся, следующий проход берёт только их. Повтор снаружи видит всю картину и умеет остановиться; повтор внутри шага не знает даже, сколько таких же шагов рядом.
- **Результат сохраняется после каждого прохода**, а не в конце. Падение на третьем проходе не отменяет сделанное на первом.
- **Полный провал — событие другого рода.** Если провалились все единицы, это уже не отчёт, а ошибка задачи, и она летит наверх.

**Ловушка, за которую там заплатили.** Итог задачи считался по **всем попыткам подряд**, а не по последнему состоянию каждой единицы. Клиент упал в первом проходе и успешно отработал во втором — задача всё равно осталась «провалившейся». Свод результата — работа агрегатора (E8), и считать его надо **по последнему состоянию каждой единицы**, а не по всей истории попыток. История нужна для разбора, итог — для решения.

**В telebot.** Любой фоновый тик, идущий по карточкам: одна карточка не должна ронять проход, её неудача — строка в отчёте тика. И тот же вопрос — про отложенную отправку: где именно исключение становится результатом, и кто этот результат читает.

## §7. Каждый шаг — наблюдаемая единица процесса

Объект-шаг делает две вещи одновременно: **выполняет свою часть работы** и **объявляет её миру** через единый контракт наблюдаемости (process node):

- в начале `run()` — `processNode.start(...)`
- по ходу — `processNode.update(...)`
- при успехе — `processNode.complete(...)`
- при ошибке — `processNode.fail(...)`

В payload — только смысловые данные шага: входные параметры, стадия, результат, ошибка. Вопрос для самопроверки: *«что мне нужно видеть в UI, чтобы понять состояние этого шага без чтения исходников?»*

Важный нюанс: `parentNode` — это **структурная связь** (место узла в дереве), а не цепочка пересылки сообщений. Каждый шаг пишет своё состояние напрямую в общий store; дерево собирает store, а не объекты друг через друга.

Выгода: новый модуль, следующий этому контракту, автоматически получает телеметрию, дерево выполнения и почти готовую визуализацию — отдельный UI писать не нужно.

### Куда это ведёт: изоморфный UI (backend ↔ frontend)

Цель, к которой стремимся: frontend строится не как отдельно спроектированная витрина, а как **визуальное зеркало backend-дерева**:

- backend-дерево объектов исполняет бизнес-операцию;
- frontend-дерево одноимённых компонентов отображает те же узлы;
- **события — контракт между ними**: backend-узел эмитит lifecycle, frontend-узел подписывается и обновляет своё состояние;
- дочерний frontend-компонент вкладывается в родительский блок — DOM-структура повторяет архитектурное дерево процесса.

Для типовых узлов (агрегат, шаг, ожидание, успех, ошибка, retry) вводятся дефолтные шаблоны отображения — тогда любой новый backend-модуль получает рабочую визуализацию «из коробки», а поверх дефолта можно навешивать скины: логика и контракт событий стабильны, меняется только визуальная интерпретация.

Формула: разработчик пишет прежде всего бизнес-логику, а UI возникает как следствие структуры и событий.

Шаблон нового шага:

```js
class SomeStep {
  constructor(childStep) {
    this.childStep = childStep;
    this.processNode = null;
    this.treeContext = null;
  }

  init(treeContext = null) {
    this.treeContext = treeContext || {};
    return this;
  }

  async run(input) {
    this._ensureProcessNode(input);
    this.processNode.start({ input, stage: 'started' });
    try {
      this.childStep.init({ parentNode: this.processNode });
      const childResult = await this.childStep.run(input);
      this.processNode.complete({ stage: 'completed', childResult });
      return { childResult };
    } catch (error) {
      this.processNode.fail(error, { payload: { input, stage: 'failed' } });
      throw error;
    }
  }
}
```

### В iron-back

Для бэкенда без UI это скромнее: не дерево процессов на фронте, а структурные логи через `CustomLoggerService` с `LogContext` — с осмысленным контекстом (какой урок, какой пользователь, какая стадия). Механизм уже есть и используется — правило лишь в том, чтобы новый шаг подключался к нему сразу, а не «потом, когда понадобится дебажить».

Вопрос для самопроверки: *что мне нужно увидеть в логе, чтобы понять состояние этого шага, не открывая исходники?* Если ответ «ничего не увижу» — шаг не наблюдаем.

Сюда же примыкает пункт P1 из [todo-month.md](todo-month.md) про мониторинг: наблюдаемость на уровне шагов — это то, что делает алерт полезным, а не просто «сервис не отвечает».

### Gpt §8. События — декларативный контракт асинхронного объекта

Цепочки вида:

```js
node.run().onRes(...).onData(...).onEnd(...).onErr(...)
```

показывают попытку описывать асинхронный объект не набором случайных callback, а конечным словарём событий. Это предшественник идеи process node из §7.

Принцип:

> Асинхронный объект должен объявлять ограниченный и единообразный алфавит событий своего жизненного цикла.

Разные сущности могут иметь дополнительные события (`data`, `progress`), но `ready`, `complete`, `fail`, `stop` должны иметь одинаковую семантику во всём дереве. Тогда оркестрация и наблюдаемость строятся поверх структуры, а не пишутся отдельно для каждого класса.

### E7. Технические события сводятся к одному доменному

Внешний мир говорит на своём языке: у ffmpeg два потока, и каждый закрывается отдельно. Узел-обёртка обязан свести это к одному смысловому событию:

```js
.onEnd(std => {
    this.stdio_end_counter += 1;
    if (this.stdio_end_counter > 1) {      // закрылись и stdout, и stderr
        this.cbRes(this);                  // наружу — одно: «кадр готов»
    }
})
```

То же в `SocketKeepAliveConfirmation`: поток «я жив» превращается в одно доменное событие `keep_alive_timeout`, когда тишина длится дольше `time_to_panic`. И в `FileFullInfo`: множество `data`-чанков накапливаются и отдаются наверх **один раз**, под защитой флага `isDataEmpty`, чтобы родитель не получил результат дважды.

**Правило:** узел, граничащий с внешней системой, переводит её события в события своего уровня — «готов», «результат», «ошибка», «истёк». Наверх не просачиваются `stdout`, `close`, `ECONNRESET`, коды ретраев вебхука.

**Проверка себя:** родитель должен корректно работать, если внешнюю систему заменили на другую с другой механикой событий. Если при замене ffmpeg на другой кодировщик придётся править родителя — перевода не произошло.

Смежное: Gpt §8 про алфавит событий — здесь про то, кто и где обязан этот алфавит **произвести** из чужого шума. И явная ловушка: событие «готово» должно быть ровно одно; идемпотентность отдачи результата так же обязательна, как идемпотентность `release()`.

### E24. Сигнал и команда — разные вещи

Тонкое различение, на котором построен весь возврат ресурсов в `me_preview`, и которое обычно смазывают:

- **команда** — «сделай»: `resourceHandle.release()`. Есть отправитель, есть ожидаемый эффект, есть ответственность за результат;
- **сигнал** — «что-то изменилось, пересчитай»: события пула `resource_released`, `resource_connected`. Подписчик решает сам, надо ли что-то делать.

Формулировка из документа прямая: события пула «триггерят перепроверку очереди, но **не являются основным API возврата ресурса**».

Почему это стоит держать в голове: если сигнал начинает работать как команда, у одного действия появляется **два маршрута** — прямой вызов и подписка. Дальше либо гонка (оба сработали), либо тишина (каждый решил, что сделает другой). Это тот же класс багов, что двойная отдача «готово» из E7.

**Практические следствия:**

- сигнал имеет право потеряться или прийти дважды — система обязана это пережить (поэтому реакция на сигнал — «пересчитай состояние», а не «сделай шаг»);
- команда обязана быть идемпотентной, раз уж её могут повторить (§6, E19);
- **признак путаницы:** подписчик события делает работу, за которую отвечает вызывающий. Или, зеркально, вызывающий не доводит дело до конца в расчёте, что подписчик доделает.

**В telebot.** Хуки «чат ожил» в очереди исходящих — это сигнал («появился повод пересчитать, кому теперь можно доставить»), а не команда «отправь». Разница видна в поведении при дубле события: сигнал перечитает очередь и не найдёт работы, команда отправит второй раз.

### Gpt §12. Декларативное дерево может совпадать с визуальным деревом

`region_selector` особенно ясно показывает соответствие:

- `App` содержит `Iface` и `Field`;
- `Iface` содержит действия;
- `Field` содержит изображение и `Layers`;
- `Layers` содержит `Layer`;
- `Layer` содержит `Canvas`.

Это не просто удобная организация JavaScript: дерево объектов почти напрямую объясняет дерево UI и владение DOM-элементами.

Принцип:

> Если предметная область сама имеет иерархическую форму, программное дерево, lifecycle и визуальное дерево должны по возможности сохранять одну топологию.

Тогда родитель программного узла владеет и визуальным контейнером, ребёнок сам умеет представить себя внутри него, а удаление поддерева симметрично удаляет его визуальное представление.

**Спор (E).** Как идеал — да, но у правила есть цена, которую Gpt §12 не называет: backend-дерево оптимизируется под поток управления, а UI — под восприятие человеком, и расходятся они ровно там, где экрану нужно свести данные из разных веток (сводка, дайджест, доска). Точнее так: **совпадает дерево процессов, а сводные экраны строятся из потока вех** (E19), а не из дерева. Иначе появится соблазн ломать backend ради витрины.

**Спор снят практикой** (E26): в `me_preview` это сделано ровно так — дерево процессов отвечает «что произошло», отдельный слой проекции — «как это показать», и фронт подписан на проекцию, а не на домен.

### E19. Снимок дерева, история вех и откат

Продолжение E12: если сущность умеет транслировать вехи и сохранять себя, то в пределе **всё доменное дерево умеет то же самое**. По дереву сверху вниз идёт команда «отдай своё состояние», каждый узел возвращает свой кусок и складывает в него ответы детей — получается снимок системы целиком. Обратная команда восстанавливает дерево из снимка.

```python
class Snapshotable(Protocol):
    def snapshot(self) -> dict: ...
    def restore(self, state: dict) -> None: ...


def snapshot(self) -> dict:
    return {
        "v": SNAPSHOT_VERSION,
        "kind": "outbound_queue",
        "self": {"captured": self._captured, "ttl_hours": self._ttl},
        "children": {child.key: child.snapshot() for child in self._items},
    }
```

Идея правильная, но у неё есть шесть развилок. Пройденные сознательно, они дают отладку и восстановление; пройденные по инерции — второй источник истины и дубли сообщений после каждого рестарта.

#### 1. Снимается не всё: четыре рода узлов

| Род узла | Где живёт состояние | Что попадает в снимок |
|---|---|---|
| Сущность (E12) | в БД — она и есть истина | идентификатор и версия, **не копия полей** |
| Процесс в полёте | нигде — только в памяти | всё: стадия, попытка, дедлайн, взятый ресурс |
| Каркас (роутеры, реестры, пулы) | структура из точки сборки | только «что сейчас занято/в очереди» |
| Кэш и производное | пересчитывается | ничего |

> Снимается то, что **нельзя пересчитать** и что **не лежит в БД**.

Отсюда неожиданный вывод: главные бенефициары снимка — не сущности (они и так сохранены), а **процессы в полёте**. Именно они молча исчезают при рестарте.

#### 2. Снимок производный, БД — истина

Как только снимок начинает считаться источником правды, появляется второй источник, и он немедленно разъезжается с первым. Снимок — либо диагностический артефакт, либо способ поднять то, чего в БД нет по определению (пункт 1).

#### 3. Ключ узла — путь, а не позиция

`vanna/outbound/queue/item:417` — стабильный путь. Индекс в списке непригоден: перестановка детей молча приведёт чужое состояние в чужой узел. И **версия схемы обязательна с первого дня** (`"v": 3`): снимок переживает деплой, а неизвестные поля при восстановлении сохраняются, а не выбрасываются.

#### 4. Согласованность — это два разных режима, а не один

Дерево живёт, пока его обходят, поэтому:

- **для отладки** годится несогласованный снимок — но он обязан честно помечаться (`"consistent": false`), иначе им однажды попробуют восстановиться;
- **для восстановления** годится только согласованный: мир остановлен (graceful shutdown) либо снимок собран из истории вех, а не обходом.

Смешивать нельзя: это разные гарантии под одним именем.

#### 5. История: вехи — истина, снимки — чекпойнты

Если вехи уже эмитятся (E12), история получается бесплатно, а снимок в момент T — это свёртка вех до T. Тогда отдельный механизм снимков не нужен, нужен `apply(milestone)`. На практике берут гибрид: **журнал вех как истина + редкие снимки как чекпойнты**, чтобы не проигрывать историю с начала.

Дешёвая половина этой идеи окупается сразу и без всякого восстановления: поток именованных переходов — это готовый ответ на «что вообще происходило с этой сделкой», без чтения логов и исходников.

#### 6. Откат состояния — не машина времени

Самая опасная развилка. Откатить поля объекта легко; откатить то, что он уже сделал во внешнем мире, невозможно — сообщение блогеру отправлено, оффер показан, деньги ушли. Объект, которому вернули прежнее состояние, **забыл, что он сделал**, и сделает это второй раз.

Поэтому три режима, и их нельзя путать:

- **Диагностический откат** — в тесте, в песочнице, на копии данных: можно всё, внешних эффектов нет.
- **Доменный откат** — только **компенсирующим переходом вперёд**: не `deal.rollback_to(prev)`, а `deal.cancel_offer(cause=…)` — новое состояние, которое возвращает предмет в прежнее положение и **остаётся в истории**. История не переписывается никогда.
- **Аварийное восстановление** — снимок плюс повтор незавершённых процессов, и вот здесь начинается пункт 7.

#### 7. Восстановление без идемпотентности = дубли

Если подняли процесс «отправка в полёте», он обязан сначала спросить «а не сделано ли уже?». Значит, у каждого внешнего эффекта нужен ключ идемпотентности, а у восстановления — проверка по нему. Это то же правило, что «`release()` идемпотентен» (§6) и «готово отдаётся ровно один раз» (E7), только цена ошибки выше: без него каждый рестарт множит сообщения людям.

> Снимок без идемпотентных эффектов делает систему не надёжнее, а опаснее.

#### Три уровня зрелости — и не перепрыгивать

1. **Вехи наружу.** Именованные переходы, один эмиттер, подписчики (журнал, доска, зеркало, UI). Даёт отладку и наблюдаемость. Дёшево.
2. **Снимок по требованию.** Диагностический эндпойнт: дерево отдаёт своё состояние, помеченное как несогласованное. Даёт «повторить баг прода в тесте». Тоже дёшево.
3. **Восстановление и чекпойнты.** Требует согласованности, версий схемы и идемпотентности эффектов. Дорого — и оправдано только там, где потеря процесса в полёте реально болит.

Перепрыгивать через ступени нельзя: уровень 3 без уровня 1 — это снимок неизвестно чего, а без идемпотентности — генератор дублей.

#### Куда это приходит: тот же контракт, что у UI

Снимок дерева — это ровно то, что рисует фронт в §7 (изоморфный UI). Один контракт закрывает три задачи: наблюдаемость, визуализацию и сохранение. Отдельных механизмов «телеметрия», «UI-состояние» и «persistence» строить не нужно — это три читателя одного дерева.

**В telebot — где начать.** Не строить общий фреймворк (§9), а взять один узел с настоящей болью: отложенная отправка блогеру живёт в `threading.Thread` с паузой 15–30 секунд и при рестарте контейнера исчезает вместе со статус-сообщением «⏳ Отправляю…», которое так и остаётся «⏳». Рядом есть готовый образец: `outbound_queue` уже хранит состояние в БД и умеет возвращать зависшие захваты — то есть уровень 3 для одной сущности написан руками. Обобщать стоит именно с него.

### E26. Наблюдаемость: плоская шина с указанием родителя

E19 предполагал, что снимок собирается **обходом дерева**. `me_preview` прошёл этот путь дальше и сделал иначе — и это прямая поправка к E19.

**Дерево наблюдаемости не собирается пересылкой событий вверх.** Каждый объект регистрирует свой узел в общем хранилище и указывает, кто его **смысловой родитель**. Дерево потом строится по ссылкам `parentNodeId`. Родитель здесь — semantic parent, а не транспортный узел:

```js
this.processNode = processTreeStore.createNode({
    parentNode: this.treeContext?.parentNode || null,
    nodeType: 'OneClientSubtask',   // род узла → правила отображения
    title: 'OneClientSubtask #3',   // имя конкретного экземпляра
    payload: { device: 'yandex' },
});
this.processNode.start({ stage: 'started' });
```

Выигрыш по сравнению с обходом: ребёнок не зависит от ретрансляции через родителя, связность меньше, формат один, а согласованность снимка перестаёт быть проблемой — дерево не обходят живым, его **накапливают**.

**Алфавит узла — шесть глаголов:** `start`, `update`, `complete`, `fail`, `child`, `syncState`. Объект делает ровно три вещи: регистрируется, меняет свой жизненный цикл, кладёт смысловые данные в `payload`. Он не знает ни логгера, ни UI, ни транспорта.

**Пара `nodeType` / `title`** — это E15, вынесенный в наблюдаемость: род узла задаёт правила отображения (иконка, шаблон, цвет), имя экземпляра отвечает на вопрос «какой именно из них».

**Подписчики — снаружи.** Хранилище публикует одно событие в одну локальную шину; мост в логгер и WebSocket, проекция для UI, будущие аудит и аналитика подписываются в точке сборки. Хранилище о них не знает, и добавление подписчика не трогает ни одного доменного узла.

**Проекция — отдельный слой, и это главное.** Два вопроса разведены:

> `process-tree` отвечает: «что реально произошло?»
> `ui-mirroring` отвечает: «как это удобно показать?»

Проекция считает `displayStatus`, тон статуса, глубину, цепочку родителей, готовых детей, счётчики — фронт получает не поток фактов, а почти готовую модель для рисования. Это снимает спор вокруг Gpt §12 (выше): **дерево процессов действительно совпадает с деревом отображения, но витрина строится проекцией над потоком вех, а не ломает backend под себя.**

**UI становится диагностической поверхностью.** Реальный случай оттуда: в UI задача осталась «провалившейся» после успешного повтора. Это оказался не баг отрисовки, а доменная ошибка свода результата (та самая из E23). Правило, которое из этого следует: **если UI подписан на процессную модель, странность в UI — это гипотеза о дефекте домена, а не о вёрстке.**

**Два механизма наблюдаемости — это дубли.** Когда появилось дерево процессов, прежний накопитель состояния партии удалили целиком; у хранилища оставили один канал публикации вместо двух. Иначе получаются две правды об одном процессе, и однажды они разъедутся.

**Честная цена косвенности.** Тот же проект **отказался** доводить это до полного observer-паттерна, и аргумент стоит запомнить: вместо самодокументирующейся строки `processNode.update({status: 'running'})` получается `emit(...)` плюс подписчик в другом файле — «два прыжка глазами вместо одного». Минимальный шаг, который дёшев и окупается сразу, — не наблюдатель, а **инъекция вместо синглтона** (узел получает хранилище в конструктор). Это поправка к спору вокруг Gpt §15 (§3): «узел эмитит, не зная подписчиков» — верно; «поэтому нужен полноценный observer» — не обязательно.

**Как это ложится на E19:** дерево процессов — это уровни 1–2 (вехи наружу плюс снимок по требованию), живущее в памяти; рестарт его обнуляет, и там это честно названо текущим поведением, а не багом. Уровень 3 (восстановление) из него не следует и требует всего, что перечислено в E19.

**В telebot.** Панель «Диалоги», журнал переездов по канбану (`funnel_transitions`), зеркало и дайджесты — это **три-четыре подписчика, которых стоит кормить одним потоком вех**, а не тремя независимыми механизмами. Первый шаг тот же, что в `me_preview`: один эмиттер и `parent`-ссылка, подписчики — снаружи, в точке сборки.

## §8. Смысловые территории и имена

- У проекта явно зафиксированы крупные территории (в naf: contracts, gateway, queue, router, runtime, tools, approval, llm, memory, ledger + domains). Каждый модуль знает свою территорию и не лезет на чужую.
- Имена классов отражают **роль в процессе**, а не технологию: `TaskRouter`, `ResourcePool`, `ExecutionEnvironment` — а не `KafkaHelper2`, `Utils`, `Manager`.
- Иерархия имён отражает иерархию композиции: `MultiClientTask → MultiClientPass → OneClientSubtask → OneScreenshot → OneNavigate` — по имени понятно, кто в кого вложен и какой у кого масштаб.
- Ошибки — именованные классы с контекстом (`UnroutableMessageError(bot_type)`), а не голые строки.

Почему суффикс `Service` — такое же туманное имя, как `Manager`, и как по имени найти одну роль объекта — Gpt §20 и E13 (часть III).

### В iron-back

- Хорошие ролевые имена в проекте уже есть: `PushNotificationPostman`, `ViewedLessonTracker`, `ProductLessonsStorage`. `Manager`, `Utils`, `Helper2` — плохие.
- Именованные ошибки тоже заведены (`ResourceNotFoundException`, `ValidationBadRequestException`, `PaymentRequiredException`) — продолжаем так же.

Отдельно про `helpers/`. Сейчас их 10 файлов. Это не запрещено, но каждый `helper` — кандидат в метод объекта: `is-profile-completed.helper.ts` почти наверняка должен быть `user.isProfileCompleted()` (§4). Новые хелперы заводим, только если функция действительно ничья.

## §9. Не абстракции ради абстракций

Каждый новый контракт/слой должен отвечать на практический вопрос: **что мы хотим заменить, не трогая остальное?** Если ответа нет — слой не нужен.

Рефакторинг к этой архитектуре делаем **постепенно**: не большой механический rename, а ввод контрактов и адаптеров через композицию рядом с работающим кодом, с compatibility-псевдонимами на публичной границе, пока их кто-то использует.

Когда объект оправдан, а когда хватит функции, — E14 (часть III). Где резать первым — E14.1. Как заменять разбиение рядом с работающим кодом — §11.4.

### В iron-back

Для этого репозитория это особенно важно: тестов сейчас **ноль**, поэтому единственная страховка — совпадение ответа с baseline. Крупный рефакторинг без тестов и без baseline — это не улучшение архитектуры, а лотерея.

Отсюда практический порядок: **сначала smoke-baseline (шаг 0.5 [плана апгрейда](upgrade-plan.md)), потом любой рефакторинг.** Композиционный стиль как раз и нужен, чтобы тесты стало возможно писать: класс с зависимостями через конструктор тестируется без БД, а метод внутри 700-строчного сервиса — нет.

### E27. Цена, риск, выигрыш и условие возврата

Последнее, что стоит забрать из `me_preview`, — не приём, а **форма принятия архитектурного решения**. Итерация улучшений закрыта таблицей:

| # | Шаг | Цена | Риск | Выигрыш | Статус |
|---|---|---|---|---|---|
| 3 | handle отдаёт ресурс | ~2 часа | низкий | древовидность зависимостей | СДЕЛАНО |
| 5 | контракты + валидаторы | ~3 часа | нулевой | страховка и моки | СДЕЛАНО |
| 8 | вынести источник задач | 1–2 дня | повышенный | большой при втором источнике | **WONTFIX** |
| 9 | сквозные службы через observer | 2–3 дня | средний | большой при втором проекте | **WONTFIX** |

Семь пунктов из девяти сделаны, два **сознательно отклонены** — с записанной аргументацией и, главное, с **условием возврата**: «появится конкретный второй источник — сделаем тогда, имея реальные требования».

Почему это ценнее самих решений: §9 («не абстракции ради абстракций») из лозунга превращается в процедуру. Отказ зафиксирован вместе с триггером — и через полгода спор не начинается заново, а проверяется условие.

**Отсюда же — как мигрировать, не ломая:**

- **не переименовывать всё и не строить иерархию наследования**, а вводить контракты и адаптеры **через композицию**; существующие классы остаются рабочими реализациями этих контрактов;
- совместимые псевдонимы старых методов оставлять только на публичной границе — и с явным сроком снятия (в примере мёртвые совместимые ветки потом вычищали отдельным пунктом роадмапа);
- **начинать с самого нагруженного шва** — там, где сходятся три разные вещи. У них это была точка, где встречаются ресурс, работа одной задачи и освобождение ресурса; разъединение начали с неё, а не с самого лёгкого места;
- **два режима одного сценария** как приём перехода: линейная версия и собранная из объектов живут рядом, переключатель — в декларации. Цена известна: два пути со временем расходятся, поэтому у такого режима должен быть срок годности, а не «пусть полежит».

**В telebot.** Ровно так стоит вести список того, что решили не делать: снимок дерева, общий эмиттер вех, контракт транспорта. У каждого — цена, риск и условие возврата. Без этого «отложено» и «отказались» выглядят одинаково.

## §10. Территория и её корень (агрегат — но по-питоновски)

Родилось из разбора Этапа 3 в telebot (Сергей + ИИ, 2026-07-25). Здесь зафиксировано, как идея DDD-агрегата применяется в Python-коде; поправка для NestJS — в подразделе «В iron-back».

### §10.1. Территория = пакет, корень = единственная дверь

Крупная подсистема живёт **пакетом** — директорией с `__init__.py` (в Node это папка с `index.js`; в Python — ровно то же самое, так устроены `requests`, `sqlalchemy` и стандартная библиотека):

```
vanna/artifacts/
    __init__.py   → class Artifacts — корень, наружу торчит только он
    detect.py     → разбор и политика   (внутренность)
    store.py      → журнал и витрина    (внутренность)
    flow.py       → шаги сценариев      (внутренность)
```

У корня — **сценарии предметной области**, а не механика:

```python
artifacts = Artifacts(ask=…, forget=…)        # точка сборки: только инфраструктура
artifacts.notice(blogger=…, raw_artifacts=…)  # заметили → спросили менеджера
artifacts.confirm(question, by=…)             # менеджер подтвердил → записали
```

Внутренние шаги собирает сам корень, вызывающий их не знает.

**Зачем.** Без корня контроллер обрастает фабрикой на каждую операцию: сегодня две, завтра пять, и любой новый шаг внутри подсистемы тянет правку контроллера. С корнем состав территории — её личное дело; `vanna.py` не меняется, когда внутри появляется новый шаг. Это и есть практический ответ на вопрос §9 «что мы хотим заменить, не трогая остальное».

⚠️ **Дверь бывает на сценарии — и не бывает на запись** (28.08). `deal/` в telebot — территория **сценариев**: `DealDesk.after_status_change` собирает всё, что происходит вместе со сменой статуса. Но состоянием сделки территория не владеет: оно лежит колонкой `bloggers.status`, а задачи менеджера — строками `pending_actions`, и писать их может кто угодно. Пока так, инвариант «у закрытой сделки нет открытых разговоров» **бездомный**: его удерживают в момент перехода и нарушают позже, любой записью мимо. Разбор — E29; почему сторож здесь не замена двери — E30.

### §10.2. Питоновская поправка: корень оправдан сценариями, а не группировкой

В Node/Java класс нужен, чтобы сгруппировать функции — другого способа нет. **В Python модуль уже является пространством имён**, поэтому класс, который только группирует и делегирует, — известный анти-паттерн («класс вместо модуля»). Отсюда правило:

- корень заводим, когда у него есть **сценарии** (методы, выражающие операции предметной области целиком);
- если хочется корень только чтобы писать `store.journal.record()` вместо `journal.record()` — корень не нужен, хватит модуля;
- чистые данные (константы, DDL, карты соответствий) остаются **константами модуля**, их не заворачивают в класс ради симметрии.

Имя корня — по роли в процессе (§8): `Artifacts`, а не `ArtifactStore` («Store» обещает только хранилище, а корень шире) и тем более не `Manager`.

### §10.3. Что мы берём из DDD, а что нет

Берём: **агрегат как границу** (снаружи — только корень), **инварианты живут внутри** (в `vanna/artifacts` их три, они перечислены в докстринге пакета), **имена из языка предметной области**.

Не берём буквально: внутри территории соседствуют доменные объекты и репозитории — отдельного «слоя инфраструктуры» с persistence-ignorance мы не строим. Причина практическая: подсистема небольшая, а разнесение по слоям дало бы вдвое больше файлов без единого ответа на вопрос §9. Драйвер БД при этом всё же спрятан за инъектируемым исполнителем (`ArtifactTable`) — этого достаточно, чтобы территория тестировалась без базы.

### §10.4. Цепочка шагов или последовательность

Каноническая композиция `new FrameExtract(new FramesAmount(new FileInfo()))` (§0) элегантна, когда шаги — **конвейер над одними и теми же данными**: каждый берёт результат предыдущего и обогащает его.

Если шаги разнородны — «снять прежний вопрос» ничего не передаёт дальше, «записать в журнал» отдаёт id, «спросить менеджера» отдаёт message_id — вкладывать их друг в друга значит склеивать несвязанное ради формы. Тогда пишем **последовательность внутри сценарного метода** корня; оглавление всё равно читается, потому что метод короткий и состоит из вызовов-шагов.

### В iron-back

Крупная подсистема живёт **модулем**, наружу торчит одна дверь. В NestJS это выражено буквально массивом `exports`: что не экспортировано — внутренность территории.

У корня — **сценарии предметной области**, а не механика. Внутренние шаги корень собирает сам, вызывающий о них не знает. Без корня контроллер обрастает знанием о внутренностях модуля: сегодня два шага, завтра пять, и каждый новый шаг тянет правку контроллера. С корнем состав территории — её личное дело.

**Поправка для NestJS.** Здесь, в отличие от Python, файл сам по себе не является достаточным пространством имён для DI — сущностью инъекции выступает класс-провайдер. Но правило §9 остаётся: корень заводится, когда у него есть **сценарии**, а не для того, чтобы писать `store.journal.record()` вместо `journal.record()`. Чистые данные — конфигурационные карты, константы, справочники — остаются экспортами модуля и не заворачиваются в класс ради симметрии. [`modules/config/index.ts`](../src/modules/config/index.ts) (422 строки конфигурационной карты) — правильно, что это данные, а не класс.

Имя корня — по роли: `Experts`, а не `ExpertsManager`.

### §10.5. Схему объявляет территория, порядок задаёт лента

DDL таблицы лежит рядом с запросами, которые её используют (`store.SCHEMA`) — заводя колонку, правишь один файл. Но **порядок исполнения** остаётся в общей ленте `db.py::init_db()`: там внешние ключи и бэкфиллы, читающие соседние таблицы, а неверный порядок падает не в тестах, а на холодном старте прода. Формула: *территория говорит «вот мой DDL», лента говорит «вот когда он выполняется»*.

**В iron-back** миграции лежат в `migrations/` единым списком с временными метками, и это правильно по той же причине: порядок важен. Правило: entity живёт в своём модуле рядом с логикой, миграция — в общей ленте.

⚠️ **Поправка к версии от 2026-08-02.** Там было написано: «`synchronize: false` в `ormconfig.ts` не трогать никогда» — как будто это защищает схему. Рантайм читает не `ormconfig.ts`, а [`main.module.ts`](../src/main.module.ts), где `synchronize` включён в режиме DEVELOPMENT, а DEV работает именно в нём. Разбор и решение — [db-backup.md](db-backup.md) и [upgrade-plan.md](upgrade-plan.md).

### E29. Инвариант состояния ≠ уведомление о переходе

**Случай, из которого выведено (28.08).** Менеджер: «Блогер уже в „Отказе“ в Boyscout, но в Telegram висит в pending, и дальше не продвинуться». Диагноз с первого взгляда — классическое «где-то случилось, а в другом месте не знают»: сделка закрылась, а очередь задач об этом не узнала. Отсюда напрашивается лекарство: подписка, событие `deal_closed`, наблюдатель.

**Проверка по базе лекарство отменила.** `rejected_at = 07.08`, а задачи-разговоры на этой карточке заведены **24.08 и 27.08** — через семнадцать и двадцать дней после закрытия. Задача не «пережила» закрытие сделки: её завели заново, кнопкой «💬 Показать диалог», которая пересоздаёт черновик и не спрашивает, жива ли сделка.

То есть **со стороны сделки в тот момент не происходило ничего**. Событию не на что срабатывать, подписчику нечего ловить.

#### Различение

- **Событие** — уведомление о **переходе**: «сделка только что закрылась».
- **Инвариант** — свойство **состояния**: «у закрытой сделки нет открытых разговоров».

Свойством состояния переходы не управляют. Между двумя переходами всегда есть промежуток, и любой писатель, пришедший в этот промежуток, свободен нарушить всё, о чём его не спросили. Событийная модель закрывает моменты, а дыра — в промежутках между ними.

E24 подходит к этому вплотную: «сигнал вправе потеряться, поэтому реакция на сигнал — *пересчитай состояние*, а не *сделай шаг*». Здесь то же правило, доведённое до конца: если реакция на сигнал — всё равно пересчёт, то **сам сигнал не является механизмом согласованности**. Он про реактивность и удобство: узнать раньше, чем при следующем опросе. Согласованность держит тот, кто пересчитывает и спрашивает.

Вторая цена подписки — прямо запрещённая в telebot: чтобы подписчик мог **решать**, ему нужна копия чужого состояния («сделка 4240 закрыта»). Это вторая правда, против которой четыре правила в `iron.telebot/docs/CONCEPT_2026-08-12_PROJECTION_OBJECTS.md`.

#### Три уровня, по возрастанию цены

1. **Спрашивать, а не быть уведомлённым.** Перед записью спросить у хозяина состояния: жива ли сделка. Дёшево — и ровно поэтому легко поставить не туда. Спросить *на кнопке* значит вылечить одну кнопку; следующий писатель придёт мимо.
2. **У невозможного состояния не должно быть двери.** Запись идёт через территорию, которая знает инвариант, и «закрытая сделка с открытым разговором» становится невыразимой. Это и есть сильная форма — та, ради которой §10 заводит корень-дверь.
3. **Сторож, который замечает расхождение** (E30) — страховка на то, что писатели бывают вне объектного графа.

**Признак, что лечите не то:** обсуждение сводится к «давайте добавим ещё одно уведомление». Уведомлений станет больше, промежутки останутся прежними.

#### Где инвариант живёт

Инвариант принадлежит тому, кто владеет **обеими** его сторонами. Случай из telebot — инвариант бездомный: состояние сделки лежит колонкой `bloggers.status`, а задачи-разговоры — строками `pending_actions`, и не владеет ими никто. `deal/` сегодня — территория **сценариев** (что делать вместе со сменой статуса), а не хозяин состояния: объекта «Сделка», которого можно спросить «жива ли ты» и который отвечал бы за свои задачи, там нет вовсе. Отсюда и то, что статус пишут из полутора десятков мест (E28), и сегодняшний зомби.

**Цена шага 2 невелика, и её стоит назвать вслух (E27):** `db.add_pending` зовут из **четырёх** мест, все в `vanna.py`. Дверь «задачу-разговор заводит территория сделки, потому что только она знает, жива ли сделка» — это вечер работы, а не рефакторинг.

### E30. Сторож: орган восприятия или отсутствующая дверь

**Возражение, из которого выведено (Сергей, 28.08).** «Если есть сторож-контроллер — значит архитектура неправильная. В правильном ООП объекты как люди: автономны, знают, как им жить, и общаются друг с другом, а не живут под надзором».

Возражение верное, но неотличимо сформулированное: сторож стороже рознь, и разделяет их один вопрос.

#### Критерий: что именно сторож чинит

- **Чинит истину** → это **второй писатель**. Значит, у истины нет двери, и сторож занял её место. Диагноз не «сторож лишний», а «двери нет»; убирать надо не сторожа, а причину, по которой он что-то находит.
- **Пересчитывает производное из истины** → это **орган восприятия**, и он законен. Он не командует сущностями, он заново выводит то, что и так выводится из состояния. Ровно «пересчитай состояние» из E24. На языке концепта проекций — линза, а не владение.

Три свойства законного сторожа:

1. **Не пишет сам** — зовёт единственного писателя (иначе появляется второй маршрут записи, E24).
2. **Подписывает свою работу** — по следу видно, что это починка, а не нормальный ход.
3. **В здоровой системе не находит ничего** — то есть каждая находка является симптомом, а не работой.

#### Сверка с кодом telebot

`artifacts.board.FunnelStamper` проходит все три: пишет не сам, а через `FunnelHistory.notice`; помечает `cause='tick'`, `actor='tick'`; в докстроке записано «в здоровой системе тик не находит ничего», а на находку пишет `log.warning: какая-то точка вызова журнала не сработала`. И чинит он **производное** — `column_key`/`column_since`, вычисляемые `FunnelBoard` из статуса и интеграции; истина остаётся в `bloggers.status`.

Но вывод из этого ровно тот, к которому ведёт возражение: **сторож — термометр, а не лечение**. Раз он что-то находит, где-то нет двери. Правильная реакция на находку сторожа — не «хорошо, что поймали», а **заявка на дверь**.

#### Почему сторожа всё же нельзя вычесть до нуля

Автономия объектов покрывает то, что является объектом. У системы есть писатели **вне объектного графа**, и им автономия не адресована:

- правки SQL руками по проду (в telebot это штатная процедура, `DEV_CHEATSHEET §6`);
- строки, записанные до появления правила (`pending_actions` старше `deal/`);
- соседний сервис в другом репозитории, пишущий в ту же базу;
- падение между двумя записями, не накрытыми одной транзакцией.

Поэтому аналогия «объекты как люди» доводится так: арбитр в организации существует не потому, что сотрудники калеки, а потому что у организации есть **граница с миром**, которой не владеет ни один сотрудник. Сторож смотрит на границу, а не на коллег.

#### Правило

> Сторож, который чинит истину, — отсутствующая дверь. Сторож, который пересчитывает производное и говорит вслух, — орган восприятия. Первого убирают вместе с причиной, второго держат и следят, чтобы он молчал.

## §11. Живая иерархия: время, масштаб, изменчивость

Здесь — три свойства, без которых дерево остаётся снимком одного прохода, а не живой системой (§11.1–§11.3), и два следствия для работы с кодом: как заменять разбиения (§11.4) и чем разбиение становится деталью конструктора (§11.5).

В основном каноне эти пункты изложены кратко, а в `OOP_PRINCIPLES_extra.md` — подробно, с пересечениями и примерами. Здесь они слиты: §11.1 = E31, §11.2 = E32, §11.3–§11.4 = E33, §11.5 = E34. План внедрения в telebot — `plan/PLAN_2026-09-13_PARTITIONS.md`.

### §11.1. Объект — путь от рождения до смерти: повторение есть экземпляр, а не подписка (E31)

**Откуда (Сергей, 13.09).** Разбор заряженных кнопок (`plan/PLAN_2026-09-12_ANOMALIES_TRIAGE.md`, Ф2): карточка «взять в работу?» переживала свой вопрос четырьмя путями. В обсуждении связь сначала записали подпиской — `deactAfterWork.watch(cardToWork)`, черновым ходом, чтобы пройти тему. Сергей тут же её снял:

> «watch — это реакция на повторяющееся событие, а в правильном ООП каждое повторяющееся событие — экземпляр нового объекта. Цикл — это коллекция объектов, где на каждой итерации один умирает и рождается новый. Каждый объект — путь от рождения до смерти.»

И два уточнения того же дня:

> «Если после A должно произойти B, значит нам нужен ещё один объект, смысл которого — сделать A, а потом вызвать B.»
>
> «Если родитель слушает события своего ребёнка, это не подписка: ребёнок транслирует родителю своё жизненное состояние, чтобы тот поменял поведение и раздал новые команды.»

#### Правило

> **У каждого объекта есть повод рождения и условие смерти; всё между ними — его путь. Повторяющееся событие — это цикл во времени: каждое вхождение рождает экземпляр. Порядок «после A — B» — тоже объект: родитель, чей путь — A, затем B.**

Три следствия:

1. **В домене нет подписок.** Если после A должно произойти B, то B не следит за A, и A не зовёт B изнутри. Нужен **ещё один объект — родитель**, смысл которого «сделать A, затем B». A и B друг о друге не знают; порядок, связь и решение «идти ли дальше» принадлежат родителю (§0, E2, E8). Там, где хочется `watch`, пропущен объект: экземпляр повторения или родитель, связывающий шаги.
2. **Смерть объявляется у объекта, а не у тех, кто его убивает.** Условие смерти — часть определения объекта. Процессы, которые его наступление вызывают, спрашивают объект или его хозяина (E29), а не хоронят его каждый своими руками.
3. **Объект без условия смерти — зомби.** Он молчит, пока его кто-нибудь не заденет, — и тогда действует от имени решения, которого уже нет.

Как это выглядит на случае из telebot (эскиз, не код проекта):

```python
# ✗ B подписан на A — связь спрятана в подписке
close_entry.watch(take_to_work)

# ✗ A зовёт B изнутри — A знает о B, а в описании A появилось «и» (E13)
class TakeToWork:
    def run(self, blogger):
        ...
        CloseEntryQuestion(db).run(blogger)

# ✗ пара переписана в каждой двери — родитель есть, но безымянный и размножен;
#   новая дверь забудет второй шаг
def on_scout_take_button(blogger):
    take_to_work.run(blogger)
    close_entry.run(blogger)

def on_manager_reply(blogger):
    take_to_work.run(blogger)
    close_entry.run(blogger)

# ✓ связь — отдельный объект, названный по смыслу целого, а не «A и B» (Gpt §14)
class EnterFunnel:
    """Вход блогера в воронку: взять в работу, затем закрыть вопрос входа."""

    def __init__(self, take: TakeToWork, close_entry: CloseEntryQuestion):
        self._take, self._close_entry = take, close_entry

    def run(self, blogger):
        taken = self._take.run(blogger)     # ребёнок сообщает, что с ним стало
        if taken.happened():                # решение — у родителя
            self._close_entry.run(blogger)  # и следующая команда — тоже
        return taken

# двери знают одно имя
def on_scout_take_button(blogger):
    enter_funnel.run(blogger)
```

`TakeToWork` не знает про карточку, `CloseEntryQuestion` не знает про взятие в работу; об их связи знает только `EnterFunnel`, и в оглавлении она видна его именем. «Затем» в описании родителя не нарушает тест на «и» (E13): сам он не берёт в работу и не гасит карточку, его работа — порядок и решение, идти ли дальше. По форме это комбинатор Gpt §24 (`Sequence` с условием продолжения), получивший предметное имя.

⚠️ «Цикл» здесь — повторение: `for`, тик расписания, поток однородных событий. В `CONCEPT_2026-08-10_PHASE_LOOPS.md` «цикл» — фаза ожидания сделки. Это разные слова.

#### Два масштаба пути

| путь | примеры | где живёт память |
|---|---|---|
| **короткий** — секунды | попытка доставки, разбор пачки, показ напоминания | в памяти процесса; рестарт его обнуляет (E19) |
| **длинный** — дни и недели | заход «В работу → Успех/Отказ», такт разговора «повод → решение» (концепт 10.08 §11.1) | строка в БД; объект Python поднимает её на время вопроса (E12 «память о себе») |

Длинный путь состоит из коротких: заход рождает такты, такт рождает попытки доставки и показы напоминаний. **Напоминание — не новый такт, а короткий экземпляр «показать ещё раз»** внутри длинного пути такта.

#### Где событие законно

- **На границе с чужим миром.** Telebot присылает update, и адаптер (E7, E9) превращает его в рождение экземпляра. В telebot так уже устроено: `webhook_intake` (update → разбор), накопитель входящих (`InboxBatch` на пачку), `outbound_queue` (запись на сообщение).
- **В вехах пути.** Объект сам объявляет, где он (§7, E26). Журнал, доска, зеркало и UI — линзы над вехами, а не участники доменных отношений. Хранить вехи можно (E19; концепт 10.08 §11.6 «хранить события, а не состояния»). Строить на подписке логику — нельзя.
- **В жизненном состоянии ребёнка — для его родителя.** Ребёнок транслирует родителю, что с ним происходит, — «начал», «жду», «готово», «ошибка», — чтобы родитель сменил поведение и раздал новые команды (E8: дети сообщают факты, решает родитель; Gpt §7–§8: управление идёт сверху вниз, готовность, результат и ошибка — снизу вверх, единым алфавитом событий жизненного цикла). Это не подписка: слушает только тот, кто запустил, связь выдана в момент запуска и умирает вместе с ребёнком.

Одно и то же событие ребёнка может уйти двумя адресами: **вехой** — в журнал и на доску (§7: узел пишет в общий store напрямую, а не пересылкой через родителей) и **состоянием** — своему родителю. Веху читают, но по ней не решают; по состоянию решает только родитель. Линза, которая начала решать, — это и есть подписка.

#### Родитель связи: класс и метод корня

Сергей (13.09): «не стоит параноидально создавать класс на каждый малейший случай, но цена нового класса невелика — остаётся только придумать имя».

- **В сомнении — класс.** Память объект почти не занимает; платим именем, и эта плата полезна: не получается назвать связь — значит, она ещё не понята (E13, тест на имя).
- **Класс и метод корня — не выбор, а два слоя.** Если связь — операция территории (§10: пакет с одной дверью, у корня сценарии), снаружи она видна **сценарным методом корня**, и двери знают только его. Внутри метода — короткая последовательность (§10.4), пока у связи нет своих решений, или класс вроде `EnterFunnel` из эскиза, когда решения и варианты появились. Переход от одного к другому — дробление из §11.3: контракт корня прежний, двери правок не видят. Обязательно одно: связь живёт в одном месте и под именем, а не в A, не в B и не в каждой двери.
- **Для случая из telebot метод уже задуман.** `DEAL_DESK_RATIONALE.md` §1 (02.08) предлагал `desk.take_to_work(manager, source=…)`, а `vanna/deal/__init__.py` оставил `DealDesk` классом, чтобы следующий сценарий был «дописать метод рядом». Шаг 2 не решён (там же, §11.4). Сегодня дверь `deal/` протекает: `vanna.py` зовёт мимо `DealDesk` двух исполнителей, меняющих состояние, — `ConversationTasks.clear` (три места) и `CardTasks.retire` (Ф2, через `_retire_outdated_cards`).
- **Связь чуть изменилась — параметр, метод, класс, по нарастанию.** Отличается «откуда и кто» при том же пути — параметр, переданный явно, а не угаданный по месту вызова (так в `DealDesk` сделаны `cause` и `actor`, инвариант 2 территории; родственное — E3). Отличается шаг — второй метод рядом, а общие шаги остаются детьми, которых зовут оба, а не копией. Методы разошлись по двум признакам из трёх (данные, причина изменений, вызывающие; E13) — это две связи и два класса.

Почему разница обязана жить в родителе, видно на двух дверях взятия в работу. Кнопка Boyscout (`POST /api/bloggers/<id>/take`) после записи статуса пишет аудит, гасит карточку, шлёт веху в бизнес-зеркало, двигает доску, обновляет Sheets, переводит задачи взявшему и выбирает стартовый шаг. Авто-взятие по ответу менеджера (`_auto_take_inbound_on_reply`) гасит карточку, двигает доску и пишет аудит. Часть разницы законна: менеджер уже в диалоге — переводить и подсказывать нечего. Про зеркало и Sheets неизвестно, намеренно ли: `DEAL_DESK_RATIONALE.md` §11.4 держит это открытым продуктовым вопросом. У родителя с параметром `source` разница была бы строкой, которую видно и можно обсудить; без родителя двери разошлись молча.

#### Чем это отличается от функционального программирования

Сергей: «в ФП всё пролетает за один раз, а у объекта есть состояние». Уточнение для кода telebot: объект Python там живёт миллисекунды, а заход — недели в базе. Значит, ценность объекта не в том, что он **держит** состояние в памяти, а в двух вещах: у него есть **путь со смертью**, и он **единственный вправе** этот путь двигать (§11.2). Сами решения внутри объекта по-прежнему пишутся чистыми функциями (E25): **решения — функции; путь, владение и отношения — объекты.**

#### Проверка себя

Для каждого объекта четыре вопроса: что его рождает? что его убивает? кто узнаёт о его состоянии? что идёт после него?

- нет ответа на второй — в проекте зомби;
- по его состоянию решает кто-то, кроме родителя, — пропущен экземпляр или родитель (линзам читать вехи можно, решать по ним — нет);
- «после него» записано в нём самом или переписано в каждой двери — пропущен родитель, который свяжет его со следующим шагом.

**Ограничитель (E16).** У повторения без судьбы — перебора данных, суммы, склейки — объект не нужен: путь из одной строки не путь.

### §11.2. Главная дорога относительна: старшинство — роль в масштабе (E32)

**Откуда (Сергей, 13.09).**

> «in_work — главная дорога только для своих детей, а для других внешних процессов может быть дочерним. Как оглавление книги: можно смотреть крупные модули всего приложения, приблизиться — отношения внутри модуля, ещё приблизиться — наш in_work, который просто часть чего-то.»

#### Правило

> **Старшинство — не свойство объекта, а его роль на уровне масштаба. На каждом уровне у вопроса одна главная дорога, и второстепенные спрашивают её, прежде чем действовать. Уровнем выше главная дорога сама становится второстепенной.**

Что это значит в коде:

1. **Второстепенный спрашивает, главный отвечает вердиктом с причиной.** Не `bool`, а «нельзя, потому что…» (§4, E5, E6 «отказ конкретен»). В Ф2 так сделан `deal.PressGate.check` → `PressVerdict.reason`.
2. **Главная дорога не знает о второстепенных** (E12, п. 3: «сущность не знает о процессах»).
3. **Один вопрос — одна главная дорога в пределах уровня.** Две главные дороги на одном перекрёстке — авария. До 13.09 на вопрос «в работе ли блогер» отвечали двое: отправка карточки спрашивала «открыта ли интеграция», напоминания — статус. По блогеру в «Отказе» интеграция закрыта, и отправка рисовала карточке кнопки, которые напоминания считали справкой.
4. **Власть кончается границей поддерева.** Объект главный для своих детей и отвечает о себе снаружи (§4), но за пределами своего поддерева не командует. Вопрос задают своему уровню или родителю, а не «чужим внукам»: сиблингов знакомит родитель (§0, E2).

Систему читают как книгу с приближением — сервисы (Vanna, Boyscout) → части и главы (`APP_MAP.md`) → территория (`deal/`) → объект и этапы его пути. На каждом уровне своё оглавление, своя главная дорога и свои отношения.

#### Масштабы книги telebot

```
уровень 0   сервисы       Vanna · Boyscout · соседи в iron-telegram
уровень 1   части, главы  APP_MAP.md: I Машина · II Ядро · III Спутники · IV Витрина
уровень 2   территория    vanna/deal/ — DealDesk · PressGate · CardTasks · ConversationTasks
уровень 3   объект        CardTasks — этапы его пути: прочитать статус → решить → погасить → снять кнопки
```

По этой модели цикл «в работе» — главная дорога уровней 2–3: у него спрашивают карточка, кнопки и напоминания. На уровне 1 он — часть ядра, на уровне 0 — деталь Vanna, о которой Boyscout не знает вовсе (Boyscout спрашивает Vanna через `/proxy`).

Честная оговорка: **сегодня этого объекта нет одним куском.** Его вопросы живут в SQL `db.take_blogger_to_work`, в правиле `message_kinds.card_is_decision` и в `deal/`, а на уровне 1 разнесены по нескольким главам. E32 объясняет, почему это больно: главная дорога есть, но её не видно.

#### Оглавление с отношениями

Сегодня в telebot записан **состав**: `APP_MAP.md`, `__init__` территорий. Но не **отношения**: шесть вызовов `_retire_outdated_cards` находятся только поиском по коду — ровно то «устное знание», которое E2 требует записывать.

Часть отношений записывается сама, если следовать §11.1: связь «после A — B» — это родитель, а родитель — строка состава. Шесть вызовов `_retire_outdated_cards` стали бы двумя именами в составе территорий (родитель взятия и родитель мерджа) и попали бы в оглавление без отдельной таблицы.

Отдельного объявления требуют отношения «кто кого спрашивает». Цель — на каждом уровне одним экраном объявлять, кто главная дорога и кто её спрашивает, и **сверять это объявление с кодом замком**, как уже сделано с `APP_MAP` и `message_registry.json`. Иначе оглавление с отношениями станет ещё одной таблицей, которая врёт.

#### Проверка себя

Назовите уровень, на котором стоит объект, и его главную дорогу. Если объект главный «вообще» — масштаб не назван. Если на один вопрос в пределах уровня отвечают двое — это будущая авария.

### §11.3. Разбиение не единственно: процесс мутирует мягко (E33)

**Откуда (Сергей, 13.09).**

> «У нас больше нет единственного верного подхода с уникальным кодом. Процесс 1 сегодня состоит из 1.1, 1.2, 1.3. Завтра мы разбили 1.2 на 1.2.1 и 1.2.2. Потом 1.2.2 забрал часть логики у 1.3 — и 1.3 мы заменили на 1.4, чуть короче. Код становится органичным, перестаёт быть жёстким, и под меняющиеся требования его можно мягко мутировать.»

И два продолжения того же дня — о том, как новое разбиение входит в код:

> «Пишем новое разбиение, которое призвано заменить часть кода. Та часть, что планируется к замене, пока не удаляется: она инкапсулируется в оболочку — „старое разбиение“, — а новое вставляется вместо него или даже поверх него. Старое можно не удалять, а исключить из цепочки с пометкой на удаление.»
>
> «Несколько разбиений планируют себя так, чтобы по-новому покрыть ландшафт. Процесс из пяти шагов a, b, c, d, e покрыт пятью разбиениями. Изменилась доменная логика: a, b, e остаются, а c и d надо совершенно перекроить и заменить новыми x1, x2, x3. К такому рефакторингу тоже надо подходить в несколько этапов.»

#### Правило

> **Процесс — это множество шагов поведения, а его декомпозиция — одно из разбиений этого множества. Верных разбиений много. Разбиение законно, пока объединение его блоков — тот же процесс, то есть тот же контракт родителя.**

Так код перестаёт угадывать единственную правильную форму и меняет её вслед за требованиями.

⚠️ О словах. «Множество» в документах telebot уже занято дважды: у линз, которые вправе пересекаться (концепт 12.08), и у вех — «множество храповиков» (концепт 10.08 §2.4). Здесь третье значение, поэтому ключевое слово — **разбиение**: раскладка одних и тех же шагов поведения по объектам.

#### Три операции над разбиением — все в telebot уже случались

| операция | что происходит | пример |
|---|---|---|
| **дробление** 1.2 → 1.2.1 + 1.2.2 | блок делится, объединение прежнее | 23.08: разбор входящего разделён швом «приём / разбор» — `identify_and_record` и `analyze_blogger_message`, между ними встал накопитель (`tz/TZ_2026-08-23_INBOX_BATCHING.md`) |
| **перенос** кусок 1.3 → 1.2.2, на месте 1.3 — 1.4 | шаг уходит в соседний блок, имя следует за ответственностью | 13.09: вопрос «решение ли ещё карточка» ушёл из `_send_blogger_card_to_manager` в правило `message_kinds.card_is_decision`; теперь его задают отправка, напоминания, кнопка, гашение и перепоказ |
| **слияние** | несколько блоков — в один | 24.08: пять разрозненных вызовов Claude сведены в одну дверь `blogger._ask_claude` (`incident/INCIDENT_2026-08-24_ANTHROPIC_CREDIT_BALANCE.md`) |

#### Четыре условия, без которых мутация перестаёт быть мягкой

1. **Контракт родителя стабилен.** Клиенты не замечают смены разбиения (§0: «внутренний узел можно заменить, не ломая корень»).
2. **Дети не знают братьев.** Перенос куска трогает двух соседей и строку сборки, а не весь граф (§0, E2).
3. **Имя следует за ответственностью.** Укоротившийся 1.3 с прежним именем обманывает оглавление: новый объём — новое имя 1.4 (E1 «имя — выход», E13, Gpt §17 «честность структуры»).
4. **Замок стоит на объединении, а не только на блоках.** При смене разбиения блоки меняются вместе со своими замками. Доказательство, что процесс остался тем же, даёт замок на контракте родителя, который исполняет путь целиком. 13.09 это видно на живом примере: проверка отдельного шага — порядка вызовов по AST — пропустила «мёртвый» гейт, а исполнение пути нажатия целиком его поймало.

#### Где блоки вправе пересекаться

- **Временно** — пока новое разбиение идёт рядом со старым: рубильник, откат без деплоя и **срок годности** (§9, E27; «идти рядом» у Сергея). Накопитель входящих в telebot 24.08 жил рядом со старым путём с долгом «убрать одну из двух веток».
- **Постоянно** — только линзы, которые читают и ничем не владеют (концепт 12.08 §1.1, `CONCEPT_2026-08-12_PROJECTION_OBJECTS.md`).

Владение — запись и решение — в устойчивом состоянии не пересекается: у каждого шага поведения один хозяин (E29, §11.2 п. 3). Иначе «органичный» код становится двумя правдами.

### §11.4. Замена разбиения: рядом, а не вместо (E33, продолжение)

Разбиение не переписывают на месте — рядом строят новое и меняют их местами. Выгода — рефакторинг без отката рефакторинга: откатывают рубильник, а не правки. В telebot так уже сделан накопитель входящих (`tz/TZ_2026-08-23_INBOX_BATCHING.md`): новый путь рядом со старым, переключение — значение в `search_config`, откат — один UPDATE.

| стадия | что происходит | чем доказано |
|---|---|---|
| **1. шов и оболочка** | заменяемый код заворачивается в оболочку с контрактом будущего разбиения; тело не меняется или переносится как есть | старые замки зелёные без правок |
| **2. новое рядом** | новое разбиение пишется на тот же контракт | один контрактный замок проходит на обоих; намеренные отличия записаны списком |
| **3. переключение** | рубильник ставит в цепочку новое; по желанию сначала тень — новое только решает (E25), применяет старое | расхождения тени в логе; откат — значением, без деплоя |
| **4. снос со сроком** | старое вне цепочки, на карте разбиений — срок и условие сноса (§11.5) | после срока замок краснеет |

«Поверх» — тот же путь по частям: новое встаёт перед старым, делает то, что уже умеет, остальное отдаёт старому, и старое худеет до сноса. В индустрии путь целиком зовут Branch by Abstraction, а постепенное обрастание — Strangler Fig.

Пять оговорок, без которых замена перестаёт быть мягкой:

1. **Срок обязателен.** «Удалить потом» без даты — копия. Копия уже стоила telebot пустой колонки на доске 10.08: разбор строки жил в двух файлах, поле добавили в одном. План 12.08 §2.8 записал прямо: «Чего делать нельзя — оставить оба пути „на всякий случай“. Именно так копия и живёт годами». Старое без срока кто-нибудь починит вместо нового или снова позовёт из новой двери.
2. **Рубильник исключающий.** Эффекты не применяются обоими путями сразу — иначе блогер получит два сообщения. Одновременно оба могут только решать.
3. **Данные совместимы назад.** Пока старое не снесено, новое не пишет того, чего старое не прочтёт: схема сначала расширяется, сужается — после сноса.
4. **Откат возвращает старые правила бизнеса.** Если они уже недопустимы, рубильник не страховка — страхуют тень и замки до переключения.
5. **Рубильник — по риску** (E27). Он стоит двух живых путей и двух наборов замков. Нужен там, где поломка тихая или путь горячий. Где поломка громкая, как у витрины Boyscout (план 12.08 §2.3: «ломается громко и сразу»), хватает отката ревизии.

#### Перекройка сегмента: несколько разбиений сразу

Когда c и d заменяются на x1, x2, x3, пары 1-к-1 нет — у c может не найтись «своего» x. Единица замены определяется так:

> **Разбиения, которые делят между собой хоть кусок поведения, меняются вместе. Единица замены — участок между общими швами старого и нового разбиения.**

В терминах множеств это самое мелкое общее огрубление двух разбиений: остаются только границы, которые есть в обоих.

```
старое  a | b |    c     |    d     | e
новое   a | b | x1  |    x2   | x3  | e       x2 взял хвост c и голову d
```

Общие швы — a|b, b|c, d|e; шва c|d в новом разбиении нет. **Одна единица:** [c d] → [x1 x2 x3].

```
старое  a | b |    c     |    d     | e
новое   a | b |    x1    | x2 | x3  | e       x1 покрыл ровно c
```

Шов c|d общий. **Две единицы:** [c] → [x1] и [d] → [x2 x3]; их можно менять в разные дни, каждую своим путём замены. Одну единицу делить нельзя: цепочка «c → x2» смешивает внутренние контракты двух разных разбиений, и у неё нет ни старого поведения, ни нового.

| этап | что | чем доказано |
|---|---|---|
| **0. разметка** | на карте: сегмент, старые и новые разбиения, общие швы, единицы замены, намеренные изменения домена | карта сходится с кодом |
| **1. швы по краям** | что пересекает швы b\|c и d\|e: данные, записи в БД, эффекты. Скрытые связи через шов (e читает колонку, которую пишет d) выводятся на шов без изменения поведения | контрактный замок сегмента записал эталон старого |
| **2. оболочка сегмента** | c и d за одной дверью, внутри не меняются | замки a, b, e и сегмента зелёные |
| **3. новый сегмент рядом** | x1–x3 за той же дверью; внутренние контракты у них свои, новые | контрактный замок сегмента на обоих + список намеренных отличий |
| **4. переключение** | по единицам замены, каждая целиком | тень, затем рубильник |
| **5. снос** | старый сегмент уходит целиком и со сроком; схема сужается после сноса; замок на швах остаётся и сторожит новый сегмент | замки a, b, e не менялись с этапа 0 |

Две развилки решаются на этапе 0:

- **Меняется шов — сосед входит в сегмент.** Если e должен получать другое, e тоже перекраивается, даже если по смыслу он «тот же».
- **Перекройка и смена домена — одним проходом или двумя.** Намеренных отличий немного и их можно назвать поштучно — одним: контрактный замок проверяет, что всё остальное совпало. Отличий много — двумя: сначала перекроить при старом поведении (замок доказывает равенство), потом менять поведение внутри нового разбиения, где оно уже локально. Список отличий, который не удаётся дописать, — продуктовый вопрос, а не технический (`DEAL_DESK_RATIONALE.md` §10).

#### Где пересекается

| принцип | что там сказано | что добавляет E33 |
|---|---|---|
| §9 | рефакторинг постепенно, рядом с работающим кодом | мутация — нормальный режим жизни кода, а не разовое событие |
| §0 | внутренний узел заменяется, не ломая корень | законна не только замена, но и дробление, перенос, слияние |
| E14.1 | где резать — по истории правок, куда бил бизнес | мутировать — туда же |
| E18, шаг «переносить, а не переписывать» | переносить, а не переписывать | перенос — одна из трёх операций над разбиением |
| E27 | два режима рядом со сроком годности | это и есть законное временное пересечение блоков; путь замены делает его процедурой из четырёх стадий |
| E25 | решение отдельно от применения | тень: новое разбиение решает, старое применяет |
| план 04.08 §5 | «перенос, а не переписывание»; старое имя остаётся дверью, псевдонимы удаляются отдельной фазой в конце | второй режим — новое рядом под рубильником, и снос по сроку вместо «в конце» |
| концепт 12.08 §11 | архитектура отбором, а не декретом; «единственно верного разреза нет, суставов больше одного» | то же для **владения**, а не только для линз: разбиение процесса тоже выбирают и меняют |
| концепт 10.08 §2.4 | «цепочка и множество» у вех | другое значение слова; см. оговорку в §11.3 |

#### Проверка себя

Можно ли переразбить процесс, не трогая его клиентов и не переписывая замок на его контракте? Если перенос куска из 1.3 в 1.2.2 требует править третий узел — дети знают братьев. Если после переноса 1.3 остался с прежним именем — оглавление врёт.

Для замены: назван ли срок сноса старого? Проходит ли один контрактный замок на старом и новом? При перекройке нескольких разбиений — названы ли общие швы и не пытаемся ли переключать по кускам единицу, которую делить нельзя?

**Ограничитель.** Мягкость — не повод перекраивать без причины. Мутация идёт туда, куда бьёт бизнес (E14.1), и оставляет запись с условием возврата (E27). Иначе органичность превращается в дрейф.

### §11.5. Умный монолит: разбиение — деталь конструктора (E34)

**Откуда (Сергей, 13.09).** Самой ценной мыслью разговора Сергей назвал не объекты и не «единственно верные связи», а разбиения:

> «Главная цель — чтобы внутри одного приложения работали как бы много микросервисов: наши разбиения весьма автономны и при необходимости могут быть достаточно легко вынесены в отдельные сервисы. Тогда приложение очень живучее: это не один большой монолит, который упал из-за одной ошибки, а умный монолит, где каждое разбиение — один объект или связка объектов, решающая свою задачу как часть более крупного процесса. Мы можем, как в конструкторе лего, менять архитектуру или расширять функционал и не бояться сломать приложение так, что потом не хватит контекста собрать всё обратно.»
>
> «Если мы что-то ломаем, то ломается в конкретном „микросервисе“, и поэтому нам всегда легко исправить. Новый программист должен быстро понять, как устроено приложение. Когда программистов несколько, каждый сосредоточен на своём „микросервисе“ и они не мешают друг другу — главное соблюсти контракты между модулями.»

#### Правило

> **Разбиение — деталь конструктора: у него есть паспорт, дверь-контракт и ступень автономии. Архитектура движется храповиком: каждое изменение оставляет разбиения не менее автономными, чем было, и карта разбиений сверяет это с кодом.**

#### Паспорт

То, что о разбиении нужно знать, не открывая его тела:

- **смысл и родитель** — какой процесс исполняет и частью чего является (§11.2);
- **дверь** — что зовут снаружи; какие имена открыты как правила и типы;
- **владение** — какое состояние пишет только оно (E29);
- **отношения** — кого зовёт и кто зовёт его;
- **где смотреть при поломке** — логгер, поля `/_status`, события аудита, алерты вотчдога;
- **замки** — какие проверяют его дверь;
- **ступень автономии** и **статус**: живое, в постройке, в тени, уходящее до даты.

Паспорт живёт в докстринге самого разбиения, рядом с кодом: так он меняется в одном коммите с телом. Образец текста уже есть в telebot — `vanna/deal/__init__.py`: зачем территория заведена, что в неё переезжает, её инварианты. Карта разбиений собирает паспорта, а связи, протечки и сигналы считает по коду — тот же приём, что у `APP_MAP.md`. Руками написанная карта отстаёт: размер `vanna.py` в `DEV_CHEATSHEET.md` однажды разошёлся с кодом в 2,5 раза.

#### Ступени автономии

| ступень | признак | чем проверяется |
|---|---|---|
| **0** размазано | логика живёт парами в обработчиках | — |
| **1** названо | глава `APP_MAP` или объект с именем | карта `APP_MAP` |
| **2** дверь на сценарии | снаружи зовут только корень; правила и типы открыты | счётчик вызовов мимо двери |
| **3** дверь на запись | своё состояние пишет только оно; у инварианта есть дом (E29) | счётчик чужих записей равен нулю |
| **4** сбой в границах | сбой не выходит за дверь; замки вызывают дверь, а не читают файл | замки разбиения; счётчик замков на файл |
| **5** выносимо | наружу только контракт: команды внутрь, состояние и вехи наружу (§11.1); память и транзакции с соседями не делит | разбор «что сломается при выносе» |

Та же шкала уже рисовалась руками — маркеры ✅ ◐ ✖ в матрёшке плана 04.08 §2. Ступени делают её мельче и считаемой.

**Ступень 5 — способность, а не цель.** Вынос отнимает то, что монолит даёт даром, — одну транзакцию и один деплой: мердж дублей переносит сообщения и задачи одной транзакцией (`db.merge_bloggers`), а между сервисами это стало бы цепочкой шагов с компенсациями. Выносят по поводу — нагрузка, отдельная команда, свой ритм выкатки, отдельный домен отказа (E27). Одно такое разбиение в telebot уже есть: витрина Boyscout — отдельный сервис Cloud Run, данные о блогерах берёт у Vanna только по HTTP (`boyscout/app.py`, `/proxy/*`).

#### Что это даёт — и где сегодня предел

- **Поломка локализуется**, если у разбиения свой логгер, свои поля `/_status`, свои события и свои замки — и всё это записано в паспорте. Тогда ответ не «ой, всё сломалось», а «сломалось разбиение X, чинить в нём Y». Сегодня так можно сказать о вынесенных модулях — у каждого логгер `vanna.<модуль>`, — а о коде внутри `vanna.py` только с точностью до главы: все его 8125 строк пишут в один логгер `vanna`.
- **Новичок читает контракты, а не тела:** один экран разбиений со стрелками, дальше — паспорт нужного.
- **Несколько программистов не мешают друг другу,** пока правят разбиения за их дверями. Смена контракта двери — событие для всех, кто её зовёт, и карта их перечисляет. Пока восемь тысяч строк лежат в одном файле, мешать друг другу они будут — храповик снимает это постепенно.

#### Храповик: правила

Изменение не поднимает ни одного счётчика протечек, а починенная протечка опускает счётчик, и без записанного решения он назад не поднимается.

1. **Новая сквозная логика ложится в дверь разбиения,** а не парой в каждый обработчик (§11.1).
2. **Задача, зашедшая в разбиение, чинит протечки на своём пути.** Счётчик на карте опускается и назад не поднимается без записанного решения.
3. **Код переходит между разбиениями только путём замены** (§11.4). Замки переносимого кода переводятся с текста на поведение двери **до** переноса: отрицательная проверка по тексту после переноса зеленеет, ничего не проверив (план 12.08 §1.4).
4. **Новый модуль без разбиения и разбиение без паспорта роняют замок карты.**
5. **Ступень не заявляют выше, чем подтверждают счётчики.**
6. **Уходящее разбиение живёт до срока.** После срока — снос или записанное продление с причиной.

Храповик не заменяет решений о том, *что* трогать: переносы по-прежнему идут по поводу, куда бьёт бизнес (E14.1), с условием возврата у каждого отказа (E27).

# Часть II. Композиция: виды, комбинаторы, анти-приёмы

## Виды композиции (Gpt §4 · E1 · E4 · сверка)

Примеры выявляют как минимум четыре формы композиции, которые не следует смешивать (Gpt §4). Сверка с живым кодом добавила ещё две, самые частые в нём, — обёртку и политику. Итого **шесть видов**, и связь в точке сборки должна опознаваться как один из них (Gpt §3, §3 этого документа).

### 1. Структурная композиция (Gpt §4.1)

Объект является частью более крупного механизма:

```js
Field(ImageCanvas(...), Layers(...))
```

Она отвечает на вопрос: **из чего состоит территория?**

### 2. Конвейер преобразований (Gpt §4.2)

Результат нижнего шага постепенно преобразуется:

```js
FrameExtractQuery(
  FileInfoFramesAmount(
    FileInfoJSON(
      FileInfoArray(
        FileFullInfo(FileStreamInfo(ffmpeg))
      )
    )
  )
)
```

Она отвечает на вопрос: **через какие смысловые формы проходят данные?** Критерий шага такого конвейера — E1.

#### E1. Лестница абстракций: один узел — одна ступень

Самая длинная цепочка во всех пяти проектах (Thumbnail) устроена так, что **каждый узел поднимает данные ровно на одну ступень**:

```js
FrameExtractQuery(                      // → аргументы команды ffmpeg
  new FileInfoFramesAmount(             // → доменный факт: кадров больше 10?
    new FileInfoJSON(                   // → {duration, bitrate, fps}
      new FileInfoArray(                // → массив строк
        new FileFullInfo(               // → накопленный текст целиком
          new FileStreamInfo(FFMPEG_PATH))))))   // → куски байтов из stdout/stderr
```

Байты → текст → строки → структура → доменный факт → команда. Ни один узел не перепрыгивает ступень.

Из этого следуют два практических правила:

- **Имя узла называет то, что на выходе**, а не то, что он делает: `FileInfoArray`, а не `SplitFileInfo`. Тогда цепочка читается как перечень форм данных, и видно, где именно теряется или появляется смысл.
- **Тестируемость появляется сама**: у каждой ступени есть проверяемый вход и выход. Подменить источник байтов (другой бинарь, файл-фикстура) можно, не тронув разбор.

Gpt §4.2 называет такую композицию «конвейером преобразований»; здесь добавляется критерий шага — **одна ступень абстракции, названная по выходу**. А когда ступеней становится слишком много для одного выражения, группе ступеней с самостоятельным смыслом нужно имя (Gpt §14, §3).

**Проверка себя:** если в одном классе `parse` превращает сырой поток сразу в доменный ответ — внутри спрятаны 3–4 безымянные ступени, и подменить можно только всё целиком.

### 3. Агрегация однотипных возможностей (Gpt §4.3)

```js
Iface({
  LoadImgAction,
  AddZoneAction,
  DeleteZoneAction
})
```

Она отвечает на вопрос: **какие возможности подключены?** Подключаются они реестром без правки агрегатора — Gpt §9 (§3).

### 4. Прототипная композиция (Gpt §4.4)

```js
Layers(new Layer(new Canvas()))
RunningJobs(new RunningJob())
```

Переданный объект описывает не единственный runtime-экземпляр, а **образец создаваемых объектов**. Граница свежести — Gpt §5 (§5); как делить состояние между хозяином и экземпляром — E15 (часть III).

### 5. Обёртка-способность (E4)

Принципиально отличается от остальных тем, что **реализует тот же контракт, что и обёрнутый узел**: `FrameLimit`, `UpdatableHostCluster`, `QuietGuarded`.

#### E4. Способность добавляется обёрткой, а не флагом внутри рабочего узла

Повторяющийся приём: сквозная способность вводится **отдельным узлом над** рабочим, а не условием внутри него.

```js
FrameLimit(                    // квота: не более N параллельных ffmpeg + очередь
  new ExtractFrame(...),       // рабочий узел — про лимит ничего не знает
  MemDb()                      // где живёт очередь и счётчик
)

new UpdatableHostCluster(      // обновляемость
  new Manifest(new DirStructure(), new DirsComparing()),
  new HostCluster(...),        // сам кластер про обновление не знает
  JOBS_CONFIG
)

new ConnectedAgentsThrottle(   // троттлинг подключений
  new RedundantAgentsReservation()
)
```

`ExtractFrame.run()` не содержит ни `if (limitExceeded)`, ни очереди: он умеет ровно одно — вытащить кадр. Постановка в очередь, запуск следующего после завершения, восстановление незавершённых задач после рестарта — целиком в `FrameLimit`.

Так же ложатся: ретрай, кэш, дедупликация, троттлинг, аудит, feature-флаг, кап на количество сообщений.

**Проверка себя:** снимите обёртку — рабочий узел должен остаться полностью работоспособным, просто без ограничения. Если он сломался, способность протекла внутрь.

**Куда применить в telebot:** кап напоминаний, антидубли исходящих, ограничение частоты обращений к LLM — это узлы-обёртки над отправкой/вызовом, а не условия внутри отправки. Тогда «почему не отправилось» отвечает один класс с говорящим именем, а не разбросанные проверки.

### 6. Политика-правило (E5)

Передаётся в конструктор, но не является ни частью, ни шагом, ни участником, ни прототипом: `AgentRecognizing`, `QuietHours`. Подробно — E5 (§4).

### Вывод

Декларативность усиливается, когда форма связи названа явно. Например, `steps`, `actions`, `prototype`, `children`, `adapters` лучше безымянного массива зависимостей. Если связь не опознаётся ни как один из шести видов, лучше ввести именованный параметр, отдельный агрегат или именованное поддерево (Gpt §3).

## Gpt §24. Управляющие конструкции образуют алгебру процессов

Цикл и ветвление (часть III) подводят к более общему выводу. Объектами могут становиться не только бизнес-действия, но и способы их соединения:

```js
new Sequence(stepA, stepB, stepC)
new Choice(condition, thenStep, elseStep)
new ForEach(itemProcess)
new RepeatUntil(condition, process)
new Retry(policy, process)
new Timeout(duration, process)
new Parallel(processA, processB)
new Limit(concurrency, process)
```

Это **объекты-комбинаторы**. Они ничего не знают о конкретной предметной области, но задают грамматику, из которой собирается предметный процесс.

Тогда граф объектов становится похож на AST программы:

- листья — конкретные действия;
- внутренние узлы — последовательность, выбор, повторение, параллельность;
- `run()` — интерпретатор этого дерева;
- lifecycle-события — трасса его исполнения;
- UI — визуализация того же дерева.

Это одна из центральных интуиций подхода:

> Управляющая логика поднимается из скрытого синтаксиса методов в явную структуру объектов.

В результате сложный процесс можно читать, заменять, тестировать и отображать как данные, не теряя способности исполнять его.

Когда комбинатор получает предметное имя (`EnterFunnel` — это `Sequence` с условием продолжения), он становится родителем связи «после A — B» из §11.1.

## Что из примеров мы сознательно не берём

Прототипы не только показывают приём — они показывают, где приём ломается. Ниже — то, что в этих файлах работает против собственной идеи (подробный разбор «дырявых» мест — Gpt §15–§17 в §3, здесь только сводка).

- **Мешок глобальных переменных через дерево.** `iFace.global_vars(name)` / `set_global_var(name, value)` и `Layer.data("matrix")` — универсальные геттеры по строковому ключу. Это отменяет §4: снаружи снова читают чужое состояние, только через посредника, и ошибка в имени ловится в рантайме. Вместо этого — именованные методы-вопросы или явный объект-контекст, переданный в `init`.
- **Свитч по типу внутри объекта, при таблице снаружи.** Zoopark декларирует маршруты красиво (`Pages().with("/", new Page("/"))...`), но внутри `Page` стоит `if (page_type === '/') ... else if (page_type.endsWith(".js"))`. Аналогично `abstract_query(msg)` в Thumbnail — цепочка `if (msg.cmd == ...)` вместо объектов-запросов. Реестр снаружи имеет смысл только тогда, когда внутри элементы действительно разные.
- **`{stub:true}` без контракта.** Идея заглушки как видимого участника декларации правильная (см. `MockDomain` в naf), но безымянный объект не показывает, чью роль он занимает. Заглушка должна быть реализацией контракта с говорящим именем (Gpt §13, §2).
- **Флаг режима внутри узла.** `SavedMatrix.testmode()` выставляет `is_test_mode` и добавляет ветку внутрь `run()`. Подмена источника в точке сборки — верная идея; исполнение должно быть отдельным объектом того же контракта, а не ветвлением внутри рабочего.

# Часть III. Объект: что это, когда он нужен и как повторяется

## Объект — исполняемое намерение, и у него три рода (Gpt §18 · E12)

Школьный пример ООП обычно начинается с существительных: `Car`, `Animal`, `Employee`, `Shape.area()`. Он создаёт ложную интуицию, будто класс нужен прежде всего для моделирования предмета реального мира.

В рассмотренных проектах сильнее работает другой взгляд:

```js
ExtractFrame
FileInfoFramesAmount
ManagersBroadcast
AgentRecognizing
TableRenderFilesUpdate
SaveZonedImageAction
```

Формально эти имена тоже являются существительными или отглагольными конструкциями, потому что так принято называть классы. Но по смыслу они обозначают **действие, роль, процесс или намерение**: извлечь кадр, распознать агента, разослать состояние, обновить файлы.

> Объект — это овеществлённое действие: намерение, получившее зависимости, состояние, lifecycle и имя.

`ExtractFrame` можно читать как команду `extract frame`. Его `run()` означает: «исполни то единственное намерение, которым ты являешься».

Начинать поиск объектов полезнее не со списка вещей, а со списка **происходящих действий**. Но объявить, что сущностей не бывает, было бы перегибом: `Task`, `Page`, `Point`, `Layer` оправданы, если у них есть собственная идентичность, инварианты или поведение. Полезны оба рода, важно их не путать и правильно связать — а данные остаются третьим, отдельным родом.

### Процесс — работа с именем

Реальные имена процессов:

```
Thumbnail:       ExtractFrame, ExtractFrameStream, FrameExtractQuery, FrameLimit, ListeningSocket
region_selector: LoadImgAction, ShowGridAction, AddZoneAction, ChangeZoneOrderAction, StringToArrayParse
Zoopark:         AgentRecognizing, DirsComparing, RedundantAgentsReservation, SocketKeepAliveConfirmation
MUMO:            ManagersBroadcast, JobLifeBroadcast, TableRenderSyncedWithJobStatus, ManagersAutoSyncOps
me_preview:       ResourceAllocator, BatchProcessor, ExecutionEnvironment, MailScreenshotWorkflow
```

Это глаголы, опредмеченные в существительное: «извлечение кадра», «опознание агента», «подтверждение живости сокета». Не `Car` — а `Drive`.

При этом **данные остаются данными**: `payload`, `msg`, `identifiers`, `matrix`, `arr2d`, `res` — простые структуры без поведения. Разделение осознанное:

> Процесс — это работа с именем. Данные — снимок без поведения, и заворачивать его в класс ради симметрии не нужно.

Питоновский код telebot живёт по тому же закону, хотя писался отдельно:

```python
# работа — класс с ролью в имени
UnattendedIncomingFinder, UnsavedWebhookFinder, ApprovedButUnsentFinder,
BloggerTransferProposer, TransferNoticeComposer, ProfileMetricsCalculator,
BloggerDuplicateReconciler, UpdateDeduper, ManagerContactResolver

# данные — dataclass без поведения
WatchdogAlert, MergeProposal, DupCandidate, MetricResult, AutonomyDecision
```

Форма имени процесса — отглагольная: `-er/-or` (`Finder`, `Composer`, `Allocator`), `-ing` (`AgentRecognizing`) или прямо глагол+объект (`ExtractFrame`). Годится любая, лишь бы читалось как работа.

### Сущность — то, у чего есть идентичность и судьба

Второй законный род объектов. Сущность отличается от данных тремя вещами:

- **идентичность** — она та же самая, даже когда все поля изменились (сделка №417 остаётся собой после смены статуса, менеджера и текста);
- **жизненный цикл** — набор именованных состояний и разрешённых переходов между ними, а не свободный набор полей;
- **память о себе** — она умеет сохранить себя и восстановиться: живёт дольше процесса, который её тронул, и дольше самого приложения.

И третье, самое ценное для наблюдаемости: **сущность транслирует вехи своего жизненного цикла**. Переход — это не `UPDATE status`, а событие с именем, которое видно снаружи:

```python
class Deal:
    """Сделка с блогером: идентичность, состояния, вехи."""

    def move_to(self, status: str, *, cause: str, actor: str) -> None:
        transition = self._transitions.allow(self.status, status)   # правило-политика (E5)
        self.status = transition.target
        self._store.save(self)                     # память о себе
        self._milestones.emit(transition.name,     # веха наружу (§7)
                              deal_id=self.id, cause=cause, actor=actor)
```

Такой объект — прямой ответ на «судьбу» из E14: у него есть состояние, оно меняется по правилам, и каждое изменение видно снаружи без чтения исходников. Вехи попутно закрывают журнал, доску и уведомления: читателей может быть несколько, а точка эмиссии — одна. Строить на вехах доменную логику через подписку нельзя — §11.1.

### Как процессы и сущности уживаются

Это и есть главный вопрос, и на него есть пять рабочих правил:

1. **Процесс получает сущность аргументом, а не хранит её в поле.** `RemindSilent().run(deal)` — да; `RemindSilent(deal)` в конструкторе — нет, иначе короткоживущий процесс становится владельцем чужой долгой жизни (это же различение — в E15: повторитель против экземпляра).
2. **Процесс не трогает поля сущности — он вызывает её сценарии.** Не `deal.status = "no_reply"`, а `deal.park_as_silent(cause=…)`. Инвариант перехода живёт внутри сущности, иначе его придётся повторять в каждом процессе, который её меняет (§4).
3. **Сущность не знает о процессах.** Она не ходит в Telegram, не решает, кто её обработает, и не запускает рассылку. Как только она это делает — она перестала быть сущностью и стала плохим процессом.
4. **Найти и достать сущности — работа отдельного объекта-реестра** (`Deals.awaiting_reply()`, `Deals.by_id()`). Это тот же повторитель из E15: долгоживущий владелец множества + короткоживущие экземпляры.
5. **Между собой процессы обмениваются данными, а не сущностями.** `MergeProposal`, `MetricResult`, `WatchdogAlert` — снимки без поведения: их можно сериализовать, отдать в UI и сравнить в тесте.

### Кто сохраняет сущность

Два законных варианта, и выбор простой:

- **Сущность сохраняет себя сама** (через инъектированный `store`) — когда жизненный цикл богат: много переходов, у каждого свой смысл, и они должны быть атомарны с записью. Тогда «изменилось и сохранилось» — одно действие, и рассинхрон невозможен.
- **Сохраняет репозиторий** (`Deals.save(deal)`) — когда сущность фактически строка с полями, а переходов один-два. Плодить `save()` внутри незачем.

В обоих случаях **драйвер БД инъектируется**, а не импортируется: сущность обязана тестироваться без базы (§10.3).

### Где здесь код telebot

Все три рода в `vanna/` уже есть — кроме сущностей:

```python
# процессы    — есть и названы хорошо
UnattendedIncomingFinder, TransferNoticeComposer, BloggerDuplicateReconciler
# данные      — есть, чистые dataclass
WatchdogAlert, MergeProposal, MetricResult, AutonomyDecision
# сущности    — почти нет: их роль исполняют dict-строки из БД
blogger = db.get_blogger(bid)   # словарь; статусы и переходы разбросаны по вызывающим
```

Отсюда и характерная боль: `status` меняют в десятке мест, и рядом с каждым `update_blogger(status=…)` приходится не забыть журнал, доску и уведомление. Это не аргумент «завернуть блогера в класс ради класса» — это аргумент завести сущность там, **где есть настоящий жизненный цикл**: сделка, исходящее сообщение, напоминание.

**Проверка себя:** спросите об объекте — «что он делает?» (процесс), «что с ним происходит?» (сущность), «что он такое?» (данные). Если подходит ровно один вопрос — род выбран верно. Если ни один (`ManagerHelper`, `DataService`) — работа ещё не найдена, резать рано.

## Одна роль — один глагол: `run()` и имя как предназначение (Gpt §20 · E13)

Во многих примерах у объекта один главный метод — `run()`. Даже у пустых:

```js
function SetColorAction(){ this.init=(iFace)=>{return this;} this.run=(field)=>{return this;} }
function LoadedImage(){ this.run=()=>{} }
```

Это выражает важную дисциплину:

> Имя объекта говорит, **зачем он существует**, а `run()` просит его выполнить именно это предназначение.

```js
new AgentRecognizing(...).run(input)
new FileInfoArray(...).run(file)
new SaveZonedImageAction(...).run(field)
```

Смысл не в имени `run`, а в том, что **глагол один**. `ExtractFrame.run()` читается как «извлечение кадра — исполнить». Отсюда формула:

> Имя объекта = имя его единственного метода. Если их приходится называть по-разному — объект делает не своё дело.

Из этого следуют полезные ограничения:

- `run()` не должен означать «сделай всё, что умеет этот большой сервис»;
- публичные вспомогательные методы допустимы, но обслуживают ту же цель;
- имя `Manager`, `Helper`, `Utils`, `Service` часто скрывает отсутствие одной роли;
- имя действия и единый вход `run()` делают разные узлы взаимозаменяемыми элементами композиции.

**Это ориентир, а не запрет.** Два-три метода — норма, когда они грани одной роли: небольшие, близкие по смыслу, работают с одним и тем же состоянием и меняются по одной и той же причине. `artifacts.notice()` и `artifacts.confirm()` — две фазы одного разговора об артефактах; `SketchCoords.add()/line_coords()/has_min_length()` — одна работа, показанная с разных сторон. Дробить такое до одного метода на класс — это уже обряд, а не архитектура (§9).

Разделять пора, когда расходится **хотя бы два** признака из трёх: методы работают с разными данными, меняются по разным причинам и вызываются разными местами. Тогда это не грани роли, а две роли, живущие в одном файле.

Два теста, которые помогают увидеть границу:

1. **Тест на «и».** Хороший объект с `run()` можно описать одной фразой без союза «и». Если описание звучит как «получает файл, считает кадры, ограничивает очередь и сохраняет результат» или «считает метрики **и** отправляет отчёт» — перед нами несколько ролей. Это тот же тест §0, но применяемый к *имени*, а не к телу метода.
2. **Тест на два `run`.** Если объекту нужны два разных публичных сценария, которые не вызывают друг друга и не делят состояние, — это два объекта, случайно живущие в одном файле.

**У сущности может не быть `run()`:** у `Task` естественны `cancel()` и `complete()`, у `Point` — координаты и геометрические операции. Правило относится прежде всего к **объектам-процессам**.

**Питоновская поправка.** В Python механический `run()` не нужен: метод называется по сценарию предметной области (§10.2) — `artifacts.notice(...)`, `artifacts.confirm(...)`. Правило сохраняется в другой форме: **у объекта один глагол-сценарий; если их несколько, они должны быть гранями одной роли** (`notice/confirm` — две фазы одного разговора об артефактах, а не две разные работы).

Исключение, которое не считается нарушением: методы-вопросы (`isFree()`, `has_min_length()`, `isAllowLimit()`) — они не работа, а ответы объекта о себе (§4).

**Тест на именах в telebot.** В `vanna/` соседствуют два стиля имён:

```
UnattendedIncomingFinder   ← сразу ясно: находит входящие без ответа
ApprovedButUnsentFinder    ← находит согласованные, но не отправленные
TransferNoticeComposer     ← составляет уведомление о передаче
        против
SilentDigestService, FollowUpService, DirectReminderService, ManagerQualityService
```

Суффикс `Service` не отвечает ни на «что делает», ни на «что на выходе» — это то же самое «туманное» имя, что и `Manager` из §8. Само по себе это не приговор классу: имя — индикатор, а не диагноз. Но при следующей правке такого модуля первым делом стоит спросить: **какой у него один глагол?** Если глагол находится — переименовать; если находятся два — это два объекта.

## Когда объект оправдан (Gpt §19 · E14)

Самый частый вопрос при рефакторинге — «а тут точно нужен класс?». Не каждую функцию нужно превращать в класс. Практическая проверка:

> Можем ли мы осмысленно сказать: «создай X, передай ему зависимости и попроси его исполнить свою цель»?

Если да, `X` — кандидат в объект. Ниже — критерии, выведенные из того, где объекты в этих проектах реально появлялись.

**Заводим объект, если верно хотя бы одно из семи:**

1. **У работы находится имя** — двумя словами и без «и» (E13). Найденное имя — само по себе главный аргумент: значит, у работы есть отдельный смысл в предметной области.
2. **У работы есть судьба** — она может упасть, длиться, ждать, требовать ресурс, ретраиться, отчитываться о прогрессе. Всё, о чём хочется знать «в каком оно состоянии», обязано быть объектом (§7). **Это самый сильный из семи сигналов.** В полном виде судьба означает жизненный цикл: именованные состояния и переходы, вехи наружу для журнала и доски, умение сохранить себя и восстановиться после рестарта (E12). Если у предмета есть все четыре — сомнений быть не может, это объект, и заводить его надо в первую очередь.
3. **У работы есть собственное состояние на время исполнения** — накопители, счётчики, промежуточные результаты. Локальные переменные, которые «путешествуют» через три и более шага, — это уже поля будущего объекта.
4. **Работу хочется подменить** — в тесте, для другого источника, для другого режима. Прямой ответ на вопрос §9: «что заменяем, не трогая остальное?».
5. **Работа — ступень абстракции данных** (E1): на входе одна форма, на выходе другая, и обе можно назвать.
6. **Работа — нетривиальное правило решения** (E5): больше одного условия, может измениться отдельно от носителя.
7. **Работа повторяется на каждую единицу** — на задачу, слой, хост, блогера (E15).

**Ещё три оси самостоятельности** (Gpt §19), которые не всегда видны в семи сигналах: работа **требует зависимостей**; **создаёт или координирует дочерние процессы**; **имеет отдельную причину изменяться**.

**Не заводим объект, если:**

- **Это чистая функция без состояния и без судьбы** — форматирование даты, арифметика, склейка строки. Функции достаточно, когда преобразование чистое, короткое, не имеет состояния, lifecycle, заменяемых зависимостей и самостоятельного смысла в архитектурной схеме. Функция и останется функцией.
- **Это данные без поведения** — dataclass, dict, строка БД (E12).
- **Он только делегирует.** В Python модуль уже является пространством имён; класс ради группировки — анти-паттерн (§10.2).
- **Он «на будущее».** Абстракция без ответа на вопрос «что заменяем» — не нужна (§9).

Объект вводится не ради синтаксиса `new`, а ради появления **именованного участника системы**.

**Пограничный случай, который стоит помнить:** дублирование кода само по себе оправдывает **функцию**, но не объект. Объект появляется, когда к дублированию добавляется хотя бы один из семи сигналов — чаще всего судьба (2) или подменяемость (4).

### E14.1. Другой вопрос: не «нужен ли объект», а «где резать первым»

Семь сигналов отвечают на вопрос про **природу работы**. В зрелом приложении они срабатывают сразу во многих местах — и тогда нужен второй критерий, уже про **очерёдность**. Он выведен из разговора с Сергеем 23.08.

**Резать надо там, куда бизнес бил чаще всего. Не там, где больше строк.**

Размер — плохой указатель: длинная функция может быть длинной последовательностью записей, которую никто никогда не менял, и объект в ней ничего не заменит. А короткий `if/elif` из пяти веток, в который за полтора месяца четырежды вставляли новое условие, — это место, где шов уже прорезан историей, просто он не оформлен.

**Критерий проверяемый, а не вкусовой:** `git log -L` по диапазону строк или `git log --follow` по файлу. Считаем не коммиты вообще, а те, где менялось именно **поведение этого куска**, и смотрим, приходили ли правки **от бизнеса** (жалоба менеджера, новое требование), а не от рефакторинга.

Это заодно даёт прямой ответ на запрет «объект „на будущее“» (выше): git говорит, что мы уже заменяли этот кусок четыре раза. Значит вопрос «что заменяем, не трогая остальное» имеет не гипотетический ответ, а исторический.

**Живой пример из telebot.** Выбор формы передачи разбора менеджеру (`vanna._after_blogger_analysis`, цепочка `if can_auto / elif card_text / elif suggested / elif needs_pavel / else`) — ~70 строк, пять веток. Правки:

| когда | что вставили в ту же цепочку |
|---|---|
| 22.07 | тип карточки: pending до взятия в работу, подводка после |
| 30.07 | пятая ветка — «разбор пустой, но адресат-человек обязан быть» |
| 09.08 | `decision` умеет устаревать + выход «✅ Я ответила сама» |
| 11.08 | сверка дат вклеена в четыре точки из пяти |

Соседние простыни того же файла — обогащение профилем Instagram (~46 строк) и применение разбора к карточке (~35) — за тот же период правились редко и снаружи. По размеру они сопоставимы, по истории — нет.

⚠️ **Критерий не отменяет остальные.** История говорит, ГДЕ шов назрел; нужен ли там объект и какой — по-прежнему отвечают семь сигналов и E27 (цена · риск · выигрыш · условие возврата). И отдельно: частые правки бывают и признаком того, что кусок просто ещё не устоялся, — тогда объект застынет вокруг неверной границы. Разница в том, менялось ли **правило** (шов нужен) или **сама постановка задачи** (рано).

## Повторитель процесса и экземпляр итерации (Gpt §21 · E15)

В проектах повторяется двухуровневая конструкция, и это отдельный, очень устойчивый вид объекта — **долгоживущий хозяин, который на каждую единицу работы порождает короткоживущий экземпляр процесса**:

1. один раз создаётся долгоживущий объект, который принимает задания, слушает события, держит очередь или выполняет цикл;
2. на каждое задание или итерацию он создаёт свежий объект-процесс.

В декларации это выглядит так:

```js
RunningJobs(new RunningJob())
Layers(new Layer(new Canvas()))
FrameLimit(new ExtractFrame(...))
```

А в рантайме — так:

```js
Layers      → aLayer.instance(layer_id, theField)        // на каждый слой
TrackedJobs → interestingJob.instance(render_id)         // на каждый отслеживаемый рендер
FrameLimit  → extractFrame.create()                      // на каждую задачу ffmpeg
HostCluster → HostAsPair(...)                            // на каждый хост
AgentService→ workflowFactory / executionEnvironmentFactory  // на каждую задачу агента
```

`RunningJobs`, `Layers`, `FrameLimit` — **повторители/владельцы процесса**. Они живут долго и отвечают за множество запусков. `RunningJob`, `Layer`, `ExtractFrame` — **объекты одной попытки или итерации**.

> Повторитель владеет правилом повторения, а процесс — состоянием одного выполнения.

Отсюда видна и конвенция имён: **хозяин — во множественном числе, прототип — в единственном**. `Layers/Layer`, `RunningJobs/RunningJob`, `ConnectedUsers/ConnectedUser`, `TrackedJobs/InterestingJob`, `Pages/Page`. В точке сборки это читается вслух: `new ConnectedUsers(new ConnectedUser())` — «много вот таких».

Это разделение не даёт состоянию одной итерации протечь в другую:

```js
class TaskRepeater {
  constructor(taskFactory) {
    this.taskFactory = taskFactory
  }

  async run(inputs) {
    for (const input of inputs) {
      const task = this.taskFactory.create()
      await task.run(input)
    }
  }
}
```

Повторитель может отвечать за очередь, concurrency, остановку, backpressure, retry между попытками. Процесс отвечает только за одно выполнение.

**Как делить состояние между ними** — это и есть главная польза приёма:

| Живёт в повторителе (долго) | Живёт в экземпляре (одна итерация) |
|---|---|
| реестр активных экземпляров, счётчик, лимит | входные данные этой единицы |
| очередь ожидающих, порядок | промежуточные результаты, накопители |
| подписки на внешние источники | таймауты и ретраи этой попытки |
| политика: кого пускать, сколько параллельно | ошибка и статус этой попытки |
| решение «что делать с итогом итерации» | взятый ресурс и его освобождение |

**Правило:** ни одного поля, относящегося к одной итерации, в долгоживущем объекте. Нарушение этого правила — самый частый источник плавающих багов при параллельной работе: две задачи начинают делить один накопитель.

В самих примерах есть и предупреждение. Thumbnail пересоздаёт ребёнка так:

```js
this.extractFrame = this.extractFrame.create();   // прототип перезаписан экземпляром
```

Работает только потому, что экземпляр тоже умеет `create()` из сохранённых `args`. Прототип при этом теряется. Правильнее — держать прототип в отдельном поле и никогда его не перезаписывать:

```js
const unit = this.extractFramePrototype.create();   // прототип цел, экземпляр локален
this.units.push(unit);
```

Связь с §5: там `instance()` вводится как приём, а Gpt §5 — как граница свежести; здесь названа **пара ролей**, между которыми делится состояние, и правило этого деления. Для повторения во времени (событие, приходящее снова и снова) — §11.1.

## Тело цикла с судьбой — это объект (Gpt §22 · E16)

Обычный `for` меняет данные, но архитектурно часто скрывает более важный факт: каждая итерация является самостоятельным процессом. `for`/`while` — самое частое место, где объект уже назревает, но ещё не выделен.

Поэтому вопрос при ревью любого цикла:

> Не является ли тело цикла отдельной ролью, которой нужен свежий экземпляр?

```js
// region_selector: каждая итерация создаёт участника со своей жизнью
for (let i = 0; i < max_layers; i++) {
    const layer = this.aLayer.instance(this.created_layer_ord += 1, this.theField);
    this._layers[layer_id] = layer;
    layer.run(this.iFace, arr2d);
}
```

```js
for (const client of clients) {
  await new ProcessOneClient(dependencies).run(client)
}
```

Или, если зависимости уже собраны:

```js
for (const client of clients) {
  await processOneClientFactory.create().run(client)
}
```

Хозяин сохраняет за собой **«сколько раз и в каком порядке»**, объект берёт себе **«что делаем один раз»**. Выигрыш конкретный: одна итерация становится наблюдаемой (§7), её можно ретраить, логировать, тестировать в одиночку и выполнять параллельно.

**Признаки, что телу цикла пора стать объектом:**

- в теле больше 5 строк, или есть `try/except`, `await`, обращение к ресурсу;
- внутри заводятся временные переменные, живущие только эту итерацию (это будущие поля), — изменяемое состояние итерации;
- у итерации отдельный результат или ошибка, и её неудача не должна ронять цикл;
- нужен timeout или retry;
- есть освобождаемый ресурс;
- итерации выполняются параллельно;
- по итерации хочется отдельную строку в логе, журнале процесса или в UI.

Сам `for` после этого тоже может стать объектом:

```js
new ForEachClient(
  new ProcessOneClient(...)
)
```

`ForEachClient` описывает политику повторения, а `ProcessOneClient` — тело одной итерации. Технический цикл остаётся внутри, но в архитектуре появляется его предметный смысл.

**Ограничитель, чтобы не переусердствовать:** если у итерации **нет судьбы** — она не падает, не ждёт, не держит ресурс, не отчитывается — объект не нужен. Вложенные `for row / for col` при заполнении матрицы так и останутся циклами: там перебираются данные, а не выполняются работы. Для тривиального локального перебора вроде суммирования пяти чисел отдельный объект не нужен. Критерий — самостоятельность итерации, а не наличие ключевого слова `for`.

> Объект на итерацию заводят там, где итерация — это **работа**, а не там, где она — просто **перебор**.

## Ветвление как структура: ветка-объект, таблица или обычный `if` (Gpt §23 · E17)

`if/else` может быть не локальной деталью алгоритма, а самостоятельным узлом процесса — но не всякий. Полезны три разных ответа, и выбор между ними важнее самого приёма.

### 1. Ветка-объект — когда обе ветки суть работы, а условие суть правило

```js
new IfSomething(
  condition,
  new ThenThisObject(),
  new ElseOther()
)
```

Такой объект означает:

1. проверить именованное условие;
2. выбрать одну из переданных стратегий;
3. исполнить выбранное поддерево через общий контракт.

Более предметная запись ещё выразительнее — условие уходит в имя:

```js
new IfAgentRecognized(
  new StartKnownAgent(),
  new RejectUnknownAgent()
)
```

В Zoopark это уже сделано: два режима переданы объектами, и внутри `Jobs` нет `if (mode === 'special')`:

```js
new Jobs(JOBS_CONFIG, new SpecialControllerMode(), new NormalControllerMode())
```

На питоне это выглядело бы так:

```python
class RemindWhenSilent:
    """Молчит дольше окна → напоминаем, иначе — ждём дальше."""

    def __init__(self, silence: QuietPolicy, then_step, else_step):
        self._silence, self._then, self._else = silence, then_step, else_step

    def run(self, ctx):
        step = self._then if self._silence.holds(ctx) else self._else
        return step.run(ctx)
```

Что за это получаем:

- обе ветки видны в CompositionRoot;
- ветки заменяемы и тестируются отдельно;
- условие подменяемо (E5), решение получает имя;
- каждая ветка может иметь собственное поддерево, lifecycle и телеметрию (§7);
- условие перестаёт размазываться по вызывающим, и «почему не сработало» отвечает один объект.

Чего за это платим: лишний уровень косвенности. Поэтому механически превращать каждый `if` в класс не следует. Объект-ветвление оправдан, когда выбор является частью предметного процесса, имеет крупные ветви, повторяется, конфигурируется или должен быть виден в архитектуре.

### 2. Таблица — когда веток много и они однородны

Диспетчер по типу события в MUMO выглядит так:

```js
if (obj.type == "frame_update") { ... }
else if (obj.type == "last_frame_update") { ... }
else if (obj.type == "new_job_appear") { ... }
else if (obj.type == "job_queuing_up") { ... }
// ...ещё несколько
```

Это не ветвление, а **реестр, записанный вручную**. Правильная форма — то, что тот же автор сделал для маршрутов (`Pages().with(path, page)`):

```python
HANDLERS = {
    "frame_update":      FrameUpdate(),
    "last_frame_update": LastFrameUpdate(),
    "new_job_appear":    NewJobAppear(),
}
HANDLERS[event.type].run(event)
```

**Правило большого пальца:** третий `else if` подряд по одному и тому же полю — это таблица. Новый тип события должен добавляться строкой в карту, а не правкой диспетчера. Таблица законна, пока принадлежит своему агрегату, а не доступна глобально (Gpt §9, §3).

### 3. Оставить `if` — и это нормально

Не подлежат объективизации: guard-проверки (`if not blogger: return`, `if (!value) throw ...` — локальный инвариант), валидация входа, `?:`-выбор значения, проверки `None`, ранние выходы. Они не выражают выбор *процесса* — они не пускают дальше. Превращать их в объекты значит хоронить смысл приёма.

**Различитель:** спросите, что стоит по обе стороны условия. Если **работы** — объекты или таблица. Если **значение или отказ** — оставьте `if`.

# Часть IV. Декомпозиция

## E28. Как делить незнакомую предметную область: от картины к объектам

E14 отвечает, **что** считать объектом. E18 — **как заходить** в чужой код. Здесь — то, что происходит раньше обоих: **как разрезать большую область на крупные части**, пока никаких объектов ещё не видно.

### Почему аналогия с картиной работает — и где она кончается

Картину делят глазом: небо и земля видны сразу, горизонт нарисован. У домена геометрии нет, и делить приходится не картину, а **рассказ о ней** (E18, шаг «рассказать вслух»).

Но одно аналогия даёт точно, и это важнее остального: **на картине не бывает «слоя контроллеров» и «слоя моделей».** Там небо, земля, битва, лошадь, всадник. Первый рез идёт **по мирам, а не по техническим слоям**. Деление на `handlers / services / models` — это разрез холста по линейке: части получаются ровные, и ни в одной нет смысла.

Второе — **порядок**. Сначала 2–3 огромные части, потом внутри одной сюжет, потом внутри сюжета фигуры. Никто не начинает картину с копыта.

### Правило горизонта

Между двумя частями проходит горизонт, если при переходе через него меняются **минимум два признака из пяти**:

1. **Словарь** — какими существительными говорят по обе стороны (небо: облака, свет, ветер; земля: трава, дорога, всадник).
2. **Темп** — в каком времени живёт часть: миллисекунды, минуты, сутки.
3. **Единица** — что здесь считается «одной штукой»: партия, задача, шаг, сообщение, сделка.
4. **Хозяин истины** — где лежит состояние: в чужой системе, в нашей БД, только в памяти.
5. **Причина изменения** — от чего эта часть меняется: от просьб менеджеров, от чужого API, от роста нагрузки.

Один признак — это деталь внутри части. Два и больше — горизонт. Все пять сразу — это **чужой мир**: ему нужен адаптер (E9), а не место в нашем дереве.

**Проверка горизонта — рассказать одну часть, ни разу не заглянув внутрь соседней.** Получилось — линия проведена верно. Пришлось сказать «а там у них внутри…» — линия не там.

### Пять горизонтов, которые есть почти в любой системе

Готовый список, с которым можно заходить в незнакомый домен. Обычно первый рез дают два-три из пяти.

1. **Снаружи / внутри.** Всё, что говорит на чужом языке — HTTP, Telegram, Kafka, БД, ИИ, платёжный шлюз — отделяется адаптерами. Этот горизонт есть всегда и режется первым: он самый дешёвый и самый бесспорный. Признак — слова, которые придумали не мы.
2. **Ядро / спутники.** Тест выключения: что выключишь — и система перестанет быть собой (ядро), а что выключишь — и она обеднеет, но выживет (спутники). Ядро режут последним и осторожнее всех; спутники можно перекраивать смело.
3. **Кто задаёт темп / кто работает.** Источник событий и расписание — отдельно от исполнения. Разный темп почти всегда означает разные части, разные бюджеты (E21) и, буквально, разные пулы соединений.
4. **Дефицит / работа.** Если чего-то мало — браузеров, слотов ИИ, живых сессий, одного менеджера на карточку — раздача дефицита всегда становится самостоятельной частью, и она доменно-нейтральна (E22).
5. **Каркас / домен.** Что переживёт смену предметной области, а что умрёт вместе с ней. Находится мысленным примером «та же система на другой платформе» (E20).

И то, что **не является частью**: журнал, метрики, зеркало, доска, дайджест. Это **читатели** дерева, а не его ветки (E4, E26). Если при разрезании системы у вас получилась часть «Логирование» — разрезано не то.

### Признак самостоятельной части: потребители разного рода

Самый надёжный сигнал на верхнем уровне. Пока у узла один потребитель, он может спокойно оставаться шагом внутри него. Как только появляется **второй потребитель другого рода** — узел обязан выйти наружу, иначе второй начнёт лезть во внутренности первого.

В `me_preview` пул ресурсов используют трое равноправных: батч-пайплайн, админские разовые операции и интерактивные сессии. Останься пул «внутри» главного сценария — двое других полезли бы через голову. В telebot так же устроена БД (Vanna, воркеры, диагностика) и так же просится отправка сообщений.

Обратная сторона: **часть, у которой нет ни одного потребителя,** — не часть, а мечта (§9).

### Процедура

**Ш0. Одно предложение про всю картину.** «Что здесь вообще происходит» — одним предложением, без «и». Не получается без «и» — картин две, берите одну.

**Ш1. Горизонт: 2–3 части, максимум пять.** Каждой — имя в два слова и одно предложение. Проверка рассказом. Если получилось семь частей — это не горизонт, а перечень модулей: вы назвали то, что уже видите в папках.

**Ш2. Внутри части — сюжеты («битвы»).** Сюжет — это то, у чего есть зачинщик, единица работы, исход, которого кто-то ждёт, и способность провалиться целиком. Сюжет становится территорией с одной дверью (§10). Проверка: **у сюжета можно назвать конец.** «Переписка с блогером» — не сюжет (она не кончается), «согласовать ответ» — сюжет.

**Ш3. Лестница единиц.** Внутри сюжета каждое «для каждого» — новый этаж: партия → задача → шаг; рассылка → сообщение → попытка доставки. Этаж — это пара «повторитель + экземпляр» (E15); имена во множественном и единственном числе (в `me_preview` — `Multi…` и `One…`). Спускаемся, пока у единицы есть судьба (E16).

**Ш4. Род каждого узла.** Ровно один из восьми: работа, сущность, данные (E12), правило (E5), обёртка (E4), адаптер (E9), чистое действие (E25), повторитель (E15). Узел, которому не находится род, — это обычно ещё не найденная работа с именем на `…Service`.

**Ш5. Объекты по семи сигналам (E14).** Лошадь и всадник. Здесь же — говорящие методы вместо чтения чужих полей (§4).

**Ш6. Записать всё дерево одним выражением** (E2, E11). На этом шаге обычно и выясняется, что одна часть никому не нужна, а две другие держат друг друга за руки.

**Ш7. Проверки и остановка** — ниже.

### Проверки после реза: шесть, и все механические

| Проверка | Как выполняется | О чём говорит провал |
|---|---|---|
| Рассказа | рассказать часть, не заглядывая в соседнюю | линия проведена не там |
| Одного экрана | точка сборки читается вслух как описание системы (E18) | резали, но не собрали |
| Словаря | грепнуть по «нейтральной» части слова домена (`telegram`, `blogger`, `hiker`) | домен протёк в механику (E20) |
| Переносимости | мысленно перенести на другую платформу | меняется то, что не должно, — граница выбрана плохо |
| Выключения | мысленно выключить часть | «всё встало» — это ядро; «ничего» — это мечта |
| Замены | что здесь заменят первым | есть ответ — там контракт; нет — контракт не нужен (§9) |

### Шесть признаков плохого реза

- части ссылаются друг на друга в обе стороны;
- одна часть знает имена внутренностей другой;
- типичное изменение требований правит сразу все части (резали не по причине изменения);
- часть невозможно рассказать, не рассказав соседнюю;
- часть ничего не решает, только пересылает (прокладка — запрет из E14);
- часть зависит от всех остальных: это не часть, а сквозная способность — ей место в обёртке (E4) или в потоке вех (E26).

### Границу записывают через незнание

Когда рез сделан, его надо зафиксировать. Самая полезная форма — не «что модуль делает», а **чего он не знает**. В `me_preview` это выписано списком:

- распределитель задач не знает, кто исполнит задачу;
- аллокатор ресурсов не знает, что ресурс — браузер;
- рабочий процесс не знает про очередь и пул;
- потребитель после получения ресурса не знает о существовании пула.

В telebot то же самое звучало бы так: `DealDesk` не знает про Telegram; `OutboundDeliveryQueue` не знает, почему сообщение отправляют; `webhook_intake` не знает, что такое блогер.

Такой список — исполняемая спецификация: каждую строку можно проверить грепом, и он ловит регресс раньше, чем тот станет архитектурной проблемой.

### Правило остановки

Останавливаемся, когда каждая часть отвечает одним словосочетанием на вопрос «что у тебя на выходе» (E1), ниже нет единиц со своей судьбой (E14, E16), и появился один экран (E18). Дробить дальше — обряд, а не архитектура (§9).

### Пример: область telebot, проведённая по процедуре

**Ш0.** «Ванна ведёт от лица живого аккаунта переписку с блогерами, согласует каждый шаг с менеджером и доводит договорённость до вышедшей рекламы.»

**Ш1. Горизонт — три мира.**

- **Чужой мир:** Telegram (два бота плюс Business), Instagram/HikerAPI, ИИ, Google Sheets, Cloud SQL. Другой словарь, чужая причина изменения, чужой темп — меняются все пять признаков. Отсюда адаптеры: `webhook_intake`, `outbound_transport`, `ig/`, `sheets`.
- **Ядро:** контур «входящее → черновик → согласование менеджером → отправка». Тест выключения: выключи его — продукта нет. В telebot это уже названо и защищено (`docs/CORE_DIALOG_RELIABILITY.md`).
- **Спутники:** поиск блогеров, напоминания и дайджесты, артефакты воронки, доска, зеркала, диагностика. Каждый можно выключить — контур выживет.

**Ш1′. Второй рез — по темпу**, и он проходит одинаково через ядро и спутники: горячий путь вебхука (секунды) | фоновые тики (часы) | жизнь сделки (дни). Это тот же горизонт, который объясняет `QueuePool timed out`: две части с принципиально разным темпом делят один пул соединений (`docs/tz/TZ_2026-07-30_CONNECTION_POOL_CONTENTION.md`). Горизонт был, а рез не сделан — вот и результат.

**Ш1″. Дефицит.** Живой peer у бизнес-бота (протухает от тишины), слоты ИИ, соединения к БД, один менеджер на карточку. Раздача дефицита — самостоятельная часть; в telebot она наполовину есть (`outbound_queue` с захватами), наполовину растворена по вызывающим.

**Ш2. Сюжеты ядра:** «принять входящее», «собрать черновик», «согласовать с менеджером», «доставить», «переехать по воронке». У каждого есть конец и исход. Один уже оформлен территорией с дверью — `vanna/deal/` (`DealDesk`).

**Ш3. Лестница единиц:** блогер → сделка (интеграция) → диалог → сообщение → попытка доставки. Каждый этаж просит своего повторителя.

**Ш4–Ш5.** Дальше работают E12 и E14: сделка — сущность (идентичность, статусы, вехи); `TransferNoticeComposer` — работа; «тихие часы» — правило; кап напоминаний — обёртка; `WatchdogAlert` — данные.

**Что этот проход показывает сразу, без единой строки кода:** в telebot **сильные спутники и недоописанное ядро**. Сделка и исходящее сообщение — центральные предметы всей области — существуют как строки в БД, а не как объекты с жизненным циклом (E12). Отсюда и то, что статус меняют в десятке мест, и то, что рядом с каждой сменой приходится вручную не забывать журнал, доску и уведомление. Порядок работ следует из декомпозиции, а не из списка жалоб.

## Как заходить в новую область и в чужой код (E18 · Gpt §25 · Gpt §26)

Самое главное. Ниже — процедура, а не вдохновение: её можно выполнить на чужом коде за час и получить предложение по рефакторингу. Для новой предметной области она начинается не с классов и таблиц, а с короткого рассказа о системе на естественном языке.

### Шаг 1. Рассказать систему вслух за 5–9 предложений

Не открывая код (или закрыв его), расскажите, что система делает — как рассказали бы коллеге. Ограничение в 5–9 предложений принципиально: столько узлов помещается на один экран и в одну голову. Если рассказ не укладывается в 9 предложений — вы рассказываете не одну систему, а несколько. Возьмите один сценарий.

Сначала — **глаголы**: каждый значимый глагол — кандидат в объект-процесс (E12).

> принимает задачу → распознаёт агента → резервирует ресурс → запускает работу → отслеживает состояние → публикует результат → освобождает ресурс.

Кандидаты: `AcceptTask`, `RecognizeAgent`, `ReserveResource`, `RunJob`, `TrackJob`, `PublishResult`, `ReleaseResource`.

Потом — **слова масштаба**, они выявляют внутренние узлы дерева:

- «сначала… потом…», «после A выполнить B» → конвейер, ступени абстракции (E1) или последовательность (Gpt §24, §11.1);
- «для каждого…» → повторитель + экземпляр итерации (E15, E16);
- «если… иначе…» → ветка-объект с двумя стратегиями или таблица (E17);
- «пока» → долгоживущий цикл и объект одной попытки;
- «одновременно» → агрегат параллельного запуска;
- «не более N», «но не чаще чем» → объект лимита, обёртка над рабочим узлом (E4);
- «повторить при ошибке» → retry-политика;
- «подождать не дольше» → timeout;
- «и записываем в журнал» → обёртка или поток вех, а не часть (E4, E26);
- «ждём/берём/освобождаем» → аренда ресурса (E6, E22);
- «решаем, кому/стоит ли» → политика (E5).

### Шаг 2. Разделить времена жизни, повторение, решения и границы ошибки

**Времена жизни.** Для каждого кандидата спросить: создаётся один раз на приложение? один раз на подключение? один раз на задачу? один раз на попытку? один раз на элемент коллекции? Объекты с разными временами жизни почти всегда нужно разделить. Особенно опасен долгоживущий объект, хранящий поля одной короткой операции.

**Владелец повторения и владелец состояния.** Если действие повторяется, отделить: кто решает **когда и сколько раз** запускать, и кто знает **как выполнить один раз**. Первый становится `Jobs`, `WorkerLoop`, `ForEachClient`, `Retry`. Второй — `Job`, `ProcessOneClient`, `Attempt`.

**Точки решений.** Каждое существенное бизнес-условие назвать вопросом:

```js
agentRecognition.isKnown()
resourcePool.hasAvailable()
task.shouldRetry()
```

Если у ответа крупные последствия, превратить решение в узел выбора с переданными ветками (E17).

**Границы ошибки и наблюдаемости.** Если шаг должен иметь отдельные статус, ошибку, retry, timeout или строку в UI, он уже проявляет самостоятельность и обычно заслуживает собственного объекта (E14, E23).

### Шаг 3. Собрать сначала оглавление

До реализации записать желаемую композицию:

```js
new ProcessIncomingTask(
  new RecognizeAgent(),
  new IfAgentRecognized(
    new WithReservedResource(
      new RunJob()
    ),
    new RejectUnknownAgent()
  ),
  new PublishResult()
)
```

Если эта запись не читается как рассказ о системе, границы или имена выбраны неудачно. Реализации пишутся после того, как стало понятным оглавление.

### Шаг 4. Найти маркеры в существующем коде

Читаем не логику, а форму. Каждый маркер почти однозначно указывает на пропущенный объект:

| Что видно в коде | Что это на самом деле | Первый шаг |
|---|---|---|
| Функция длиннее экрана с секциями-комментариями `# 1. … # 2. …`, `// load`, `// validate`, `// process`, `// save` | автор уже назвал объекты, но не выделил | каждый комментарий → действие с этим именем и единым входом `run()` |
| Локальная переменная живёт через 3+ шага и передаётся дальше | поле будущего объекта | границы объекта = где переменная рождается и умирает |
| Внутри цикла много локальных переменных | состояние одной итерации | тело цикла — короткоживущий объект, цикл — долгоживущий повторитель (E15, E16) |
| У функции 4+ параметра, и тот же набор — у соседних функций | набор = конструктор, функции = методы | собрать их в один класс |
| Третий `else if` по одному полю | реестр, записанный руками | таблица (E17) |
| Крупные ветки `if/else` имеют разные зависимости | две стратегии | условие — именованное решение, ветки — переданные объекты (E17) |
| Тело цикла > 5 строк или с `try`/`await` | работа на итерацию | объект итерации (E16) |
| Булев флаг, читаемый в 2+ местах (`busy`, `started`, `is_test_mode`) | состояние или подменяемый узел | state machine (§5) либо замена узла (E3, Gpt §13) |
| Имя `Manager`, `Helper`, `Utils`, `Service`, `process_data()` | работа не названа | сначала найти имя, потом резать (E13) |
| Комментарий, объясняющий условие | не хватает говорящего метода | метод-вопрос (§4) или политика (E5) |
| Несколько модулей проверяют одинаковое условие | у условия нет владельца | говорящий метод у владельца либо объект политики/решения (§4, E5) |
| Общий префикс у группы функций (`mumo_*`, `boyscout_*`) | территория просится наружу | пакет с корнем (§10) |
| Повторяющийся `try/finally`, `try/catch`, timeout, retry, счётчик или лимит вокруг действий | сквозная способность | обёртка или комбинатор: `Retry`, `Timeout`, `ObservedStep`, `WithResource` (E4, Gpt §24) либо аренда (E6) |
| Большой класс смешивает поля разных времён жизни | конфигурация приложения, состояние подключения, задачи и попытки в одном месте | разнести по разным объектам |
| Метод создаёт много инфраструктурных объектов | в нём спрятан CompositionRoot или фабрика | создание — к владельцу времени жизни, исполнителю — готовая зависимость (§3) |
| Для понимания шага нужно читать соседние модули | контракт шага неполон, есть скрытые связи | сделать явными вход, зависимости, результат и события |
| Тест на кусок чистой логики невозможно написать без БД/сети | граница объекта проходит ровно здесь | вынести логику, инфраструктуру — в аргумент |

### Шаг 5. Резать сверху вниз, а не снизу вверх

Порядок операций, при котором риск мал, а выигрыш заметен сразу:

1. **Сначала имена, потом резы.** Расставить комментарии-названия шагов в существующем коде. Это бесплатно, обратимо и уже поднимает читаемость.
2. **Выделить корень и 3–7 крупных шагов** — и остановиться. Кратный рост наглядности даёт именно верхний уровень; глубина его почти не добавляет.
3. **Переносить, а не переписывать.** Каждый шаг сначала становится объектом с прежним телом. Логика не меняется — иначе непонятно, что сломалось.
4. **Поднять зависимости в конструктор** и собрать точку сборки (E2). Обычно здесь и обнаруживается лишнее: узел, в который никто не смотрит, или связь, которой не должно быть.
5. **Углубляться только там, где болит** — где часто правят, часто ломается или никто не понимает (§9, E14.1).

### Шаг 6. Проверить результат

> Рефакторинг удался, если появился **один экран, на котором видно всю систему**, и его можно прочитать вслух как описание того, что она делает.

Цель первого рефакторинга — не получить много классов. Цель — добиться, чтобы верхний уровень превратился в короткое **оглавление процесса**, а детали оказались в независимо читаемых и заменяемых узлах. Количество классов ничего не доказывает. Если после рефакторинга такого экрана нет — работа не сделана, сколько бы объектов ни появилось. Если он есть — дальше можно не резать. И этот экран не должен врать про владение, поток управления и порядок жизни (Gpt §17).

Для каждого объекта задать вопросы независимости:

- можно ли объяснить его цель одной фразой?
- можно ли протестировать его отдельно?
- можно ли заменить его, не меняя родителя?
- понятны ли вход, результат и ошибки?
- не знает ли он о братьях или обо всём приложении?
- не хранит ли состояние с другим временем жизни?

Отрицательные ответы указывают место следующего разреза.

### Правило остановки

Режем, пока каждый узел не отвечает одним словосочетанием на вопрос «что у тебя на выходе» (E1) — и не глубже узлов **без собственной судьбы** (E14, E16). Первый признак перебора: объекты, у которых `run()` состоит из одной строки-делегирования и которым нечего рассказать о себе.

### Три вопроса при заходе в чужую систему

Если времени совсем мало, хватит трёх:

1. **Где здесь один экран, объясняющий систему?** Нет такого — вот первая и главная задача.
2. **Что здесь происходит на каждую единицу работы?** Ответ даёт пару «повторитель + экземпляр» (E15) и обычно сразу половину дерева.
3. **Что здесь придётся заменить первым?** (другой источник, другой канал, другой режим) — туда контракт и границу; остальное трогать не надо.

## Gpt §27. Фрактальность: процесс снаружи, композиция внутри

На любом масштабе узел выглядит одинаково:

- снаружи имеет имя, контракт и `run()`;
- внутри может оказаться целым деревом меньших процессов.

`ProcessClient` является одним шагом для `ProcessAllClients`, но сам состоит из `Authorize`, `Navigate`, `Capture`, `Save`. Благодаря этому архитектуру можно читать с выбранной глубиной:

> Приложение → территория → сценарий → шаг → операция.

На каждом масштабе повторяется не только форма узла, но и отношения старшинства — §11.2.

Правило остановки декомпозиции:

> Разрезать нужно до тех пор, пока каждый видимый узел не станет понятен как одна роль, но не дальше, чем появляется практическая независимость.

Если выделенный фрагмент нельзя отдельно назвать, заменить, проверить, наблюдать или наделить собственным временем жизни, возможно, это всего лишь внутренняя функция, а не объект.

# Чек-лист ревью

**Дерево, каркас, контракты (§0–§2)**

- [ ] Нет плоской простыни: процесс разбит на классы-шаги с одной ответственностью?
- [ ] Дерево однонаправленное: родитель управляет детьми, дети не знают о дереве целиком и не ходят к «братьям»?
- [ ] Дети сообщают факты, решение и инвариант — у агрегатора; поверхностью владеет родитель (`attach/detach`) (E8)?
- [ ] В каркасных модулях нет доменных слов (здесь — `lesson`, `expert`, `vimeo`, `tinkoff`) — проверено грепом, а не на глаз; мысленный перенос на другую платформу не требует менять каркас (E20)?
- [ ] У каждого контракта есть мок, и голый каркас с моками запускается без единой внешней системы (E20)?
- [ ] Транспорт — тонкий адаптер: единый конверт, ноль `try/catch` в ручках, снимок состояния в каждом ответе (E9)?
- [ ] Модули общаются через контракты, а не через конкретные классы соседей?
- [ ] Ни одного наследования наших классов друг от друга — только композиция и агрегация; общее у семейства выражено `Protocol`/`interface` и/или классом-агрегатором? (Обвязка фреймворка — `PartialType`, `HttpException`, `BaseEntity`, DTO от Entity — не считается.)
- [ ] Вариант поведения заменяется объектом с говорящим именем, а не глобальным флагом или `{stub:true}` (Gpt §13)?

**Точка сборки и композиция (§3, часть II)**

- [ ] Композиция читается в точке сборки (в Nest — `providers` модуля); зависимости — через конструктор?
- [ ] CompositionRoot читается как предложение из слов предметной области (Gpt §1)?
- [ ] По одной точке сборки можно восстановить крупную схему системы (Gpt §2)?
- [ ] У каждой вложенности понятен вид связи: часть, шаг конвейера, участник, прототип, обёртка или политика (Gpt §3–§4)?
- [ ] Каждый узел цепочки поднимает данные ровно на одну ступень, и его имя называет выход, а не действие (E1)?
- [ ] Глубокие поддеревья вынесены под смысловые имена (Gpt §14)?
- [ ] Числа, меняющие поведение (таймауты, лимиты, пороги), видны в точке сборки, а не спрятаны внутри узла (E3)?
- [ ] В точке сборки нет ничего, кроме сборки; служебное — в одном названном методе (E11)?
- [ ] Однотипные возможности подключаются реестром без правки агрегатора, и реестр принадлежит своему агрегату (Gpt §9)?
- [ ] Ребёнок не получает целого родителя; сквозные службы — обёртка или события, а не мешок возможностей в `init` (Gpt §15)?
- [ ] Нет значимых связей через глобальное или скрытое mutable-состояние (Gpt §16)?
- [ ] Видимый граф честно отражает владение, lifecycle и поток управления (Gpt §17)?
- [ ] Квота/ретрай/кэш/кап — обёртка над рабочим узлом; сняв обёртку, рабочий узел остаётся работоспособным (E4)?
- [ ] Retry, timeout, limit и parallel не размазаны, а оформлены комбинаторами (Gpt §24)?

**Говорящие методы и решения (§4)**

- [ ] Условия читаются как вопросы к объекту (`isFree()`, `isActive()`), без арифметики над чужими полями?
- [ ] Нетривиальное правило вынесено в объект-понятие с именем-существительным, а не в `if` внутри сервиса (E5)?
- [ ] Решение отделено от применения: план строится без побочных эффектов, его можно посчитать и не применить (E25)?

**Жизненный цикл (§5)**

- [ ] Соблюдён lifecycle: constructor(deps) → init(config) → run() → stop(); на задачу — `instance()`?
- [ ] Конструктор говорит «из чего», `init/run` — «где и с кем»; сиблингов знакомит родитель (E2)?
- [ ] Стабильная топология отделена от свежего состояния отдельной задачи (Gpt §5)?
- [ ] `run()` отделён от фактической готовности принимать работу (Gpt §6)?
- [ ] Команды идут вниз, а `ready/result/fail` — вверх по явным контрактам (Gpt §7)?
- [ ] Остановка зеркальна запуску: обратный порядок, свой `catch` на каждый `stop`, корректность из любого состояния (E10)?
- [ ] Состояния — явная state machine, а не набор булевых флагов?

**Ресурсы, время, ошибки (§6)**

- [ ] Ресурсы освобождаются в `finally`, `release()` идемпотентен, таймауты образуют иерархию?
- [ ] Дефицитный ресурс не выдаётся наружу: внутрь передаётся действие, освобождение гарантирует владелец (E6)?
- [ ] Ожидание овеществлено: билет можно отменить и о нём можно спросить; наружу выдан handle с идемпотентным возвратом, а не сам ресурс (E22)?
- [ ] Бюджет ребёнка строго меньше остатка родителя, вниз передаётся дедлайн, а не длительность; худшее время ответа видно из точки сборки (E21)?
- [ ] Названа граница, на которой исключение становится результатом; повтор — отдельный проход по неудачам; итог считается по последнему состоянию каждой единицы (E23)?

**Наблюдаемость (§7)**

- [ ] Каждый значимый шаг наблюдаем: start / update / complete / fail со смысловым payload (в iron-back — в логах со смысловым контекстом)?
- [ ] События внешней системы переведены в доменные; «готово» отдаётся ровно один раз (E7)?
- [ ] Сигнал («пересчитай») и команда («сделай») не перепутаны: у действия один маршрут, реакция на сигнал переживает потерю и дубль (E24)?
- [ ] Узел эмитит вехи со ссылкой на смыслового родителя, подписчики подключены снаружи в точке сборки, витрина строится проекцией, а механизм наблюдаемости один (E26)?
- [ ] В снимок попадает только то, что нельзя пересчитать и чего нет в БД; снимок производный, истина — в БД (E19)?
- [ ] У снимка есть версия схемы, ключ узла — путь, а не позиция, и назван режим («несогласованный, для отладки» ≠ «согласованный, для восстановления») (E19)?
- [ ] Откат в доменной логике сделан компенсирующим переходом вперёд; история не переписывается (E19)?
- [ ] У внешних эффектов есть ключ идемпотентности, и восстановление проверяет его перед повтором (E19)?

**Абстракции и их цена (§8–§9)**

- [ ] Имена классов отражают роль в процессе, а не технологию; ошибки — именованные классы с контекстом?
- [ ] Новый слой отвечает на вопрос «что заменяем, не трогая остальное»?
- [ ] У архитектурного решения записаны цена, риск, выигрыш — а у отказа ещё и условие возврата; совместимые псевдонимы имеют срок снятия (E27)?

**Территория и согласованность (§10)**

- [ ] У подсистемы есть корень-дверь: контроллер знает одно имя, а не список её внутренностей (§10.1)?
- [ ] Корень оправдан сценариями, а не группировкой (§10.2)?
- [ ] Схему объявляет территория, а порядок миграций остаётся в общей ленте (§10.5)?
- [ ] У инварианта есть хозяин — объект, владеющий **обеими** его сторонами; если сторон две и хозяина нет, инвариант бездомный (E29)?
- [ ] Согласованность держится вопросом к хозяину состояния в момент записи, а не уведомлением о переходе: «добавим ещё одно событие» — признак, что лечат не то (E29)?
- [ ] Запись, способная создать невозможное состояние, идёт через дверь территории, а не мимо неё — и число таких точек записи посчитано (E29)?
- [ ] Сторож чинит производное, а не истину; пишет не сам, подписывает свою работу и в здоровой системе не находит ничего (E30)?
- [ ] Каждая находка сторожа оформлена как заявка на недостающую дверь, а не как штатная работа (E30)?

**Живая иерархия (§11)**

- [ ] У объекта назван повод рождения и условие смерти; объектов без смерти (зомби) нет (§11.1)?
- [ ] Повторяющееся событие рождает экземпляр, а не будит подписчика: `watch` в домене нет; события живут только на границе с чужим миром, в вехах пути и в состоянии ребёнка, которое слышит его родитель (§11.1)?
- [ ] Связь «после A — B» — отдельный объект-родитель с именем целого: A не зовёт B, B не подписан на A, и двери не переписывают пару руками (§11.1)?
- [ ] Условие смерти объявлено у самого объекта, а не разнесено по тем, кто его убивает (§11.1)?
- [ ] Назван уровень масштаба, на котором объект главный; на один вопрос в пределах уровня отвечает один хозяин, и ответ — вердикт с причиной (§11.2)?
- [ ] Власть объекта кончается границей его поддерева; вопрос задают своему уровню или родителю, а не через голову (§11.2)?
- [ ] Оглавление уровня объявляет не только состав, но и отношения, и замок сверяет его с кодом (§11.2)?
- [ ] Декомпозиция меняется дроблением, переносом и слиянием без правки контракта родителя; после переноса имя следует за ответственностью (§11.3)?
- [ ] Замок стоит на объединении — на пути родителя целиком, а не только на блоках (§11.3)?
- [ ] Блоки пересекаются только временно (рубильник и срок годности) или как линзы; владение не пересекается (§11.3)?
- [ ] Разбиение заменяется рядом, а не на месте: шов и оболочка → новое на тот же контракт → рубильник → снос со сроком, и один контрактный замок проходит на обоих (§11.4)?
- [ ] При перекройке нескольких разбиений названы общие швы, и единица замены переключается целиком; меняется шов — сосед входит в сегмент (§11.4)?
- [ ] У разбиения есть паспорт в докстринге рядом с кодом: смысл, дверь, владение, отношения, где смотреть при поломке, замки (§11.5)?
- [ ] Заявленная ступень автономии не выше той, что подтверждают счётчики карты, и изменение не подняло ни одного счётчика протечек (§11.5)?

**Объект (часть III)**

- [ ] Род объекта выбран осознанно: процесс (работа), сущность (идентичность + жизненный цикл + память о себе) или данные (снимок без поведения) (E12)?
- [ ] Процесс получает сущность аргументом и вызывает её сценарии, а не правит её поля; сущность не знает о процессах (E12)?
- [ ] У сущности с богатым циклом переходы именованы, вехи транслируются наружу, драйвер БД инъектирован (E12)?
- [ ] Имя объекта обозначает одну роль или исполняемое намерение, а `run()` читается как «исполни предназначение этого объекта»; несколько методов — грани одной роли (одно состояние, одна причина изменения) (Gpt §20, E13)?
- [ ] Для каждого нового класса есть ответ, какой из семи сигналов его оправдывает — и это не «на будущее» и не обёртка вокруг простой функции (Gpt §19, E14)?
- [ ] Пара «повторитель (мн. ч.) + экземпляр итерации (ед. ч.)» выделена, долгоживущий повторитель создаёт свежий объект на задачу/попытку/итерацию, и в нём нет полей одной итерации (Gpt §21, E15)?
- [ ] У каждого цикла проверено, не является ли итерация отдельным процессом: тела с судьбой (ошибка, ресурс, ожидание, отчёт) стали объектами, простой перебор данных остался циклом (Gpt §22, E16)?
- [ ] Существенные ветвления процесса выражены именованным решением и заменяемыми ветками или таблицей; guard-проверки остались обычными `if` (Gpt §23, E17)?
- [ ] Объекты с разными временами жизни разделены (Gpt §25)?

**Декомпозиция (часть IV)**

- [ ] Декомпозиция начиналась с рассказа о процессе, глаголов, повторений, решений и времён жизни (E18, Gpt §25)?

- [ ] Первый рез сделан по мирам, а не по техническим слоям (`handlers/services/models` — это не декомпозиция) (E28)?
- [ ] На верхнем уровне 2–3 части (максимум пять), и каждую можно рассказать, не заглядывая внутрь соседней (E28)?
- [ ] Через каждую границу меняются минимум два признака из пяти: словарь, темп, единица работы, хозяин истины, причина изменения (E28)?
- [ ] Пройдены пять типовых горизонтов: снаружи/внутри, ядро/спутники, темп, дефицит, каркас/домен (E28)?
- [ ] Журнал, метрики, зеркало и доска оформлены как читатели дерева, а не как его части (E28)?
- [ ] У каждой выделенной части есть хотя бы один потребитель, а часть с потребителями разного рода вынесена наружу (E28)?
- [ ] У каждого сюжета можно назвать конец, а у каждого этажа лестницы — свою единицу работы (E28)?

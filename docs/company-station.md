# Станция — каркас большой системы компании

Живой документ: описание крупной системы управления компанией как **станции** — каркаса, к которому стыкуются модули, через который входят данные и выходят действия. Цель — понять, что закладывается в каркас сразу, чтобы потом безболезненно расширяться в ширину, держа всё под контролем и не теряя сопровождаемости. Пишется крупными мазками и дополняется со временем; журнал правок — в конце.

Опоры: канон [oop-principles.md](oop-principles.md) (П2, П3, П6, П25, П27, П30, П33, П39, П40), метод [app-tables-of-contents.md](app-tables-of-contents.md) (паттерны О5, О8, О10, О15, О16, О18–О21). Первый носитель — пример 6 тетради оглавлений, «умный AI-дашборд управления» по вакансии.

## 1. Метафора и место станции

| Часть станции | Что это в системе |
|---|---|
| каркас и жизнеобеспечение | ядро: общий язык, склад фактов, доступ, журнал петли, протокол исполнения, зеркало |
| стыковочные узлы | порты — стандартные контракты: источник, основание, детектор, советник, сценарий, замер, вид |
| отсеки | пакеты предметных областей: торговля, производство, склад, финансы, персонал — расширение **в ширину** |
| приборы | способности над любым отсеком: детекторы, советники, замеры, виды — расширение **в глубину** |
| грузы | на входе — факты, планы и нормы; на выходе — действия во внешних системах и уведомления |

**Что станция делает** — одним предложением: *замыкает петлю «факт → отклонение → решение → эффект» над любыми процессами компании.* Это контур управления: видеть, сравнивать, решать, действовать, мерить результат. В терминах цикла Деминга PDCA (основа ISO 9001) станция владеет половиной цикла — **Check** (прибор и детекторы) и **Act** (решения и сценарии); **Plan** приходит из слоя норм, **Do** происходит в исполнительных системах.

**Чем станция не является.** Она не исполнительная система: не ведёт учёт вместо 1С, сделки вместо CRM, рецептуры и смены вместо MES. Мир компании — три слоя (расшифровки — раздел 11):

| Слой | Вопрос | Кто живёт | Для станции |
|---|---|---|---|
| исполнение | что делаем и что сделали | CRM (Б24), ERP (1С), MES, WMS, EAM/ТОиР, маркетплейсы, банк | источники фактов и цели действий |
| знание и нормы | как должно быть | бюджеты и планы, техкарты, рецептуры (ISA-88), спецификации (PLM), регламенты | источники оснований для сравнения |
| управление | как идём и что поправить | **станция** | своё |

В производственной лестнице ISA-95 (международно — IEC 62264) уровни 0–2 — датчики и управление процессом (АСУ ТП, SCADA), 3 — управление производственными операциями (MES), 4 — планирование и логистика предприятия (ERP). Станция стоит рядом с уровнем 4 и читает уровни 3–4 на зерне «смена, партия, документ», а не потоки датчиков. Станция не превращается в SCADA.

## 2. Оглавление станции

```js
const world = new World({                                       // окружение: станции не принадлежит
  execution: [bitrix24, onec, mes, wms, wb, ozon, bank],        // делают и записывают
  knowledge: [budgets, techCards, regulations],                 // как должно быть
  llm: provider, channels: [telegram, mail], people: orgChart,
})

new Station(

  new Core(                                                     // жизнеобеспечение: закладывается сразу
    new Language(                                               // общий язык — один на станцию
      new Dimensions(new KeyMap(), { history: 'scd2' }),        // ресурсы · участники · место · время; ключи между системами
      new MetricCatalog({ versions: true }),                    // что меряем: формула, зерно, единица, направление пользы, хозяин истины, владелец
      new Bases(new Plans(), new Norms()),                      // с чем сравниваем: план, норма, порог
    ),
    new Facts(new Raw(), new Conformed(), new Measures(),       // сырьё как есть → сопоставленное → факты по зерну
      { freshness: true }),
    new BusinessState(),                                        // главный прибор: дерево метрик со значениями и базами (раздел 4)
    new Access(new OrgTree(), new Powers()),                    // охват × полномочия — на двери фактов (О20)
    new Loop(new Signals(), new Decisions()),                   // журнал: что заметили, что решили, что вышло (О15, О19)
    new Execution(new Approvals(), new Lanes(), new Outbox(), new Undo()),  // как действие выходит в мир (О16, П35, П39)
    new Mirror(new ProcessTree(), new Freshness()),             // что произошло и насколько верим цифрам (П25, О10)
    new Docks(new ModuleRegistry(), PORTS),                     // стыковка: паспорта модулей и проверка (раздел 7)
  ),

  new Bays(world, [                                             // отсеки — в ширину
    new TradeBay(),                                             // обмен на границе: продажи, закупки, каналы
    new ProductionBay(),                                        // превращение внутри: выпуск, расход, качество
    new WarehouseBay(), new FinanceBay(), new PeopleBay(),
  ]),

  new Instruments({                                             // приборы — в глубину, над любым отсеком
    detectors:  { planGap, reconcile, brokenPairs, forecast, growth },   // состояние → сигналы
    advisors:   { drivers, narrator: llm, options: llm },                // сигнал → причина, варианты (О18)
    meters:     { beforeAfter },                                         // решение → эффект (О19)
    views:      { cabinets, meetings, ask: llm },                        // читатели (О21)
  }),
)
```

Ядро не знает ни одного отсека по имени и не содержит модели: тест выключения (П30) — без LLM станция находит, решает и меряет, только без рассказов и подсказок; без ядра модель рассуждает поверх хаоса.

## 3. Почему каркас не торговый

Вакансия-носитель и первые примеры — с уклоном в торговлю: источники там — системы продаж, примеры — маржа, остатки, сделки. Но торговля — не супер-система, а отсек. Довод — модель REA (раздел 5.1): у экономического события две формы.

- **Обмен** — отдал одно, получил другое: товар ушёл ↔ деньги пришли. Это торговля, закупка, найм.
- **Превращение** — потратил одно, создал другое: сырьё и часы станка ушли ↔ изделие появилось. Это производство, оказание услуги.

Обмен есть у любой организации, потому что у любой есть граница с внешним миром: она покупает и продаёт. Отсюда ощущение, что торговля пронизывает всё. Превращение — внутренность, и оно у каждой ниши своё. Супер-система — не торговая, а экономическая: цепочка обменов и превращений. Каркас станции не различает их — различают отсеки.

Проверка — те же механизмы работают в производстве без правки ядра (как устроен сигнал — раздел 4.6):

| Сигнал | Сравнение | Торговля | Производство |
|---|---|---|---|
| отклонение | факт ↔ план | выручка отдела ниже плана | выпуск смены ниже плана |
| несоответствие | источник ↔ источник, половина пары ↔ другая | реализация WB ≠ поступления в 1С | списано сырья ≠ норма × выпуск |
| риск | прогноз ↔ порог | товар кончится раньше поставки | наработка станка подходит к межремонтному ресурсу |
| точка роста | срез ↔ лучший срез | конверсия менеджера ↔ лидера | OEE смены ↔ лучшей смены |

**Технологии, рецептуры, схемы** живут в PLM (конструкция, спецификации, техкарты; обмен данными об изделии — ISO 10303, STEP) и MES (задания, смены, учёт выпуска). В партионном производстве рецептуры устроены по ISA-88 (IEC 61512): общая → рецептура площадки → мастер-рецептура → управляющая рецептура партии. Станции всё это нужно как **основания**: норма расхода, время цикла, допуск из мастер-рецептуры или техкарты — база, с которой сравнивают факт. «Контроль изготовления» для станции — события превращения против норм. Сами рецептуры станция не хранит.

**«Эффективность отдела» — не контроль над людьми.** Станция меряет процессы и результаты; владелец метрики — тот, кто решает, а не тот, кого наказывают. Закон Гудхарта: мера, ставшая целью наказания, перестаёт мерить. Поэтому оценка отдела — метрики петли (у скольких сигналов есть решение, сколько решений исполнено, какой эффект подтверждён), а не рейтинг сотрудников.

## 4. Главный прибор: «Состояние бизнеса»

### 4.1 Что это

Одна чистая функция: `state(period, scope) → дерево метрик` — у каждого узла значение, базы сравнения рядом (план, норма, прошлый период, тот же период год назад), свежесть источников и владелец. **Прибор показывает, но не судит**: что считать сигналом, решают детекторы (О5). Своего состояния у прибора нет — его можно вынести в отдельный сервис; язык, которым он считает (дерево и формулы), живёт в ядре.

### 4.2 Как его пощупать

Четыре вопроса, на которые прибор отвечает одним экраном:

1. **Что у нас есть?** — запасы на момент: деньги, товар, сырьё, обязательства.
2. **Как быстро движется?** — потоки за период и время процессов.
3. **Здорово ли это?** — каждое число рядом со своей базой.
4. **Можно ли верить?** — свежесть, полнота, несверённые пары. «Нет данных» ≠ ноль (О10).

Экран: вершина дерева — 5–7 чисел; клик — спуск по драйверам до листа, у которого есть владелец. Прибор поверяют, как любой прибор: вершина за закрытый месяц сходится с бухгалтерией с объявленной разницей (выручка по отгрузке ≠ по оплате — это определение, а не ошибка).

### 4.3 Что в нём главное — дерево метрик

Вершина у любой коммерческой компании похожа: **деньги** (остаток и прогноз), **прибыль**, **выполнение обязательств**. Ниже дерево ветвится по отсекам до операционных мер, у которых есть владелец:

```
Валовая прибыль = Σ по каналам (Выручка − Себестоимость − Комиссии − Логистика)    торговля
  Выручка канала = Трафик × Конверсия × Средний чек
Деньги через 30 дней = Остаток + Ожидаемые поступления − Обязательные платежи      финансы
Годный выпуск = Плановое время × OEE ÷ Идеальное время цикла                       производство
  OEE = Доступность × Производительность × Качество
Расход сырья к норме = Списано ÷ (Норма техкарты × Выпуск)
```

Производственные показатели не изобретаются: их определения (OEE и около трёх десятков других) даёт ISO 22400-2 — каталог берёт формулу оттуда и ссылается на неё. Разложение «вершина = произведение драйверов» — старая традиция управленческого учёта (формула DuPont: рентабельность капитала = маржа × оборачиваемость × рычаг).

Дерево — декларация в каталоге метрик, а не код прибора: новый отсек добавляет ветви, прибор не меняется. Разложение причин отклонения — арифметика по этому же дереву; модель только рассказывает (О18).

### 4.4 Что меряем — семь классов

Классы выводятся из REA (раздел 5.1), поэтому одинаковы для торговли и производства:

| Класс | Что меряем | Единица | Род по Кимбаллу | Торговля | Производство |
|---|---|---|---|---|---|
| деньги | остаток, приток, отток | ₽ | остаток — полуаддитивный, потоки — аддитивные | выручка, дебиторка | себестоимость партии |
| запасы | количество и стоимость ресурса на момент | шт, кг, м, ₽ | полуаддитивный | товар на складе и FBO | сырьё, НЗП, готовая продукция |
| обязательства | обещанное будущее | ₽, шт | полуаддитивный снимок | сделки в воронке, заказы | план производства, заказы в работе |
| поток | сколько прошло за период | шт, ₽ за период | аддитивный | продажи, отгрузки | выпуск |
| время процесса | от входа до выхода, ожидания | ч, дни | накопительный снимок | цикл сделки, срок доставки | цикл изготовления, переналадка |
| качество | доля плохого исхода | шт → % | счётчик аддитивный, доля — нет | возвраты, рекламации | брак, пересорт |
| мощность | доступное и использованное | ч → % | часы аддитивны, доля — нет | загрузка менеджеров | OEE, простои |

Связка запаса и потока даёт самые полезные производные: **оборачиваемость** (запас ÷ поток → дни) и **дни до нуля** (остаток ÷ скорость расхода).

### 4.5 Чем меряем — единицы и правило аддитивности

- **Базовые** — то, что хранится: ₽, натуральные (шт, кг, м, м³), часы, число событий.
- **Производные** — то, что считается на лету: доли (маржа %, конверсия, брак %, OEE), скорости (₽/день, шт/ч), оборачиваемость и длительности (дни).
- **Правило:** доля и среднее не хранятся и не суммируются — в каталоге они объявлены формулой над аддитивными. Сумма процентов по отделам — классическая ложь дашборда.

### 4.6 Сигнал — один, с осями

Первая четвёрка — отклонение, несоответствие, риск, точка роста — смешивала оси. Сигнал на самом деле один (паттерн О23): **разрыв** между значением метрики в срезе и базой. Различают его пять осей:

| Ось | Значения | Откуда берётся |
|---|---|---|
| база | план, норма, история, другой источник, вторая половина пары, порог прогноза, лучший срез | что с чем сравниваем |
| время | было (факт) · будет (прогноз) | отклонение или риск |
| сторона | в пользу · во вред · вышли из коридора | направление пользы метрики в каталоге |
| вес | вклад в вершину дерева, ₽ | дерево метрик (4.3) |
| доверие | сверено · есть несоответствие · не проверяли | свежесть и сверка |

Четыре привычных имени — точки в этом пространстве:

- **Отклонение** — факт против плана, нормы или истории, **с любой стороны**: «выше плана» — тоже отклонение. Знак не равен пользе: выпуск выше плана — забитый склад и замороженные деньги; расход сырья ниже нормы — возможно, недовложение и будущий брак. Поэтому у каждой метрики в каталоге объявлено **направление пользы**: больше — лучше, меньше — лучше или **коридор** (остаток, температура, расход к норме — плохо и мало, и много).
- **Риск** — не крайняя форма отклонения, а **отклонение в будущем времени**: прогноз пересекает порог. «Наработка станка подходит к ресурсу» — та же форма: прогноз наработки против нормы ресурса. Насколько это опасно — отдельная ось, **вес**: насколько разрыв сдвинет вершину дерева (деньги, прибыль, обязательства). «Опасно для экономической модели» = большой вклад в вершину или прогноз самой вершины через порог (кассовый разрыв). ISO 31000 определяет риск как влияние неопределённости на цели и прямо оговаривает, что влияние бывает и положительным: угроза и возможность — две стороны одной неопределённости.
- **Точка роста** — не антоним отклонения. «Выше плана» — факт про один срез; точка роста — **потенциал тиражирования**: разрыв между срезом и лучшим срезом, умноженный на масштаб остальных («если пять смен дотянут до лучшей — +X шт в месяц»). Она бывает, даже когда все выполнили план. Положительное отклонение — частый **источник** точки роста: почему эта смена перевыполнила и можно ли так везде.
- **Несоответствие** — сигнал о **доверии**, а не о бизнесе: две правды не сходятся (источник ↔ источник) или событие не закрыто парой (разорванная пара, раздел 5.1). Исходов два. Ошибка учёта или интеграции — это заявка на исправление двери, как находка сторожа в П27: правят процесс, чтобы расхождение стало невозможным, а не данные руками. Настоящая потеря — оплата не пришла, товар пропал — это деньги. Пока несоответствие не разобрано, остальные сигналы этой ячейки стоят под вопросом.

Связи между ними:

```
несоответствие         ──доверие────────▶ любые сигналы этой ячейки
риск                   ──срок наступил──▶ отклонение | «не сбылся» (так калибруется прогноз)
отклонение листа       ──дерево метрик──▶ вес и риск у вершины
плюс-отклонение,
лучший срез            ──тиражирование──▶ точка роста
```

Порядок чтения для человека — тот же: сначала доверие (сходятся ли цифры), потом вершина (что с деньгами), потом вес (где больше всего), потом время (что уже случилось, что надвигается), потом рост.

Детекторы — по базам:

| База | Вопрос | Детектор |
|---|---|---|
| план | идём ли, как обещали | `planGap` |
| норма (техкарта, регламент) | делаем ли, как должно | `planGap` над нормой |
| прошлый период, год назад | меняемся ли, с поправкой на сезон | `planGap` над историей |
| другой источник | сходятся ли две правды | `reconcile` |
| вторая половина пары REA | закрыто ли событие | `brokenPairs` |
| прогноз и порог | куда придём | `forecast` |
| лучший срез | можно ли как у лидера | `growth` |

## 5. Что и как берём из источника

### 5.1 REA — что есть в мире

Модель Маккарти (W. McCarthy, *The REA Accounting Model*, 1982) — онтология учёта, не привязанная к отрасли:

- **ресурс** — то, что имеет ценность и чего бывает больше или меньше: деньги, товар, сырьё, мощность станка, время людей;
- **событие** — то, что меняет количество ресурса: продажа, оплата, выпуск, списание, отгрузка;
- **участник** — кто участвует: внутренний (сотрудник, отдел) и внешний (клиент, поставщик);
- **обязательство** (расширение Гертса и Маккарти) — обещанное будущее событие: заказ, договор, план, сделка в воронке;
- **двойственность** — каждое уменьшение ресурса парно увеличению другого: обмен и превращение (раздел 3).

Что REA даёт станции:

1. **Виды справочников** — ресурсы, участники, место, время — они общие у любой компании; согласовывать между системами надо именно их.
2. **Семь классов мер** (раздел 4.4).
3. **Бесплатный детектор несоответствий** — разорванная пара (паттерн О22): отгрузка без оплаты (дебиторка), оплата без отгрузки (аванс), выпуск без расхода сырья (учёт врёт), расход без выпуска (потери). Работает в любой нише.

### 5.2 Кимбалл — как это мерить

Размерное моделирование (R. Kimball, *The Data Warehouse Toolkit*): факт — измерение события бизнес-процесса, измерения — его контекст «кто, что, где, когда».

- **Четыре шага:** выбрать **процесс** (не отдел!) → объявить **зерно** — что означает одна строка («товар × день × склад × канал») → назвать **измерения** → назвать **меры**.
- **Три рода таблиц фактов:** транзакционный (каждое событие: продажа, оплата); периодический снимок (остаток на конец дня: склад, деньги, дебиторка); накопительный снимок (одна строка на экземпляр процесса с датами вех: заказ создан → оплачен → отгружен → доставлен). Накопительный снимок — проекция журнала этапов (О15), из него берутся длительности, ось «скорость».
- **Аддитивность:** аддитивные, полуаддитивные, неаддитивные (раздел 4.5).
- **Согласованные измерения** — один «товар», один «контрагент», одна «дата» на все процессы. Именно они делают «объединение данных» возможным; у станции это `Dimensions` + `KeyMap`.
- **Медленно меняющиеся измерения** (SCD, тип 2): менеджер перешёл в другой отдел — прошлогодние продажи остаются за старым отделом. Оргструктура меняется, история — нет.

REA отвечает, **что** есть в мире; Кимбалл — **как** это разложить для измерения. Вместе они заменяют попытку «универсального формата всех данных»: объединяется не всё, а форма наблюдения и ключи.

### 5.3 Матрица шины: процессы × согласованные измерения

Главный рабочий документ при подключении источников (у Кимбалла — bus matrix). Строки — процессы, столбцы — общие измерения; каждая ✓ — обязательство сопоставить ключ.

| Процесс (источник) | Дата | Товар | Контрагент | Сотрудник / отдел | Склад / участок | Канал |
|---|---|---|---|---|---|---|
| сделка (Б24) | ✓ | ✓ | ✓ | ✓ | | ✓ |
| заказ маркетплейса (WB, Ozon) | ✓ | ✓ | | | ✓ | ✓ |
| отгрузка (1С) | ✓ | ✓ | ✓ | ✓ | ✓ | |
| оплата (1С, банк) | ✓ | | ✓ | | | ✓ |
| выпуск (MES) | ✓ | ✓ | | ✓ | ✓ | |
| расход сырья (MES, 1С) | ✓ | ✓ | ✓ поставщик | | ✓ | |

Столбец «Товар» — самый дорогой: артикул 1С = nmID WB = offer_id Ozon = товар Б24 = номенклатура MES. Это `KeyMap` — по-русски нормативно-справочная информация (НСИ), международно — master data; требования к её качеству и обмену описывает ISO 8000.

### 5.4 Три слоя склада

```js
new Measures(        // факты по объявленному зерну, в единицах каталога
  new Conformed(     // ключи сопоставлены, виды REA назначены
    new Raw()))      // выгрузка как есть, с меткой загрузки — не меняется
```

Сырьё хранится, чтобы пересобрать факты, когда меняются правила сопоставления или формулы: преобразование называет, что теряет (П40).

### 5.5 Правила приёма

1. **Берём по нужде метрики, а не «всё».** Каталог говорит, какие процессы и поля нужны; остальное остаётся в источнике.
2. **Истина остаётся в источнике.** У каждой метрики объявлен хозяин истины; расхождение двух источников — сигнал `reconcile`, а не тихая перезапись.
3. **Зерно объявлено до загрузки.** Факт без зерна нельзя ни сложить, ни сравнить.
4. **Период перезаливается целиком** (О17). 1С перепроводит прошлые документы, маркетплейсы правят отчёты задним числом — у каждого источника объявлено окно пересчёта (П6).
5. **Повторная загрузка безопасна.** Та же выгрузка дважды даёт те же факты (П36).
6. **Свежесть и полнота — по источнику и периоду.** «Не проверяли» отличается от нуля (О10).
7. **Несопоставленный ключ — именованный исход.** Неопознанный товар попадает в очередь на сопоставление человеком, а не выпадает молча.
8. **Справочники с историей** (SCD2): изменения оргструктуры не переписывают прошлое.

## 6. Каркас: что закладывается сразу

Критерий: в ядро идёт то, что **дорого добавить потом** или без чего модули не могут говорить друг с другом.

| Механизм | Что | Почему сразу |
|---|---|---|
| общий язык | каталог метрик с версиями, справочники с `KeyMap`, планы и нормы | иначе каждый модуль изобретёт свою «выручку» |
| склад фактов | три слоя, зерно, свежесть, окно пересчёта | от формы факта зависят все приборы |
| доступ | охват по оргструктуре × полномочия, на двери фактов | добавить потом — пройти по каждому потребителю, включая модель (О20, П27) |
| журнал петли | сигналы и решения как сущности с путём; снимок «до» в решении | эффект и аудит задним числом не восстановить (О19) |
| протокол исполнения | согласование, полосы, отложенная доставка, отмена, журнал | до того, как первый сценарий тронет внешнюю систему (П35, П39) |
| зеркало | дерево процессов, свежесть, сбои | иначе «нет данных» неотличимо от нуля, а модуль — от поломки (П25) |
| реестр модулей и порты | паспорт модуля, стыковочная проверка | без этого расширение в ширину — правка ядра |
| версии определений | формула метрики изменилась — новая версия | иначе сравнение с прошлым годом молча врёт |

Ядро — умный монолит (П33): сигнал, решение и доступ связаны жёсткими инвариантами («нельзя согласовать то, чего не видишь», «один открытый сигнал на ячейку»), а жёсткий инвариант — довод не разносить (П27). Кандидаты в автономные сервисы — то, у чего свой темп, свои сбои и узкий контракт без состояния: адаптеры источников, прибор «Состояние бизнеса», детекторы, замеры, шлюз модели, доставка уведомлений.

## 7. Стыковочные узлы

| Порт | Направление | Контракт | Кто стыкуется |
|---|---|---|---|
| источник | мир → станция | `pull(period) → Raw`; `conform(Raw) → Facts + DimensionRows` | адаптеры Б24, 1С, WB, Ozon, MES, банка |
| основание | мир → станция | `bases(period) → Plan[] \| Norm[]` | бюджет 1С, техкарты, форма плана |
| детектор | внутри | `detect(state) → Signal[]` | отклонение, сверка, разорванная пара, прогноз, рост |
| советник | внутри | `explain(signal) → Cause`; `options(signal) → Option[]` | дерево драйверов, модель со сверенными цифрами |
| сценарий | станция → мир | `run(params) ↔ undo(params)`; автономия; полоса | задача в Б24, уведомление, цена, заявка на ремонт |
| замер | внутри | `measure(decision) → Effect` | «до / после», контрольная группа |
| вид | станция → люди | спека блоков над проекциями | кабинеты, планёрка, ассистент |

### Паспорт модуля

Модуль стыкуется декларацией — паспортом. Пример отсека:

```js
new ProductionBay({
  sources:    { mes: new MesAdapter(), shifts: new ShiftLogFiles() },          // заместитель на файлах — с первого дня
  processes:  ['выпуск', 'простой', 'расход сырья', 'контроль качества'],      // строки матрицы шины
  dimensions: ['дата', 'товар', 'участок', 'станок', 'смена', 'сотрудник'],    // общие — из языка, новые — объявлены
  metrics:    productionTree,                                                  // единица, зерно, хозяин истины, владелец
  bases:      { norms: new TechCardNorms() },                                  // техкарты — основания, не рецептуры
  scenarios:  { repair: new RepairRequest(), hold: new HoldBatch() },          // у каждого отмена и уровень автономии
  views:      ['Смена сейчас', 'Простои'],
  numbers:    { recalcWindow: '7d', poll: '15m' },                             // числа поведения — в паспорте (П6)
})
```

**Стыковочная проверка** — модуль не пристыкуется, пока: каждая метрика имеет единицу, зерно, хозяина истины и владельца; имена метрик не конфликтуют; каждое измерение либо общее, либо объявлено новым общим; у каждого сценария есть отмена и уровень автономии (уведомление — само, цена — с согласованием, платёж — модели запрещён); у каждого источника есть правило свежести и окно пересчёта. Отказ — с причиной.

## 8. Карта отсеков

Чтобы станция не осталась торговой по привычке, отсеки сверяются с межотраслевыми картами процессов: APQC PCF (классификатор процессов любой компании — около 13 категорий верхнего уровня: стратегия, продукты, продажи, цепочка поставок, услуги, клиентский сервис, персонал, ИТ, финансы, активы, риски и соответствие, внешние связи, развитие способностей), SCOR (эталонная модель цепочки поставок: Plan, Source, Make, Deliver, Return) и цепочка ценности Портера.

| Отсек | Форма REA | Опорная модель | Источники | Основания |
|---|---|---|---|---|
| торговля и клиентский сервис | обмен на границе | APQC: продажи, клиентский сервис | CRM, маркетплейсы | планы продаж |
| снабжение и склад | обмен на границе, хранение | SCOR Source, Deliver, Return | ERP, WMS | нормы запаса, сроки поставки |
| производство | превращение | ISA-95 ур. 3, SCOR Make, ISA-88 | MES, журналы смен | техкарты, рецептуры (PLM) |
| качество | свойство событий | ISO 9001 | MES, рекламации, лаборатория | допуски |
| оборудование и активы | ресурс-мощность | ISO 55000 | EAM/ТОиР, MES | межремонтный ресурс |
| финансы | обмен денег | APQC: финансы; РСБУ и МСФО — хозяин истины | ERP, банк | бюджет |
| персонал | обмен: труд ↔ оплата | APQC: человеческий капитал | HRM, табель | штатное расписание, нормы времени |
| риски и соответствие | над всеми отсеками | ISO 31000 | все | пороги, допустимый риск |

Строка карты — не обещание сделать отсек, а проверка ядра: каждый следующий отсек должен пристыковываться без его правки (раздел 9, правило 1).

## 9. Правила расширения

1. **Ядро не растёт от отсеков.** Если добавление производства требует правки ядра — ядро разрезано неправильно. Проверка — на каждом новом отсеке.
2. **Стыковка только через порты и паспорт.** Обходной путь в склад или в мир — запрещён.
3. **Модули не знают друг друга** (П2). Метрика на стыке двух отсеков — например, себестоимость продаж = торговля × производство — объявляется в каталоге над общим измерением «товар», а не внутри одного из отсеков (О8).
4. **Три единственных писателя.** Факты пишут только порты источников; мир меняет только протокол исполнения; журнал петли пишет только ядро. Никто не читает факты мимо доступа.
5. **Определения версионируются.** Сравнение через версии объявлено (П40).
6. **Отстыковка без следа.** Модуль снимается, его метрики уходят в архив, история остаётся (П30, тест выключения).
7. **Видно по умолчанию.** Каждый порт сообщает о себе узлом дерева процессов — новый модуль виден без своего UI (П25).
8. **Сквозной прогон с первого дня.** Новый отсек стыкуется сначала с заместителями (файлы вместо API), потом узлы заменяются живыми без правки дерева (П31, О6).

## 10. Честные границы и открытые вопросы

Границы:

- Станция не заменяет ERP, CRM и MES и не хранит рецептуры; данные датчиков приходят агрегированными до зерна смены или партии.
- Определения метрик и хозяева истины приходят из разговора с бизнесом (финансовый директор, технолог), а не из каркаса.
- Эффект решения — оценка с объявленной базой, а не доказательство: сезон и параллельные изменения честно названы.
- Каркас ускоряет расширение, а не прозрение: что именно болит у компании, покажут данные.

Открытые вопросы — дополнять:

- события из источников (вебхуки) — отдельный порт или вид источника;
- минимальный набор общих измерений для первого отсека;
- где вводятся планы: форма станции или бюджет 1С;
- холдинг из нескольких юрлиц, валюты, внутригрупповые обороты;
- срок хранения сырого слоя;
- сколько шаблонов ролей достаточно на старте (гипотеза — 4–5 на двух осях).

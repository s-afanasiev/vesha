## Что оставить как есть

- Тезис «негатив — поломка коммуникации и учёта, а не продукта» и маппинг «боль → тип софта» — главный актив плана: жалоба клиента превращается в спрос бизнеса на софт.
- «Носители боли — база первых клиентов» — самое монетизируемое место плана.
- Порядок «сначала стабильность парсинга, потом LLM», один источник на старте.
- В бизнес-логике: рез по мирам, отдельные резы по темпу и дефициту, сюжеты с концом, границы через незнание, раздел «что сознательно НЕ делаем объектами».

## А. Продукт и данные (к pain-radar-architecture.md)

### А1. Знаменатель

**Проблема.** Хранится и считается только негатив (рейтинг ≤ 3). У популярной организации жалоб больше просто потому, что больше клиентов, а утверждение «у половины автосервисов болит X» требует знать и организации без жалоб.

**Предложение.**
- На каждую карточку организации: число отзывов всего, гистограмма рейтингов, период скана (с — по).
- Организация без негатива сохраняется так же, как с негативом.
- Две меры в статистике: доля организаций ниши с болью (от просканированных) и число жалоб категории; по умолчанию — доля.

**Где.** Таблица карточек (А5), `RankPains` (Б7), переключатель «доля / число» на дашборде (Г).

### А2. 4★ с оговоркой — тоже негатив

**Проблема.** Фильтр «рейтинг ≤ 3» теряет отзывы вида «всё хорошо, но дозвониться невозможно» — часто самые конкретные жалобы.

**Предложение.** `NegativeReviewRule` = рейтинг ≤ 3 **или** (рейтинг 4 и маркер оговорки: «но», «однако», «единственный минус», «к сожалению»). Порог и список маркеров — параметры правила в декларации (П6). На дашборде — переключатель.

### А3. Несколько болей в одном отзыве

**Проблема.** JSON в промпте (раздел «LLM-разметка болей» архитектуры) — один объект на отзыв. «Ждал два часа, по телефону назвали другую цену, нагрубили» — три категории; одна выбранная моделью категория искажает статистику. Схема `pain_radar_pains` несколько болей на отзыв уже допускает, промпт — нет.

**Предложение.** Ответ разметки — массив по отзывам, в каждом — массив болей; id отзыва обязателен и в промпте, и в ответе (в батче модель теряет и переставляет элементы, Б4). Поле `churn` — маркер ухода («ушёл к другим», «больше не приеду»), см. В5.

```json
[
  { "review_id": "r-17", "pains": [
    { "pain_category": "queue_speed", "pain_summary": "…", "quote": "…", "churn": false },
    { "pain_category": "price_deception", "pain_summary": "…", "quote": "…", "churn": true }
  ] }
]
```

### А4. Версия таксономии и промпта; переразметка

**Проблема.** `other` заведён ровно для того, чтобы список категорий менялся. После первой правки старая и новая разметка несравнимы, а по сохранённой цитате переразметить нельзя.

**Предложение.**
- У каждой боли — `taxonomy_version`, `prompt_version`, `model`.
- `PainTaxonomy` знает свою версию и собирает описание для промпта.
- Переразметка — штатный сюжет: «отзывы без болей текущей версии» → тот же проход разметки (Б4).
- Статистика по умолчанию — по текущей версии таксономии.

**Ответ на открытый вопрос 4.** Полный текст хранить: без него переразметка невозможна. Наружу — короткая цитата со ссылкой на источник. Юридическую сторону показать юристу до публичного запуска.

### А5. Общий корпус вместо данных джобы

**Проблема.** В наброске БД отзыв привязан к `job_id`, данные организации продублированы в каждом отзыве. Отзывы публичных организаций не принадлежат пользователю: второй запрос той же ниши заново парсит источник. Дедупликация по одному `text_hash` склеит одинаковые короткие отзывы разных организаций («Ужасно!»).

**Предложение.**
- Организации и отзывы — общий корпус. Ключ отзыва — (`listing_id`, `external_id`), если id нет — (`listing_id`, `text_hash`).
- Джоба — запрос на обновление части корпуса и единица квоты. Отчёт — срез корпуса на момент джобы, читатель (П30).
- Организация ≠ карточка в источнике: одна организация — несколько карточек (2ГИС, Яндекс). До фазы 6 карточка одна, но модель различает их сразу, иначе второй источник даст двойной счёт.
- Координаты карточки сохраняются: без них не будет районов и белых пятен (В3).

Набросок таблиц v2:

```text
pain_radar_orgs          id, name, city, niche, lat, lon, status (active | closed), first_seen_at
pain_radar_listings      id, org_id, source, external_id, url, rubric, card_flags jsonb,
                         reviews_total, rating_hist jsonb, scanned_from, scanned_to, scanned_at
pain_radar_reviews       id, listing_id, external_id, text_hash, rating, review_date,
                         has_owner_reply, raw_text, first_job_id
                         UNIQUE (listing_id, external_id), UNIQUE (listing_id, text_hash)
pain_radar_pains         id, review_id, category, summary, quote, churn,
                         taxonomy_version, prompt_version, model, created_at
pain_radar_jobs          id, user_id / guest_id, kind (org | niche | paste), query jsonb,
                         status, error, created_at, started_at, finished_at
pain_radar_job_listings  job_id, listing_id, outcome (ok | failed | skipped), error_code
pain_radar_ideas         id, user_id / guest_id, mode (pick | check), profile jsonb, city,
                         ideas jsonb, model, created_at
```

`card_flags` — есть ли на карточке сайт, онлайн-запись, мессенджеры (В1). Прогресс джобы вычисляется из `pain_radar_job_listings`, отдельно не хранится (Б4).

### А6. Фаза 1.5: проверить тезис до парсера

**Проблема.** Самый рискованный технический кусок (парсинг, антибот) и самый рискованный продуктовый (даёт ли таксономия полезный сигнал) идут последовательно: ответ на второй появится только после решения первого.

**Предложение.** Между фазами 1 и 2:
- источник `PastedReviewsSource` — вставленный текст или CSV «рейтинг;дата;текст» по одной организации или нише;
- разметка 100–200 отзывов одной ниши одного города;
- критерий прохождения (например): распределение по категориям осмысленное, `other` — меньше 15%, на 20 отзывах разметка совпадает с ручной.

Цена — вечер. Тот же источник — мок для прогона каркаса без внешних систем (П9) и запасной вход, если парсинг сломают или запретят. Режим «Вставить отзывы» уже есть на вкладке «Сбор» мока (Г).

### А7. Позиции по открытым вопросам архитектуры

| Вопрос | Позиция |
|---|---|
| 1. Первый источник | 2ГИС; Яндекс — фаза 6 |
| 2. Ввод на MVP | для фазы 2 хватит URL; ценность сценария А появляется только на «нише + городе». Каталог 2ГИС — официальный API, его можно подключить раньше парсинга Яндекса |

| 6. Гость и логин | как в summarize и podborka |

## Б. Язык объектов (к pain-radar-business-logic.md)

### Б1. Квота на джобу и ожидание LLM-слота вместо `runGuarded`

**Что в коде.** `runGuarded(req, task)` рассчитан на один HTTP-запрос:
- личность берёт из `req` (`server/services/llmGuard.js:7`), а в фоновой джобе `req` нет;
- лимит по умолчанию — 10 вызовов в час гостю и 60 пользователю (`server/config.js:75`);
- при занятых 4 слотах сразу бросает 503 (`server/services/llmGuard.js:64`).

Даже 40 организаций × ~15 негативных отзывов = ~60 батчей: гостевая джоба упадёт на 11-м вызове, пользовательская сожжёт весь часовой лимит, а параллельные запросы других пользователей уронят батч по 503.

**По канону** (E28, «второй потребитель другого рода»): у дефицита LLM уже два потребителя — интерактивные запросы (экспорт заметок, генератор идей) и фоновая разметка. Значит, раздача слотов — самостоятельная часть; фраза «отдельной части аллокатор не заводим, пока потребитель дефицита один» больше не выполняется.

**Предложение.**
- Квоту списывать на двери `POST /api/pain-radar/jobs` за джобу целиком — дневной счётчик сборов по образцу `uploads_count` (`server/services/quota.js:32`).
- Один аллокатор LLM-слотов, два режима: интерактивный — сразу отказ, как сейчас; фоновый — `WithLlmSlot(slots, …)` **ждёт** слот (билет с позицией в очереди, П22).
- Бюджет вызовов на джобу — параметр в декларации (`maxCalls`); при исчерпании — частичный результат с причиной, а не ошибка.
- Если разметка идёт личным ключом из llm-picker, ключ живёт только в памяти, как `creds` в summarize. После рестарта джоба переходит в состояние «нужен ключ», а не падает молча.

### Б2. Парсинг — внутри адаптера; один контракт источника

**Проблема.** Граница «`ParseReviews` не знает, откуда страница — 2ГИС, Яндекс или чат» невыполнима: JSON 2ГИС и SSR Яндекса разбираются по-разному, и общий парсер вырастет в `if (source === '2gis')`. Вдобавок в документе два несовместимых контракта источника: `fetchReviews(orgRef) → ReviewSnapshot[]` (раздел «Адаптеры») и `FetchOrgPage → SourcePage → ParseReviews` (декларация).

**Предложение.** Оставить первый. Страницы, пагинация, разбор и перевод чужих полей в `ReviewSnapshot` — внутри адаптера (П9; E28: меняются все пять признаков — нужен адаптер). Наружу — поток отзывов от новых к старым, чтобы остановка по горизонту скана не тянула лишние страницы, а пересбор забирал только новое:

```
contract ReviewsSource {
  listing(ref) → Listing                                   -- карточка: флаги, всего отзывов, рейтинг
  reviews(ref, since, signal) → stream of ReviewSnapshot   -- новые сначала, до since
}
```

Граница через незнание переписывается так: «разбор страниц 2ГИС живёт внутри `TwoGisReviews`; всё после адаптера не знает, из какого источника отзыв».

### Б3. Telegram-чаты — отдельный сюжет

**Проблема.** У сообщения в чате нет организации и рейтинга, `NegativeReviewRule` к нему неприменим, лестница другая (чат → окно сообщений → запрос или жалоба). Контракт `ReviewsSource` честно оправдан Яндексом — у него та же форма, что у 2ГИС; чаты в нём — ложная таксономия.

**Предложение.** Если источник чатов появится — это отдельный сюжет «собрать запросы района» со своим контрактом и правилом «это запрос или жалоба?». Общим с картами может быть только нижний слой данных: `Signal { text, date, place, source_ref }`. Юридически: публичность чата не означает согласия на обработку персональных данных — решать с юристом до любой реализации. Сигнал «нет предложения» можно получить без чатов — В3.

### Б4. Запись в корпус видна в декларации; второй проход читает из корпуса

**Проблема.** В декларации нет ни одного узла, который пишет отзывы и боли, и не сказано, откуда `ForEachReviewBatch` берёт отзывы. Если из памяти первого прохода — рестарт теряет всё, а переразметка требует нового парсинга. Декларация умалчивает о главном побочном эффекте системы (П3: структура не должна врать о потоке данных).

**Предложение.**
- Первый проход пишет в корпус: `OneOrganizationScan(sources, corpus, …)`.
- Второй проход — `ForEachUnlabeledBatch(corpus, taxonomy, …)`: отзывы карточек этой джобы без болей текущей версии таксономии.
- Тот же узел без фильтра по джобе — сюжет «переразметить» (`relabel`).
- Отзывы, которые модель потеряла в батче, остаются неразмеченными и попадают в следующий проход сами (П24: повтор — отдельный проход по неудачам).
- Возобновление после рестарта бесплатное: сделанное находится запросом к корпусу, а не памятью процесса (П26).

### Б5. Числа в декларации; «источник сломался»; частичные провалы

**Проблема.** В декларации нет интервала троттлинга, таймаутов, числа повторов и бюджета; `Timeout` есть в словаре, но его нет в дереве — худшее время джобы по точке сборки не назвать (П6, П23). При смене вёрстки все 40 запросов упадут одинаково, продолжая нагружать источник.

**Предложение.**
- Троттлинг — один на источник для всех джоб (в реестре источников), интервал виден в декларации.
- Дедлайн джобы и таймаут страницы — в декларации; вниз передаётся дедлайн через `AbortSignal`.
- Правило `SourceLooksBroken`: N одинаковых ошибок подряд — джоба останавливается с причиной «источник изменился». Это и бережёт источник.
- Единичный провал карточки — строка отчёта (`outcome = failed` и код ошибки), а не падение джобы (П24).
- Итог джобы: `done` с отчётом о провалах; `failed` — только если провалились все карточки или сработал `SourceLooksBroken`.

### Б6. `stale` вычисляется, `closed` — состояние; пересбор по запросу

**Проблема.** `stale` записан состоянием сущности `Organization`, при этом есть `StalenessRule`. Хранимое производное состояние требует сторожа, который будет его переключать (П27).

**Предложение.**
- `stale` — ответ правила на `scanned_at`: `listing.isStale(rule)`.
- Состояния организации — `active | closed`. Закрытие — настоящее событие и само по себе сигнал (закрылась с кучей жалоб).
- Прогресс джобы тоже вычисляется, из `pain_radar_job_listings`.
- Пересбор — по запросу, когда срез устарел, а не краулером по расписанию: расписание тратит терпение источника и LLM на данные, которые никто не запрашивал.

### Б7. SQL считает, `RankPains` решает

**Проблема.** Бизнес-логика ранжирует чистой функцией над `PainRecord[]`, то есть в памяти, а архитектура — SQL-агрегацией. На нише из сотен организаций загружать все боли в память незачем.

**Предложение.** SQL отдаёт счётчики `PainCounts` (категория × карточка × месяц), `RankPains` — чистое действие над ними (П15). В нём живёт то, что отличает продукт:
- нормировка на знаменатель (А1);
- порог: боль засчитывается нише, если есть у ≥ 3 организаций;
- вес свежести (например, полураспад 12 месяцев);
- маркеры ухода (А3) весят больше обычной жалобы.

Параметры — в декларации: `RankPains({ minOrgs: 3, halfLifeMonths: 12 })`.

### Б8. Один механизм прогресса; нейтральный раннер

**Что в коде.** У summarize уже есть контракт шагов для UI: статус, прогресс, `detail`, `waitHint`, позиция в очереди (`server/services/jobSteps.js:118`, `server/services/summarizeQueue.js:82`).

**Предложение.**
- Вехи `CollectionJob` выводить в тот же контракт шагов: второй механизм прогресса дал бы две правды об одном процессе (П25).
- Радар — второй потребитель паттерна «долгая джоба + прогресс + история» (E28), поэтому раннер пишется доменно-нейтральным: греп по нему не находит «боль», «отзыв», «2gis».
- Как в summarize, одна джоба сбора за раз — так проще троттлинг источника и слоты; параллельность — отдельное решение со своим условием.

### Б9. Проверка цитат и ссылок

**Проблема.** Отличие от «спроси у ChatGPT» держится на доказательствах, а модель переформулирует «дословные» цитаты и выдумывает ссылки на боли.

**Предложение.** Два узла-обёртки в декларации:
- `VerifiedQuotes(ClassifyPainBatch)` — цитата обязана быть подстрокой текста отзыва (после нормализации пробелов и кавычек). Нет — боль сохраняется без цитаты с пометкой, а не с выдуманной.
- `VerifiedRefs(ComposeIdeas)` — у идеи остаются только ссылки на боли, переданные в промпт; идея без единой верной ссылки отбрасывается.

На дашборде — отметка «цитата дословная» (Г).

### Б10. Мелкие правки декларации и словаря

- Как JS декларация не исполнится: `sources` и `taxonomy` объявлены свойствами того же литерала ниже места использования — нужны именованные поддеревья (П5).
- `PainMapQuery` создаётся дважды, хотя текст говорит «тот же читатель»: объявить один раз и передать обоим спутникам.
- `IdeaComposer` и `ComposeIdeas` почти неразличимы по имени при разных ролях: дверь сюжета назвать по сюжету — `IdeaMatchmaking`, работа модели остаётся `ComposeIdeas`.
- Квоты записаны спутником, но по E28 это сквозная способность — обёртка на дверях `POST /jobs` и `POST /ideas`.
- Для джобы «ниша + город» нет шага `DiscoverOrganizations(catalog)` — поиска организаций через каталог 2ГИС (единственный официальный API схемы, свой ключ и лимиты).
- `KeepNegative`, `OneOrganizationScan`, `CollectionJobRunner`, `PainMapQuery`, `IdeaComposer` не получили род в словаре (E28 Ш4).
- «UI не знает про источники» уточнить: знает источник как метку в данных, но не знает механики.
- Ключ дедупликации — (`listing_id`, `text_hash`), а не один `text_hash` (А5).

### Б11. Фаза 2 начинается с разведки

**Проблема.** Писать декларацию заранее — канонично (П31), но реализовывать все комбинаторы до первого реального отзыва — нет (П34). Главная неизвестная — нужен ли 2ГИС headless-браузер. Если да, источник становится дефицитным ресурсом с арендой (П22): меняются раздел про дефицит и жизненный цикл адаптера.

**Предложение.** Фаза 2 = скрипт-разведка на одну организацию (что отдаёт веб-версия, как устроена пагинация, при какой частоте начинается блокировка) → решение «HTTP или браузер» → адаптер под контракт Б2 → раннер (Б8). Комбинаторы появляются по мере того, как у шагов появляется судьба.

### Б12. Декларация после правок (эскиз)

```js
const taxonomy = new PainTaxonomy('v1');
const corpus   = new PainCorpus(db);            // организации, отзывы, боли — общие, истина здесь

const sources = {                                // разбор страниц — внутри адаптера
  '2gis': new Throttled({ everyMs: 3000 },       // один троттлинг на источник для всех джоб
            new TwoGisReviews(http, { pageTimeoutMs: 15_000 })),
};

const classify = new WithLlmSlot(llmSlots,       // ждёт слот, а не падает 503
  new Retry({ times: 2, on: 'transient' },
    new VerifiedQuotes(new ClassifyPainBatch(llm, taxonomy))));

const labelPending = new ForEachUnlabeledBatch(corpus, taxonomy, { size: 10, maxCalls: 100 }, classify);
const painMap      = new PainMapQuery(corpus, new RankPains({ minOrgs: 3, halfLifeMonths: 12 }));

new PainRadarExperiment({
  collect: new CollectionJobRunner(jobStore, { deadlineMin: 30 },
    new ForEachOrganization(new SourceLooksBroken({ sameErrorInRow: 3 }),
      new OneOrganizationScan(sources, corpus, new ScanHorizon({ months: 24 }))),
    labelPending),
  relabel: labelPending,                         // сменили таксономию — та же фраза, без парсинга
  painMap,                                       // один экземпляр на двух читателей
  ideas: new IdeaMatchmaking(painMap,
    new WithLlmSlot(llmSlots, new VerifiedRefs(new ComposeIdeas(llm, taxonomy))),
    ideaStore),
});
```

Что изменилось относительно исходной декларации: запись в корпус видна; второй проход читает из корпуса; переразметка — одна строка, и критерий документа «рост — это дописывание предложений» выполняется буквально; числа поведения видны в сборке; один читатель карты на два спутника; ожидание слота вместо отказа; проверка цитат и ссылок стоит в оглавлении. Фазе 4 добавляется `DiscoverOrganizations(catalog)` перед `ForEachOrganization`.

### Цена крупных пунктов (оценка, П34)

| Пункт | Цена | Риск | Выигрыш | Условие отказа или возврата |
|---|---|---|---|---|
| А5 общий корпус | ~полдня сверх наброска | низкий | переиспользование данных, переразметка, возобновление | отказаться, если запросы пользователей никогда не пересекаются |
| А6 фаза 1.5 | вечер | нулевой | проверка тезиса до парсера, мок каркаса, запасной вход | — |
| Б1 слоты с ожиданием | 0,5–1 день | средний: трогает общий guard, которым пользуется экспорт заметок | джобы не падают на лимитах и чужих запросах | вернуться к `runGuarded`, если разметка станет синхронной (одна организация, ≤ 5 батчей в запросе) |
| Б8 нейтральный раннер | ~день сверх копии summarize | низкий | общий раннер для долгих экспериментов | перевести summarize при его следующей правке; если третий потребитель не появится — дальше не обобщать |

## В. Идеи развития продукта

### В1. Лид-скоринг «боль × нет решения на карточке»

На карточке организации видно: сайт, онлайн-запись, мессенджеры, отвечает ли владелец на отзывы. Скоринг:
- свежая боль, решения на карточке нет, владелец активен в сети → **горячий** лид;
- боль есть, но решение на карточке есть → другая продажа: внедрение и настройка, а не продукт;
- давняя боль → **холодный**.

Данные карточки официальные и дешёвые (каталог). Нужны поля `card_flags` и `has_owner_reply` (А5).

### В2. Режим «проверь мою идею»

Обратный сценарий Б: человек чаще приходит с идеей, чем без неё. Ввод — идея и город; вывод — жалобы за и против из корпуса, плотность конкурентов, вердикт с причинами. Тот же корпус и `PainMapQuery`, новое слово языка — `MatchIdeaToPains`.

### В3. Белые пятна вместо чатов

Сигнал «боль несуществующего предложения» без чтения переписок:
- плотность организаций ниши по районам из каталога (координаты карточек) плюс население района из открытых данных;
- частотность поисковых запросов («шиномонтаж круглосуточно Томск»).

Район с высоким спросом и без предложения — кандидат.

### В4. Идея приходит со списком первых клиентов

Для B2B-идеи генератор прикладывает организации — носители боли из сценария А, с лид-скорингом (В1). Этого не даст ни одна модель без корпуса. На дашборде — кнопка «Первые клиенты» в карточке идеи.

### В5. Аудит отзывов и маркеры ухода

Отчёт по одной организации — бесплатный «аудит отзывов» для владельца и повод для первого контакта из списка А. Маркер ухода в разметке (А3) переводит разговор о боли в разговор о потерянных деньгах.

### В6. Позитив лидеров ниши — рецепт

У кого в нише меньше всего жалоб на категорию и что о них пишут в 5★ — описание решения, которое уже работает в этом городе. Для генератора идей это «как делать», для продажи — аргумент «у соседей получилось».

### В7. Кто платит

Как эксперимент идея самодостаточна. Как продукт — нужен выбор плательщика. Ставка: ядро — сценарий А с лид-скорингом для тех, кто продаёт софт малому бизнесу (интеграторы CRM и онлайн-записи, разработчики — включая нас); сценарий Б — входная воронка. Главный риск — доступ к источникам. Шов `ReviewsSource` уже есть; «данные от пользователя» (А6) нужно держать полноправным источником, а не заглушкой.

## Г. Дашборд v1

Сделан как мок на демо-данных: `public/experiments/pain-radar/` (`index.html`, `pain-radar.css`, `pain-radar.js`). Бэкенда нет, все данные — в `pain-radar.js`. Одна страница, четыре вкладки; в шапке — пометка демо-данных и остаток квоты сборов.

**Карта болей**
- Фильтры: город, ниша, период (3 / 6 / 12 / 24 мес), источники (2ГИС; Яндекс — «скоро»).
- Переключатели: «4★ с „но“ — тоже негатив» (А2), «Только софт-категории» (первые семь категорий таксономии), «Считать: доля организаций / число жалоб» (А1).
- Показатели: организаций (и сколько не собрано), отзывов всего, негативных (процент и число болей — болей больше, чем отзывов, А3), свежесть данных со ссылкой «обновить».
- Рейтинг болей: категория и какой софт нужен, полоса доли, «22 из 42» или «118 жалоб», тренд. Под списком — версия таксономии, модель, порог засчёта (А4, Б7).
- Детали выбранной боли: цитаты с отметкой «цитата дословная», источником, датой и оценкой (Б9); число маркеров ухода (В5); носители боли: организация, жалоб, последняя жалоба, решение на карточке, отвечает ли владелец, лид-метка (В1).

**Сбор**
- Режимы ввода: ссылка на организацию; ниша и город (+ «организаций, не больше»); вставить отзывы — текст или CSV (А6).
- Параметры: глубина истории, разметка через LLM (на фазе 2 выключена), выбор модели — общий блок llm-picker.
- Квота сборов (Б1), кнопка «Запустить сбор» с проверкой ввода.
- Карточка текущей джобы в форме шагов summarize (Б8): поиск организаций → сбор отзывов (прогресс, «1 не удалось: антибот», Б5) → разметка («ждёт LLM-слот», Б1) → сведение карты; дедлайн; «Отменить».

**Идеи**
- Режимы: «Подобрать идеи» и «Проверить мою идею» (В2).
- Профиль: город, бюджет, формат, навыки, образование, время; игровые поля с пометкой «влияют только на тон ответа, не на подбор».
- Карточка идеи: название, боли-доказательства с долями, цитата, «почему вам», старт, кнопка «Первые клиенты» — переход на карту с выбранной болью (В4).

**История** — дата, тип, запрос, итог (включая частичный: «1 из 42 не собрана»), «Открыть».

Сознательно не входит в v1: карта по районам, графики динамики, настройки, отдельная страница отчёта по организации — после появления реального корпуса.

## 1. Зачем это нужно

Сейчас в Vesha смешаны три сущности с разными требованиями:

| Сущность | Что это | Требования |
|---|---|---|
| Эксперимент | проба, незаконченный проект, проверка идеи | можно ломать, можно не показывать |
| Витрина | проект, который показывают как портфолио | нельзя ломать, должен открываться без входа |
| Клиент | магазин «под ключ» | ПДн, договор, отдельный деплой |

Пока они в одном процессе и одной базе:

- миграция эксперимента может уронить витрину;
- витрина может показать клиентские данные;
- нельзя перезагрузить лабораторию, не затронув клиента;
- нельзя отдать заказчику репозиторий, не отдав всю платформу.

Разделять надо **не по проектам, а по зонам ответственности**. Один каталог, три профиля сборки, три зоны деплоя.

## 2. Что уже есть в коде

Перестройка не начинается с нуля — два ключевых примитива уже написаны.

### 2.1 Каталог

`public/experiments/registry.json` — источник правды о составе:

```json
{
  "experiments": [
    {
      "id": "roc",
      "title": "ROC",
      "description": "Canvas / matrix experiment",
      "href": "/experiments/roc/",
      "status": "wip",
      "tech": ["canvas"]
    }
  ]
}
```

`server/services/experiments.js`:

- `syncRegistry()` — upsert реестра в `experiment_tiles` / `experiment_tile_parts`;
- `listVisible(user)` — реестр × доступ из БД;
- `setVisibility()` — переключатель `all` / `admin`.

Уже есть разделение «что существует» (файл) и «кому видно» (БД). Это правильная основа.

### 2.2 Профиль сборки

`scripts/build-shop.mjs` — сборка `dist/shop` по манифесту:

```js
export const MANIFEST = {
  entry: 'shop.js',
  files: [...],
  dirs: [...],
  skip: [...],
  edits: [...],
  init: { from: '001_init.sql', to: '001_shop_init.sql', tables: [...] },
  migrations: [...],
  dependencies: [...],
  extras: { 'README.md': 'scripts/shop/README.md' },
};
```

`test/shop-build.test.js` проверяет границу require-графа: в сборке магазина нет импортов чужих экспериментов.

Это ровно тот механизм, который нужен для витрины и клиентов. Его надо обобщить, а не писать заново.

### 2.3 Чего не хватает

- `main.js` подключает 15 роутов вручную — профиль нельзя выбрать без правки кода;
- в реестре нет поля `kind` — эксперимент и витрина неразличимы;
- нет профиля `showcase`;
- нет зоны `lab`;
- клиентский профиль один (`shop`) и захардкожен под конкретный магазин.

## 3. Модель: три уровня, один каталог

| | `experiment` | `showcase` | `client` |
|---|---|---|---|
| Кто видит | вы (за входом) | все | заказчик |
| Где живёт | зона `lab` | зона `showcase` | отдельный деплой |
| Репозиторий | `vesha` | `vesha` | отдельный |
| База | `vesha_lab` | `vesha_show` | своя, отдельный инстанс |
| Качество | любое | чеклист (см. §10) | договор |
| Можно ронять | да | нет | нет |
| Домен | `vesha.pro/lab/…` | `vesha.pro/…` | домен заказчика |
| Платные API | как угодно | demo-режим + квота | по договору |
| Индексация | `noindex` | да | да |

Главное правило: **категория — свойство проекта, а не репозитория**. Путь `experiment → showcase → client` — это смена одного поля и пересборка профиля, а не переезд кода.

## 4. Манифест проекта

### 4.1 Расположение

```
projects/
  roc/
    project.json
  summarize/
    project.json
  backbone/
    project.json
```

Физически файлы **не двигаются**. Манифест ссылается на текущие пути — это позволяет внедрить его за один вечер, не трогая 22 каталога.

### 4.2 Схема

```json
{
  "id": "summarize",
  "order": 3,
  "title": "Суммаризация видео или аудио",
  "description": "Краткое содержание из ролика или записи",
  "kind": "experiment",
  "status": "wip",
  "tech": ["js", "yt-dlp", "ffmpeg"],

  "static": "public/experiments/summarize",
  "routes": [
    { "mount": "/api/summarize", "module": "server/routes/summarize" }
  ]
}
```

`routes` — массив, потому что у одного проекта бывает несколько API: у `backbone`
это `/api/backbone` и `/api/backbone-public`.

### 4.3 Поля

| Поле | Обязательно | Смысл |
|---|---|---|
| `id` | да | стабильный идентификатор, совпадает с папкой |
| `order` | да | порядок в каталоге и профилях |
| `title`, `description`, `status`, `tech` | да | карточка каталога |
| `kind` | да | `experiment` / `showcase` / `client` |
| `static` | да | каталог статики |
| `routes` | нет | массив `{ mount, module }` |
| `client` | для `kind: client` | id заказчика для `PROFILE=client:<id>` |
| `admin` | нет | плитка принудительно только для админа |
| `parts` | нет | части плитки (пульты, админские вкладки) |
| `service` | нет | пока не используется: фоновые сервисы включаются в `main.js` по `id` |

### 4.4 Пример витрины

```json
{
  "id": "backbone",
  "order": 15,
  "title": "Костяк: доска заявок и черновики счетов",
  "description": "Заявка → колонки со смысловыми типами → журнал событий",
  "kind": "showcase",
  "status": "demo",
  "tech": ["kanban@1", "table@1", "журнал"],
  "static": "public/experiments/backbone",
  "routes": [
    { "mount": "/api/backbone", "module": "server/routes/backbone" },
    { "mount": "/api/backbone-public", "module": "server/routes/backbonePublic" }
  ],
  "admin": true
}
```

Чтобы перевести проект на витрину, достаточно поменять `kind` на `showcase` и
пересобрать профиль — код и папки не переезжают.

### 4.5 Реестр

`catalog/public.json` собирается из манифестов скриптом:

```bash
npm run catalog:build
```

Он заменяет `registry.json` и содержит только `experiment` + `showcase`. Клиенты в публичный каталог не попадают никогда — они живут в `catalog/clients.json`, который не коммитится в публичный репозиторий.

## 5. Загрузчик модулей вместо main.js

### 5.1 Проблема

Сейчас:

```js
// main.js
app.use('/api/summarize', summarizeRoutes);
app.use('/api/extract-audio', extractAudioRoutes);
app.use('/api/notes-export', notesExportRoutes);
// ... ещё 12 строк
```

Чтобы собрать витрину без экспериментов, нужно править код. Это ломает саму идею профилей.

### 5.2 Решение

```js
// server/projects.js — фактическая реализация
const PROFILES = {
  full: { kinds: ['experiment', 'showcase', 'client'], platform: ['auth', 'llm', 'catalog'] },
  lab: { kinds: ['experiment'], platform: ['auth', 'llm', 'catalog'] },
  showcase: { kinds: ['showcase'], platform: ['auth', 'llm'] },
};

function select(projects, profile) {
  const p = parseProfile(profile);           // 'client:<id>' → kinds ['client'] + client
  return projects
    .filter((project) => p.kinds.includes(project.kind))
    .filter((project) => p.name !== 'client' || project.client === p.client)
    .sort((a, b) => a.order - b.order || a.id.localeCompare(b.id));
}

function mount(app, { profile = 'full', projects = load() } = {}) {
  const parsed = parseProfile(profile);
  for (const key of parsed.platform) {
    app.use(PLATFORM[key].mount, require(path.join(ROOT, PLATFORM[key].module)));
  }
  for (const project of select(projects, profile)) {
    for (const route of project.routes) {
      app.use(route.mount, require(path.join(ROOT, route.module)));
    }
  }
}
```

`main.js`:

```js
const projects = require('./server/projects');

app.use('/api', identityMiddleware);
const active = projects.mount(app, { profile: config.profile });
```

Платформенные маршруты (`auth`, `llm`, `catalog`) перечислены в `PLATFORM` и не принадлежат проектам. Профиль решает, какие из них монтировать.

### 5.3 Совместимость

`PROFILE=full` должен вести себя **ровно как сейчас**. Это проверяется тестом:

```js
// test/projects.test.js
test('full монтирует те же роуты, что и до рефакторинга', () => {
  const expected = ['/api/summarize /server/routes/summarize', /* ... 15 пар */];
  const active = projects.mount(express(), { profile: 'full' });
  assert.deepEqual(active.mounts.map((m) => `${m.mount} ${m.module}`).sort(), expected);
});
```

Рефакторинг без изменения поведения — обязательное условие. Иначе потом не отличить «сломал профиль» от «сломал проект».

Статика на этом шаге **не фильтруется**: `PROFILE=showcase node main.js` всё ещё отдаёт `public/experiments/*`. Это закрывается в неделе 2 сборкой `dist/showcase` (§6), а не рантаймом.

## 6. Профили сборки

### 6.1 Структура

```
profiles/
  full.mjs
  lab.mjs
  showcase.mjs
  client-backbone.mjs
  client-<id>.mjs
```

### 6.2 Обобщение MANIFEST

`build-shop.mjs` уже умеет: копировать файлы и каталоги, исключать, править текст, собирать подмножество миграций и зависимостей. Нужно вынести это в `scripts/build-profile.mjs`, а `MANIFEST` превратить в профиль.

```js
// profiles/showcase.mjs
export default {
  name: 'showcase',
  entry: 'server/showcase.js',
  include: (p) => p.kind === 'showcase' && p.status !== 'archived',
  deny: [
    'server/services/idea-radar',
    'server/services/pain-radar',
    'server/services/automation-leads',
  ],
  files: [
    'server/config.js',
    'server/db.js',
    'server/projects.js',
    'server/middleware/identity.js',
    'server/routes/auth.js',
    'public/style.css',
    'public/theme.js',
    'public/auth.js',
  ],
  dirs: ['server/components', 'public/c'],
  migrations: (project) => project.migrations ?? [],
  dependencies: ['bcrypt', 'cookie-parser', 'dotenv', 'express', 'pg'],
};
```

Запуск:

```bash
npm run build:profile -- showcase --out dist/showcase
npm run build:profile -- client:krepezh --out ../client-krepezh/app
```

`build-shop.mjs` остаётся как тонкая обёртка над `client:backbone`, пока идёт переход.

### 6.3 Тест границы

Главная защита от протечки — не ревью, а тест. Он уже есть для магазина:

```
test/shop-build.test.js
```

Для каждого профиля:

```js
test('showcase не тянет experiment-модули', () => {
  const graph = requireGraph(buildDir, entry);
  for (const denied of profile.deny) {
    assert.ok(!graph.has(denied), `showcase тянет ${denied}`);
  }
});
```

Без этого теста профиль деградирует за пару месяцев: кто-нибудь добавит общий импорт, и витрина потащит радары.

### 6.4 Профили и базы

| Профиль | База | Миграции |
|---|---|---|
| `full` | `vesha` (dev) | все |
| `lab` | `vesha_lab` | все экспериментальные |
| `showcase` | `vesha_show` | только миграции showcase-проектов |
| `client:<id>` | `<id>` | только миграции этого клиента |

Миграции отбираются по манифестам, а не по общему списку. Это ключевое: лабораторная миграция физически не должна попадать в базу витрины.

## 7. Репозитории

### 7.1 Этапы

| Этап | Структура | Когда |
|---|---|---|
| Сейчас | всё в `vesha`: `projects/`, `catalog/`, `profiles/` | 0–1 клиент |
| 2-й клиент | `@vesha/core` как npm-пакет в реестре GitFlic; `vesha` и `client-*` зависят от него | появился второй клиент |
| 5+ клиентов | multi-tenant SaaS вместо N копий | если модель — хостинг, а не передача |

### 7.2 Почему не дробить сразу

- 22 эксперимента в отдельных репозиториях — это 22 CI, 22 README, 22 обновления зависимостей;
- общий UI-кит, auth и LLM-шлюз всё равно придётся синхронизировать;
- один разработчик — цена координации выше выгоды изоляции.

Дробить имеет смысл только то, что **передаётся наружу**.

### 7.3 Клиентский репозиторий

```
client-<id>/
  app/              # сгенерированный профиль (build:profile)
  overrides/        # логотип, тексты, .env.example
  upstream.json     # коммит vesha, из которого собрано
  sync.sh           # пересборка + diff
  README.md         # как поднять, как обновить
```

`sync.sh`:

```bash
#!/usr/bin/env bash
set -euo pipefail
VESHA=${VESHA_PATH:-../vesha}
ID=${1:?usage: sync.sh <client-id>}

(cd "$VESHA" && npm run build:profile -- "client:$ID" --out "../client-$ID/app")
(cd "$VESHA" && git rev-parse HEAD) > upstream.json
git add -A
git commit -m "sync from vesha@$(cat upstream.json)"
```

Обновление — осознанный diff, а не «перезалил и надеюсь».

### 7.4 Границы внутри vesha

Даже в одном репозитории нужны жёсткие правила:

- `platform/` не знает о конкретных проектах;
- `projects/<id>/` не импортирует другой `projects/<other>/`;
- общий код — только через `platform/`.

Проверять тестом на require-граф, как в `shop-build.test.js`. Иначе монолит через год станет неразбираемым.

## 8. Серверы: зоны, а не проекты

### 8.1 Ограничение, от которого всё зависит

**1 vCPU / 1 GB — это только Caddy и статика.**

| Компонент | RSS |
|---|---|
| ОС + systemd | 200–300 MB |
| Caddy | 30–50 MB |
| Node-приложение | 60–120 MB |
| Postgres | 80–150 MB |
| Пик сборки | 300–800 MB |

Node + Postgres + ОС на 1 GB уже дают ~500 MB и ноль запаса. Ставить туда приложение с базой — гарантированные OOM.

### 8.2 Зоны

| Зона | Размер | Что | Можно ронять |
|---|---|---|---|
| `edge` | 1/1 | Caddy: TLS, статика витрины, rate limit | нет |
| `lab` | 2/2 | эксперименты + `vesha_lab` | да |
| `showcase` | 2/4 | витрина + демо с бэкендом + `vesha_show` | нет |
| `clients` | 2/4 (или 1/2 на клиента) | клиентские деплои | нет |
| `ci` | 2/2 | GitFlic/GitHub runner, preview | да |

### 8.3 Три варианта

**Эконом (2 VDS):**

- 1/1 — edge: Caddy + статика.
- 2/4 — lab + showcase + Postgres, разделение контейнерами, базами и лимитами.

Дешево, но общая точка отказа: упал процесс — упало всё.

**Изоляция (4 VDS):**

- 1/1 edge, 2/2 lab, 2/4 showcase, 2/4 clients.

Лабораторию можно перезагружать в любой момент, витрина и клиенты живут отдельно.

**Передача (3 VDS + клиентские):**

- 1/1 edge, 2/2 lab, 2/4 showcase;
- каждый клиент — свой VDS, который платит клиент.

Рекомендация: начать с «эконома», перейти на «изоляцию» с первым платящим клиентом. Четыре машины «на всякий случай» — это +1500–2500 ₽/мес за простой.

### 8.4 Маршрутизация

Не делать один центральный прокси на все зоны: лишний хоп, лишняя точка отказа, нужна приватная сеть.

Проще: **DNS указывает субдомен на нужную машину, на каждой машине свой Caddy**.

```
vesha.pro          → IP showcase
lab.vesha.pro      → IP lab
<id>.vesha.pro     → IP showcase
<client>.vesha.pro → IP clients
```

Wildcard-сертификат тогда не нужен: каждый Caddy выпускает HTTP-01 только на свои хосты.

Центральный edge добавлять позже — когда понадобится единый WAF, лимитер или ботозащита.

### 8.5 Что где запускать

| Зона | Процесс | База | Секреты |
|---|---|---|---|
| lab | `PROFILE=lab node main.js` | `vesha_lab` | dev-ключи, можно общие |
| showcase | `PROFILE=showcase node main.js` | `vesha_show` | demo-режим, квоты |
| clients | `PROFILE=client:<id> node main.js` | своя | только ключи клиента |

Секреты разных зон не пересекаются. Ключ лаборатории не должен лежать в окружении витрины.

## 9. Домен и адреса

| Что | Адрес | Индексация |
|---|---|---|
| Витрина | `vesha.pro` | да |
| Эксперименты | `vesha.pro/lab/` | `noindex`, за basic auth |
| Showcase без бэкенда | `vesha.pro/<id>/` | да |
| Showcase с бэкендом | `<id>.vesha.pro` | да |
| Клиент (демо) | `<client>.vesha.pro` | `noindex` |
| Клиент (прод) | домен заказчика | да |

Технические детали:

- основной домен — **`vesha.pro`**, ASCII: punycode-слой в конфигах не нужен;
- `веша.рф` остаётся на старом сервере (`212.57.115.30`) как legacy, новый стек его не использует;
- старые ссылки `/experiments/<id>/` не ломать сразу: 301 на `/lab/<id>/` на один релиз;
- витрина должна быть отдельным профилем, а не страницей внутри эксперимента.

Сейчас `public/index.html` — заглушка со ссылкой «Эксперименты →». Это и есть точка, куда встанет showcase-профиль.

### 9.1 Nginx

Текущая схема (`docs/deploy-linux-vds.md`) остаётся рабочей. Меняется только то, что на разных машинах разные `server_name` и разные upstream-порты:

```nginx
# showcase
server_name vesha.pro;
location / { proxy_pass http://127.0.0.1:3000; }

# lab
server_name lab.vesha.pro;
auth_basic "Vesha lab";
auth_basic_user_file /etc/nginx/.htpasswd;
location / { proxy_pass http://127.0.0.1:3001; }
```

`TRUST_PROXY=true` обязателен на всех зонах — иначе лимиты видят адрес nginx.

## 10. Продвижение experiment → showcase

Без формального гейта витрина через полгода снова станет свалкой.

### 10.1 Чеклист

1. Открывается **без входа**.
2. Нет ошибок в консоли и 404 на ассеты.
3. Работает на телефоне, без горизонтальной прокрутки.
4. Есть описание в одну фразу и скриншот 800×500.
5. Демо-данные, а не реальные ПДн.
6. Платные API — в demo-режиме или с дневной квотой.
7. Главный экран отвечает < 3 с.
8. Указан стек и ссылка на исходники (если публичные).

### 10.2 Скрипт

```bash
npm run promote -- summarize
```

Что делает:

1. проверяет наличие обязательных полей в манифесте;
2. дёргает smoke-тест: HTTP 200, консоль чистая (playwright уже есть в зависимостях);
3. меняет `kind` на `showcase`, ставит `promotedAt`;
4. пересобирает `catalog/public.json`;
5. запускает `build:profile showcase`.

Обратный ход:

```bash
npm run demote -- summarize
```

Ставит `status: archived`. Плитка исчезает из витрины, но остаётся в lab.

### 10.3 Что не идёт на витрину

Не все эксперименты должны стать showcase. Внутренние инструменты — `pain-radar`, `idea-radar`, `automation-leads` — на витрине бессмысленны: они собирают данные для вас, а не показывают навык.

Это нормально. Витрина — не «все проекты», а «лучшие демонстрации».

### 10.4 Статусы на витрине

| Статус | Значит | Как выглядит |
|---|---|---|
| `live` | работает, публично | кнопка «Открыть» |
| `demo` | ограниченный режим | бейдж «демо» |
| `archived` | только исходники | без кнопки |

Честные статусы лучше, чем 20 битых ссылок.

## 11. Клиентские проекты

### 11.1 Две модели

| | Хостинг у вас | Передача |
|---|---|---|
| Где живёт | ваш VDS | VDS заказчика |
| Кто платит железо | вы (входит в тариф) | заказчик |
| Ответственность за аптайм | ваша | их |
| 152-ФЗ | вы оператор | заказчик |
| Обновления | вы | вы по договору |
| Маржа | подписка | разовая + поддержка |

Для «под ключ» по умолчанию рекомендую **передачу**: вы разворачиваете, настраиваете, отдаёте доступы, дальнейшее железо — на заказчике. Это снимает аптайм и ПДн.

Хостинг — платная опция. И тогда **отдельный VDS на клиента**, а не соседний контейнер.

### 11.2 Что уже готово

- `docs/backbone-handover.md` — модель передачи;
- `scripts/build-shop.mjs` — сборка самодостаточного подмножества;
- `shop.js` — отдельная точка входа с собственным кабинетом.

Осталось обобщить `shop` на `client:<id>`.

### 11.3 Что входит в передачу

- репозиторий `client-<id>` с исходниками профиля;
- `docker-compose.yml` или systemd-юнит;
- `.env.example` с описанием каждой переменной;
- список миграций, которые надо накатить;
- README: установка, обновление, резервное копирование;
- инструкция по переносу на другую машину.

### 11.4 Данные

Клиентская база не должна жить на машине с лабораторией. Причины:

- 152-ФЗ: оператор ПДн — заказчик, а не вы;
- случайный `DROP` в лаборатории не должен касаться клиента;
- при передаче достаточно отдать дамп и доступы.

## 12. Порядок работ

### Неделя 1 — каталог и загрузчик

Цель: внедрить манифесты, не меняя поведения.

1. `projects/<id>/project.json` для всех записей каталога — **15**, а не 22: папки `ui-*` и `ocenka-site-v2` — подстраницы `showcases` и `ocenka-site`, отдельных записей у них нет.
2. `server/projects.js` + `mount(app, { profile })`.
3. `main.js` = `PROFILE=full` (по умолчанию).
4. Тест: `full` монтирует ровно те же 15 API, что и раньше.
5. `npm run catalog:build` собирает `public/experiments/registry.json` из манифестов; `catalog:check` ловит расхождение.

Сделано: манифесты, `server/projects.js`, `scripts/build-registry.mjs`, `test/projects.test.js`; `main.js` больше не содержит `app.use('/api/...')`.

Критерий готовности: `npm test` зелёный (единственный красный — `superNotes` без локального Postgres), поведение не изменилось.

### Неделя 2 — showcase-профиль

1. `profiles/showcase.mjs` + `server/showcase.js`.
2. Отобрать 4–6 проектов, прошедших чеклист §10.
3. `npm run build:profile -- showcase`.
4. Тест границы require-графа.
5. Поднять showcase-зону, переключить `vesha.pro`.
6. `public/index.html` заменить на витрину из каталога.

Критерий: витрина открывается без входа, экспериментов на ней нет.

### Неделя 3 — lab отдельно

1. `PROFILE=lab` на отдельной машине.
2. `vesha_lab` — отдельная база.
3. Basic auth на весь lab.
4. `noindex`.
5. 301 со старых `/experiments/*` на `/lab/*`.

Критерий: падение лаборатории не влияет на витрину.

## 13. Антипаттерны

| Антипаттерн | Почему плохо |
|---|---|
| Один деплой на всё | эксперимент роняет витрину и клиента |
| Одна база на всё | миграция лаборатории ломает клиентские данные |
| `main.js` с 15 require | нельзя собрать профиль без правки кода |
| Автоматически показывать всё из реестра | витрина превращается в свалку |
| Клиент на вашем VDS «пока что» | через год это продакшн с ПДн |
| 22 репозитория сразу | 22 CI на одного человека |
| Копировать код в клиентский репозиторий руками | расходятся за месяц |
| 1 CPU / 1 GB под Node + Postgres | OOM при первой же сборке |
| Нет теста границы профиля | через полгода витрина тянет радары |
| Секреты лаборатории в окружении витрины | утечка ключей |

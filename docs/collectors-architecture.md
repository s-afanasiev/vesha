# Сборщики — общий каркас внешних источников

План территории «сборщики» (`collectors`): одна дверь Vesha в чужой мир источников — RSS-ленты, гос-API, карты, каталоги, поисковые запросы. Сборщики опрашивают ресурсы, хранят сырьё и отдают его радарам; интерпретация остаётся у радаров: радар идей превращает публикации в сдвиги, радар болей — отзывы в боли, будущие срезы — предложения и спрос в знаменатели.

Статус: **принято по ключевым развилкам** (02.10.2026): сырьё у каркаса (В1), ступень 1 выполнена. Остальные ступени — предложение. Потребители: [idea-radar-architecture.md](idea-radar-architecture.md) (уже собирает ленты) и [pain-radar-architecture.md](pain-radar/pain-radar-architecture.md) (фаза 2 — карты). Канон — [oop-principles.md](oop-principles.md).

## Зачем одна дверь

- **Чужой мир опознан обоими радарами независимо.** Разбор pain-radar (Ш1): «источники сигнала — меняются все пять признаков: свой словарь, чужой темп, чужая единица, истина у них, причина изменения — их релизы. Вывод канона однозначен: адаптеры». Idea-radar вынес этот мир в адаптеры с первого дня. Второй потребитель уже есть, значит контракт — не «на будущее» (П13, П34): механика сбора написана для idea-radar (`http.js`, `text.js`, `states.js`, жизненный цикл опроса, реестр адаптеров) и планировалась к копированию в pain-radar (`collector.js`, `sources/twogis.js`). Дублирование оправдывает выделение.
- **Карты дорогие, ленты дешёвые, терпение у всех разное — но каркас один.** Троттлинг, потолки, дедлайны, «источник сломался», сырьё для повторного разбора — одно и то же для RSS и для 2ГИС; домена в этом ноль.

## Почему не отдельный сервис (пока)

| | Территория в Vesha (предложение) | Отдельный сервис |
|---|---|---|
| Деплой | общий | второй процесс, очереди, healthchecks |
| Транзакции | одна БД, ссылочная целостность | через API, консистентность руками |
| Вызов | обычная функция | HTTP + аутентификация сервиса |
| Когда оправдан | сейчас | при условиях выноса ниже |

Вынос отнимает общую транзакцию и единый деплой — ступень 5, способность, а не цель (П33). Дверь проектируется выносимой сразу: каркас — обычные функции с контрактом; при выносе к ним добавляется тонкий HTTP-адаптер, без переписывания (П9: транспорт тонкий).

Условия выноса (любое из):
1. второй процесс-потребитель (например, отдельный воркер браузеров);
2. у сбора свой ресурсный цикл — пул прокси/браузеров с арендой и здоровьем (П22);
3. поломки сбора стали главной причиной падений общего деплоя;
4. радары разъехались по инстансам.

## Ш0–Ш1: рез по мирам (П30)

Ш0: «Сборщики опрашивают внешние ресурсы по расписанию и по запросу, сохраняют сырьё и отдают его радарам; каждый радар интерпретирует сырьё по-своему».

| Мир | Что внутри | Темп | Дефицит |
|---|---|---|---|
| чужой мир | RSS, pravo, trudvsem, 2ГИС, Яндекс Карты, Вордстат | минуты → кварталы | терпение источника, IP-репутация |
| каркас (сбор) | HTTP с лимитами, жизненный цикл опроса, троттлинг, реестр ресурсов, сырьё | минуты | окно сбора |
| интерпретаторы | idea-radar (сдвиги), pain-radar (боли), срезы | дни → недели | LLM-вызовы |

Границы через незнание (каждая строка — греп):
- в каркасе не находится «сдвиг», «боль», «ниша», «публикация», «отзыв», «idea», «pain»;
- радары не знают, как устроена страница ресурса — разбор живёт внутри адаптера (Б2 разбора pain-radar);
- адаптер не знает, кто и как интерпретирует его поток.

## Контракты источников — два, честно

| Контракт | Для кого | Форма |
|---|---|---|
| ленты `pages(resource, ctx)` | rss, pravo, trudvsem, будущие ленты | асинхронный поток пачек от новых к старым; раннер останавливается на пачке без нового |
| карточные `listing(ref)` + `reviews(ref, since, signal)` | 2ГИС, Яндекс Карты | карточка + поток отзывов от новых к старым, до `since` (Б2 pain-radar) |

Общий низ каркаса: `fetchText` / `fetchJson` (таймаут, потолок байт, кодировки), `SourceHttpError`, нормализация текста и дат, алфавит состояний опроса, бюджет-контекст (дедлайн → таймаут страницы → потолок байт, П23), троттлинг **на ресурс для всех потребителей**, правило «источник сломался» (N одинаковых ошибок подряд — пауза с причиной, Б5), похожесть записей (`similarity.js`: триграммы — потребители: склейка перепечаток idea-radar, дедупликация отзывов pain-radar с двух карт).

## Данные: главная развилка — где живёт сырьё

- **В1 — принято (02.10.2026): сырьё у каркаса.** `collector_items` — сырой факт: ресурс, external_id, url, fetched_at, content_hash, payload jsonb. Радар хранит интерпретацию со ссылкой на item. Выигрыш: повторный разбор без обращения к источнику — критично для карт, где повторный парсинг = риск бана; одна копия страницы кормит боли, карточные флаги (В1 pain-radar) и срез предложения (И7 idea-radar); переразметка новой моделью — без нового парсинга (П26: производное пересчитывается из истины).
- В2 (хранение остаётся у радаров, каркас — только механика) — отклонён: каждая карточка парсилась бы заново каждым потребителем.

Таблицу `collector_items` создаём при ступени 2 (фаза 2 pain-radar). Переход idea-radar на ссылки — мягко (П32): писать в оба места → читать из нового → снос старого по сроку.

### Реестр ресурсов

Механика — у каркаса, доменные подсказки — у радаров:

```text
collector_resources   id, slug UNIQUE, kind (gov | news | events | jobs | initiatives | serendipity
                      | maps | catalog | search), adapter, settings jsonb,
                      poll_every_min, min_interval_sec, page_timeout_ms, throttle_ms,
                      active_from, active_to                    -- период, держит каркас
```

Радарные подсказки (рубрика, ниша-хинт, регион, роль `local_signal | lead_indicator` — И5 idea-radar) остаются в `idea_radar_sources` со ссылкой на ресурс; pain-radar держит свои. Один ресурс могут читать два радара — темп и лимиты у каркаса общие, каждый бьёт по источнику один раз.

## Ступени

| Ступень | Что | Когда |
|---|---|---|
| 1 | `http.js`, `text.js`, `states.js`, `adapters/{rss,pravo,trudvsem}` → `server/services/collectors/`; idea-radar импортирует оттуда; поведение и тесты не меняются | **сделано 02.10.2026** |
| 2 | карточный контракт + реестр `collector_resources` + троттлинг per-resource + решение В1/В2 + разведка 2ГИС (Б11) | фаза 2 pain-radar |
| 3 | ресурсы спроса и предложения: Вордстат, каталог 2ГИС по нише (срез предложения, И7 idea-radar) | после фазы 2 |
| 4 | вынос в отдельный сервис — только по условиям выше | по поводу |

## Критерии

- Греп каркаса по доменным словам пуст; каркас запускается на моках без внешних систем (П9).
- pain-radar фаза 2 подключает первый карточный ресурс, не написав ни одной новой обёртки таймаутов/лимитов.
- При В1: повторный разбор карточки читает сырьё, обращения к источнику нет.

## Открытые вопросы

1. `idea_radar_sources`: мигрировать реестр целиком в каркас или оставить радарным профилем со ссылкой на ресурс? (рекомендация: профиль со ссылкой)
2. Расписание: таймер idea-radar остаётся своим или при ступени 2 переезжает в каркас — один планировщик на все ресурсы?
3. Яндекс Карты: браузер/прокси/антибот — вопрос разведки pain-radar (Б11); каркас получает его вывод как настройки ресурса.

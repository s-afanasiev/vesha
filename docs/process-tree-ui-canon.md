# Архитектурный стандарт гомоморфного интерфейса: Process-Tree и UI-Mirroring

Настоящий стандарт формализует парадигму **автоматической генерации пользовательского интерфейса (Zero-Manual-Frontend)** как детерминированной проекции дерева вычислительных процессов. Документ заменяет фрагментарные описания («писанину») строгим нормативным регламентом для промышленных систем.

---

## 1. Концептуальный базис: Принцип гомоморфизма UI и Домена

В традиционной архитектуре Frontend и Backend разделены искусственным семантическим барьером:
- Backend реализует граф исполнения.
- Frontend вручную дублирует структуры данных, агрегирует состояния, эмулирует роутинг и верстает экраны под каждый бизнес-сценарий.

В парадигме **UI-Mirroring**:
> **Пользовательский интерфейс не проектируется как отдельное приложение.** UI представляет собой **гомоморфную проекцию (Homomorphic Projection)** графа живого доменного процесса. Визуальное отображение полностью выводится из топологии связей (`parentNodeId`), жизненного цикла (`status`) и семантического типа (`nodeType`) вычислительных узлов. Разнообразие интерфейса достигается не переписыванием разметки, а применением подключаемых **визуальных тем и адаптеров отображения (Skins / Render Rules)**.

---

## 2. Архитектурный пайплайн трансформации

Сквозной контур состоит из 4 изолированных уровней ответственности с однонаправленным потоком фактов:

```
[Уровень 0: Доменный объект (Step / Job)]
   │   Регистрация узла (createNode) и эмиссия жизненного цикла (start / update / complete / fail)
   ▼
[Уровень 1: In-Memory Process-Tree Store]
   │   Материализация снапшота (nodesById) + Единая локальная шина (process-tree-event)
   ▼
[Уровень 2: Проекционный слой (UiMirroringRuntime)]
   │   Нормализация в Read-Model: расчет иерархии (lineage, depth, children), stats, displayStatus
   ▼
[Уровень 3: Транспорт и Терминал отображения (WebSocket ➔ Generic Skin Renderer)]
   │   Трансляция дельт/снапшота ➔ декларативный рендер по nodeType и payload
```

## 3. Спецификация контрактов и моделей данных

### 3.1. Канонический контракт узла исполнения (Raw Process Node)
Каждый инструментированный шаг процесса на Backend регистрирует себя со следующей инвариантной схемой:

```typescript
interface RawProcessNode<TPayload = Record<string, unknown>> {
  nodeId: string;              // Глобальный UUID экземпляра шага
  parentNodeId: string | null; // Идентификатор структурного родителя в графе
  nodeType: string;            // Семантический классификатор типа (имя доменного класса)
  title: string;               // Человекочитаемая метка конкретного запуска
  status: NodeLifecycleStatus; // Машина состояний жизненного цикла
  payload: TPayload;           // Смысловой контекст шага (входы, промежуточные вехи, артефакты, ошибки)
  createdAt: string;           // ISO 8601 метка рождения
  updatedAt: string;           // ISO 8601 метка последней мутации
}

type NodeLifecycleStatus = 
  | 'created' 
  | 'started' 
  | 'running' 
  | 'completed' 
  | 'failed';
```

### 3.2. Handle управления жизненным циклом (`ProcessNodeHandle`)
Интерфейс, через который доменный объект транслирует свои изменения в мир:
- `start(payload?: object): void` — фиксация перехода в активную фазу исполнения.
- `update(payload: object): void` — публикация промежуточной динамики (прогресс, смена стадии).
- `complete(payload: object): void` — фиксация успешного завершения с итоговым результатом.
- `fail(error: Error | object, payload?: object): void` — фиксация аварии с сохранением контекста.

### 3.3. Проекционная модель чтения (UI Projected Node)
Слой `UiMirroringRuntime` обогащает плоский узел метаданными отображения и иерархией:

```typescript
interface ProjectedTreeNode<TPayload = Record<string, unknown>> extends RawProcessNode<TPayload> {
  displayStatus: 'pending' | 'running' | 'success' | 'danger';
  statusTone: 'neutral' | 'info' | 'positive' | 'critical';
  depth: number;                // Глубина вложенности (0 для корней)
  lineage: string[];            // Цепочка родительских идентификаторов
  hasChildren: boolean;
  children: ProjectedTreeNode[]; // Материализованные дочерние узлы
  updateCount: number;
}
```

## 4. Нормативные инварианты Process-Tree

1. **Инвариант независимости транспорта (Transport Decoupling):**
   `ProcessTreeStore` не имеет зависимостей от HTTP, WebSocket, логгеров или UI. Store выступает исключительно как in-memory snapshot-хранилище и локальный Event Publisher. Интеграция с внешним миром реализуется через внешние мосты-адаптеры (`ProcessTreeLoggerBridge`, `WebSocketBridge`).
2. **Инвариант структурной адресации (No Routing via Parents):**
   Ссылка `parentNodeId` задает топологию графа владения, но **не является маршрутом передачи сообщений**. Дочерний объект не делегирует свои события вверх по цепочке через родителей; он публикует факт напрямую в единый store.
3. **Инвариант истинности последнего состояния (Terminal Evaluation Invariant):**
   Итоговый статус составного узла (оркестратора множества) вычисляется строго по **последнему актуальному состоянию каждого его листового потомка**, а не по исторической сумме попыток. Ошибки ранних попыток, устраненные последующими ретраями, не должны переводить составной узел в терминальный `failed`.
4. **Инвариант диагностического зеркала (Diagnostic Mirroring Invariant):**
   Аномалия отображения в UI признается первичной гипотезой о дефекте семантики жизненного цикла на Backend. Если визуальный блок "завис", "моргнул" или отображает некорректный статус — запрещается маскировать дефект версткой на фронтенде; ошибка локализуется и устраняется в доменном коде эмиттера.

## 5. Архитектура визуальных тем (Skin Architecture / UI Render Registry)

Фронтенд сводится к единственному универсальному контейнеру (Generic Shell), использующему реестр рендереров:

$$R: (\text{nodeType}, \text{status}, \text{payload}) \longrightarrow \text{Component}$$

1. **Рендерер по умолчанию (Default Structural Skin):**
   Универсальное иерархическое дерево (аккордеон/граф), отображающее `title`, статус-бейдж (`statusTone`), прогресс и JSON-инспектор `payload`. Любой вновь созданный бэкенд-класс визуализируется немедленно без написания фронтенд-кода.
2. **Семантические специализированные скины (Type-Specific Skins):**
   Если узел имеет тип, требующий специализированного визуального представления (например, `OneScreenshot` требует тега `<img>`, `AudioTranscribe` — звуковой дорожки, `DiffViewer` — side-by-side текста), создается изолированный визуальный компонент, регистрируемый по ключу `nodeType`.
3. **Глобальные скины оформления (Atmospheric Skins):**
   Цветовые схемы, плотность интерфейса (compact/spacious), анимации переходов и стили контейнеров переключаются глобально как CSS-переменные или токены тем (принцип скинов Winamp) без затрагивания логики проекции.

## 6. Регламент разработки нового функционального модуля

При создании любой новой доменной подсистемы инженер обязан следовать 3 шагам:
1. **Декомпозиция на классы-глаголы:** Реализовать конвейер или сценарий как дерево композиции (П1, П10, П12).
2. **Инструментирование жизненного цикла:** Каждый объект принимает `treeContext`, регистрирует свой `processNode` и вызывает методы жизненного цикла (`start/update/complete/fail`).
3. **Отказ от ручной верстки UI:** Проверить работоспособность модуля через стандартный экран `process-tree`. Разработка специализированного скина допускается только при наличии уникальных требований к отображению доменного `payload`.

## 7. Поправки 13.10.2026 и реализация в Vesha

Канон сверен с [oop-principles.md](oop-principles.md) и реализован в `server/process-tree/` (хранилище и проекция), `server/components/tree.js` (контракт `tree@1`) и `public/c/tree.js` (скин по умолчанию). Первый потребитель — эксперимент «Кому автоматизировать» ([automation-leads-architecture.md](automation-leads-architecture.md)). Где реализация расходится с разделами 1–6, действует этот раздел.

1. **Статусы с именованными исходами (П38, П24).** `created | running | waiting | completed | skipped | failed | cancelled` вместо пяти статусов §3.1: «пусто с причиной» — самый частый честный исход, и в пять статусов он ложится либо ложным успехом, либо ложной ошибкой. `started` слит с `running`. Исход на границе узла — `outcome: { ok, code, detail }`. Терминальный статус окончателен: поздние вызовы ничего не меняют.
2. **Узел едет в контексте запуска (П7, П37).** Шаг §6.2 «каждый объект регистрирует свой processNode» заменён: узел открывает обёртка `node.step({ nodeType, title }, work)`, работа получает его аргументом и не знает хранилища. Исключение ставит `failed` и летит дальше — где ошибка становится результатом, решает вызывающий (П24).
3. **Гранулярность — лестница единиц (П13, П17).** Узел — единица с судьбой: прогон → группа → место → замер. HTTP-запросы и отзывы — счётчики в payload, а не узлы. Хранилище держит потолок узлов на прогон (переполнение видно у корня) и вытесняет старые завершённые прогоны, не трогая идущие.
4. **Свёртка глубины в проекции.** Кроме `stats` (дети по статусам) проекция считает `deep` — исходы внуков и глубже по виду узла. Без неё у группы из 150 мест видно «✓ 150», а 68 пропусков «сайта нет» прячутся уровнем ниже.
5. **Payload — канал наружу.** Ключи с секретами режутся на входе; экран дерева — служебный, за `requireAdmin` эксперимента.
6. **Транспорт — опрос, а не WebSocket.** Как у остальных рендереров Vesha: `GET /tree?since=<version>` отвечает `unchanged`, если ничего не менялось. WebSocket — когда опрос перестанет справляться.
7. **Два зеркала, а не одно.** Дерево процессов отвечает «что произошло при прогоне»; экраны сущностей (лиды, воронка) — проекции результата на тех же контрактах (`table@1`, `kanban@1`). «Zero-Manual-Frontend» честно выполним для служебных экранов и экранов сущностей; продуктовый экран — специализированный скин.
8. **Пока не сделано.** Хранилище только в памяти: мост вех в Postgres (прогоны переживают рестарт, незавершённый показывается прерванным) — шаг 2 automation-leads. Ретраи как новые попытки узла (инвариант §4.3) — когда появится первый узел с повтором.

# Кому автоматизировать — архитектура (`automation-leads`)

Эксперимент для задачи №1: найти в нише города компании, которым я как программист могу предложить автоматизацию, и показать, что именно предложить и почему. Задача №2 — идея молодому предпринимателю — живёт в радарах спроса и идей и сюда не тянется: смешение двух целей в одном приложении дало размытую реализацию (решение 13.10.2026).

Статус: **шаг 1 сделан** (13.10.2026) — сквозной прогон на файлах первого прогона ниши «Крепёж и сантехника, Курск», дерево процессов и UI из спеки. Канон — [oop-principles.md](oop-principles.md), зеркало UI — [process-tree-ui-canon.md](process-tree-ui-canon.md), компоненты — [ui-components.md](ui-components.md). Прототип скриптами — `data/pain-radar-corpus/runs/2026-10-11/` (`niche-collect`, `niche-audit`, `leads-build`, вне git).

## Рассказ (П31)

1. Выбираем нишу и город.
2. Источник отдаёт места ниши; правило рубрик отделяет нишу от рубрики карт.
3. Для каждого места собираются факты трёх видов: карточка (каналы связи, гигиена, масштаб), сайт (каталог, цены, заказ, чат) и свежие отзывы клиентов (сбой процесса с цитатой, ответы владельца).
4. Чистое действие решает, кто лид, что ему предложить и почему, — или почему нет.
5. Сводка показывает, какой продукт нужен скольким местам и с какими доводами: это и есть «ниша автоматизации».
6. Дерево прогона показывает, что реально произошло, включая отрицательные исходы с причиной.

## Белые пятна заполняются по потребности

В перспективе это глобальная база по всем регионам и всем видам организаций. Заполняется она не сразу, а постепенно, по мере потребности: сейчас один регион (Курск) и 2–3 сферы, со временем — больше сфер и регионов. Отсюда правила:

- **Единица роста — разбор «ниша × город».** Новая сфера или регион — запись в `niches.js` и прогон, а не перестройка системы.
- **Пятно видно, а не спрятано (П38).** Таблица ниш — карта покрытия: «не разбиралась» — это честный статус. Место без свежих отзывов — «свежих отзывов нет», а не «сбоев нет»; не проверенный сайт — «не проверяли», а не «нет сайта».
- **Копаем туда, где нужно.** Сферу добавляем, когда у нас есть продукт или клиент, которому она нужна, а не «для полноты». Сырьё карт хранится у каркаса сборщиков (В1 в [collectors-architecture.md](collectors-architecture.md)): одну и ту же карточку можно потом переразметить для другой цели без повторного сбора.

## Продукты

Почти любому слабо автоматизированному бизнесу нужны три базовых инструмента. Мы пишем их как универсальные юниты: сначала сами пользуемся ими для своих продаж, потом предлагаем бизнесам.

| Продукт | Что это | Какие доводы его зовут |
|---|---|---|
| Сайт с каталогом | каталог с ценами и наличием, заказ или резерв с самовывозом | нет сайта, сайт не открывается, нет цен, нельзя заказать; сбои «склад и наличие», «цены», «карточка на картах» |
| Умный ассистент | отвечает в чате сайта и в мессенджере: наличие, цены, часы, подбор, статус заказа (основа — `chat-engine`) | нет мессенджера; сбои «консультация и подбор», «связь и статусы» |
| Канбан-воронка | заявки и заказы на доске со статусами; клиент по ссылке видит этап своей заявки (основа — `kanban@1`) | сбои «очередь и выдача», «доставка и сроки», «связь и статусы» |
| Подбор крепежа — модуль ниши | модуль каталога и ассистента: подбор по параметрам и совместимости (дюбель → саморез, болт → гайка и шайба), линейка 1:1 на экране | предлагается местам с рубрикой «Крепёж»; довод — сбои «консультация и подбор», «склад и наличие» |

Определитель резьбы по фото ([bolt_thread_measure_pwa_plan.md](bolt_thread_measure_pwa_plan.md)) — отдельное приложение для маркетплейсов на весь мир, а не то, что продают одному магазину. Для магазинов крепежа идея упрощена до модуля подбора (решение 13.10.2026).

**Канбан как универсальный юнит.** `kanban@1` уже есть — он вынесен из `chat-engine` (контракт — §2а в ui-components.md). Чтобы внедрять его в сайты клиентов, к шагу 2 контракт нужно ужесточить:

- сборка без глобального `VeshaUI`;
- граница доступа на стороне сайта;
- карточка с подробностями и действиями;
- контракт хранилища (свой SQL или дверь домена);
- журнал переходов: кто, когда, почему;
- **окно статуса для внешней стороны** — одна карточка по ссылке, только чтение.

Первый потребитель с такими требованиями — воронка наших же лидов.

Почему окно статуса обязательно, видно на случае из практики госорганизации. Работодатели подают заявки на субсидию при простое письмом с документами. Письмо не дошло — выплат нет, и обе стороны узнают об этом слишком поздно. Внутренняя доска сотрудников эту аварию не лечит: лечит квитанция отправителю — «получено», «на проверке», «возвращено: причина». Универсален не сам канбан, а форма передачи между сторонами: «отправил и жду» — это состояние со сроком и выходом, а не тишина (разбор — пример 5 в [app-tables-of-contents.md](app-tables-of-contents.md)). Тот же сбой в отзывах — линии «связь и статусы» и «доставка и сроки».

Отсюда и сегмент шире магазинов: учреждения, принимающие заявки (субсидии, справки, обращения). Пока это белое пятно — заполним, когда появится потребность.

## Оглавление (П3)

Точка сборки — `server/services/automation-leads/index.js`:

```js
const tree = new ProcessTreeStore({ keepRoots: 20 })              // вехи прогонов: что реально произошло

const scan = new NicheScan({
  worldOf: (niche) => ({                                          // внешний мир прогона
    source: new NicheFiles(dataDir, niche.files),                 // листинг, карточки, сайты, отзывы
    marking: new RecordedMarking(dataDir, niche.files),           // разметка отзывов (заместитель LLM)
  }),
  places: new Places(),                                           // места ниши: рубрика ≠ ниша
  each: new EachPlace(new PlaceAudit({                            // узел дерева на каждое место (П16)
    card: new CardFacts(),                                        // каналы, гигиена, масштаб
    site: new SiteFacts(),                                        // каталог, цены, заказ, чат
    reviews: new ReviewFailures({ catalog: new FailureCatalog(), freshFrom: '2024-01-01' }),
  })),
  plan: new LeadPlan({                                            // чистое действие: кому, что, почему
    gaps: new DigitalGaps(),
    rule: new LeadRule({ maxBranches: 3 }),
    offers: new OfferCatalog(),
  }),
})

const scans = new Scans({ scan, tree, niches: NICHES })           // хозяин прогонов: start ↔ stop
```

Отличие от наброска 13.10: работы аудита называются `CardFacts` и `SiteFacts`, а не `CardGaps` и `SiteGaps`. Они сообщают факты, а пробелы выводит правило `DigitalGaps` внутри `LeadPlan` (П2: дети сообщают факты, решает родитель; П15: решение отдельно от сбора).

Незнания (проверяются грепом): работы аудита не знают хранилища дерева — узел приходит аргументом (П7, П37); `LeadPlan` не знает про файлы, сеть и дерево; каркас `server/process-tree/` и `server/components/tree.js` не знают доменных слов (П9); источник не знает, кто и как интерпретирует его данные.

## Лестница единиц и исходы

```
NicheScan (прогон «ниша × город»)
├─ Places                 166 найдено → 150 в нише
├─ EachPlace              150 мест проверено · свёртка: сайт ⤼ 68 · отзывы ⤼ 74
│  └─ PlaceAudit × 150    сайт есть · линий сбоя: 2
│     ├─ CardFacts        мессенджера нет · карточка не подтверждена · 1 точка
│     ├─ SiteFacts        skipped no_site | not_audited | completed
│     └─ ReviewFailures   skipped no_fresh_reviews | completed
└─ LeadPlan               лидов 106 (со сбоем 22, по пробелам 84) · отказ 44
```

Отрицательные исходы — именованные (П38): `no_card`, `no_site`, `not_audited`, `no_fresh_reviews`; неразмеченный отзыв считается отдельно («не размечено N»), а не как «сбоев нет». Неудача одного места — строка итога, а не авария прогона (П24). Остановка — действие «Остановить» в той же таблице, где «Разобрать» (П39); прогон по `AbortSignal` уходит в `cancelled`.

## Правило лида и балл

- **Сеть — отказ первым:** больше 3 точек в городе или «сеть …» в описании 2ГИС — у сети своя IT-служба.
- **Сильный лид** — есть сбой процесса в свежих отзывах клиентов; **слабый** — только цифровой пробел, который закрывает наш продукт; иначе отказ «доводов нет».
- **Балл разложен на три оси:** боль (линии сбоя × 2), пробел (нет сайта 2, прочие пробелы продукта 1, гигиена карточки 0), досягаемость (реклама в 2ГИС +1, ответы владельца на отзывы +1 — читает отзывы, довод из них до него дойдёт).
- Справочник сбоев — коды «Радара спроса» v2 (одна разметка, своя интерпретация, П41). Отношение персонала, уровень цен и брак не считаются сбоем процесса: софт их не чинит.

## UI — проекции, а не вёрстка

Страница `public/experiments/automation-leads/` только монтирует спеку `server/services/automation-leads/pages.js` через boot@1. Своего фронтенд-кода у эксперимента нет:

| Блок | Контракт | Что видно |
|---|---|---|
| Ниши | `table@1` + действия «Разобрать» / «Остановить» | карта покрытия: состояние, мест, лидов, когда разобрана |
| Лиды | `table@1` | вердикт, балл, что предложить, модуль ниши, сбои, цитата, пробелы, почему, контакты |
| Продукты | `table@1` | скольким местам нужен продукт: с доводом в отзывах и без, доводы, пример |
| Прогон | `tree@1` | дерево процессов, фишки статусов-фильтры, свёртка исходов глубже, инспектор payload |

Таблицы и дерево обновляются тихим опросом (`data-poll`). Плитка служебная (`admin: true` в реестре), всё API — за `requireAdmin`: в лидах контакты мест.

## Первый прогон (13.10.2026)

Данные — файлы ниши `hardware` (2ГИС, Курск, 11.10.2026) и разметка отзывов «Радара спроса» v2 (286 отзывов). Без сети и LLM.

- **Места:** 150 в нише из 166; отказ — 44: 30 сетей по числу точек, 3 по описанию, 11 «доводов нет».
- **Лиды:** 106 — 22 со сбоем в отзывах, 84 только по пробелам.
- **Продукты:** сайт с каталогом — 98 мест (13 с доводом в отзывах), умный ассистент — 70 (7), канбан-воронка — 10 (все 10 с доводом), подбор крепежа — 39 (6).
- **Консультация и подбор** (`info.explain`, «не знают ассортимент», «подбирает совсем не то») — вторая по частоте жалоба корпуса (13 мест), но 10 из них — сети. Среди лидов таких мест 3. Прототип эту потребность не учитывал.
- **Ограничения:**
  - разметка отзывов человеком не проверена (пример: «продавец опаздывает» размечен как «очередь и выдача»);
  - федеральную сеть с 1–2 точками в городе без слова «сеть» в описании («Лемана Про») правило не ловит;
  - у 74 мест нет свежих отзывов — для них доводы только по пробелам;
  - план и дерево живут в памяти процесса — после рестарта разбор запускается заново (на файлах это мгновенно);
  - на проде файлов нет (`data/` вне git) — данные появятся с живыми источниками.

## Шаги (сквозной прогон, П31)

| Шаг | Что | Статус |
|---|---|---|
| 1 | каркас process-tree + `tree@1` + `<v-tree>`; плитка, сквозной прогон на файлах ниши, UI из спеки | **сделано 13.10.2026** |
| 2 | `Lead` — сущность «я × компания × оффер» со своей судьбой (П38) и журналом в Postgres; воронка на `kanban@1` с ужесточённым контрактом; мост вех дерева в Postgres (прогоны переживают рестарт) | дальше |
| 3 | живые узлы по одному: листинг и карточки 2ГИС через каркас сборщиков (его ступень 2), аудит сайта, LLM-разметка отзывов вместо записанной | после 2 |
| 4 | новые сферы и регионы по потребности; исходы воронки — в веса `LeadRule` | по поводу |

Воронка лида (шаг 2, набросок):

```
found → qualified → pitched → replied → meeting → won | lost(причина)
found → rejected(причина)                 pitched → parked(until)  -- нет ответа: выход по сроку или кнопкой
любое → do_not_contact                    -- навсегда; назад только руками с причиной
```

Ничего не отправляется автоматически: система готовит карточку с доводами и цитатами, пишет и звонит человек. Авторов отзывов не храним, контакты — только из карточки организации.

## Чего не делаем (П34)

- Общий базовый «радар» с радарами спроса и идей: единицы разные (компания против потребности и сдвига), общие только каркас сборщиков и язык разметки.
- Тип-специфичные скины дерева: пока хватает скина по умолчанию с `payload.summary`. Вернуться, когда появится узел, которому нужен свой вид (карточка лида с цитатами).
- Отправка сообщений компаниям из системы.

# Компоненты UI — контракты и склад

Повторяющиеся куски UI становятся **компонентами с контрактом**. Главное — не
готовый фронтенд-код, а стандартизированный API на бэкенде: у компонента есть
id, по которому каркас конструирует эндпоинты, а фронтенд (наш складской
рендерер или написанный с нуля под другой стек) конфигурируется сам по `/meta`.
Родословная: разбор дублей песочниц `ui-convert/ui-trust/ui-cab` (тосты, шапки,
диалоги, `escapeHtml` — копипаста), пульт 2ГИС (таблица организаций без
сортировки, механика джобов), прецеденты общих блоков `auth.js` / `llm-picker`.

Каталог витринных паттернов — [ui-patterns.md](ui-patterns.md) (что чем
наполнять), материя тем — [ui-designs.md](ui-designs.md). Здесь — служебный
слой: как кусок UI становится компонентом с id и бэкенд-контрактом.

## 1. Два имени: контракт и экземпляр

**`table@1` — контракт (вид@версия).** Замороженное обещание: какие параметры
понимает (`sort`, `q`, `limit`, `offset`), схема ответа, алфавит действий,
семантика выбора. Один на все проекты. Ломающее изменение — `table@2`; старая
живёт, пока живы потребители (П32). Рендерер проверяет версию по `/meta` при
подключении и честно падает при несовпадении (П8: контракт проверяют при
сборке, а не на первом вызове).

**`pain-radar/orgs` — экземпляр.** Привязка контракта к данным: колонки,
сортируемость, пресеты выбора, действия, лимиты. Объявляется в точке сборки
домена — декларация читается как оглавление (П3):

```js
// server/services/pain-radar/components.js
Components({
  'orgs': Table({
    rows: async () => scrape.latestOrgs().items,   // домен: где брать строки
    columns: [
      { key: 'name', name: 'Название', sortable: true },
      { key: 'rating', name: 'Рейтинг', type: 'num', sortable: true },
      // ...
    ],
    search: ['name', 'address'],
    select: { presets: [{ id: 'nosite', name: 'Только без сайта', where: r => r.site_scanned && !r.site }] },
    actions: [
      { id: 'scan-sites', name: 'Скан контактов', bulk: true, max: 120,
        run: async ({ ids }) => ({ jobId: scrape.startJob('firmScan', { ... }) }) },
    ],
  }),
})
```

Дальше каркас сам конструирует эндпоинты — ручки не пишутся руками (П9,
тонкий транспорт). Монтирование в роуте эксперимента, служебное — целиком за
`requireAdmin`:

```js
// server/routes/pain-radar.js
router.use('/c', experiments.requireAdmin, require('../services/pain-radar/components'));
```

## 2. Контракт `table@1`

База экземпляра: `/api/<namespace>/c/<id>`.

| Эндпоинт | Что делает |
|---|---|
| `GET /meta` | контракт+возможности: колонки, пресеты, действия, лимиты, idKey |
| `GET /rows?sort=&q=&limit=&offset=` | `{ ok, total, rows }`; `sort=колонка` / `sort=-колонка` |
| `GET /ids?q=&preset=` | `{ ok, ids }` — все id отфильтрованного (для «выбрать всё» и пресетов), потолок `maxIds` |
| `POST /actions/:id` | тело `{ ids, ...params }` → `{ ok, result }` / `400 { error }` |

Семантика (зафиксирована контрактом):

- **Состояние просмотра** (сортировка, поиск, страница) живёт в параметрах
  запроса; **состояние выбора** — клиентское, сервером не хранится, в действие
  уезжает списком `ids`. «Выбрать всё» = клиент берёт `GET /ids`, поэтому
  работает и через пагинацию.
- Сортировка — только по колонкам с `sortable: true` (белый список, чужой
  параметр молча игнорируется). `type: 'num'` — числовой порядок, null внизу.
- Колонка `render: 'link'` рисует ссылку (host вместо полного URL),
  `note: '<ключ>'` — приглушённый текст, если значения нет.
- Bulk-действие требует непустой `ids`; `max` — потолок строк за раз, лимиты
  объявлены в декларации (П6: числа поведения — в точке сборки).
- Движок v1 — в памяти: `rows()` отдаёт всю выборку, каркас сам фильтрует,
  сортирует и режет. SQL-источник (`source(params)`) — рост-точка при
  переносе на таблицы БД.

Реализация: `server/components/table.js` — каркас, доменно-нейтральный
(словарный греп пуст, П9). Декларация вида — `Table({...})` из того же модуля.

## 3. Склад рендереров — `public/c/`

Один комплект vanilla-рендереров на все проекты; контракт позволяет заменить
любой из них на свою реализацию, включая другой стек.

| Файл | Что |
|---|---|
| `/c/ui.js` | `VeshaUI`: `escapeHtml`, `fmtInt`, `getJson`/`postJson` (ошибка = `Error(j.error)`), `debounce` |
| `/c/table.js` | custom element `<v-table src="/api/<ns>/c/<id>">` — рендерер `table@1` |
| `/c/table.css` | тема рендерера: токены `--vt-*` с тёмными дефолтами («приборная»), переопределяются страницей |

`v-table` умеет из `/meta`: клик по шапке — сортировка (`aria-sort`, стрелка),
поиск с debounce, чекбоксы + «Выбрать всё / Снять / <пресеты>», bulk-кнопки
действий (loader до ответа), пагинация, пусто/ошибка/загрузка. События наружу:
`v-select { ids }`, `v-action { id, response?, error? }`; метод `refresh()`.
Тема — то, что вчера копировали руками: шапку и строку статуса держит страница.

## 4. Каталог id

Присвоены и чем обоснованы:

**Служебные (кабинет/пульт) — контракт и рендерер:**

| id | Что умеет | Откуда родом |
|---|---|---|
| `table@1` | сортировка, поиск, выбор+пресеты, bulk-действия, пагинация | пульт 2ГИС (orgs), идея-радар (collectors) |
| `console@1` | кнопки→джобы→поллинг→loader→строка статуса | `scrape-console.js` (`startJob`/`withLoading`/`showJob`/`poll`) |
| `log@1` | сырой лог с инкрементальным поллингом | пульт, песочница playwright-mcp |
| `kanban@1` | колонки, WIP-шкала, drag&drop + кнопочный фолбэк | `ui-cab`, chat-engine dashboard |
| `kpi-dash@1` | KPI-карточки + sparklines | `ui-cab` |
| `form@1` | поля+валидация+submit с loading/ошибкой | лид-форма (дубль ×4) |
| `empty@1` | empty states, один на все списки | `ui-cab` |

**Общие:** `toast@1` (дубль convert↔cab), `modal@1` (`<dialog>`+подложка),
`header@1/2` (шапка служебной страницы), `section-head@1`, `status-pill@1`.

**Витринные** — уже описаны в [ui-patterns.md](ui-patterns.md), соответствие:
§1.1 `quiz@1`, §1.2 `calc@1`, §2.1 `before-after@1`, §2.2 `reviews-wall@1`,
§2.3 `docs-shelf@1`, §2.4 `timeline@1`, §2.5 `status-pill@1`, §2.6 `count-up@1`,
§2.7 `marquee@1`, §3.1 `segment@1`, §3.2 `spotlight@1`. Витринным контракт
бэкенда нужен, когда появятся живые данные (сейчас все статичны — П34).

## 5. Язык сборки служебного UI

Служебная страница — список блоков `kind@variant + props + src`. «Шапка_типа_2,
таблица_типа_1, дашборд_тип_3» = `header@2, table@1, kpi-dash@1` (номер
варианта = версия контракта).

1. **Сейчас** — язык = этот каталог: агент собирает консоль из складских
   блоков по контракту, монтирование `<v-table src=…>`.
2. **Рост-точка: спека страницы + boot.** Бэкенд отдаёт список блоков
   (`GET /api/<id>/c/pages/<page>`), крошечный `boot.js` превращает его в HTML,
   custom elements сами инициализируются. Новая консоль из готовых блоков —
   правка JSON без деплоя кода.
3. **Рост-точка: редактор блоков** с сохранением спеки. Условие возврата:
   консолей больше пяти и их собирает не-программист.

## 6. Порядок внедрения

1. ✅ **Пилот:** каркас `table@1` + `<v-table>` + экземпляр `pain-radar/orgs` —
   таблица организаций пульта 2ГИС переезжает на контракт и получает
   сортировку, поиск, пресет «только без сайта», «Скан контактов» становится
   bulk-действием таблицы.
2. `toast@1` + `modal@1` + утилиты в `/c/` — убрать дословные дубли песочниц
   (пере-одевание попутно, при касании кода).
3. `console@1` + `log@1` — обобщение механики джобов пульта (поллинг, loader,
   jobline).
4. `kanban@1` + `kpi-dash@1` — из `ui-cab`/chat-engine, источник — агрегаты БД
   (вот где понадобится SQL-`source`).
5. Спека страницы + `boot.js` — когда блоков станет три-четыре.

## 7. Чего не делаем (П34)

- Без реактивности, virtual DOM и сборщика — vanilla-регламент каркаса
  ([universal-framework.md](universal-framework.md) §2).
- Без авто-CRUD по БД: источники объявляются декларацией, а не отражаются из
  схемы.
- Без SSR спеки: JSON + клиентский монтаж достаточны для служебного UI.
- Без унификации тем витрин: темы — токены поверх, рендерер нейтрален.
- Редактор-конструктор — позже, по условию возврата.

# Компоненты UI — контракты и склад

Повторяющиеся куски UI становятся **компонентами с контрактом**. Главное — не
готовый фронтенд-код, а стандартизированный API на бэкенде: у компонента есть
id, по которому каркас конструирует эндпоинты, а фронтенд (наш складской
рендерер или написанный с нуля под другой стек) конфигурируется сам по `/meta`.
Родословная: разбор дублей песочниц `ui-convert/ui-trust/ui-cab` (тосты, шапки,
диалоги, `escapeHtml` — копипаста), пульт 2ГИС (таблица организаций без
сортировки, механика джобов), прецеденты общих блоков `auth.js` / `llm-picker`.

Каталог витринных паттернов — [ui-patterns.md](ui-patterns.md) (что чем
наполнять), материя тем — [ui-designs.md](ui-designs.md). Здесь — служебный
слой: как кусок UI становится компонентом с id и бэкенд-контрактом.

## 1. Два имени: контракт и экземпляр

**`table@1` — контракт (вид@версия).** Замороженное обещание: какие параметры
понимает (`sort`, `q`, `limit`, `offset`), схема ответа, алфавит действий,
семантика выбора. Один на все проекты. Ломающее изменение — `table@2`; старая
живёт, пока живы потребители (П32). Рендерер проверяет версию по `/meta` при
подключении и честно падает при несовпадении (П8: контракт проверяют при
сборке, а не на первом вызове).

**`pain-radar/orgs` — экземпляр.** Привязка контракта к данным: колонки,
сортируемость, пресеты выбора, действия, лимиты. Объявляется в точке сборки
домена — декларация читается как оглавление (П3):

```js
// server/services/pain-radar/components.js
Components({
  'orgs': Table({
    rows: async () => scrape.latestOrgs().items,   // домен: где брать строки
    columns: [
      { key: 'name', name: 'Название', sortable: true },
      { key: 'rating', name: 'Рейтинг', type: 'num', sortable: true },
      // ...
    ],
    search: ['name', 'address'],                    // или (row, q) => bool — домен сам читает запрос (телефон любой записью)
    select: { presets: [{ id: 'nosite', name: 'Только без сайта', where: r => r.site_scanned && !r.site }] },
    actions: [
      { id: 'scan-sites', name: 'Скан контактов', bulk: true, max: 120,
        run: async ({ ids }) => ({ jobId: scrape.startJob('firmScan', { ... }) }) },
    ],
  }),
})
```

Дальше каркас сам конструирует эндпоинты — ручки не пишутся руками (П9,
тонкий транспорт). Монтирование в роуте эксперимента, служебное — целиком за
`requireAdmin`:

```js
// server/routes/pain-radar.js
router.use('/c', experiments.requireAdmin, require('../services/pain-radar/components'));
```

## 2. Контракт `table@1`

База экземпляра: `/api/<namespace>/c/<id>`.

| Эндпоинт | Что делает |
|---|---|
| `GET /meta` | контракт+возможности: колонки, пресеты, действия, лимиты, idKey |
| `GET /rows?sort=&q=&limit=&offset=` | `{ ok, total, rows }`; `sort=колонка` / `sort=-колонка` |
| `GET /ids?q=&preset=` | `{ ok, ids }` — все id отфильтрованного (для «выбрать всё» и пресетов), потолок `maxIds` |
| `POST /actions/:id` | тело `{ ids, ...params }` → `{ ok, result }` / `400 { error }` |

Семантика (зафиксирована контрактом):

- **Состояние просмотра** (сортировка, поиск, страница) живёт в параметрах
  запроса; **состояние выбора** — клиентское, сервером не хранится, в действие
  уезжает списком `ids`. «Выбрать всё» = клиент берёт `GET /ids`, поэтому
  работает и через пагинацию.
- Сортировка — только по колонкам с `sortable: true` (белый список, чужой
  параметр молча игнорируется). `type: 'num'` — числовой порядок, null внизу.
- Колонка `render: 'link'` рисует ссылку (host вместо полного URL),
  `note: '<ключ>'` — приглушённый текст, если значения нет.
- Bulk-действие требует непустой `ids`; `max` — потолок строк за раз, лимиты
  объявлены в декларации (П6: числа поведения — в точке сборки).
- Действие получает `{ ids, body, user }`: `user` — инициатор (как в `/move`
  у `kanban@1`), от его имени вехи прогона и квоты (П37).
- **Поля действия** (16.10.2026, первый потребитель — черновик счёта
  [костяка](backbone-architecture.md), 6.5): `fields: [{ key, label, required,
  placeholder }]` — рендерер перед запуском показывает короткую форму в
  панели, значения едут в тело рядом с `ids`; обязательное пустое поле каркас
  отклоняет `400`. `multiline: true` — многострочное поле (вставка таблицы
  из учётной системы). `max` уходит в `/meta`: кнопка гаснет, если выбрано
  больше. После успешного действия рендерер перечитывает строки,
  `result.message` — сообщение в ноге, `result.download` (путь на этом же
  сайте) — браузер скачивает файл. Без `fields`, `max` и `download` контракт
  прежний.
- **Поле-файл и выбор** (17.10.2026, первый потребитель — выгрузка каталога
  магазина [костяка](backbone-architecture.md), шаг 6): `type: 'file'`
  (`accept`, `maxBytes`, по умолчанию 10 МБ) — рендерер шлёт тело multipart,
  `ids` — повтором ключа; каркас кладёт файл в `body[key]` как
  `{ name, size, data }` (имя — в UTF-8), больше `maxBytes` — `400`.
  `options: ['a', { value, name }]` — выпадающий список, чужое значение — `400`.
  `render: 'link'` рисует и путь этого сайта (`/…`) — как есть; `label: '<ключ>'`
  у такой колонки — текст ссылки из поля строки («Открыть» вместо длинного адреса,
  18.10.2026).
- Движок v1 — в памяти: `rows({ user })` отдаёт всю выборку, каркас сам
  фильтрует, сортирует и режет (`user` — для выборки владельца, например
  журнал его воронки; 17.10.2026). SQL-источник (`source(params)`) —
  рост-точка при переносе на таблицы БД.

Реализация: `server/components/table.js` — каркас, доменно-нейтральный
(словарный греп пуст, П9). Декларация вида — `Table({...})` из того же модуля.

## 2а. Контракт `kanban@1`

База экземпляра: `/api/<namespace>/c/<id>`.

| Эндпоинт | Что делает |
|---|---|
| `GET /meta` | колонки `{id, name, type?, color?, limit?, ask?}` — от источника при каждом запросе; ключи полей карточки (`card.title/snippet/time`); возможности `move.enabled`, `create {enabled, label, fields}`, `configure {enabled, types}`, `details {enabled, stages?}`, `actions [{id, name, fields?}]` |
| `GET /cards` | `{ ok, cards }` — плоский список; порядок внутри колонки = порядок источника |
| `POST /move {cardId, to, …ask}` | единственная дверь переноса; правило колонки проверяет домен. Колонка с `ask` — поля, которые домен спрашивает при входе в неё; уходят только они, обязательное пустое — `400` |
| `POST /cards {…поля}` | новая карточка, если домен объявил `create`; уходят только поля из `meta.create.fields` |
| `POST /columns {op, …}` | операция конструктора колонок, если домен объявил `configure`: `add`, `rename`, `retype`, `move`, `recolor`, `limit`, `remove {moveTo}`; инварианты доски проверяет домен; ответ — колонки после правки |
| `GET /cards/:id` | подробности, если домен объявил `details`: `{ card {title, subtitle}, facts [{label, value, href?}], journal [{at, what, actor, why}], actions [id…] }` — `actions` говорит, какие из объявленных действий доступны карточке сейчас; необъявленные каркас отбрасывает |
| `POST /cards/:id/actions/:action {…поля}` | действие над карточкой из `meta.actions`; уходят только объявленные поля, обязательное пустое — `400`; неизвестное действие — `400` |

Семантика: карточка — снимок; бейджи (`{text, kind}`) считает источник — это
доменные факты («ждёт ответа», «черновик готов ×N»), рендерер знает только
вид. Перемещение — drag&drop и кнопки ←/→ в рендерере, оба пути идут в один
`POST /move` (второго пути к данным нет, §4.3 ui-patterns). WIP-лимит из
колонки рендерер рисует и подсвечивает перегруз, но не блокирует. Состояние
выбора — клиентское; сбой переноса — честный тост, карточка остаётся.
Реализация: `server/components/kanban.js`.

**Конструктор колонок** (16.10.2026, первый потребитель — [костяк](backbone-architecture.md), 6.2): декларация `columns` — массив или функция-источник; у колонки смысловой `type` (`inbox`, `working`, `waiting_client`, `done`, `refused`); операции — через `POST /columns`, инварианты (обязательные типы, перенос карточек при удалении, версия доски) проверяет домен (`backbone/board/Board.js`). Рендерер: кнопка «+ новая карточка» с формой из `meta.create.fields` и режим «настроить колонки» — название, тип, порядок, цвет, лимит, удаление с выбором, куда перенести карточки, новая колонка. Пока открыта форма или настройка, опрос доску не перерисовывает; колонки с конструктором перечитываются из `/meta` на каждом такте. Без `create` и `configure` контракт прежний — chat-engine не заметил изменения. Экземпляр: `backbone/board`.

**Подробности, действия, вопрос колонки** (17.10.2026, первый потребитель — воронка лидов [automation-leads](automation-leads-architecture.md), шаг 2) — ужесточённый контракт канбана как универсального юнита:

- источник колонок и карточек получает `{ user }` — доска владельца (у каждого «я» своя воронка); функции без аргументов работают как раньше;
- `ask` у колонки — поля, которые правило пути спрашивает при входе: причина для колонки отказа, срок «ждём до» (`type: 'date'`) для колонки ожидания. Рендерер перед переносом — drag&drop или ←/→ — показывает короткую форму и шлёт поля в тот же `POST /move`; второй рубеж — домен;
- `details` — клик по карточке открывает панель: факты (ссылки — только `http(s)`, `tel:`, `mailto:` и свои страницы), путь карточки `<v-stages>` (если `details.stages` и подключён `/c/stages.js`), журнал «кто, когда, почему», кнопки доступных действий с короткой формой;
- пока открыта форма (новая карточка, вопрос колонки, действие) или настройка, опрос доску не перерисовывает; открытые подробности — перерисовывает, но `<v-stages>` переносится тем же элементом, а прокрутка колонок и журнала сохраняется.

Без `ask`, `details` и `actions` контракт прежний — chat-engine и костяк не заметили изменения. Экземпляр: `automation-leads/funnel`.

Пример-пилот — `chat-engine/leads`: колонки из `Funnel.snapshot()`, карточки
через дверь `ChatDesk.board()`, перенос — `ChatDesk.setStage` (воронка
проверяет правило). Первый источник не из памяти: карточки приходят из
Postgres через доменную дверь.

### `stages@1` — путь одной карточки (17.10.2026)

«Упрощённый канбан»: тот же журнал переходов, но одна карточка во времени,
а не много карточек по этапам: «документ загружен → зарегистрирован →
перенаправлен». Это окно статуса для ждущей стороны (квитанция вместо тишины)
и живая версия витринного таймлайна «как мы работаем» (ui-patterns §2.4): там
обещание, здесь факт по этой заявке. Где есть этапность, кладут пару
`kanban@1` + `stages@1` над одним журналом. Только чтение (П14).

| Эндпоинт | Что делает |
|---|---|
| `GET /meta` | `{ kind: 'stages', version: 1, title }` |
| `GET /path?key=` | `{ ok, title, subtitle?, steps [{name, state, at?, note?}], exit: null \| {name, tone, reason?, at?}, updatedAt? }`; `state` — `done \| current \| next`, `tone` — `done \| refused \| waiting`; неизвестное состояние шага — ошибка контракта |

Что такое ключ, решает домен: id карточки за границей доступа (лид — за
`requireAdmin`) или токен ссылки (окно заявки клиенту — шаг 4 костяка, сделано 17.10.2026: экземпляр `backbone-public/status`, страница `/backbone/status.html?t=<токен>`, вне границы админа).
Какие шаги показать, решает тоже домен; у лида — пройденные колонки из
журнала с датами, текущая колонка (с пометкой «ждём до 24.10» / «срок вышел»),
впереди — колонки главного пути до первой колонки «готово» без колонок отказа;
отказ и «не беспокоить» — плашка выхода с причиной. Рендерер `<v-stages src key
data-poll data-compact>`; в спеке страницы — блок `{ kind: 'stages@1', src,
param: 'lead' }`, ключ boot@1 берёт из `?lead=` адреса. Реализация:
`server/components/stages.js`, `/c/stages.js`, `/c/stages.css`. Экземпляр:
`automation-leads/lead-path` — в подробностях карточки воронки и отдельной
страницей `/experiments/automation-leads/?page=lead&lead=<id>`.

## 2б. Контракт `tree@1`

Зеркало дерева процессов ([process-tree-ui-canon.md](process-tree-ui-canon.md)):
домен объявляет `Tree({ store, title, labels })` над хранилищем
`server/process-tree/` (`ProcessTreeStore`), каркас конструирует ручки. Только
чтение (П14): запуск и остановка — доменные действия. База: `/api/<namespace>/c/<id>`.

| Эндпоинт | Что делает |
|---|---|
| `GET /meta` | заголовок, подписи видов узлов `labels: { nodeType: 'подпись' }` |
| `GET /roots` | `{ ok, version, roots }` — прогоны (корни), новые первыми |
| `GET /tree?root=<id\|latest>&since=<version>` | `{ ok, version, unchanged: true }`, если с версии ничего не менялось, иначе `{ ok, version, rootId, tree }`; `tree: null` — прогонов нет |

Узел: `nodeId`, `parentNodeId`, `nodeType`, `title`, `status`
(`created | running | waiting | completed | skipped | failed | cancelled`),
`payload` (строка `payload.summary` показывается в строке узла), `outcome`
`{ ok, code, detail }`, времена. Проекция добавляет `displayStatus`,
`statusTone`, `depth`, `lineage`, `children`, `stats` (дети по статусам) и
`deep` — исходы внуков и глубже по виду узла: у группы из 150 мест видно
«сайт: пропущено 68», не раскрывая каждое место. Ключи payload с секретами
(`apiKey`, `token`, `password`…) режутся на входе в хранилище.

Узел едет в контексте запуска: доменный шаг получает его аргументом и зовёт
`node.step({ nodeType, title }, (child) => …)` — обёртка открывает ребёнка,
закрывает его по возврату, на исключении ставит `failed` (`AbortError` —
`cancelled`) и пробрасывает дальше; где ошибка становится результатом,
решает вызывающий (П24). Реализация: `server/components/tree.js`,
`server/process-tree/{index,projection}.js`. Пилот — `automation-leads/scans`.

**Мост вех в Postgres** (17.10.2026, `server/process-tree/persist.js`,
таблица `process_tree_nodes`, миграция 021): хранилище остаётся в памяти,
`TreeLog` подписан на его события и пишет снимки узлов пачкой раз в 500 мс
(последний снимок узла побеждает, пачка — один запрос). При старте мост ждёт
`db.migrated`, читает прошлые прогоны своего дерева (`tree` — имя, деревья не
смешиваются) и отдаёт их `store.restore()`: незакрытые узлы прошлого процесса
закрываются `failed` с исходом `interrupted` («прервано рестартом сервера»),
выселенные хранилищем прогоны уходят и из базы. Сбой базы — строка в логе и
повтор следующим тактом, дерево в памяти живёт дальше (П24). Окно потерь —
вехи последних ~500 мс перед падением процесса.

## 2в. Контракт `switch@1` (18.10.2026)

Тумблер на несколько положений: одно текущее, смена — решение домена. Над
тумблером — фразы-пояснения простыми словами и необязательная кнопка-призыв к
следующему положению. Домен может не запретить, а спросить: ответ `{ confirm }`
— рендерер показывает предупреждение с «Да» / «Отмена» и повторяет смену с
`confirm: true`. Первый потребитель — тумблер разбора заявок костяка
(«Выключен / Сравнение / Помощь») и «До и после» на его замерах; второй
напрашивается — таймер опроса радара идей (включён / выключен).

| Эндпоинт | Что делает |
|---|---|
| `GET /meta` | `{ kind: 'switch', version: 1, title }` |
| `GET /state` | `{ ok, value, options [{value, name, note?}], lines?: [фраза], cta?: {value, name}, hint? }`; текущее положение вне `options` — ошибка контракта |
| `POST /set {value, confirm?}` | `{ ok, result: { message } }` или `{ ok, result: { confirm: 'предупреждение' } }`; положение вне `options` — `400` |

Домен объявляет `Switch({ title, state({ user }), set({ value, confirm, user }) })`.
Рендерер `<v-switch src data-poll>` (`/c/switch.js`, `/c/switch.css`, токены
`--vsw-*`): сегменты-радио переносятся на узком экране, после смены — событие
`v-changed` (всплывает). В спеке — `{ kind: 'switch@1', src }`.

## 2г. Контракт `extract@1` — источник и его прочтения (18–19.10.2026)

Источник и то, что из него извлекли: слева — строки текста целиком, правее — одна
или несколько колонок прочтений (`results[]`; у костяка — механический разбор и
разбор нейросетью). Пункт колонки — с тоном `ok | ask | miss`, пометкой (`tag`),
заметкой и ссылками на строки источника (`anchors`): щелчок по пункту подсвечивает
его место в источнике и пункты других колонок на том же месте, щелчок по строке
источника — её пункты. Колонка бывает закрыта (`closed` — с причиной: «откроется
после вашего счёта») или спрятана под «глаз» (`peek` — открывает человек), у неё —
совет (`hint`: «стоит распознать нейросетью») и свои действия. У пункта — сверка с
эталоном (`pair: { text, tone: same | diff }`), варианты (`choices`, у каждого —
отличие `note`), свёрнутые «ещё N» (`more`) и, если нужно, свой список действий
(`actions`); пункты эталона без пары — `extra`. Первый потребитель — карточка заявки
костяка (текст покупателя, механика, нейросеть); второй виден — разметка сдвигов
радара идей (текст госакта и сдвиги с цитатами).

| Эндпоинт | Что делает |
|---|---|
| `GET /meta` | `{ kind: 'extract', version: 1, title, legend: {ok, ask, miss}, actions: [{id, name, scope: all \| item, tones?, choose?, primary?, fields?}] }` |
| `GET /view?key=` | `{ ok, title, subtitle?, facts [{label, value}], source: {title, lines, note?}, results: [{id, title, state: open \| closed \| peek, reason?, peek?, hint?, facts, actions: [id], items [{id, text, tone, anchors, sub?, tag?, note?, choices?: [{value, text, note?}], more?, pair?, actions?}], extra [{text, tone}]}] }`; чужой тон или состояние — ошибка контракта, ссылка за пределы источника отбрасывается |
| `POST /actions/:id {key, item?, value?, …поля}` | `{ ok, result: { message?, download? } }`; действия нет ни в одной колонке («сейчас недоступно»), пункт не из колонки этого действия, не того тона или не из `item.actions`, вариант не из `choices`/`more`, пустое обязательное поле — `400` |

Какие действия доступны сейчас, решает вид — у каждой колонки свой список; каркас
проверяет это ещё раз при запуске (кнопка со старой страницы не проходит). Домен
объявляет `Extract({ title, legend, view({ key, user }), actions: [{ id, name, scope,
tones, choose, fields, run({ key, item, value, body, user }) }] })`. Рендерер
`<v-extract src key data-poll>` (`/c/extract.js`, `/c/extract.css`, токены `--vx-*`):
источник и две колонки — три рядом шире 1100 px, уже — источник сверху и колонки
рядом, на телефоне — друг под другом; длинные строки переносятся. Действия колонки —
над пунктами; варианты пункта — кнопками всегда, с отличием жирным; «ещё N
вариантов» — `<details>` с поиском и фишками-отличиями (до 12); прочие действия
пункта — у выбранного; после действия — `v-changed`. Пока открыта форма или список
«ещё N», тихий опрос не перерисовывает. В спеке — `{ kind: 'extract@1', src,
param: 'order' }`, ключ boot@1 берёт из `?order=`.

страницы), рекурсивный setTimeout. Домен отвечает «что делать» — колбэк
`onState` рисует свою панель:

```js
const jc = new VeshaUI.JobConsole({

await jc.startJob('rubrics', body, (job) => { /* done/error */ });
```

## 5. Язык сборки служебного UI

Служебная страница — список блоков `kind@variant + props + src`. «Шапка_типа_2,
таблица_типа_1, дашборд_тип_3» = `header@2, table@1, kpi-dash@1` (номер
варианта = версия контракта).

1. ✅ **Сейчас** — язык = каталог: агент собирает консоль из складских блоков
   по контракту, монтирование `<v-table src=…>`.
2. ✅ **Спека страницы + boot.** Домен объявляет спеку в реестре
   (`server/components/pages.js`, `Pages({...})`, валидация блоков при старте —
   неизвестный блок валит запуск, П8), каркас отдаёт её на
   `GET /api/<ns>/c/pages/<имя>`. Общий хост `/c/page.html?spec=…` +
   `/c/boot.js` (boot@1): заголовок из спеки, блоки → `<v-table>`/`<v-kanban>`,
   неизвестный блок — честная плашка. Новый служебный экран = правка
   декларации, не код. Пилот — `pain-radar/orgs-review` («Обзор организаций»).
3. **Рост-точка: редактор блоков** с сохранением спеки. Условие возврата:
   консолей больше пяти и их собирает не-программист.

Конвенция конвертов: контрактные `/meta`, `/rows`, `/cards`, `/pages/:name`
отдают `{ ok, ... }` без обёртки — читаются `VeshaUI.getJson`; доменные ручки
эксперимента могут держать свой конверт `{ ok, result }`. Смешивать на одной
ручке нельзя.

### 5.1. Рецепт: «собери UI из компонентов id1, id2…»

Просьба уровня *«собери служебный UI: таблица организаций и канбан воронки
на одной странице»* — рабочая фраза. У каждого блока есть id, сборка —
декларация, не код. Агент идёт по меню от дешёвого к дорогому:

**Шаг 1 — экземпляры есть.** Компоненты уже подключены к данным
(`pain-radar/orgs`, `chat-engine/leads` — реестр в `server/services/*/components.js`)
→ написать спеку в `pages.js` того домена, которому принадлежит экран:

```js
// server/services/pain-radar/pages.js
Pages({
  'my-screen': {
    title: 'Разбор ниши: организации и воронка',
    subtitle: 'собрано из компонентов: table@1 + kanban@1',
    blocks: [
      { kind: 'table@1',  src: '/api/pain-radar/c/orgs' },
      { kind: 'kanban@1', src: '/api/chat-engine/c/leads', poll: 5000 },
    ],
  },
})
```

Готово: `/c/page.html?spec=/api/pain-radar/c/pages/my-screen`. Заголовок,
порядок блоков, опрос — в спеке; тема — токены в `page.css` (или свои поверх).

**Шаг 2 — контракт есть, экземпляра нет.** Данные новые, вид из каталога (§4)
→ декларация экземпляра в точке сборки домена — `Table({...})` (§2) или
`Kanban({...})` (§2а) с колонками/действиями/дверью, монтирование роутера,
дальше шаг 1.

**Шаг 3 — вида нет.** Первый в истории потребитель нового вида (форма, лог)
→ контракт `server/components/<kind>.js` + рендерер `public/c/<kind>.js` +
id в каталог §4 + строка в `KNOWN_BLOCKS` (pages.js) и `MOUNT` (boot.js),
потом шаги 2 → 1. Редкий шаг: только при втором потребителе или явной
просьбе (П34).

Блоки, которые умеет boot@1 сегодня: `table@1`, `kanban@1`, `tree@1`,
`stages@1`, `switch@1`, `extract@1`; у каждого необязательные `poll` (мс тихого
опроса) и `title` (заголовок секции над блоком), у `stages@1` и `extract@1` —
`param` (из какого `?параметра` адреса взять ключ). Проверка сборки: неизвестный блок в спеке валит старт сервера,
на странице — плашку. Страница эксперимента может сама быть хостом спеки:
`public/experiments/automation-leads/index.html` — общий хром и
`VeshaBoot.boot('/api/automation-leads/c/pages/main')`, своего JS у
эксперимента нет.

### 5.2. «Меняем в одном месте — меняется везде?»

Да, но у компонента четыре уровня, и «одно место» у каждого своё:

| Меняем | Где одно место | Что меняется везде |
|---|---|---|
| рендерер вида | `public/c/table.js` | все `<v-table>` во всех проектах: баг-фикс, общая фича (CSV, экспорт, новый тип колонки) |
| тема | токены `--vt-*`/`--vk-*` страницы | все блоки этого вида на этой странице |
| экземпляр | декларация в `components.js` домена | только свои экраны: колонки, пресеты, действия, дверь |
| контракт | `table@1` → `table@2` | ничего сразу: версии соседствуют, потребители переезжают по своей дороге (П32) |

Единственное, что **не** меняется «в одном месте», — домен: данные и правила
принадлежат эксперименту (П28). Компонент знает контракт, а не домен (П9) —
поэтому таблица организаций и канбан лидов собираются из одних деталей, но
решения о колонках и переносах остаются у своих территорий.

## 7. Чего не делаем (П34)

- Без реактивности, virtual DOM и сборщика — vanilla-регламент каркаса
  ([universal-framework.md](universal-framework.md) §2).
- Без авто-CRUD по БД: источники объявляются декларацией, а не отражаются из
  схемы.
- Без SSR спеки: JSON + клиентский монтаж достаточны для служебного UI.
- Без унификации тем витрин: темы — токены поверх, рендерер нейтрален.
- Редактор-конструктор — позже, по условию возврата.

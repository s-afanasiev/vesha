# Chat Engine — скелет универсального движка «сайт-виджет + дашборд + LLM-черновик ответа»

Эксперимент `chat-engine`. Происхождение: минимум из рабочего проекта Scout+Anna
(neuro.telebot), где менеджеры ведут переписку с блогерами в полуавтомате: каждое
входящее → LLM предлагает ответ → менеджер соглашается или правит. Здесь то же ядро,
но платформа — не Telegram, а сайт заказчика, и всё переписано на Node.js как
отдельный эксперимент Vesha.

Родительский разбор: `c:\CODE\Neuro_project\neuro.telebot\docs\START_PROMPT.md`
(Anna — Flask+Telegram+БД, Scout — веб-дашборд через `/proxy/*`). Этот документ —
план и карта нового скелета; привязка к канону — `docs/oop-principles.md` (метки §N).

## Рассказ системы (П31)

Посетитель пишет в виджет на сайте заказчика — его сообщения собираются в диалог.
Менеджер видит диалоги на доске воронки и в чате; на каждое новое входящее движок
(по кнопке менеджера, позже — автоматически) просит LLM предложить сбалансированный
ответ. Менеджер отправляет черновик как есть, правит или отклоняет и пишет своё.
Каждая смена этапа воронки идёт через одну дверь и остаётся в журнале.

## Точка сборки (П3)

```
routes/chat-engine.js  — тонкий транспорт: envelope + делегирование (П9)
ChatDesk(              — дверь территории, сценарии домена (П28)
  DialogueRepository,  — владелец истины: диалоги, сообщения, журнал этапов, персона
  ReplySuggester(db,   — работа «предложи ответ»: промпт → LLM → текст (один глагол)
                 llm),
  Funnel               — правило: этапы воронки, подписи и пастельные цвета колонок
).run()
```

Незнания (П30, проверяются грепом): `DialogueRepository` не знает про LLM;
`ReplySuggester` не пишет в БД и не знает про HTTP; `Funnel` не знает про хранение;
роуты не знают про SQL. Платформа (web-виджет / vk / telegram) — адаптер над
`ChatDesk.receiveVisitorMessage`, у диалога есть `channel`; скелет реализует только
`web` (гость Vesha = идентификатор посетителя).

## Данные (миграция 012_chat_engine.sql)

- `chat_engine_dialogues` — карточка диалога: `channel`, `visitor_key` (UNIQUE-пара —
  один диалог на посетителя канала), `visitor_name`, `stage`, `notes`,
  `last_incoming_at`, `last_outgoing_at`.
- `chat_engine_messages` — единая история: `role` ∈ visitor/manager/draft,
  `state` (для draft: open/approved/edited/rejected/superseded), `external_id`
  (UNIQUE — дедуп повторных доставок), черновик эволюционирует в своей строке
  (`text` правится при «править и отправить»).
- `chat_engine_stage_log` — журнал смен этапа (from/to/actor/cause) — вехи (П26).
- `chat_engine_settings` — KV; ключ `persona` — текст персоны ассистента
  (тон, правила, запреты), редактируется в дашборде.

## Поток одного сообщения

1. **Входящее** (виджет): POST с `external_id` (uuid клиента) → дедуп → диалог по
   `(channel, visitor_key)` или новый со stage `new` → запись visitor-сообщения →
   **все открытые черновики диалога гасятся** (`superseded`, урок Scout+Anna F4:
   новое входящее устаревает черновик).
2. **Черновик**: менеджер нажимает «Предложить ответ» (скелет — по кнопке; рост-точка
   — авто-черновик фоновым воркером) → `ReplySuggester`: промпт = дата + персона +
   карточка (имя, этап, заметки) + история (до 30) + задача → LLM → строка draft
   `state=open`. Сбой LLM — честный результат `{ok:false, code, message}` менеджеру,
   конвейер не падает, клиенту тишина (урок F3). Вызов — только через `runGuarded`.
3. **Согласование**: «Отправить» → draft `approved`; «Править и отправить» → текст
   замещается, `edited` (рост-точка — петля стиля на парах предложено/отправлено);
   «Отклонить» → `rejected`. Кнопка отправки есть только у `open`-черновика —
   структурный гейт, как kind=`reply` у Анны.
4. **Ответ менеджера своим текстом**: POST replies → строка manager, `last_outgoing_at`,
   авто-переход `new → in_work` (через дверь, cause `manager_reply`).
5. **Этап**: любая смена — только через `ChatDesk.setStage` → валидация по `Funnel` →
   запись в журнал. Одна дверь на запись статуса (урок F1, П27).
6. Виджет читает свой диалог по гостю; черновики посетителю не видны.

## Воронка (минимум канбана)

`new` (Новое) → `in_work` (В работе) → `offer` (Предложение отправлено) →
`negotiation` (Переговоры) → `won` (Успех) / `lost` (Отказ). Переходы свободные,
но все — через дверь и журналыруются. Два измерения Scout+Anna (жизненный цикл vs
этап переписки) в скелет не тянутся — одно измерение `stage`.

## Промпт ответа (минимум из Анны, разбор D)

Состав: (1) персона из настроек — тон, продукты/правила, запреты; (2) сегодняшняя
дата — первым динамическим блоком; (3) контекст карточки — имя, канал, этап, заметки;
(4) история диалога + задача «верни только текст ответа». Блоки Анны «ссылка
менеджера», петля стиля, недоставленные — рост-точки, архитектура их вмещает.

## Что взято, что выброшено

Взято: карточка диалога как центр; pending-конвейер согласования (черновик с
состояниями); дедуп входящих по `external_id`; суперсед черновиков при новом
входящем; одна дверь статуса + журнал переходов; честный сбой LLM; единая шкала
времени (UTC в БД); персона как редактируемый блок промпта.
Выброшено (с мотивом): Telegram Business и аренда аккаунта — платформа заменена
виджетом; поиск/скоринг кандидатов, Instagram, Sheets, экономика интеграций,
артефакты, реферальное дерево, мультименеджеры, система напоминаний, вотчдоги и
зеркала — чужие миры Scout+Anna, не ядро полуавтомата.

## Рост-точки (порядок добавления)

1. Авто-черновик: входящее ставит задачу, воркер зовёт `ReplySuggester` (очередь —
   ФИФО одного воркера, как у Анны; UI уже готов показывать draft).
2. Адаптеры платформ: `vk`, `telegram` → тот же `ChatDesk.receiveVisitorMessage`.
3. Петля стиля: пары «предложено → отправлено» подмешивать в промпт.
4. Гейт менеджеров на дашборде (сессии Vesha), авто-переходы этапов по правилам.
5. Деплой на сайт заказчика: виджет как embed-скрипт; дашборд под админом.

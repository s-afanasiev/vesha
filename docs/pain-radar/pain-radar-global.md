# Радар болей — глобальный план (`pain-radar-global`)

Большой план проекта «Радар болей». Исполняется по частям: каждый пункт прорабатывается отдельно, и по нему создаётся **план исполнения** — файл рядом в этой папке (`pain-radar-plan-*.md`, реестр — раздел 4). Принятое по пункту решение уходит в постоянные документы: [pain-radar-architecture.md](pain-radar-architecture.md), [pain-radar-review.md](pain-radar-review.md), [pain-radar-business-logic.md](pain-radar-business-logic.md). Сам глобальный план дополняется новыми пунктами по мере движения — это не мешает исполнять уже записанные.

План создан 04.10.2026 на основе обсуждения. Пункты 1.1–1.4 и 2 — исходное видение, зафиксированное дословно по смыслу; 1.5 — добавлен 04.10.2026 как следующий шаг после 1.4; по мере проработки пункт получает статус и свой файл-план.

## Два радара — одна задача

Радар болей и радар идей — близкие замыслы, решающие по сути одну большую задачу: **разведку востребованности региона** — найти ниши, где есть потребность, и подкрепить её доказательствами, прежде чем кто-то вложит деньги. Радар идей отвечает «почему сейчас» (сдвиги: обязанности, деньги, технологии), радар болей — «что болит и у кого» (боли: жалобы, дефициты, дыры в предложении). Связка зафиксирована формулой из [idea-radar-architecture.md](../idea-radar-architecture.md): **идея = сдвиг × боль × человек**. Отдельный глобальный план радара идей появится рядом; в этом документе фиксируются только точки стыка (раздел 3).

## 1. Как мы ищем боли

Сбор сигналов: четыре направления. Каждое — отдельный пункт проработки.

### 1.1. Движок парсинга карт: Puppeteer vs Playwright и конкуренты

Контекст: официального API отзывов нет ни у Яндекса, ни у 2ГИС. Пути два — разбор внутренних JSON-endpoint'ов веб-версии или headless-браузер; выбор между ними — за разведкой (1.2, Б11 разбора). Для браузерного пути кандидаты по умолчанию — Puppeteer и Playwright.

Исследование-сравнение:

| Ось сравнения | Что смотрим |
|---|---|
| Скорость | запуск браузера, рендер страниц, объём отдаваемых данных, накладные расходы |
| Удобство и поддерживаемость | API и локаторы, отладка (trace, инспектор), стабильность контракта между версиями |
| Анти-обнаружение | видимость автоматизации (WebDriver-флаги, JS-отпечатки, TLS/JA3), stealth-надстройки (`puppeteer-extra-stealth`, `patchright`, `camoufox`), поведение против SmartCaptcha и защиты 2ГИС |
| Поддержка и экосистема | активность разработки, коммьюнити, документация |
| Конкуренты | Selenium/WebDriver, `nodriver`, `camoufox` и прочие; управляемые браузерные сервисы (Browserless, ZenRows…) — отметить, но ориентир для локального проекта — self-hosted |

Куда ложится результат: движок прячется внутри адаптера источника (контракт `ReviewsSource`, Б2 разбора); троттлинг и лимиты терпения источника — в каркасе сборщиков ([collectors-architecture.md](../collectors-architecture.md)).

Выход: план исполнения `pain-radar-plan-headless.md` (сравнение + выбор движка). Статус: **выполнен 04.10.2026** — движок выбран: Playwright (+ patchright как drop-in стелс-надстройка); предложения Д1–Д4 (базовый движок, надстройка, ресурсный режим, политика капчи) ждут решения; открытое «что не проверено» передаётся разведке 1.2.

### 1.2. Ручной запуск из UI: сферы → рубрики → организации

Видение: периодичность настроим потом; для начала — ручной запуск по кнопке из UI. В UI список сфер (авто, медицина, продукты, …); выбираем сферу и жмём «Поиск» — управление переходит в headless-браузер.

Сценарий разведки рубрик (2ГИС первым, Яндекс — следом):

1. открыть карты; найти селектор элемента, открывающего рубрики (в 2ГИС это `<a title="Рубрики">`), кликнуть по нему;
2. среди открывшихся найти один из `<a title="Поесть">`, `<a title="Автосервис">` и т.д.;
3. подняться от найденного элемента к родителю на 3–4 уровня — получить селектор блока со всеми категориями;
4. распарсить блок и показать в наш UI: «нашли такие-то рубрики».

ИИ-агент над браузером: дать агенту собственный API над движком («найди рубрику», «найди все рубрики», «дай 5 организаций из рубрики»), чтобы цепочку кликов строил он, а не зашитый скрипт.

Расследование: есть ли готовые MCP над headless-браузерными движками? (известные кандидаты — Playwright MCP от Microsoft, puppeteer-based MCP-серверы, browser-use и т.п.). Вопрос проработки: агент над готовым MCP против агента над собственным API — возможности, зависимости, лицензии, контроль.

Связь: Б11 разбора (фаза 2 начинается с разведки источника, а не с комбинаторов), чек-пойнт «HTTP или браузер» из архитектуры.

Выход: план исполнения `pain-radar-plan-browser-recon.md` (разведка селекторов + MCP + выбор «агент или скрипт»); прототип «сферы → рубрики» на плитке pain-radar. Статус: **выполнен 06.10.2026** — разведка 05.10 (HTTP-канал отзывов, справочник рубрик со стабильными ID, SSR-листинг), 06.10 собран **пульт сбора** — плитка `pain-radar-scrape`: путь данных и город → рубрики (URL + «обновить» + список + счётчик) → подрубрики с числом мест → организации (рейтинг, оценки, **сайт или только телефон** — без сайта подсвечены «кандидаты на предложение сайта») → отзывы (ndjson + сырые ответы) + произвольный поиск по строке; против злоупотребления: серверная очередь с троттлингом 1,2 с, счётчики обращений (всего/в минуту/по видам), повторы страниц, живой лог (время + URL + статус), пауза, потолки (≤20 страниц, ≤300 отзывов/орг, ≤600 обращений/сессия), стоп при 403/429. Проверен живым прогоном в браузере (рубрики → Шиномонтаж → 12 организаций → скан контактов → 40 отзывов). Решения Р1–Р5 по факту приняты заказом пульта; перенос в архитектуру — по правилу разбора. 06.10 пульт перенесён из отдельной плитки внутрь pain-radar: введена служебная таблица плиток `experiment_tiles` (+ `experiment_tile_parts`) с `visibility` all/admin — истина состава в registry.json, истина доступа в БД ([experiments.md](../experiments.md), «Доступ к плиткам»); каталог отдаёт `GET /api/experiments` с серверным фильтром; админ — email из `.env` (`ADMIN_EMAILS`); scrape-эндпоинты закрыты `requireAdmin`.

Открытые вопросы пункта: селекторы плывут при смене вёрстки — нужна стратегия ремонта (записанные карты селекторов, тест-контур); город/регион как параметр запроса в браузере.

### 1.3. Резюме «Работа России»: срезы образования и профессий

Вход: список резюме по региону в JSON/NDJSON — выгрузка из открытых данных портала «Работа России» по API. Функционал выгрузки уже есть: считаем, что список всех резюме региона у нас в кармане. Интересные поля: **образование** и **желаемая профессия**.

Три расчёта (каждый — чистое действие над выгрузкой, тестируется как функция):

- **а) топ желаемых профессий** — по убыванию: 20 водителей, 10 поваров, 5 инженеров;
- **б) тот же срез по колонке «образование»**;
- **в) матрица совпадений «образование × желаемая профессия»** — сколько людей хочет уйти из своей сферы: зеркало рынка труда региона.

Зачем радару болей: срез людей — третий источник сигнала после карт. Дефицит профессий и исход людей из сфер = боли организаций («некому работать») и государства (ЦЗН, программы поддержки). Сшивки: источник `jobs` радара идей уже собирает вакансии области (адаптер `trudvsem`) — резюме дополнят вакансии до полной картины «спрос ↔ предложение» (И7); «белые пятна» В3; шкала дефицита пойдёт в витрину ниш (2.1).

Открытые вопросы пункта: точный контракт входа (какие поля реально есть в выгрузке, объём по региону); нормализация профессий — словарь и синонимы (опыт `radar_niches` переносится); персональные данные — работаем только с агрегатами, без персоналий.

Выход: план исполнения `pain-radar-plan-resumes.md` + экран срезов в плитке. Статус: **не начато**.

### 1.4. Формула боли: расследование и формулировка запроса

Цель: понять, пытался ли кто-то в науке или практике выжать из отзывов людей реальную потребность, и уточнить нашу формулу боли.

**Шаг 1 — сформулировать сам запрос.** Три варианта (черновик для выбора):

1. **«Насколько отзывы отражают реальную ситуацию в сервисе»** — связь мнений и фактов: правда ли за жалобой стоит системная проблема;
2. **«Извлечение потребностей и спроса из негативных отзывов клиентов»** — практический angle: жалоба → востребованный сервис (review mining, voice of customer);
3. **«Как определить востребованные услуги региона по отзывам людей»** — рыночный angle: от мнений к нишам для предпринимателей.

Выбираем самый точный → **Шаг 2 — поиск статей, эссе, исследований** по выбранному запросу (академия: аспектный анализ тональности, качество сервиса; практика: анализ жалоб, прогноз оттока). **Шаг 3 — синтез**: уточнить формулу боли.

Что уже есть в проекте (база для сравнения с найденным): вес сигнала `W = Σ Score·e^(−λΔt)` в архитектуре; `RankPains` (Б7 разбора) — знаменатель А1, порог «боль засчитана, если есть у ≥ 3 организаций», полураспад свежести, маркеры ухода (А3, В5).

Выход: план исполнения `pain-radar-plan-pain-formula.md` — реферат находок и синтез. Статус: **выполнен 04.10.2026** — нашли формулу боли: подтверждена внешним эталоном (review mining, ODI, таксономия Reader, Kano); найдены дополнительные уточнения формулы — Ф1–Ф4 (нижняя граница боли, класс «пожелание», таксономия v2 по Reader/SERVQUAL, формулировка боли по ODI). Уточнения записаны в плане исполнения и принимаются по обычному правилу разбора по ходу фаз; пункт 1.4 закрыт.

### 1.5. Корпус сырых данных и уровни ответа радара

Добавлен 04.10.2026 как следующий шаг после 1.4: формула боли есть, но применять её не к чему — нужен **корпус сырых данных**. Собираем реальные отзывы **сначала в сыром виде**, без спешки с разметкой, и только затем на живом корпусе решаем, как применить формулу из 1.4 и как категоризировать.

Почему это непростой вопрос, а не «прогнали LLM и готово»:

- категоризация должна вписываться в **общую экосистему радаров**: стыковаться со словарём ниш (`radar_niches`), чтобы запрос «боли ниши X» имел одинаковый смысл у pain-radar и idea-radar;
- от формата категоризации зависит **контракт ответа**: в каком виде потребителю (нашей плитке, idea-radar, внешнему API из 2.2) удобно получать информацию, чтобы строить на ней вывод, какой бизнес рождается.

**Развилка уровней ответа.** Что вообще возвращает pain-radar как сервис:

| Уровень | Что возвращает | Пример |
|---|---|---|
| 1. Боль (сырая) | категория, формулировка, цитата, носители | «боль коммуникации: не дозвониться» — у 22 организаций |
| 2. Бизнес-потребность | потребность, выраженная из сырой боли | «нужен виджет онлайн-записи / приём заявок» |
| 3. Бизнес-ниша | готовая ниша для запуска | «ниша: онлайн-запись для автосервисов города N» |

Рабочая гипотеза (из обсуждения 04.10.2026): проблемы в совмещении уровней нет — можно возвращать и то и другое, ответом вида «боль такая-то, вытекающие потребности такие-то». Тогда idea-radar, обратившись к pain-radar, получает и сырую боль, и рекомендации. Уровень 2 при фиксированной таксономии — детерминированный перевод категории (таблица «боль → тип софта» уже есть в архитектуре), то есть дешёвый и не спорный. Уровень 3 — открытый вопрос: по формуле «идея = сдвиг × боль × человек» ниша требует сдвигов и анкеты человека, а этого у pain-radar нет; возможно, поиск бизнес-ниши — overhead для pain-radar и его место внутри idea-radar. Решение — на живом корпусе.

Путь корпуса без парсера: вставленные отзывы (А6 разбора — `PastedReviewsSource`; режим «вставить отзывы» уже есть на вкладке «Сбор» мока) — 100–200 отзывов одной ниши одного города достаточно, чтобы пробовать категоризацию и формулировки Ф4. Основной путь — парсер из 1.2.

Открытые вопросы пункта:

1. Уровень 3 (ниша): отвечает pain-radar или idea-radar? Смежное с 2.2 — контракт API.
2. Канон формулировки боли на живом корпусе: ODI-форма Ф4 против свободного текста; как склеивать одинаковые боли разных организаций.
3. Знаменатель сырого корпуса: что считать «организацией без жалоб» (А1), пока нет полного каталога ниши.

Выход: план исполнения `pain-radar-plan-corpus.md` (сбор сырого корпуса + эксперименты категоризации + решение об уровнях ответа). Статус: **в работе** — сырой корпус-выборка с 2ГИС собран 06.10.2026: рубрика «Шиномонтаж» Курск, 60 организаций, **1252 отзывов** (негатив ≤3★ — 276, 22%), файлы в `data/pain-radar-corpus/` (ndjson + сырые ответы API + лог запросов), коллектор — `scripts/pain-radar-corpus-sample.mjs`. Терпение источника: 74 запроса с троттлингом 1.6 с — все 200, бана и капчи нет; HTML-страницы требуют браузерных заголовков (голый curl — 403 openresty), отзывное API открыто без заголовков. Инсайты для 1.6: провайдеры агрегируются в одном API (2gis 1181 / flamp 70 / tbank 1), официальный ответ есть у 445 отзывов (35%) — отдельное поле, текст непустой у всех (медиана 138 симв.), свежесть до 2015 г.; листинг SSR отдаёт не все поля карточки — рейтинги пачкой брать `ratings/light`; полный список 195 мест рубрики листингом не покрывается (60 уникальных из «Места 195») — контракт каталог-API ещё подобрать. Категоризация и уровни ответа — на живом корпусе после схемы 1.6.

## 2. Продукт: инструмент ниш и сервис с API

### 2.1. Инструмент поиска ниш региона

Итог раздела 1 в одном экране: инструмент, который находит **ниши региона, в которых есть потребность** — у населения (боли с карт, «несуществующее предложение»), у организаций (B2B-боли, дефицит кадров из среза резюме), у государства (гос-сигналы радара идей: новые обязанности, бюджетные деньги). Сшивка срезов: карта болей × срез резюме × сдвиги → витрина «где ниша и почему».

Продуктовая рамка сценариев А/Б — в архитектуре; замечание из [radar-projects-evaluation.md](../radar-projects-evaluation.md) держим в голове: аудитории разные (разработчик софта ≠ будущий предприниматель), UI не смешивать.

Выход: план исполнения появится, когда сойдутся срезы 1.2 и 1.3. Статус: **не начато**.

### 2.2. Сервис с API

Вторая роль того же приложения — API-сервис, к которому можно обратиться с запросом:

- «поищи боли в сфере электротехнических работ» / «в сфере автосервисов» — запрос по нише;
- «найди самые большие боли» — глобальный топ;
- «верни список топ-3 болей» — параметризованный топ.

Вопросы проработки:

- разбор естественного языка → параметры запроса (LLM-парсер против фиксированных `?niche=&city=&top=N`);
- контракт ответа: JSON — ниши, категории болей, частоты и знаменатели, цитаты-доказательства, свежесть данных;
- поверх существующего наброска `/api/pain-radar/` (jobs, reports, pains/top в архитектуре) — добавить запросный эндпоинт;
- аутентификация и квоты (`quota`, `llmGuard`); для кого API: наши плитки, радар идей (запрос «боли ниши X» при сборке идей), внешние потребители.

Выход: план исполнения `pain-radar-plan-api.md`. Статус: **не начато**.

## 5. Открытые вопросы

Наследованные из [pain-radar-architecture.md](pain-radar-architecture.md) (раздел «Открытые вопросы»): первый источник (2ГИС), ввод на MVP, приоритет сценариев, хранение полного текста отзыва, районные чаты, гость vs логин. Позиции по ним предложены в разборе (А7) и пока не приняты.

Новые из этого плана:

1. **MCP против собственного агента** (1.2): что даёт готовый MCP над headless-браузером и не проще ли свой API над движком?
2. **Анти-обнаружение и терпение источников** (1.1): при какой частоте запросов начинаются блокировки; где граница «исследовательский сбор» и ToS.
3. **Контракт выгрузки резюме** (1.3): какие поля реально приходят из «Работы России» и каков объём по региону.
4. **Публичность API** (2.2): кто потребители на старте и нужен ли ключ.
5. **Юридическая сторона парсинга карт** (1.1–1.2): оценка рисков до публичного запуска (позиция А7: показать юристу).
6. **Уровни ответа pain-radar** (1.5, 2.2): возвращает ли радар бизнес-нишу (уровень 3) — или его дело остановиться на боли (1) и потребности (2), а нишу ищет idea-radar.

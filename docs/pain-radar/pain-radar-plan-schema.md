## 2. Финальная схема (8 таблиц, два слоя)

### Слой каркаса (ступень 2 [collectors-architecture.md](../collectors-architecture.md))

Три уровня каркаса (миграция 017): **источник** `collector_sources` («откуда парсили»: slug `2gis` / `yandex-maps`, человеческое title) → **ресурс** `collector_resources` (что и как собираем от этого источника: отзывы / листинг / рейтинги, темп и потолки) → **item** `collector_items` (сырой факт). Радарные таблицы ссылаются на источник FK `source_id` — свободного текста «2gis/2ГИС/twogis» в БД нет; `provider` в отзывах — другой уровень (площадка размещения внутри источника: 2gis/flamp/tbank), источник отзыва выводится через организацию.

- **`collector_resources`** — реестр ресурсов: slug, kind, adapter, `settings jsonb` (фронтовый ключ, потолки), темп (`throttle_ms`, `min_interval_sec`, `page_timeout_ms`). Темп и терпение источника — территория каркаса, домена тут нет (греп-правило).
- **`collector_items`** — сырьё как есть: один item = один сырой факт (`kind`: review / branch / listing_page), `payload jsonb`, `content_hash`, `UNIQUE (resource_id, kind, external_id)` — повторный сбор апдейтит payload. Решение В1: «повторный разбор читает сырьё, обращения к источнику нет» — критично для карт, где пересбор = риск бана.

### Слой радара (интерпретация)

- **`pain_radar_rubrics`** — справочник рубрик 2ГИС со стабильными ID и самосвязью `parent_id`. Своего словаря ниш не заводим: города — `radar_regions`, ниши — `radar_niches` (общий слой радаров, 005); сшивка ниша↔рубрика — будущая таблица-связка, когда у idea-radar дойдёт до неё.
- **`pain_radar_organizations`** — организации: `external_id` = branch_id, контакты, координаты, `city_region_id → radar_regions`. `website IS NULL` — рабочий признак «кандидат на предложение сайта» (заказано пользователем в пульте).
- **`pain_radar_jobs`** — джобы сбора по образцу `summarize_jobs` (user/guest, статус, прогресс), с FK на регион и нишу — сразу под фазу 4 «ниша + город».
- **`pain_radar_reviews`** — интерпретация отзыва: rating, даты создания/правки (`edited_date` — вход полураспада веса W), provider, текст, официальные ответы колонками, `item_id → collector_items` и `prompt_version` (0 = сырой, не размечен; частичный индекс для очереди разметки).
- **`pain_radar_pains`** — боли: `category` (таксономия v1 + `wish` по Ф2 + `other`), `summary` в ODI-форме Ф4, `quote`-доказательство, model. Статистика — SQL-агрегацией поверх (отдельной таблицы нет, по решению архитектуры).
- **`pain_radar_ideas`** — сценарий Б (профиль + боли → выдача), структура из архитектуры.

### Регионы: смена города — штатная операция (решение 06.10.2026)

Пользовательское требование: при смене города не должно быть путаницы, фильтр по региону работает всегда. Правила:

1. **Регион нигде не строка** — только FK на `radar_regions` (`city_region_id` у организаций, джоб, идей). Смена города не «переименовывает» данные — новые строки получают другой region_id, старые остаются на своём.
2. **Храним самый точный уровень — город**; область/страна вытягиваются иерархией словаря (`parent_id`). Фильтр «Курская область» = организации в городах поддерева, а не отдельное поле — это и убирает главную путаницу «город и регион в двух колонках».
3. **Организация без города не импортируется**: правилом импортёра (не NOT NULL — чтобы сбой источника не ронял джобу): не определился город → item остаётся в сырьё до починки, радарной строки нет. Поэтому «потерянных» строк, ломающих фильтры, не бывает.
4. **Новый город — одна строка в `radar_regions`** (kind='city'); далее сбор и фильтры работают без каких-либо миграций. Импортёр автосоздаёт город при первом сборе нового slug.
5. Данные разных городов живут в одних таблицах, разделение — по FK; быстрые фильтры обеспечивают индексы (миграция 015). Статистика считается с `GROUP BY city_region_id`.

### Сознательные компромиссы (проговорены)

1. **Текст отзыва дублируется** (в `payload` item'а и в `pain_radar_reviews.text`): рабочая копия нужна для SQL-агрегаций и выдачи цитат без join'ов на jsonb. Истина при расхождении — payload: переразметка читает сырьё и перезаписывает поля интерпретации (П26).
2. **Официальный ответ — колонки, а не отдельная таблица**: 1:1 к отзыву, 35% непустых, всегда читается вместе с отзывом (отдельная таблица дала бы join ради колонок).
3. **`rating` хранится, а не выводится из отзывов**: счётчик источника и наш список отзывов расходятся по определению (оценки без текста недоступны API) — знаменатели А1 берём из счётчиков источника, доли считаем по своим строкам.
4. **ПДн автора не храним** — юр. рамка (открытый вопрос 5 глобального плана).

## 3. Связь с пультом (ответ на «сохраняются ли данные»)

Пульт пишет **файловый корпус** `data/pain-radar-corpus/` (вне git): `reviews.ndjson`, `orgs-<rubricId>.json`, `raw/*.json`, `log.jsonl` — это экспериментальная зона. Схема БД теперь есть; следующий шаг — **импортёр**: файлы корпуса → `collector_items` (сырьё) + `pain_radar_organizations`/`pain_radar_reviews` (интерпретация), после чего пульт получает кнопку «влить корпус в БД», а продовый сбор фазы 2 пишет прямо в БД минуя файлы.

## 3.1. Универсальность: не overfit ли схема на 2ГИС

Требование: завтра Яндекс Карты, потом другие карты — данные должны ложиться на ту же схему. Проверка по слоям:

**Источник-нейтрально по построению** (2ГИС-специфика разрешена ровно в двух местах):

| Слой | Что там | Почему ляжет Яндекс |
|---|---|---|
| `collector_items` + `collector_resources` | сырьё как есть, `adapter`, `payload jsonb` | Яндекс-отзывы — новый ресурс (`adapter='yandex-reviews'`), свои items; формат payload вообще не важен схеме |
| `pain_radar_reviews` | `source`-независимые факты: rating, даты, текст, хэш | у Яндекса те же сущности; `provider='yandex'` |
| `pain_radar_pains` | категория + формулировка + цитата | боли — наша интерпретация, источник в неё не проникает вообще |
| `radar_regions` / `radar_niches` / таксономия | общие словари радаров | не принадлежат ни одной карте |

**Где 2ГИС-специфика есть и как изолирована:**

1. **`pain_radar_rubrics`** — справочник рубрик **одного** источника. Таблица рассчитана на несколько карт (`source` в ключе): Яндекс добавит свои рубрики параллельными строками. Но **сопоставление рубрик разных карт между собой схемой не решается** — это зона `radar_niches` (общий зонт): ниша «автосервис» сшивает рубрику 9041 из 2ГИС с категорией Яндекса. Таблица-связка появится, когда будет вторая карта.
2. **Идентичность организации между картами**: одна шиномонтажка в 2ГИС и в Яндексе — **две строки** `pain_radar_organizations` (`source+external_id` уникальны, дедуп по названию+адресу+координатам схемой не делается сознательно). Знаменатели А1 считаем per-source; склейка карточек — будущий слой entity-resolution, схема ему не мешает (нет ограничений на name+address).

**Контракт нормализации адаптера** (что адаптер обязан привести к схеме): шкала оценки 1..5 (CHECK в БД, миграция 016), даты → TIMESTAMPTZ, текст отзыва без ПДн автора, стабильный `external_id` факта, контакты → website/phones/socials, город → `radar_regions`. URL карточки источника **не храним** — собирается из `source` + `external_id` + город (производное, П26).

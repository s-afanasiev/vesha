# SYSTEM INSTRUCTION: REST & RESOURCE-ORIENTED API DESIGN STYLE GUIDE

Данный документ — нормативный технический регламент по проектированию и разработке бэкенд-API. Разработан на основе спецификаций Google AIP (API Improvement Proposals) и книги Дж. Дж. Гивакса «Паттерны проектирования API».

---

## 1. URI & RESOURCE DESIGN

### 1.1. Базовые правила именования и структуры путей
- **ВСЕГДА** используй `kebab-case` для сегментов URI (включая имена коллекций и составные слова): `/chat-rooms`, `/user-profiles`.
- **ВСЕГДА** используй существительные во множественном числе для именования коллекций ресурсов: `/users`, `/orders`, `/devices`.
- **НИКОГДА** не используй единственное число для стандартных коллекций: запрещено `/user`, `/order`. Исключение — подресурсы-одиночки (Singleton Sub-resources).
- **НИКОГДА** не помещай глаголы действий в путь коллекции или ресурса CRUD: запрещено `/getUsers`, `/createOrder`, `/users/123/delete`.
- **ВСЕГДА** ограничивай глубину иерархической вложенности URI: глубина <= 2 уровней коллекций.
  - Разрешено: `/v1/orgs/{org_id}/teams/{team_id}` (глубина 2).
  - Запрещено: `/v1/orgs/{org_id}/teams/{team_id}/projects/{project_id}/tasks/{task_id}` (глубина 4).
  - Правило декомпозиции: если ресурс имеет глубокую иерархию, выноси глубокие сущности в коллекции верхнего уровня со ссылочным полем внешнего ключа: `/v1/tasks/{task_id}` с полем `project_id`.
- **ВСЕГДА** используй символы косой черты (`/`) исключительно как разделители иерархии «коллекция -> ресурс -> подколлекция -> подресурс».
- **НИКОГДА** не завершай URI замыкающим слешем (`trailing slash`): `/users/123/` запрещен, используй `/users/123`.

```
# Каноническая схема иерархии URI
/v1/{collection}
/v1/{collection}/{resource_id}
/v1/{collection}/{resource_id}/{sub_collection}
/v1/{collection}/{resource_id}/{sub_collection}/{sub_resource_id}
```

---

### 1.2. Подресурсы-одиночки (Singleton Sub-resources)
- **ИСПОЛЬЗУЙ** подресурс-одиночку, если дочерний объект существует строго в единственном числе в контексте родителя, создается/удаляется каскадно вместе с родителем и имеет иной профиль доступа или высокую частоту обновлений (волатильность).
- **ВСЕГДА** именуй подресурс-одиночку существительным в **единственном числе** без сегмента `{id}`.
- **ВСЕГДА** поддерживай для одиночек только методы `GET` и `PATCH`.
- **НИКОГДА** не создавай методы `POST` (Create), `DELETE` или `GET` (List) для одиночки:
  - Создание: происходит неявно при создании родительского ресурса.
  - Удаление: происходит неявно при удалении родительского ресурса.
  - Сброс в дефолтное состояние: выполняй через кастомный метод `:reset`.
- **НИКОГДА** не делай одиночку ресурсом верхнего уровня (глобальный singleton = глобальный lock). Одиночка **ОБЯЗАНА** иметь родителя.
- **НИКОГДА** не делай одиночку родителем для другой одиночки.

```http
# Получение данных одиночки
GET /v1/drivers/drv_9823/location

# Частичное обновление одиночки
PATCH /v1/drivers/drv_9823/location?update_mask=lat,lng
Content-Type: application/json

{"lat": 55.7558, "lng": 37.6173}

# Сброс настроек одиночки к дефолту
POST /v1/users/usr_441/settings:reset
```

---

### 1.3. Действия вне CRUD (Custom Methods / RPC-Style)
- **ИСПОЛЬЗУЙ** пользовательские методы (Custom Methods), когда операция:
  1. Вызывает существенный побочный эффект (отправка email, списание средств, запуск физического устройства).
  2. Представляет собой транзитивный переход машины состояний (`:publish`, `:archive`, `:cancel`, `:approve`).
  3. Не сохраняет состояние (stateless-вычисления: конвертация валют, перевод текста).
  4. Применяется пакетно ко всей коллекции (`:batchDelete`, `:purge`).
- **ВСЕГДА** отделяй кастомное действие двоеточием `:` в конце канонического пути ресурса или коллекции: `/{path}:{action}`.
- **ВСЕГДА** используй `camelCase` для имени действия в URI: `:send`, `:undelete`, `:batchGet`, `:export`.
- **ВСЕГДА** используй HTTP-метод `POST` для кастомных действий с мутацией состояния.
- **ИСПОЛЬЗУЙ** HTTP-метод `GET` для кастомных действий только если действие строго идемпотентно и безопасно (например, `:calculateTax`).
- **НИКОГДА** не используй предлоги (`with`, `for`, `to`, `by`) в имени действия:
  - Разрешено: `:export`, `:validate`, `:archive`.
  - Запрещено: `:exportWithFilter`, `:sendToExternalService`.

```http
# Действие над конкретным ресурсом
POST /v1/documents/doc_1029:publish

# Действие над подколлекцией в контексте родителя
POST /v1/chat-rooms/cr_551/messages:export

# Stateless-действие без сохранения сущности
POST /v1/translations:translate
Content-Type: application/json

{"source_lang": "en", "target_lang": "ru", "text": "Hello world"}
```

### 1.4. Моделирование связей «Многие ко многим» (M:N)
Выбирай между двумя взаимоисключающими паттернами:

#### Вариант А: Ассоциирующий ресурс (Join Resource) — по умолчанию при наличии метаданных
- **ИСПОЛЬЗУЙ**, если связь содержит собственные атрибуты (дата вступления, роль, кем выдан доступ, срок действия) или требует прямого аудита жизненного цикла связи.
- **ВСЕГДА** представляй связь как полноправный ресурс с CRUD-методами:
  - Имя: существительное в единственном числе для сущности, множественное для коллекции (`/memberships`, `/enrollments`).
  - Уникальность: связка `(resource_a_id, resource_b_id)` строго уникальна. При попытке повторного добавления возвращай `409 Conflict`.
  - Поля связи в теле `Create`: `user_id`, `group_id` — неизменяемые (`read-only` после создания).

```http
# Создание ассоциации
POST /v1/group-memberships
Content-Type: application/json

{
  "user_id": "usr_901",
  "group_id": "grp_442",
  "role": "editor"
}
```

#### Вариант Б: Методы `:add` и `:remove` — легковесная связь без метаданных
- **ИСПОЛЬЗУЙ**, если связь бинарна (только факт связи «есть/нет»), не имеет атрибутов и не требует версионирования.
- **ВСЕГДА** выдели управляющий ресурс (родитель) и связываемый ресурс (аргумент).
- **ВСЕГДА** передавай только ID связываемого ресурса в теле запроса.
- **ВСЕГДА** возвращай `409 Conflict` или `412 Precondition Failed`, если сущность уже состоит в связи (при `:add`) либо отсутствует в ней (при `:remove`).

```http
# Добавление связи
POST /v1/groups/grp_442/users:add
Content-Type: application/json

{"user_id": "usr_901"}

# Удаление связи
POST /v1/groups/grp_442/users:remove
Content-Type: application/json

{"user_id": "usr_901"}
```

### 1.5. Ресурсные идентификаторы (Resource IDs)
- **ВСЕГДА** генерируй ID на стороне сервера через криптографически стойкие генераторы (CSPRNG).
- **НИКОГДА** не используй автоинкрементные целочисленные ID (`1, 2, 3...`) в публичных контрактах API (уязвимость к перебору IDOR, утечка бизнес-метрик, коллизии при шардировании).
- **ВСЕГДА** отдавай предпочтение URL-безопасным строковым ID с префиксом типа сущности (Type-prefixed identifiers):
  - Формат: `{type_prefix}_{random_base32_or_nanoid}`
  - Примеры: `usr_01H7AB9Z6WXY`, `ord_9k8a2mf7c0b2`.
- **ИСПОЛЬЗУЙ** алфавит Crockford Base32 (`0-9`, `A-Z`, исключая `I`, `L`, `O`, `U` во избежание опечаток и ненормативной лексики) с контрольным символом (Checksum modulo 37).
- **ВСЕГДА** делай идентификаторы неизменяемыми (`immutable`) и непереиспользуемыми (при удалении ресурса его ID отправляется в вечный `tombstone`).
- **ВСЕГДА** нормализуй строковые ID в Unicode NFC (Normalization Form C) и кодируй в UTF-8.

## 2. HTTP METHODS & STATUS CODES

### 2.1. Матрица соответствия методов HTTP

| Метод | Семантика действия | Безопасный (Safe) | Идемпотентный (Idempotent) | Успех (Success) | Ошибка клиента | Ошибка сервера |
|---|---|---|---|---|---|---|
| `GET` | Чтение ресурса или списка | ДА | ДА | `200 OK` | `400`, `401`, `403`, `404` | `500`, `503`, `504` |
| `POST` | Создание ресурса / Кастомное действие | НЕТ | НЕТ (без ключа) | `201 Created`, `200 OK`, `202 Accepted` | `400`, `401`, `403`, `409`, `422` | `500`, `503`, `504` |
| `PATCH` | Частичное обновление ресурса | НЕТ | ДА (с field mask) | `200 OK` | `400`, `401`, `403`, `404`, `409`, `412`, `422` | `500`, `503`, `504` |
| `PUT` | Полная замена (Replace) ресурса | НЕТ | ДА | `200 OK` | `400`, `401`, `403`, `404`, `409`, `412`, `422` | `500`, `503`, `504` |
| `DELETE` | Удаление ресурса | НЕТ | НЕТ (в императивной модели) | `200 OK`, `204 No Content` | `400`, `401`, `403`, `404`, `412` | `500`, `503`, `504` |
| `HEAD` | Чтение заголовков ресурса | ДА | ДА | `200 OK` | `400`, `401`, `403`, `404` | `500`, `503`, `504` |

---

### 2.2. Правила назначения HTTP-кодов ответа
- **`200 OK`**:
  - Успешный `GET`, `PATCH`, `PUT`.
  - Успешный `POST` для кастомных действий, возвращающих синхронный результат.
  - Успешный `DELETE`, если возвращается представление удаленного ресурса (или мягко удаленный ресурс).
- **`201 Created`**:
  - **ВСЕГДА** возвращай для успешного создания ресурса через `POST`.
  - **ВСЕГДА** сопровождай заголовком `Location: /v1/{collection}/{new_id}`.
  - **ВСЕГДА** возвращай созданный объект в теле ответа.
- **`202 Accepted`**:
  - **ВСЕГДА** возвращай для долгих асинхронных операций (LRO) и пакетных фоновых задач.
  - **ВСЕГДА** сопровождай заголовком `Location` со ссылкой на опрос ресурса операции `/v1/operations/{op_id}`.
- **`204 No Content`**:
  - **ИСПОЛЬЗУЙ** только при `DELETE`, если тело ответа строго пустое.
- **`400 Bad Request`**:
  - Синтаксически некорректный JSON, недопустимые типы данных, отсутствие обязательных HTTP-заголовков.
- **`401 Unauthorized`**:
  - Учетные данные отсутствуют или невалидны (заголовок `Authorization`).
- **`403 Forbidden`**:
  - Клиент аутентифицирован, но не имеет прав (RBAC/ABAC) на выполнение операции над данным ресурсом.
- **`404 Not Found`**:
  - Запрошенный URI ресурса не существует.
- **`405 Method Not Allowed`**:
  - Метод HTTP не поддерживается для данного типа ресурса (например, попытка вызвать `POST` на одиночке).
  - **ВСЕГДА** передавай заголовок `Allow: GET, PATCH`.
- **`409 Conflict`**:
  - Нарушение уникальности (дубликат ID/ключа), состояние гонки, конфликт связей M:N.
- **`412 Precondition Failed`**:
  - Несовпадение версии при оптимистичной блокировке (`If-Match`), удаление уже удаленного ресурса, вызов `:undelete` для активного ресурса.
- **`422 Unprocessable Content`**:
  - Семантическая ошибка валидации бизнес-логики при синтаксически корректном JSON (например, дата начала позже даты окончания).
- **`429 Too Many Requests`**:
  - Превышение лимита запросов. **ВСЕГДА** сопровождай заголовком `Retry-After`.
- **`503 Service Unavailable`**:
  - Временная перегрузка или обслуживание. **ВСЕГДА** сопровождай заголовком `Retry-After`, если время восстановления известно.

---

### 2.3. Семантика DELETE: Императивная против Декларативной
- **ВСЕГДА** реализуй императивную модель для стандартного `DELETE`:
  - Первый вызов `DELETE /v1/chat-rooms/1`: возвращает `200 OK` (с удаленным объектом) или `204 No Content`.
  - Второй вызов `DELETE /v1/chat-rooms/1`: возвращает `404 Not Found` (или `412 Precondition Failed`, если ресурс уже в мягком удалении).
- **НИКОГДА** не возвращай `200/204` на повторный `DELETE` несуществующего ресурса в ресурсных API. Клиент должен точно знать, привел ли его вызов к фактическому уничтожению объекта.

## 3. PAYLOADS & DATA CONTRACTS

### 3.1. Стандарты именования полей
- **ВСЕГДА** используй единый регистр для JSON полей: `camelCase` (стандарт Google Cloud / OpenAPI) либо `snake_case` (стандарт Python / REST core). Проект обязан строго зафиксировать один стандарт.
- **ВСЕГДА** именуй булевы поля в утвердительной позитивной форме:
  - Разрешено: `is_active`, `has_access`, `allow_chatbots`, `enabled`.
  - Запрещено: `disallow_chatbots`, `not_archived`, `is_disabled` (двойное отрицание при проверке недопустимо).
- **ВСЕГДА** указывай единицы измерения в имени поля для скалярных чисел:
  - Разрешено: `size_bytes`, `timeout_ms`, `price_usd_cents`, `max_bandwidth_mbps`.
  - Запрещено: `size`, `timeout`, `price`, `bandwidth`.
- **ВСЕГДА** передавай даты и время как строки в формате ISO-8601 (RFC 3339) в UTC:
  - Пример: `"created_at": "2026-10-09T21:40:00Z"`
  - Суффиксы: `_at` для меток времени (`created_at`, `updated_at`, `expires_at`), `_date` для календарных дат (`birth_date`).
- **ВСЕГДА** передавай 64-битные целые числа (`int64`, `uint64`) и числа с произвольной точностью (`decimal`) как строки во избежание потери точности IEEE-754 в JavaScript:
  - Пример: `{"balance_amount": "9007199254740993.25"}`

---

### 3.2. Формат ответов: Flat Payload против Envelope
- **НИКОГДА** не заворачивай одиночные ресурсы в envelope верхнего уровня (`{"data": {...}}`) для успешных REST ответов:
  - Используй **плоский payload (Flat Payload)** для одиночных ресурсов:

```json
// GET /v1/chat-rooms/cr_102
{
  "id": "cr_102",
  "name": "General Discussion",
  "created_at": "2026-10-09T20:00:00Z",
  "message_count": 42
}
```

- **ВСЕГДА** используй контейнер для коллекций (List Resources) с обязательным массивом элементов и метаданными пагинации:

```json
// GET /v1/chat-rooms
{
  "items": [
    {
      "id": "cr_102",
      "name": "General Discussion"
    }
  ],
  "next_page_token": "cGFnZV90b2tlbl8wMDI="
}
```

### 3.3. Пагинация

#### Cursor-based (Page Tokens) — СТАНДАРТ ПО УМОЛЧАНИЮ
- **ВСЕГДА** используй курсорную пагинацию на базе непрозрачных токенов (`page_token` / `next_page_token`) для всех масштабируемых коллекций.
- **Параметры запроса (Query Params):**
  - `page_size` (int, optional): желаемое число элементов. Сервер имеет право вернуть меньше (вплоть до 0 при долгом сканировании), но не больше.
  - `page_token` (string, optional): непрозрачный строковый курсор (opaque string, закодированный Base64).
- **Поля ответа:**
  - `items` (array, mandatory): коллекция ресурсов текущей страницы.
  - `next_page_token` (string, optional): токен следующей страницы. Если элементов больше нет — поле **ОТСУТСТВУЕТ** или равно `null`/пустой строке.
- **НИКОГДА** не делай токены страниц расшифровываемыми клиентом. Токен — внутренняя деталь реализации сервера (содержит зашифрованное ID последнего элемента, смещение или timestamp).
- **Критерий завершения:** список завершен **ТОЛЬКО** когда `next_page_token` пуст. Неполный массив `items` **НЕ ЯВЛЯЕТСЯ** признаком конца выборки (сервер мог прервать сканирование по тайм-ауту).

```http
GET /v1/chat-rooms?page_size=20&page_token=eyJpZCI6ImNyXzEwMiJ9 HTTP/1.1
Host: api.example.com
```

```json
{
  "items": [
    {"id": "cr_103", "name": "Dev Ops"},
    {"id": "cr_104", "name": "Frontend Architecture"}
  ],
  "next_page_token": "eyJpZCI6ImNyXzEwNCJ9"
}
```

#### Offset / Limit — ДОПУСТИМАЯ АЛЬТЕРНАТИВА (Только для малых статических таблиц)
- **ИСПОЛЬЗУЙ** только для административных UI с произвольным переходом по страницам («Перейти на страницу 5») и объемом данных < 10 000 строк.
- **Параметры:** `offset` (int, default 0), `limit` (int, default 20, max 100).
- **Поля ответа:** `items`, `total_count` (int), `offset`, `limit`.

### 3.4. Фильтрация, сортировка и проекция

#### Фильтрация
- **ВСЕГДА** используй единый строковый query-параметр `filter` для сложных запросов.
- **НИКОГДА** не плоди десятки узкоспециализированных query-параметров (`?min_age=...&max_age=...&status=...`).
- **Синтаксис выражения фильтра (CEL / SQL-диалект):**
  - Логические операторы: `AND`, `OR`, `NOT`.
  - Сравнение: `=`, `!=`, `<`, `<=`, `>`, `>=`.
  - Вхождение в массив / подстрока: `:` или `IN`.
  - Защита исполнения: выражение оценивается строго в контексте одного ресурса (герметичность). Запрещены перекрестные вызовы внешних сущностей внутри фильтра.
  - Строгость: при обращении к несуществующему полю фильтр **ОБЯЗАН** возвращать `400 Bad Request`.

```http
GET /v1/users?filter=status="active" AND profile.age >= 18 AND "admin" IN roles
```

#### Сортировка
- **ВСЕГДА** используй единый параметр `sort` (или `order_by`).
- **Синтаксис:** разделенный запятыми список полей. Префикс `-` означает сортировку по убыванию (`DESC`), отсутствие префикса — по возрастанию (`ASC`).

```http
# Сортировка сначала по убыванию даты создания, затем по статусу
GET /v1/orders?sort=-created_at,status
```

#### Проекция (Field Masks)
- **ВСЕГДА** используй параметр `fields` или `field_mask` для частичного извлечения полей ресурса.
- **Синтаксис:** разделенный запятыми список путей атрибутов. Для вложенных сущностей используй точку: `profile.avatar_url`.
- Для запроса всех полей используй wildcard `*`.
- Массивы: запрещена адресация по индексу `items[0]`. Разрешен wildcard: `authors.*.name`.

```http
GET /v1/users/usr_901?fields=id,name,contacts.email,roles
```

## 4. ERROR HANDLING (RFC 7807)

### 4.1. Спецификация Problem Details
- **ВСЕГДА** возвращай `Content-Type: application/problem+json` при ошибках 4xx и 5xx.
- **ВСЕГДА** соблюдай минимальную каноническую структуру схемы RFC 7807:
  - `type` (string, URI): глобальный URI-идентификатор класса ошибки (не должен меняться от инстанса к инстансу).
  - `title` (string): краткое статическое человекочитаемое резюме ошибки на английском языке.
  - `status` (integer): HTTP-статус код, строго дублирующий реальный HTTP status line.
  - `detail` (string): развернутое объяснение конкретной причины сбоя для данного запроса.
  - `instance` (string, URI): уникальный URI вызова или ID операции для трейсинга.
  - `code` (string): машиночитаемый строковый код ошибки в верхнем `SNAKE_CASE` (для клиентских `switch/case`).
  - `invalid_params` (array, optional): детализация ошибок валидации конкретных полей.

```json
// HTTP/1.1 422 Unprocessable Content
// Content-Type: application/problem+json

{
  "type": "https://api.example.com/errors/validation-failed",
  "title": "Validation Failed",
  "status": 422,
  "code": "REQUEST_VALIDATION_FAILED",
  "detail": "The request parameters failed schema and constraint validation rules.",
  "instance": "/v1/orders/ord_99812",
  "invalid_params": [
    {
      "field": "items[2].quantity",
      "reason": "Quantity must be a positive integer greater than zero.",
      "rejected_value": 0
    },
    {
      "field": "customer.email",
      "reason": "Email address format is invalid.",
      "rejected_value": "user@@example..com"
    }
  ]
}
```

### 4.2. Правила формулирования ошибок
- **НИКОГДА** не передавай стек вызовов (stack trace), пароли, токены или сырые ошибки SQL в полях `detail` публичного API.
- **ВСЕГДА** используй стабильные `code` (`RESOURCE_ALREADY_EXISTS`, `INSUFFICIENT_FUNDS`), не опирайся на парсинг текста `detail`.

## 5. IDEMPOTENCY & CONCURRENCY

### 5.1. Ключи идемпотентности (`Idempotency-Key`)
- **ВСЕГДА** поддерживай HTTP-заголовок `Idempotency-Key` для всех мутирующих `POST`-запросов (создание платежей, заказов, списание средств, длительные действия).
- **Схема работы сервера:**
  1. Клиент генерирует UUIDv4 и передает `Idempotency-Key: {uuid}`.
  2. Сервер проверяет наличие ключа в кэше/хранилище идемпотентности.
  3. Если ключ найден и хэш тела запроса (SHA-256) **совпадает**: вернуть сохраненный ответ из кэша (тот же HTTP-код и тело ответа) с заголовком `Idempotent-Replayed: true`.
  4. Если ключ найден, но хэш тела запроса **отличается**: немедленно вернуть `409 Conflict` (коллизия ключа при изменении тела).
  5. Если операция еще в процессе выполнения первым потоком: вернуть `409 Conflict` или блокироваться до завершения первого запроса.
  6. TTL ключа в кэше: минимум 24 часа.

```http
POST /v1/payments HTTP/1.1
Host: api.example.com
Idempotency-Key: 7b567b43-26bb-4bc4-9d5f-b52adfe5a03e
Content-Type: application/json

{
  "amount_cents": 5000,
  "currency": "USD",
  "target_account": "acc_00192"
}
```

---

### 5.2. Оптимистичные блокировки (ETag & If-Match)
- **ВСЕГДА** используй заголовок `ETag` при `GET`-запросах мутабельных ресурсов.
- **ВСЕГДА** требуй заголовок `If-Match` при операциях `PATCH`, `PUT` и `DELETE` над ресурсами, подверженными конкурентному обновлению (Lost Update Problem).
- **Формат ETag:**
  - Сильный (Strong): `"v_3a8f1"` (хэш состояния данных или номер ревизии).
  - Слабый (Weak): `W/"v_3a8f1"` (допустим, если представление может незначительно варьироваться без потери семантики).
- **Поведение сервера:**
  - Если заголовок `If-Match` отсутствует в мутирующем запросе: отклони запрос со статусом `428 Precondition Required`.
  - Если значение в `If-Match` не совпадает с текущим `ETag` ресурса: отклони со статусом `412 Precondition Failed`.

```http
# Шаг 1: Чтение ресурса с получением ETag
GET /v1/documents/doc_551 HTTP/1.1

# HTTP/1.1 200 OK
# ETag: "a4f89c02"

# Шаг 2: Безопасное обновление с проверкой совпадения
PATCH /v1/documents/doc_551 HTTP/1.1
If-Match: "a4f89c02"
Content-Type: application/json

{"title": "Updated Title"}
```

---

### 5.3. Частичное обновление: PATCH и Маски полей (Field Masks)
- **ВСЕГДА** используй `PATCH` для модификации полей ресурса.
- **НИКОГДА** не используй `PUT` для частичных изменений (PUT полностью перезаписывает ресурс, стирая опущенные поля).
- **Реализация через Field Mask:**
  - Явная маска: передается через query-параметр `?update_mask=title,description` или в теле запроса.
  - Неявная маска: выводится сервером из переданных в JSON ключей (ключ присутствует -> обновляется; ключ опущен -> не трогается; ключ передан как `null` -> очищается в БД).
- **Удаление поля в динамических объектах (Maps):**
  - Передача ключа в `update_mask` при физическом отсутствии ключа в теле JSON означает удаление этого ключа из структуры (семантика `DELETE key`).

```http
PATCH /v1/users/usr_10?update_mask=display_name,avatar_url HTTP/1.1
Content-Type: application/json

{
  "display_name": "New Name",
  "avatar_url": null
}
```

## 6. BATCH & ASYNC OPERATIONS

### 6.1. Длительные асинхронные операции (LRO / Async Tasks)
- **ИСПОЛЬЗУЙ** модель LRO, если исполнение метода занимает > 2 секунд.
- **Статус ответа:** `202 Accepted`.
- **Заголовок:** `Location: /v1/operations/{operation_id}`.
- **Тело ответа на инициацию:** объект `Operation` со статусом `done: false`.
- **Контракт ресурса Operation:**
  - `id` (string): уникальный ID операции.
  - `done` (boolean): флаг завершения (успех или отказ).
  - `metadata` (object): промежуточный прогресс, шаги, процент выполнения.
  - `result` (object, optional): итоговый созданный/измененный ресурс.
  - `error` (object RFC 7807, optional): заполняется только при `done: true` в случае сбоя.

```json
// GET /v1/operations/op_export_99120
{
  "id": "op_export_99120",
  "done": false,
  "created_at": "2026-10-09T21:40:00Z",
  "metadata": {
    "progress_percent": 65,
    "processed_records": 6500,
    "total_records": 10000
  }
}
```

```json
// GET /v1/operations/op_export_99120 (после завершения)
{
  "id": "op_export_99120",
  "done": true,
  "created_at": "2026-10-09T21:40:00Z",
  "result": {
    "download_url": "https://storage.example.com/exports/messages_2026.csv.gz",
    "file_size_bytes": 10485760
  }
}
```

- **Стандартные методы управления операциями:**
  - `GET /v1/operations/{id}`: опрос текущего статуса (Polling).
  - `POST /v1/operations/{id}:wait`: Long-polling ожидания завершения.
  - `POST /v1/operations/{id}:cancel`: отмена выполняющейся операции.
  - `GET /v1/operations`: список операций с фильтром по статусу.

---

### 6.2. Пакетные операции (Bulk / Batch Operations)
- **ВСЕГДА** именуй пакетные методы по шаблону: `:batchGet`, `:batchCreate`, `:batchUpdate`, `:batchDelete`.
- **ВСЕГДА** обеспечь полную транзакционную атомарность: «все или ничего» (All-or-Nothing).
- **НИКОГДА** не возвращай частичный успех (`207 Multi-Status`) в стандартных пакетных ресурсных API. При сбое одного элемента весь пакет откатывается с кодом `400/404/409/422`.
- **ВСЕГДА** сохраняй строгий порядок элементов в ответе: `response.items[i]` строго соответствует `request.requests[i]`.
- **Ограничение объема:** жесткий лимит на размер пакета (например, максимум 100 элементов). При превышении — `400 Bad Request`.

```http
# Пакетное удаление
POST /v1/chat-rooms/cr_1/messages:batchDelete HTTP/1.1
Content-Type: application/json

{
  "ids": ["msg_001", "msg_002", "msg_003"]
}

# Пакетное обновление
POST /v1/chat-rooms/cr_1/messages:batchUpdate HTTP/1.1
Content-Type: application/json

{
  "requests": [
    {"id": "msg_001", "text": "Updated 1"},
    {"id": "msg_002", "text": "Updated 2"}
  ],
  "update_mask": "text"
}
```

---

### 6.3. Массовая зачистка по критерию (`:purge`)
- **ИСПОЛЬЗУЙ** кастомный метод `:purge` для удаления данных на основе фильтра.
- **ВСЕГДА** делай превью (`dry-run`) поведением по умолчанию:
  - Без `force=true`: данные **НЕ УДАЛЯЮТСЯ**, возвращается оценка `purge_count` и выборка удаляемых ID `purge_sample`.
  - С `force=true`: выполняется физическое/логическое удаление.
- **НИКОГДА** не удаляй данные при пустом или отсутствующем фильтре без явного подтверждения.

```http
POST /v1/chat-rooms/cr_1/messages:purge HTTP/1.1
Content-Type: application/json

{
  "filter": "created_at < '2025-01-01T00:00:00Z'",
  "force": false
}

# HTTP/1.1 200 OK
{
  "purge_count": 1420,
  "purge_sample": ["msg_1", "msg_2", "msg_3"]
}
```

## 7. VERSIONING & EVOLUTION

### 7.1. Правило версионирования
- **ВСЕГДА** версионируй публичный API через префикс в URL path: `/v1`, `/v2`.
- **НИКОГДА** не используй версионирование через query-параметры (`?version=1`) или кастомные заголовки для публичных REST-контрактов.
- **Формат версии:** мажорная версия в пути (`/v1`). Минорные и патч-версии обязаны быть обратно совместимыми и развертываться без изменения пути `/v1`.

### 7.3. Политика устаревания (Deprecation Policy)
- При выводе из эксплуатации версии или поля:
  1. Выстави HTTP-заголовок `Deprecation: @{timestamp}` (RFC 9651 / Draft).
  2. Передай заголовок ссылки на документацию о миграции: `Link: <https://api.example.com/docs/v2-migration>; rel="deprecation"`.
  3. Установи заголовок даты окончательного отключения: `Sunset: Wed, 11 Nov 2026 00:00:00 GMT` (RFC 8594).
- Гарантированный период поддержки deprecated версии: минимум 6–12 месяцев.

## 8. SECURITY & PERFORMANCE

### 8.1. Заголовки безопасности (Security Headers)
Бэкенд **ОБЯЗАН** возвращать следующий набор HTTP-заголовков в каждом ответе:

```http
# Запрет определения MIME-типа браузером
X-Content-Type-Options: nosniff

# Запрет открытия во фреймах (защита от Clickjacking)
X-Frame-Options: DENY

# Принудительный HTTPS (HSTS) на 1 год с поддоменами
Strict-Transport-Security: max-age=31536000; includeSubDomains; preload

# Политика Content Security Policy для API (запрет выполнения любого контента)
Content-Security-Policy: default-src 'none'; frame-ancestors 'none'

# Запрет кэширования чувствительных данных
Cache-Control: no-store
Pragma: no-cache
```

---

### 8.2. Rate Limiting (IETF Standard Draft)
- **ВСЕГДА** возвращай стандартные заголовки лимитирования в каждом ответе API:
  - `RateLimit-Limit`: максимальное количество запросов в окне.
  - `RateLimit-Remaining`: остаток доступных запросов в текущем окне.
  - `RateLimit-Reset`: количество секунд до сброса лимита.
- **При исчерпании лимита (Status 429):**
  - **ВСЕГДА** возвращай заголовок `Retry-After: {seconds}` (в секундах, не timestamp во избежание рассинхронизации часов).

```http
# Пример ответа при штатной работе
HTTP/1.1 200 OK
RateLimit-Limit: 100
RateLimit-Remaining: 84
RateLimit-Reset: 12

# Пример ответа при превышении лимита
HTTP/1.1 429 Too Many Requests
Retry-After: 30
RateLimit-Limit: 100
RateLimit-Remaining: 0
RateLimit-Reset: 30
Content-Type: application/problem+json

{
  "type": "https://api.example.com/errors/rate-limit-exceeded",
  "title": "Too Many Requests",
  "status": 429,
  "code": "RATE_LIMIT_EXCEEDED",
  "detail": "Rate limit exceeded. Please retry after 30 seconds."
}
```

---

### 8.3. Алгоритм повторных попыток клиента (Exponential Backoff + Full Jitter)
Клиентские библиотеки и фоновые воркеры обязаны выполнять ретраи по формуле:

t_wait = min(t_max, t_base * 2^attempt) + random(0, jitter)

- t_base = 1.0 c, t_max = 32.0 c, jitter in [0, 1000] мс.
- **НИКОГДА** не делай повторные запросы без рандомизированного джиттера (Jitter), чтобы исключить «эффект толпы» (Stampeding Herd).
- Ретраи разрешены строго при кодах: `408`, `429`, `500`, `502`, `503`, `504`.
- Ретраи строго запрещены при кодах: `400`, `401`, `403`, `404`, `405`, `412`, `422`.

---

### 8.4. Правила CORS (Cross-Origin Resource Sharing)
- **НИКОГДА** не используй `Access-Control-Allow-Origin: *` в API с авторизацией по `Authorization` или `Cookie`.
- **ВСЕГДА** проверяй заголовок `Origin` по whitelist доверенных доменов и возвращай совпавший Origin:
  `Access-Control-Allow-Origin: https://app.example.com`.
- **ВСЕГДА** кешируй результат preflight-запроса (`OPTIONS`):
  `Access-Control-Max-Age: 86400` (24 часа).
- **Разрешенные методы и заголовки:**
  - `Access-Control-Allow-Methods: GET, POST, PATCH, PUT, DELETE, OPTIONS`
  - `Access-Control-Allow-Headers: Authorization, Content-Type, If-Match, Idempotency-Key, X-Requested-With`

## 9. ПРАКТИЧЕСКИЙ ЧЕК-ЛИСТ ДЛЯ РАЗРАБОТЧИКА (CODE REVIEW CHECKLIST)

При написании любого эндпоинта проверяй:
1. [ ] Имя пути состоит из существительных во множественном числе в `kebab-case` (`/api/v1/user-accounts`).
2. [ ] Вложенность URI не превышает 2 уровней.
3. [ ] Кастомное действие оформлено через двоеточие (`/v1/orders/ord_1:cancel`).
4. [ ] Метод HTTP соответствует семантике (изменение полей = `PATCH`, а не `PUT` или `POST`).
5. [ ] При `POST` возвращается `201 Created` + `Location` + тело созданного ресурса.
6. [ ] Для мутирующих `POST` поддержан заголовок `Idempotency-Key`.
7. [ ] При `GET` списка реализована курсорная пагинация (`page_token`, `max_page_size`, `next_page_token`).
8. [ ] Конкурентные обновления защищены через `ETag` и `If-Match`.
9. [ ] Все ошибки форматированы строго по стандарту RFC 7807 `application/problem+json`.
10. [ ] Любая операция длительнее 2 секунд возвращает `202 Accepted` и ресурс `Operation`.

# Радар болей — бизнес-логика как язык объектов

Разбор предметной области `pain-radar` по процедуре E28 из `docs/oop-principles.md`: от картины к объектам. Документ абстрактный намеренно — здесь нет кода реализации, есть **язык**: словарь сущностей и работ, грамматика композиции и одна исполняемая декларация (Gpt §1). Конкретные классы появятся, когда декларация ниже перестанет меняться от обсуждения.

Разбор этой декларации и предложенные правки — [pain-radar-review.md](pain-radar-review.md), раздел Б.

## Ш0. Одно предложение о картине

> Радар собирает жалобы клиентов локального бизнеса из чужих источников, превращает каждую в именованную боль и складывает боли в карту востребованных ниш региона, по которой предпринимателю подбирается идея дела.

«И» внутри одного предложения осталось два, но это не две картины: вторая половина — **читатель** первой. Генератор идей потребляет карту болей, не участвуя в её построении. Это зафиксируем горизонтом.

## Ш1. Горизонты: три мира

Режем по мирам, а не по техническим слоям (E28: «на картине не бывает слоя контроллеров»).

**Чужой мир — источники сигнала.** 2ГИС, Яндекс Карты, районные Telegram-чаты, LLM-провайдер. Меняются все пять признаков: свой словарь (филиалы, рубрики, звёзды), чужой темп (антибот, троттлинг), чужая единица (страница отзывов), истина у них, причина изменения — их релизы. Вывод канона однозначен: адаптеры (E9), а не место в нашем дереве.

**Ядро — фабрика болей.** Сюжет «вход: ссылка на организацию → выход: размеченные боли в базе». Тест выключения: выключи — продукта нет, есть пустая плитка.

**Спутники — читатели болей.** Карта болей (сценарий А), генератор идей (сценарий Б), история отчётов, квоты. Каждый выключается без разрушения ядра: радар без генератора идей всё ещё радар.

**Второй рез — по темпу**, и он проходит через все три мира:

| Темп | Что живёт | Единица |
|---|---|---|
| секунды | HTTP-запрос UI, поллинг прогресса | запрос |
| минуты | джоба сбора и разметки | организация → отзыв → батч |
| дни | жизнь отчёта и карты болей, повторный сбор той же ниши | отчёт, ниша |

**Третий рез — дефицит.** Дефицитны два ресурса: терпение источника к парсингу (частота запросов) и LLM-вызовы (деньги, конкурентность). Оба уже имеют или просят обёртку-лимит: `runGuarded` для LLM есть в платформе, лимит источника появится вместе с первым парсером. Отдельной части «аллокатор» не заводим, пока потребитель дефицита один (E28: часть без второго потребителя — мечта).

## Ш2. Сюжеты

Сюжет — то, у чего есть зачинщик, единица работы, исход и конец.

1. **«Собрать и разметить»** (ядро). Зачинщик — пользователь или расписание. Единица — джоба сбора. Конец: джоба завершена, боли в базе, отчёт доступен. Может провалиться целиком (антибот, смена вёрстки) — и это нормальная судьба, а не исключение.
2. **«Свести карту болей»** (читатель, сценарий А). Зачинщик — запрос UI. Единица — пара ниша+город. Конец: ранжированный список категорий с носителями.
3. **«Подобрать идеи»** (читатель, сценарий Б). Зачинщик — предприниматель с профилем. Единица — один профиль. Конец: список идей с привязкой к болям.

«Следить за источником постоянно» — не сюжет (не кончается). Повторный сбор — это новый запуск сюжета 1 по расписанию, а не бессмертный процесс.

## Ш3. Лестница единиц

```
сюжет «собрать и разметить»
  └── джоба сбора            (единица верхнего этажа, есть судьба)
        └── организация      (повторитель: для каждой организации ниши)
              └── отзыв      (повторитель: для каждого отзыва)
                    └── батч отзывов в LLM   (этаж экономии: 10 отзывов = 1 вызов)
                          └── боль           (дно лестницы: судьбы нет, это запись)
```

Этажи — пары «повторитель + экземпляр» (E15): `ForEachOrganization` гоняет `OneOrganizationScan`, `ForEachReviewBatch` гоняет `OneBatchClassification`. Боль — дно: ниже нет единиц со своей судьбой, там данные (правило остановки E28).

## Ш4–Ш5. Словарь домена

Каждый узел — ровно один род из восьми (E28 Ш4). Имена ролевые: у процесса — отглагольное имя, у сущности — предметное (Gpt §18, §8).

### Сущности (идентичность + жизненный цикл + память о себе, E12)

| Сущность | Состояния | Вехи наружу |
|---|---|---|
| `CollectionJob` — джоба сбора | `queued → fetching → classifying → done / failed / aborted` | переходы с причиной; прогресс «3 из 40 организаций» |
| `Organization` — носитель боли | `discovered → scanned → stale` (данные протухли, нужен пересбор) | первое появление, протухание |

`CollectionJob` — центральная сущность: у неё есть всё из E14(2): падения, длительность, ожидание, ретраи, прогресс. Именно её вехи бесплатно дадут поллинг в UI, журнал и историю. `Organization` обретает судьбу, только когда появляется пересбор (фаза 4); до того она строка в БД — и не стыдно.

Сохранение: `CollectionJob` хранит себя через инъектированный store (переходы атомарны с записью); остальное — репозитории (E12 «кто сохраняет»).

### Данные (снимки без поведения, заворачивать в класс запрещено)

`ReviewSnapshot` (текст, рейтинг, дата, хэш) · `PainRecord` (категория, формулировка, цитата) · `PainMapEntry` (категория, частота, носители) · `EntrepreneurProfile` (ввод сценария Б) · `IdeaList` (результат генерации) · `SourcePage` (сырой ответ адаптера).

Процессы обмениваются между собой только ими — сериализуемо, отдаётся в UI, сравнивается в тесте (E12, правило 5).

### Работы (овеществлённые глаголы)

| Работа | Один глагол | Вход → выход |
|---|---|---|
| `FetchOrgPage` | тянет | ссылка → `SourcePage` |
| `ParseReviews` | разбирает | `SourcePage` → `ReviewSnapshot[]` |
| `ClassifyPainBatch` | размечает | `ReviewSnapshot[]` → `PainRecord[]` |
| `RankPains` | ранжирует | `PainRecord[]` → `PainMapEntry[]` |
| `ComposeIdeas` | сочиняет | профиль × `PainMapEntry[]` → `IdeaList` |

Тест на «и» пройден: каждая работа описывается без союза «и». «Скачал, распарсил и отфильтровал» — это три работы, не одна.

### Правила (объекты-политики, E5)

- `NegativeReviewRule` — «этот отзыв — сигнал боли?». Сейчас одно условие (рейтинг ≤ 3), но правило **уже менялось в обсуждении** (добавились: длина текста, не спам, язык) — по E14.1 это шов, прорезанный историей, заводим объект сразу.
- `PainTaxonomy` — владелец фиксированного списка категорий и приёмника `other`. Отвечает на вопросы `known(category)`, `describeForPrompt()` — промпт LLM собирается из таксономии, а не живёт строкой в трёх местах.
- `StalenessRule` (фаза 4) — «данные ниши протухли?».

### Адаптеры (чужой мир, E9)

`TwoGisReviewsSource` · `YandexReviewsSource` · `TelegramChatsSource` — три реализации одного контракта «источник отзывов»: `fetchReviews(orgRef) → ReviewSnapshot[]`. Контракт оправдан проверкой замены: второй источник уже в плане, это не абстракция «на будущее» (§9). LLM-адаптер не пишем — есть платформенный `completeChat`.

### Обёртки и комбинаторы (E4, Gpt §24)

- `WithLlmGuard(...)` — обёртка вокруг `ClassifyPainBatch` над `runGuarded`.
- `WithSourceThrottle(...)` — обёртка вокруг `FetchOrgPage`: минимальная пауза, уважение к источнику.
- `ForEachOrganization`, `ForEachReviewBatch` — повторители лестницы (E15).
- `Retry(twice, ...)`, `Timeout(minutes(15), ...)` — стандартные комбинаторы вокруг шагов джобы.

### Чистые действия (решение отдельно от применения, E25)

`RankPains` — чистое действие: вход множество болей, выход ранжированная карта, ноль побочных эффектов. Тестируется как функция, «сухой прогон» карты болей бесплатный, в журнале видно «что насчитали» отдельно от «что сохранили».

## Ш6. Исполняемая декларация

Всё дерево одним выражением — читается как оглавление системы (§3, Gpt §2):

```js
new PainRadarExperiment({

  // ядро: фабрика болей
  collectAndMark: new CollectionJobRunner(
    new ForEachOrganization(
      new OneOrganizationScan(
        new WithSourceThrottle(new FetchOrgPage(sources)),
        new ParseReviews(),
        new KeepNegative(new NegativeReviewRule()),
      ),
    ),
    new ForEachReviewBatch(
      new WithLlmGuard(llmGuard,
        new Retry(twice, new ClassifyPainBatch(llm, taxonomy))),
    ),
    jobStore,                       // память сущности CollectionJob
  ),

  // чужой мир: источники (реестр возможностей, Gpt §9)
  sources: {
    '2gis':   new TwoGisReviewsSource(http),
    'yandex': new YandexReviewsSource(http),   // фаза 6: playwright
    // 'chats': new TelegramChatsSource(gramjs), // фаза 6+
  },

  // спутник А: карта болей
  painMap: new PainMapQuery(
    new RankPains(),                // чистое действие
    painStore,
  ),

  // спутник Б: генератор идей
  ideas: new IdeaComposer(
    new WithLlmGuard(llmGuard,
      new ComposeIdeas(llm, taxonomy)),
    new PainMapQuery(new RankPains(), painStore),   // тот же читатель
    ideaStore,
  ),

  taxonomy: new PainTaxonomy(),
});
```

Что видно из декларации, не заходя в тела: два спутника делят один читатель болей; источники взаимозаменяемы одной строкой; дефицит (guard, throttle) — видимые обёртки, а не спрятанные if-ы; `taxonomy` упомянута дважды, потому что владеет словарём болей и для разметки, и для идей.

## Границы через незнание

Фиксируем рез списком «кто чего не знает» — каждую строку можно проверить грепом (E28):

- `FetchOrgPage` не знает, что из отзывов делают боли;
- `ParseReviews` не знает, откуда страница — 2ГИС, Яндекс или чат;
- `ClassifyPainBatch` не знает про HTTP, антибот и guard;
- `CollectionJob` не знает, кто её запустил и кто читает её вехи;
- `RankPains` не знает про БД и LLM;
- `ComposeIdeas` не знает про парсинг — только карту болей и профиль;
- UI не знает про источники — только статусы джобы и готовые записи.

## Проверки реза (механические, E28)

- **Рассказа:** «фабрика болей» рассказывается без упоминания того, как устроен 2ГИС; «источник» — без упоминания таксономии. ✔
- **Выключения:** выключаем генератор идей — радар жив; выключаем карту — сбор жив; выключаем сбор — две пустые страницы: значит сбор — ядро. ✔
- **Замены:** первым заменят источник (антибот/вёрстка) и список категорий (копится `other`) — там контракты (`ReviewsSource`, `PainTaxonomy`). ✔
- **Словаря:** в `RankPains` грепом не находится `2gis`, `telegram`, `http` — домен не протёк в механику. ✔

## Что сознательно НЕ делаем объектами (§9)

- `ReviewSnapshot`, `PainRecord` — данные; у боли нет судьбы, не обижаем её классом.
- Отдельный `PainRadarService`-оркестратор — имя-туман; его работу выполняет сама декларация `collectAndMark`.
- Аллокатор дефицита как самостоятельная часть — один потребитель у каждого лимита; появится второй (расписание + ручной сбор) — вынесем.
- Абстрактный `ISourceFactory`, `BaseParser` — наследование и фабрики без второй реализации запрещены §2/§9; контракт рождается из второго источника, не раньше.

## Соответствие фазам архитектурного плана

Декларация выше — конечная форма. По фазам из `docs/pain-radar-architecture.md` она вырастает так: фаза 2 ставит `collectAndMark` без `ClassifyPainBatch` (только `KeepNegative` по рейтингу); фаза 3 вставляет классификатор и таксономию — **структура декларации не меняется, меняется один узел**; фазы 4–5 добавляют спутников `painMap` и `ideas`. Это и есть критерий удачного языка: рост системы — это дописывание предложений, а не переписывание грамматики.

# Передача сайта магазина заказчику: простой VDS без docker

Как отдать «костяк» (docs/backbone-architecture.md) первому магазину в самом
простом варианте: отдельный VDS на 1 vCPU и 1–2 ГБ памяти, Postgres и Node без
docker, домен магазина. Заказчику уходит не весь Vesha, а сборка магазина
`dist/shop` (`npm run build:shop`, раздел 4.4). Общие детали деплоя Vesha —
docs/deploy-linux-vds.md; проверка перед запуском — там же, §7.

Состояние на 18.10.2026: шаги MVP 1–5 и кодовая часть шага 6 сделаны: на
витрине есть ассистент (шаг 5), сотрудник магазина входит в кабинет только
своего магазина, магазину приходит письмо о новой заявке, у витрины есть
страница политики обработки персональных данных. Сайт магазина отпочкован
отдельной сборкой: костяк, вход, шлюз моделей, каркас компонентов и ядро
chat-engine — без остальных экспериментов Vesha.

## 1. Что получает заказчик

**Витрина** — сайт для покупателей магазина, `https://<домен>/` (корень ведёт на
витрину магазина `SHOP_HOME`), полный адрес — `https://<домен>/backbone/?shop=<адрес>`:

- каталог магазина: поиск по наименованию и размеру («м10х50» находит «М10×50»),
  фильтр по группам, цена, упаковка, «в наличии / под заказ»;
- «заявка списком»: покупатель вставляет список текстом или прикладывает xlsx /
  pdf с текстом, оставляет почту или телефон и согласие на обработку данных —
  галочка ведёт на политику магазина `/backbone/privacy.html?shop=<адрес>`
  (кто обрабатывает, зачем, какие данные, срок хранения, почта для отзыва согласия);
- сразу — номер заявки и ссылка на окно статуса (путь заявки по шагам);
- письмо-квитанция: «получена, ответим до …» (в рабочих часах магазина),
  «ждём вашего ответа», «готово», «закрыта»; ответ покупателя на письмо уходит
  на почту магазина.

**Кабинет** — для сотрудников магазина, `https://<домен>/cabinet/` (в самом Vesha
тот же кабинет — плитка `/experiments/backbone/`).
Сотрудник входит своей почтой и паролем и видит только свой магазин; магазины и
сотрудников заводит наш админ (почта из `ADMIN_EMAILS`):

- письмо о новой заявке на почту магазина: номер, клиент, контакт, срок ответа,
  первые строки списка, ссылка на доску; ответ на письмо уходит покупателю.
  Тот же список ещё раз — тоже письмо: покупатель ждёт или заказывает повторно;
- доска заявок: колонки настраиваются (переименовать, добавить, удалить с
  переносом карточек), заявки перетаскиваются, каждое действие — в журнале;
- черновики счетов: заявка разбирается в строки счёта по каталогу магазина
  (правила, остаток — модель), менеджер принимает, заменяет позицию, правит
  количество; замена учит систему (синонимы); выгрузка черновика в xlsx для 1С;
- замеры: время до ответа и до счёта, точность черновика, «до / после»;
  первые 14 дней — тень (черновик скрыт, менеджер работает как обычно);
- каталог: загрузка выгрузки xlsx из 1С, МойСклад или прайса;
- магазины (только админ): адрес, название, часы работы, почта магазина
  (письма о заявках, ответы покупателей, отзыв согласия в политике),
  сотрудники магазина — «Добавить сотрудника» и «Убрать сотрудника».

**Каталог хранится в базе** (Postgres, таблица `backbone_catalog_items`) и
меняется целиком новой выгрузкой. **База обязательна**: в ней магазины, заявки,
журнал, черновики, каталог, квитанции, пользователи.

## 2. Что есть и чего нет

| Есть | Нет (пока) |
|---|---|
| Витрина с каталогом, поиском и группами | Фото и описание товара, карточка позиции |
| «Заявка списком»: текст, xlsx, pdf с текстом | Корзины — сознательно: B2B-покупатель шлёт список |
| Окно статуса по ссылке, письма-квитанции по SMTP | Уведомлений в мессенджер: только почта |
| Письмо менеджеру о новой заявке на почту магазина | Ролей внутри магазина («владелец / менеджер»): сотрудники магазина равны |
| Вход сотрудника: почту добавляет админ, сотрудник видит только свой магазин | Приглашения письмом: адрес сайта и почту сотруднику сообщают сами |
| Доска заявок с настройкой колонок | Прямого обмена с 1С: только xlsx туда и обратно |
| Разбор заявки в черновик счёта, выгрузка xlsx в 1С | Правки одной позиции или цены в кабинете: только новой выгрузкой |
| Загрузка каталога из xlsx: колонки сопоставляются, брак — списком | Удаления данных покупателя кнопкой: по отзыву согласия и сроку — вручную в базе |
| Согласие на обработку ПДн в форме и страница политики магазина | Реквизитов оператора (юрлицо, ИНН, адрес) в политике |
| Защита формы: ловушка для ботов и 5 заявок за 10 минут с адреса | Капчи |
| Ассистент в чате на витрине: наличие и цена из каталога магазина, статус заявки — только её клиенту, часы работы; список из чата — заявка (тот же список с сайта и из чата — одна заявка); остальное — менеджеру с черновиком модели в кабинете («Ассистент») | Мессенджеров (Telegram, VK): только чат на витрине; адреса магазина в ответах — в описании магазина его нет |
| Отдельная сборка магазина `dist/shop`: без других экспериментов Vesha, 9 пакетов вместо 17, свои миграции, кабинет по `/cabinet/` | Обновления «кнопкой»: новая версия — новый архив сборки (раздел 6) |

### Правка цен и каталога

Отдельной формы «изменить цену позиции» нет. Цены и остатки меняются так:

1. Менеджер выгружает прайс из 1С, МойСклад или Excel в **xlsx**.
2. Кабинет → «Каталог» → «Загрузить файл выгрузки».
3. Проверяет, какие колонки взяты (артикул, наименование, единица, упаковка,
   цена, остаток, группа); при необходимости — «Указать колонку».
4. «Загрузить каталог». Каталог подменяется целиком, если файл прочитан;
   строки с браком (нет артикула, цена словами, дубль) — списком с номером
   строки. Битый файл старый каталог не трогает.

Для магазина, который ведёт цены в 1С, это и есть рабочий порядок: правят в 1С,
выгружают раз в день или после изменения. Форма поштучной правки — отдельная
задача, если заказчик попросит.

## 3. Сервер

- VDS в России (152-ФЗ: контакты покупателей хранятся здесь): **1 vCPU,
  2 ГБ** памяти — с запасом; **1 ГБ** — минимум, со swap 1–2 ГБ.
- Диск от 15 ГБ: система, Postgres, код с зависимостями (сборка — ~115 МБ), бэкапы.
- Ubuntu 24.04 LTS (или 22.04).
- Домен магазина: A-запись на IP сервера.

Замер на 18.10.2026, сборка `dist/shop` (Node 22): процесс после пути
«регистрация админа → магазин → каталог xlsx → заявка с витрины → ассистент →
сотрудник» — рабочий набор около 67 МБ, пик 70 МБ (весь Vesha на 17.10.2026 —
70–90 МБ); Postgres с настройками ниже — 100–200 МБ. Пик — `npm ci` при
установке и разбор pdf-заявки (pdf.js подгружается по требованию).

## 4. Установка по шагам

Команды — от пользователя с `sudo`. В угловых скобках — свои значения.

### 4.1. Система и swap

```bash
sudo apt update && sudo apt upgrade -y
sudo apt install -y git nginx certbot python3-certbot-nginx
# swap: на 1 ГБ памяти обязателен, на 2 ГБ — страховка
sudo fallocate -l 2G /swapfile && sudo chmod 600 /swapfile
sudo mkswap /swapfile && sudo swapon /swapfile
echo '/swapfile none swap sw 0 0' | sudo tee -a /etc/fstab
```

### 4.2. Node.js 22

```bash
curl -fsSL https://deb.nodesource.com/setup_22.x | sudo -E bash -
sudo apt install -y nodejs
node -v   # v22.x; проекту нужен 20+
```

### 4.3. Postgres без docker

```bash
sudo apt install -y postgresql        # Ubuntu 24.04 — Postgres 16, pgcrypto входит
sudo -u postgres createuser --pwprompt shop      # пароль базы — в .env ниже
sudo -u postgres createdb -O shop shop
```

Под маленький сервер (одно приложение, пул соединений Node):

```bash
sudo -u postgres psql -c "ALTER SYSTEM SET max_connections = 30;"
sudo -u postgres psql -c "ALTER SYSTEM SET shared_buffers = '128MB';"
sudo -u postgres psql -c "ALTER SYSTEM SET work_mem = '4MB';"
sudo systemctl restart postgresql
```

Расширения кроме `pgcrypto` не нужны. Postgres слушает только localhost — так
и оставить.

### 4.4. Код — сборка магазина

На сервер идёт не репозиторий Vesha, а сборка `dist/shop`: точка входа
`shop.js`, костяк, вход, шлюз моделей, каркас компонентов и ядро chat-engine,
витрина и кабинет, свои `package.json` и `package-lock.json` (9 пакетов тех же
версий, что в Vesha), миграции магазина (`001_shop_init` — только вход и квота
гостя, `012_chat_engine`, `018`–`020`, `022`–`026`; `021` automation-leads не
входит), `README.md`, `.env.example`, `build.json` (коммит и дата сборки). Ключей
и `.env` в сборке нет. Состав — манифест в `scripts/build-shop.mjs`, границу
держит `test/shop-build.test.js`.

На своей машине, в корне Vesha:

```bash
npm run build:shop                     # dist/shop собирается заново целиком
tar -czf shop.tar.gz -C dist shop      # ~0,2 МБ
scp shop.tar.gz <сервер>:/tmp/
```

На сервере:

```bash
sudo useradd -r -m -d /opt/shop -s /usr/sbin/nologin shop
sudo -u shop mkdir /opt/shop/app
sudo -u shop tar -xzf /tmp/shop.tar.gz -C /opt/shop/app --strip-components=1
cd /opt/shop/app
sudo -u shop npm ci --omit=dev         # ~110 МБ зависимостей
```

### 4.5. Переменные окружения

`/opt/shop/app/.env` из `.env.example` сборки (права `600`, владелец `shop`):

```bash
# сервер и база
PORT=3000
HOST=127.0.0.1                         # за nginx — только локальный адрес
TRUST_PROXY=true                       # за nginx: иначе у всех покупателей один IP
DATABASE_URL=postgres://shop:<пароль базы>@localhost:5432/shop
SESSION_SECRET=<длинная случайная строка: openssl rand -hex 32>

# админ экземпляра: заводит магазины и сотрудников, видит все магазины.
# Почты сотрудников магазина сюда НЕ пишем — их добавляют в кабинете (раздел 5)
ADMIN_EMAILS=<наш@почта>

# витрина и письма
SHOP_HOME=<адрес магазина из кабинета> # корень сайта ведёт на его витрину (4.8, шаг 2)
BACKBONE_PUBLIC_URL=https://<домен в punycode, если кириллический>
BACKBONE_MAIL_FROM=<ящик-отправитель, тот же, что SMTP_USER>
BACKBONE_SMTP_HOST=<smtp.yandex.ru>
BACKBONE_SMTP_PORT=465
BACKBONE_SMTP_USER=<ящик-отправитель>
BACKBONE_SMTP_PASS=<пароль приложения почты>

# модель для строк заявки, которые не разобрали правила (шлюз, OpenAI-совместимый)
LLM_OPENAI_BASE_URL=<адрес шлюза>
LLM_OPENAI_API_KEY=<ключ>
LLM_OPENAI_MODEL=<модель>
```

Не задавать: `BACKBONE_MODEL` (нужен только для демо без сети). Без ключа
модели заявки всё равно разбираются правилами; строки, которые правила не
поняли, менеджер видит как «не разобрано». Без SMTP письма пишутся файлами в
`data/backbone-mail/` папки сборки — покупатель их не получит.

### 4.6. Запуск как служба

`/etc/systemd/system/shop.service`:

```ini
[Unit]
Description=Сайт магазина
After=network.target postgresql.service

[Service]
User=shop
WorkingDirectory=/opt/shop/app
ExecStart=/usr/bin/node shop.js
Restart=always
RestartSec=5
Environment=NODE_ENV=production

[Install]
WantedBy=multi-user.target
```

```bash
sudo systemctl daemon-reload
sudo systemctl enable --now shop
journalctl -u shop -n 50       # «Shop running at …»; миграции накатываются при старте
```

### 4.7. nginx и HTTPS

Конфиг — как в docs/deploy-linux-vds.md §6 (общий прокси-фрагмент оттуда же),
с отличием для магазина: тело запроса — до 12 МБ. Корень домена на витрину
ведёт сам `shop.js` (`SHOP_HOME`), отдельный `location = /` не нужен.

```nginx
server {
    listen 80;
    server_name <домен>;

    client_max_body_size 12m;   # прайс до 10 МБ, файл заявки до 5 МБ

    location / {
        proxy_pass http://127.0.0.1:3000;
        include /etc/nginx/proxy_params_vesha.conf;
    }
}
```

```bash
sudo nginx -t && sudo systemctl reload nginx
sudo certbot --nginx -d <домен>
```

### 4.8. Первичная настройка в кабинете

1. `https://<домен>/cabinet/` → «Войти» вверху → «Регистрация» с
   почтой из `ADMIN_EMAILS` (корень домена ведёт на витрину, входа там нет).
2. `https://<домен>/cabinet/?page=shops` → «Завести магазин»:
   адрес (латиница, например `metiz-kursk` — его же в `SHOP_HOME` в `.env` и
   `sudo systemctl restart shop`), название,
   ниша, дни и часы работы, почта магазина. Почта обязательна для живого
   магазина: на неё приходят письма о новых заявках и ответы покупателей, она
   же — в политике ПДн для отзыва согласия. Без почты письмо менеджеру
   «пропущено», а в политике — «магазин ещё не указал почту».
3. Выбрать магазин вверху → «Каталог» → загрузить выгрузку → «Загрузить
   каталог» → прочитать список «Не загружено».
4. «Магазины» → отметить магазин → «Добавить сотрудника» — почта менеджера
   (дальше — раздел 5).
5. Тестовая заявка с витрины на свой ящик: пришли два письма — квитанция на
   ваш ящик и «Новая заявка №…» на почту магазина; в кабинете в таблице писем
   у обоих — «отправлена», заявка на доске.
6. Открыть `https://<домен>/backbone/privacy.html?shop=<адрес>` (ссылка из
   галочки согласия): название магазина и его почта — верные.
7. Ассистент на витрине («Спросить магазин»): «есть ли <позиция из
   выгрузки>?» — цена и наличие из каталога; «где заявка <номер тестовой>?» —
   её шаг и ссылка (из другого браузера — «не вижу»); вопрос не из трёх —
   в кабинете «Ассистент» → «Предложить ответ» → «Отправить черновик».
8. Пройти чек-лист docs/deploy-linux-vds.md §7.

Демо-магазин `demo-krepezh` заводится сам и остаётся по своему адресу; на
домен заказчика он не выходит — корень ведёт на магазин `SHOP_HOME` (пока он не
задан — на демо).

## 5. Что отдаём заказчику

- Адрес витрины: `https://<домен>/` (ведёт на магазин).
- Адрес кабинета: `https://<домен>/cabinet/?shop=<адрес>`.
- Вход сотрудников — без правки `.env` и без перезапуска:
  1. Админ: `https://<домен>/cabinet/?page=shops` → отметить
     магазин → «Добавить сотрудника» → почта сотрудника.
  2. Сотрудник: `https://<домен>/cabinet/?shop=<адрес>` → «Войти»
     вверху → «Регистрация» с этой же почтой и своим паролем; дальше — просто
     «Войти». Видит доску, черновики, замеры и каталог только своего
     магазина; экран «Магазины», чужие магазины и демо отвечают отказом (403).
  3. Ушёл сотрудник — таблица «Сотрудники магазинов» → отметить →
     «Убрать сотрудника»: вход закрывается сразу, учётка остаётся.
  Кто и когда добавил или убрал — в журнале магазина. Регистрация с почтой,
  которую не добавили, пускает на сайт, но не в кабинет: «Вашей почте пока не
  открыт ни один магазин».
- Короткая инструкция менеджеру: о новой заявке приходит письмо на почту
  магазина (ответ на него уходит покупателю), сама заявка — на доске, колонка
  «Новая заявка»; как разобрать заявку и выгрузить счёт в 1С, как обновить
  прайс (раздел 2).
- Политика обработки ПДн — `https://<домен>/backbone/privacy.html?shop=<адрес>`:
  заказчик проверяет текст и обещания (срок хранения 3 года, удаление по отзыву
  согласия — не позже 30 дней) — это его обязательства как оператора.
- Что первые 14 дней — тень: менеджер работает как раньше, к заявке
  прикладывает счёт из 1С; потом решение о помощи — по точности черновика.

## 6. Обслуживание

**Бэкап базы** — раз в сутки, 14 дней хранения:

```bash
sudo mkdir -p /var/backups/shop && sudo chown postgres /var/backups/shop
# /etc/cron.d/shop-backup
15 3 * * * postgres pg_dump -Fc shop > /var/backups/shop/shop-$(date +\%F).dump && find /var/backups/shop -name '*.dump' -mtime +14 -delete
```

Копию бэкапа держать и вне сервера. Восстановление:
`pg_restore -d shop --clean <файл>`.

**Обновление кода — пересборкой.** Новая версия — новый архив сборки (4.4);
на сервере он распаковывается рядом, `.env` переносится, прежняя папка остаётся
для отката. Какая версия стоит — `/opt/shop/app/build.json` (коммит и дата).

```bash
cd /opt/shop
sudo -u shop rm -rf app.new && sudo -u shop mkdir app.new
sudo -u shop tar -xzf /tmp/shop.tar.gz -C app.new --strip-components=1
sudo -u shop cp app/.env app.new/.env
(cd app.new && sudo -u shop npm ci --omit=dev)
sudo systemctl stop shop
sudo -u shop rm -rf app.old && sudo -u shop mv app app.old && sudo -u shop mv app.new app
sudo systemctl start shop        # новые миграции накатятся при старте
```

Откат кода — обратная подмена папок (`app.old` → `app`); миграции назад не
откатываются, поэтому сначала бэкап базы. Письма без SMTP (`data/backbone-mail/`)
лежат в папке сборки — при подмене остаются в `app.old`.

**Логи:** `journalctl -u shop -f`; несданные письма — в кабинете, таблица
писем (квитанции покупателям и письма менеджеру), колонка «Почему не ушла».

**Отзыв согласия покупателем** (письмо на почту магазина): кнопки пока нет —
не позже 30 дней обезличить его заявки в базе и ответить покупателю. Так же —
заявки старше 3 лет (срок из политики). Контакт — как в заявке: почта строчными
или телефон `+7…`:

```sql
BEGIN;
DELETE FROM backbone_receipts WHERE order_id IN
  (SELECT id FROM backbone_orders WHERE contact = '<контакт>');  -- письма: адрес, контакт, начало списка
UPDATE backbone_orders
  SET client = 'удалено', contact = '', text = '[удалено по отзыву согласия]', content_key = NULL
  WHERE contact = '<контакт>';
COMMIT;
```

Журнал событий контактов не хранит; строки черновика — наименования и
количества, без контакта.

## 7. Что доделать до первого живого покупателя

По важности для передачи:

1. **Проверка на живой выгрузке заказчика** — формат его 1С или МойСклад.
2. **Реквизиты оператора в политике ПДн** — юрлицо или ИП, ИНН, адрес: в
   таблице магазина их нет, политика называет магазин по названию. До запуска —
   поле у магазина или текст заказчика на странице.
3. **Удаление данных покупателя кнопкой** — по отзыву согласия и по сроку
   хранения (3 года); пока — вручную в базе (раздел 6).
4. **Зависимости с предупреждениями `npm audit`** — `multer`, `proxy-addr` и
   `qs` (через express), `body-parser`: версии те же, что в Vesha; обновить в
   корне Vesha (`npm audit fix`), прогнать тесты и пересобрать магазин.
5. **Окно входа в кабинете** показывает формы входа и регистрации разом:
   `.vesha-auth-form` в `public/style.css` перебивает `hidden` (так же и в Vesha).
6. По желанию заказчика: поштучная правка цены, фото позиций, адрес магазина
   в описании (ассистент пока отвечает только о часах), ассистент в мессенджерах.

# Передача сайта магазина заказчику: простой VDS без docker

Как отдать «костяк» (docs/backbone-architecture.md) первому магазину в самом
простом варианте: отдельный VDS на 1 vCPU и 1–2 ГБ памяти, Postgres и Node без
docker, домен магазина. Общие детали деплоя Vesha — docs/deploy-linux-vds.md;
проверка перед запуском — там же, §7.

Состояние на 18.10.2026: шаги MVP 1–5 и кодовая часть шага 6 сделаны: на
витрине есть ассистент (шаг 5), сотрудник магазина входит в кабинет только
своего магазина.

## 1. Что получает заказчик

**Витрина** — сайт для покупателей магазина, `https://<домен>/backbone/?shop=<адрес>`:

- каталог магазина: поиск по наименованию и размеру («м10х50» находит «М10×50»),
  фильтр по группам, цена, упаковка, «в наличии / под заказ»;
- «заявка списком»: покупатель вставляет список текстом или прикладывает xlsx /
  pdf с текстом, оставляет почту или телефон и согласие на обработку данных;
- сразу — номер заявки и ссылка на окно статуса (путь заявки по шагам);
- письмо-квитанция: «получена, ответим до …» (в рабочих часах магазина),
  «ждём вашего ответа», «готово», «закрыта»; ответ покупателя на письмо уходит
  на почту магазина.

**Кабинет** — для сотрудников магазина, `https://<домен>/experiments/backbone/`.
Сотрудник входит своей почтой и паролем и видит только свой магазин; магазины и
сотрудников заводит наш админ (почта из `ADMIN_EMAILS`):

- доска заявок: колонки настраиваются (переименовать, добавить, удалить с
  переносом карточек), заявки перетаскиваются, каждое действие — в журнале;
- черновики счетов: заявка разбирается в строки счёта по каталогу магазина
  (правила, остаток — модель), менеджер принимает, заменяет позицию, правит
  количество; замена учит систему (синонимы); выгрузка черновика в xlsx для 1С;
- замеры: время до ответа и до счёта, точность черновика, «до / после»;
  первые 14 дней — тень (черновик скрыт, менеджер работает как обычно);
- каталог: загрузка выгрузки xlsx из 1С, МойСклад или прайса;
- магазины (только админ): адрес, название, часы работы, почта для квитанций,
  сотрудники магазина — «Добавить сотрудника» и «Убрать сотрудника».

**Каталог хранится в базе** (Postgres, таблица `backbone_catalog_items`) и
меняется целиком новой выгрузкой. **База обязательна**: в ней магазины, заявки,
журнал, черновики, каталог, квитанции, пользователи.

## 2. Что есть и чего нет

| Есть | Нет (пока) |
|---|---|
| Витрина с каталогом, поиском и группами | Фото и описание товара, карточка позиции |
| «Заявка списком»: текст, xlsx, pdf с текстом | Корзины — сознательно: B2B-покупатель шлёт список |
| Окно статуса по ссылке, письма-квитанции по SMTP | Письма менеджеру о новой заявке: он видит её на доске |
| Доска заявок с настройкой колонок | Ролей внутри магазина («владелец / менеджер»): сотрудники магазина равны |
| Вход сотрудника: почту добавляет админ, сотрудник видит только свой магазин | Приглашения письмом: адрес сайта и почту сотруднику сообщают сами |
| Разбор заявки в черновик счёта, выгрузка xlsx в 1С | Прямого обмена с 1С: только xlsx туда и обратно |
| Загрузка каталога из xlsx: колонки сопоставляются, брак — списком | Правки одной позиции или цены в кабинете: только новой выгрузкой |
| Согласие на обработку ПДн в форме | Страницы политики обработки ПДн |
| Защита формы: ловушка для ботов и 5 заявок за 10 минут с адреса | Капчи |
| Ассистент в чате на витрине: наличие и цена из каталога магазина, статус заявки — только её клиенту, часы работы; список из чата — заявка (тот же список с сайта и из чата — одна заявка); остальное — менеджеру с черновиком модели в кабинете («Ассистент») | Мессенджеров (Telegram, VK): только чат на витрине; адреса магазина в ответах — в описании магазина его нет |
| | Отдельной сборки «только магазин»: на сервер ставится весь Vesha |

### Правка цен и каталога

Отдельной формы «изменить цену позиции» нет. Цены и остатки меняются так:

1. Менеджер выгружает прайс из 1С, МойСклад или Excel в **xlsx**.
2. Кабинет → «Каталог» → «Загрузить файл выгрузки».
3. Проверяет, какие колонки взяты (артикул, наименование, единица, упаковка,
   цена, остаток, группа); при необходимости — «Указать колонку».
4. «Загрузить каталог». Каталог подменяется целиком, если файл прочитан;
   строки с браком (нет артикула, цена словами, дубль) — списком с номером
   строки. Битый файл старый каталог не трогает.

Для магазина, который ведёт цены в 1С, это и есть рабочий порядок: правят в 1С,
выгружают раз в день или после изменения. Форма поштучной правки — отдельная
задача, если заказчик попросит.

## 3. Сервер

- VDS в России (152-ФЗ: контакты покупателей хранятся здесь): **1 vCPU,
  2 ГБ** памяти — с запасом; **1 ГБ** — минимум, со swap 1–2 ГБ.
- Диск от 15 ГБ: система, Postgres, код с зависимостями (~0,5 ГБ), бэкапы.
- Ubuntu 24.04 LTS (или 22.04).
- Домен магазина: A-запись на IP сервера.

Замер на 17.10.2026: процесс Node после старта и запросов витрины — около
70–90 МБ; Postgres с настройками ниже — 100–200 МБ. Пик — `npm ci` при
установке и разбор pdf-заявки (pdf.js подгружается по требованию).

## 4. Установка по шагам

Команды — от пользователя с `sudo`. В угловых скобках — свои значения.

### 4.1. Система и swap

```bash
sudo apt update && sudo apt upgrade -y
sudo apt install -y git nginx certbot python3-certbot-nginx
# swap: на 1 ГБ памяти обязателен, на 2 ГБ — страховка
sudo fallocate -l 2G /swapfile && sudo chmod 600 /swapfile
sudo mkswap /swapfile && sudo swapon /swapfile
echo '/swapfile none swap sw 0 0' | sudo tee -a /etc/fstab
```

### 4.2. Node.js 22

```bash
curl -fsSL https://deb.nodesource.com/setup_22.x | sudo -E bash -
sudo apt install -y nodejs
node -v   # v22.x; проекту нужен 20+
```

### 4.3. Postgres без docker

```bash
sudo apt install -y postgresql        # Ubuntu 24.04 — Postgres 16, pgcrypto входит
sudo -u postgres createuser --pwprompt vesha     # пароль базы — в .env ниже
sudo -u postgres createdb -O vesha vesha
```

Под маленький сервер (одно приложение, пул соединений Node):

```bash
sudo -u postgres psql -c "ALTER SYSTEM SET max_connections = 30;"
sudo -u postgres psql -c "ALTER SYSTEM SET shared_buffers = '128MB';"
sudo -u postgres psql -c "ALTER SYSTEM SET work_mem = '4MB';"
sudo systemctl restart postgresql
```

Расширение `vector` (pgvector) не нужно: миграция заметок без него
переходит на запасной путь. Postgres слушает только localhost — так и оставить.

### 4.4. Код

```bash
sudo useradd -r -m -d /opt/vesha -s /usr/sbin/nologin vesha
sudo -u vesha git clone <адрес репозитория> /opt/vesha/app
cd /opt/vesha/app
sudo -u vesha npm ci --omit=dev
```

Репозиторий закрытый: на сервер — deploy key только на чтение, или код
архивом: на своей машине `git archive -o vesha.tar.gz HEAD`, `scp` на сервер,
`tar -xzf` в `/opt/vesha/app`.

### 4.5. Переменные окружения

`/opt/vesha/app/.env` (права `600`, владелец `vesha`). Минимум для магазина:

```bash
# сервер и база
PORT=3000
DB_MODE=native
DATABASE_URL=postgres://vesha:<пароль базы>@localhost:5432/vesha
SESSION_SECRET=<длинная случайная строка: openssl rand -hex 32>
TRUST_PROXY=true                       # за nginx: иначе у всех покупателей один IP

# админ экземпляра: заводит магазины и сотрудников, видит все магазины.
# Почты сотрудников магазина сюда НЕ пишем — их добавляют в кабинете (раздел 5)
ADMIN_EMAILS=<наш@почта>

# витрина и письма
BACKBONE_PUBLIC_URL=https://<домен в punycode, если кириллический>
BACKBONE_MAIL_FROM=<ящик-отправитель, тот же, что SMTP_USER>
BACKBONE_SMTP_HOST=<smtp.yandex.ru>
BACKBONE_SMTP_PORT=465
BACKBONE_SMTP_USER=<ящик-отправитель>
BACKBONE_SMTP_PASS=<пароль приложения почты>

# модель для строк заявки, которые не разобрали правила (шлюз, OpenAI-совместимый)
LLM_OPENAI_BASE_URL=<адрес шлюза>
LLM_OPENAI_API_KEY=<ключ>
LLM_OPENAI_MODEL=<модель>
```

Не задавать: `BACKBONE_MODEL` (нужен только для демо без сети),
`IDEA_RADAR_POLL_EVERY_MIN` (опрос лент радара — служебный эксперимент Vesha,
по умолчанию выключен). Без ключа модели заявки всё равно разбираются
правилами; строки, которые правила не поняли, менеджер видит как
«не разобрано». Без SMTP письма пишутся файлами в `data/backbone-mail/` —
покупатель их не получит.

### 4.6. Запуск как служба

`/etc/systemd/system/vesha.service`:

```ini
[Unit]
Description=Vesha (костяк магазина)
After=network.target postgresql.service

[Service]
User=vesha
WorkingDirectory=/opt/vesha/app
ExecStart=/usr/bin/node main.js
Restart=always
RestartSec=5
Environment=NODE_ENV=production

[Install]
WantedBy=multi-user.target
```

```bash
sudo systemctl daemon-reload
sudo systemctl enable --now vesha
journalctl -u vesha -n 50      # «Server running at …»; миграции накатываются при старте
```

### 4.7. nginx, HTTPS и вход на витрину с корня домена

Конфиг — как в docs/deploy-linux-vds.md §6, с двумя отличиями для магазина:

```nginx
server {
    listen 80;
    server_name <домен>;

    client_max_body_size 12m;   # прайс до 10 МБ, файл заявки до 5 МБ

    # корень домена — сразу витрина магазина
    location = / {
        return 302 /backbone/?shop=<адрес магазина>;
    }

    location / {
        proxy_pass http://127.0.0.1:3000;
        include /etc/nginx/proxy_params_vesha.conf;
    }
}
```

```bash
sudo nginx -t && sudo systemctl reload nginx
sudo certbot --nginx -d <домен>
```

### 4.8. Первичная настройка в кабинете

1. `https://<домен>/experiments/backbone/` → «Войти» вверху → «Регистрация» с
   почтой из `ADMIN_EMAILS` (корень домена ведёт на витрину, входа там нет).
2. `https://<домен>/experiments/backbone/?page=shops` → «Завести магазин»:
   адрес (латиница, например `metiz-kursk` — он же в редиректе nginx), название,
   ниша, дни и часы работы, почта магазина для ответов покупателей.
3. Выбрать магазин вверху → «Каталог» → загрузить выгрузку → «Загрузить
   каталог» → прочитать список «Не загружено».
4. «Магазины» → отметить магазин → «Добавить сотрудника» — почта менеджера
   (дальше — раздел 5).
5. Тестовая заявка с витрины на свой ящик: письмо пришло, в кабинете у
   квитанции — «отправлена», заявка на доске.
6. Ассистент на витрине («Спросить магазин»): «есть ли <позиция из
   выгрузки>?» — цена и наличие из каталога; «где заявка <номер тестовой>?» —
   её шаг и ссылка (из другого браузера — «не вижу»); вопрос не из трёх —
   в кабинете «Ассистент» → «Предложить ответ» → «Отправить черновик».
7. Пройти чек-лист docs/deploy-linux-vds.md §7.

Демо-магазин `demo-krepezh` заводится сам и остаётся по своему адресу; на
домен заказчика он не выходит — корень ведёт на магазин заказчика.

## 5. Что отдаём заказчику

- Адрес витрины: `https://<домен>/` (ведёт на магазин).
- Адрес кабинета: `https://<домен>/experiments/backbone/?shop=<адрес>`.
- Вход сотрудников — без правки `.env` и без перезапуска:
  1. Админ: `https://<домен>/experiments/backbone/?page=shops` → отметить
     магазин → «Добавить сотрудника» → почта сотрудника.
  2. Сотрудник: `https://<домен>/experiments/backbone/?shop=<адрес>` → «Войти»
     вверху → «Регистрация» с этой же почтой и своим паролем; дальше — просто
     «Войти». Видит доску, черновики, замеры и каталог только своего
     магазина; экран «Магазины», чужие магазины и демо отвечают отказом (403).
  3. Ушёл сотрудник — таблица «Сотрудники магазинов» → отметить →
     «Убрать сотрудника»: вход закрывается сразу, учётка остаётся.
  Кто и когда добавил или убрал — в журнале магазина. Регистрация с почтой,
  которую не добавили, пускает на сайт, но не в кабинет: «Вашей почте пока не
  открыт ни один магазин».
- Короткая инструкция менеджеру: где новые заявки (доска, колонка «Новая
  заявка»), как разобрать заявку и выгрузить счёт в 1С, как обновить прайс
  (раздел 2).
- Что первые 14 дней — тень: менеджер работает как раньше, к заявке
  прикладывает счёт из 1С; потом решение о помощи — по точности черновика.

## 6. Обслуживание

**Бэкап базы** — раз в сутки, 14 дней хранения:

```bash
sudo mkdir -p /var/backups/vesha && sudo chown postgres /var/backups/vesha
# /etc/cron.d/vesha-backup
15 3 * * * postgres pg_dump -Fc vesha > /var/backups/vesha/vesha-$(date +\%F).dump && find /var/backups/vesha -name '*.dump' -mtime +14 -delete
```

Копию бэкапа держать и вне сервера. Восстановление:
`pg_restore -d vesha --clean <файл>`.

**Обновление кода:**

```bash
cd /opt/vesha/app
sudo -u vesha git pull
sudo -u vesha npm ci --omit=dev
sudo systemctl restart vesha     # новые миграции накатятся при старте
```

**Логи:** `journalctl -u vesha -f`; несданные письма — в кабинете, колонка
«Почему не ушла» у квитанций.

## 7. Что доделать до первого живого покупателя

По важности для передачи:

1. **Страница политики обработки ПДн** и ссылка на неё из формы витрины (152-ФЗ).
2. **Письмо менеджеру о новой заявке** — сейчас он должен смотреть на доску.
3. **Проверка на живой выгрузке заказчика** — формат его 1С или МойСклад.
4. По желанию заказчика: поштучная правка цены, фото позиций, адрес магазина
   в описании (ассистент пока отвечает только о часах), ассистент в мессенджерах.

Вариант без отдельного сервера: один наш сервер на несколько магазинов — у
каждого свой адрес `?shop=`, сотрудники каждого видят только свой магазин
(вход сотрудника сделан 18.10.2026).
